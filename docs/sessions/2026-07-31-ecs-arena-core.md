# Разгон: Архитектура сетевой ECS-арены и выбор инструментов

## Дата
2026-07-31

## Тема / повод
Проектирование архитектуры ядра сетевой экшен-арены на 10 игроков с WASD, снарядами, рикошетами и уворотами. Выбор стратегии реализации (своя ECS vs готовая либа), распределение ответственности между Domain/Render слоями, интеграция UI и подготовка спеки для SDD (Spec-Driven Development) с LLM.

## Что обсуждали
- **Биндинг ресурсов и графика в ECS** — обсуждали, как связывать сущности с визуалом (анимации, спрайты). Пришли к выводу, что компоненты хранят только ID/хэндлы (чистые данные), а Render-система сама мапит их на ассеты. Это обеспечивает независимость логики от движка и возможность работы в headless-режиме на сервере.
- **UI в ECS-архитектуре** — рассматривали варианты полной ECS-реализации интерфейса и полного выноса наружу. Выбрали гибридный подход: стейт UI (здоровье, кулдауны) лежит в ECS-мире, а визуализация и верстка управляются внешними инструментами.
- **Готовые геймплейные ядра (дженерики)** — искали шаблоны готовых ARPG/RTS движков поверх ECS. Выяснили, что из-за атомарности ECS готовых жанровых шаблонов почти нет, но есть хорошие open-source проекты для референса (Veloren, 0 A.D.).
- **Выбор ECS-библиотеки для TypeScript** — выбирали между написанием своей ECS с нуля и готовыми решениями (`bitECS` vs `miniplex`). Написание своей ECS отклонили из-за будущей высокой сложности сетевого Rollback-кода (откаты, клонирование стейта).
- **Тупики и отброшенные идеи**:
    - *Идея*: Писать ECS-систему с нуля. *Отброшено*: Слишком высокие затраты на оптимизацию и реализацию предсказаний на клиенте (Client-Side Prediction).
    - *Идея*: Использовать `bitECS` для MVP. *Отброшено*: Для прототипирования через LLM объекты в `miniplex` подходят лучше, так как нейросети генерируют ООП/интерфейсный код стабильнее, чем манипуляции с ArrayBuffers.

## К чему пришли
- Выбрана библиотека **miniplex** (TypeScript) в качестве фундамента игрового ядра → оформлено в архитектурный стек прототипа.
- Спроектирована базовая плоская структура сущности (`Entity Type`) и определен строгий порядок выполнения систем в кадре (`Input` -> `Movement` -> `Collision` -> `Lifetime` -> `Render`) → зафиксировано в core-engine.md.
- Выделен отдельный компонент под механику уворота (`dash`) и снарядов с поддержкой счетчика отскоков (`projectile`).
