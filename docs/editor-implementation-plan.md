# План имплементации редактора (этап 12)

Ненормативный документ. Норма — `openspec/specs/editor/spec.md` (ED-1..ED-30) и соседние
capability, на которые она ссылается; при расхождении прав текст требования, а не этот план.
Здесь — порядок работ, границы параллелизма и журнал выполнения.

Референс раскладки — `openspec/changes/archive/2026-08-07-editor-ui-shell/mockup.svg`,
решения по форме — `design.md` рядом с ним.

## Принятые решения

Приняты оркестратором при составлении плана; при несогласии меняются здесь и в задачах.

| Решение | Выбор | Основание |
|---|---|---|
| Стек UI | Vanilla TS + DOM, свой тонкий слой реактивности | Ноль новых рантайм-зависимостей — как в остальном репозитории; плотность ED-22 задаётся токенами, а не темой фреймворка |
| Расположение кода | `editor/core-ts` и `editor/ui-ts` — новые члены workspace вне `engine/` | Редактор — потребитель пакетов движка, а не слой движка |
| Границы пакетов | `core-ts` headless (без DOM в `lib` tsconfig), `ui-ts` — DOM | ED-29 «операции исполнимы без интерфейса» проверяется физически, а не на слово |
| Десктоп | Интерфейс хоста среды и веб-реализация сейчас; десктопная оболочка — отдельной работой | ED-12 требует шва; вторая среда без шва — вторая реализация |
| Декорации (ED-19) | Отложены до `presentation-scene-layer` | Формата парного presentation-документа нормативно не существует |
| Текстурирование террейна | Вне этого прохода (`terrain-texturing` — стаб) | Не блокирует ни одно ED-требование этого прохода |

## Движковые блокеры

Реализация редактора упиралась в три работы в пакетах движка. Две из них были нормированы,
одна — стаб без спеки.

| Блокер | Состояние нормы | Что блокирует |
|---|---|---|
| `scene-initial-placement` | SER-7/SER-8 в главной спеке, кода нет | ED-16, ED-21 — расстановке некуда писать |
| REND-11 документный источник | В главной спеке `rendering`, кода нет | ED-15, ED-16, ED-17, ED-20 — режиму правки нечем рисовать |
| `viewport-services` | Стаб: specs/design/tasks пусты | ED-17 — picking и подсветка выделения |

Все три закрыты, и работа над ними нашла ещё пять, которых в плане не было:

- **W0-4**, из ревью W0-2: подсистема террейна инициализируется сценой (REND-8), документный
  вход карты пола не несёт, и правка уровня клетки требовала переинициализации. Сделано;
  норму на это пишет change `editor-terrain-source` (**W0-6**) — код опередил спеку осознанно.
- **W0-5**, оттуда же: превью ED-9 идёт воркер-сборкой, а `RemoteHost` вёл свой список
  подсистем мимо `PresentationStage`. Взаимоисключающесть продюсеров на реальном пути превью
  не выполнялась, и документный инстанс молча переиспользовался под сущность мира.
- **W0-7**, из спеки `viewport-services`: `CameraRig` принимает границы арены значением при
  конструировании, и после изменения размеров террейна подать новые нечем (CAM-7).
- **W0-8**, при реализации вьюпорта: подсистема моделей принимала манифест при
  конструировании, поэтому правка манифеста (ED-14) до картинки не доходила. Нормировано
  change'ем `models-manifest-resupply` (REND-17).
- **W1-7**, из отчёта W1-4: валидация и согласованность при сохранении описывали нарушение
  двумя разными типами — второе описание в одном пакете, что ED-30 запрещает.

Так же выросли и остальные ряды: почти каждая задача журнала с номером выше запланированного
пришла из отчёта ревью, а не из плана. Это и было смыслом порядка работы ниже.

## Волны и параллелизм

Волна — это то, что можно вести одновременно. Внутри волны задачи не делят файлы;
между волнами есть зависимость по коду, а не по календарю.

```
W0  ─┬─ W0-1 core-ts: initial в конфиге сцены        ─┐
     ├─ W0-2 render-ts: REND-11                       │
     └─ W1-1 скелет пакетов редактора                 │
                                                      │
W1  ─┬─ W0-3 render-ts: viewport-services   (после W0-2)
     ├─ W1-2 реестры вкладов и каталог      (после W1-1)
     ├─ W1-3 операции и история             (после W1-1)
     ├─ W1-4 валидация                      (после W1-1)
     ├─ W1-5 локали и подсказки             (после W1-1)
     └─ W1-6 хост среды и round-trip        (после W1-1)

W2  ─┬─ W2-1 визуальный язык                (после W1-1)
     ├─ W2-2 каркас областей                (после W1-2, W2-1)
     ├─ W2-3 палитра и инспектор            (после W2-2, W1-5)
     └─ W2-4 аффорданс превью               (после W2-2)

W3  ─┬─ W3-1 вьюпорт сцены                  (после W0-2, W1-6, W2-2)
     ├─ W3-2 кисти террейна                 (после W3-1, W1-3)
     ├─ W3-3 расстановка и picking          (после W3-1, W0-3, W0-1, W1-3)
     ├─ W3-4 runner превью                  (после W3-1, W2-4)
     └─ W3-5 просмотрщик ассетов            (после W0-2, W1-6, W2-2)

W4  ─┬─ W4-1 веб-приложение
     └─ W4-2 гейт, покрытие требований, roadmap
```

## Порядок работы над задачей

Одинаков для всех задач и является частью плана, а не привычкой исполнителя:

1. Исполняющий субагент читает требования по ID (`openspec spec show editor`), а не пересказ.
2. Реализация с тестами в том же коммите; тест называет требование, которое пиннит.
3. `npm run check` из корня — зелёный.
4. Ревьюирующий субагент проверяет результат против текста требований и правит найденное.
5. Строка задачи в журнале ниже получает состояние и ссылку на коммит.

## Что этим проходом не закрывается

Названо явно, чтобы отсутствие не читалось как недосмотр:

- Рабочие области объектов, систем и схем (ED-4..ED-7) — каркас их принимает вкладом,
  сами вклады пишутся следующим проходом.
- Декорации (ED-19) в части presentation-документа — ждут `presentation-scene-layer`.
- Кисть текстур террейна — ждёт `terrain-texturing`.
- Десктопная оболочка (ED-12) — реализация второго хоста среды.
