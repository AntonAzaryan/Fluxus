# Архитектура ИИ-систем для NPC в детерминированном ECS-движке Fluxus: вердикт и целевой дизайн

## TL;DR

- **NPC-поведение (крипы и боссы) нужно делать системой ВНУТРИ детерминированной симуляции** — как JSON-документы поверх существующего universal evaluator плюс тонкий нативный слой за интерфейсом `System`. Гипотеза автора «взять утилити-мозг бота, упростить и вынести в отдельный поток для крипов» — **отклоняется как основная архитектура**: она ломает детерминизм/реплей, раздувает канал вводов на сотни юнитов и добавляет паразитную задержку.
- **Правильный шаринг с ботом — не размещение, а формат**: общий словарь considerations/response curves и формат документа поведения (модель скоринга) переиспользуются, а восприятие (FoW-снапшот у бота vs прямое чтение мира у NPC) и канал влияния (`InputFrame` у бота vs Command Buffer у NPC) обязаны разойтись.
- **Целевая архитектура**: массовый крип — дешёвый utility/aggro-скоринг + threat-таблица + движение по shared flow field; уникальный босс — HFSM по фазам в данных с каст-ротациями (приоритеты + условия + телеграфы). Стоимость амортизируется staggered-обновлениями (1/N агентов в тик) и decision-бюджетом; горячий путь тика не аллоцирует пропорционально числу сущностей.

## Key Findings

1. **Индустрия не выбирает один подход — она матчит подход к типу NPC.** Массовые враги (толпы, крипы, волны) почти всегда управляются простыми реактивными механизмами: FSM/HFSM, aggro/threat-таблицами, стимул-реакцией и скриптовыми данными. Уникальные, «режиссируемые» сущности (боссы, сюжетные бои) — скриптованными ротациями и фазовыми машинами состояний. Планировщики (GOAP/HTN) окупаются только для небольшого числа «умных» агентов, где ценится эмерджентность (F.E.A.R.). Utility AI — универсальный слой выбора действия, который масштабируется и от массовых юнитов до боссов.

2. **Детерминизм — жёсткое ограничение, которое ставит крест на out-of-sim размещении для NPC.** Lockstep/rollback-игры (StarCraft, Age of Empires, Factorio) исполняют ИИ юнитов ВНУТРИ тика: сеяный RNG, синхронизированный по числу вызовов; никакого wall-clock; порядок итерации сущностей детерминирован. Реплей воспроизводится из записанных вводов. NPC как «игрок через input-канал» — анти-паттерн при сотнях юнитов.

3. **Utility-модель отлично шарится как формат, но не как runtime.** IAUS (Dave Mark) уже применялся «от NPC до армий» и как раз доказал масштабируемость на MMO (Guild Wars 2). Это подтверждает: considerations + response curves + scoring — правильный общий язык для бота И NPC. Но у бота этот код живёт в воркере поверх FoW-снапшота; у NPC он должен исполняться внутри тика поверх прямого чтения ECS.

4. **Движение масс решается flow field'ами, а не A\* на каждого.** Для арены, пока pathfinding-шов пуст, минимально достаточно: shared flow field к цели/героям + локальный steering (separation/avoidance) + «атака в контакте». Это откладывает полноценный A\* и снимает N-кратную стоимость поиска пути.

5. **Боссы — это HFSM-в-данных плюс каст-ротации.** WoW/Impossible Bosses показывают паттерн: фазы по %HP и таймерам, ротации способностей с приоритетами и условиями, телеграфирование атак (windup), реакции на позиционирование игроков. Всё это ложится на существующий Fluxus DSL (триггеры, машина состояний каста, пространственные запросы).

## Details

### 1. Классификация подходов и trade-offs

**FSM / HFSM (finite / hierarchical state machine).** Дёшево, предсказуемо, тривиально отлаживается и сериализуется в данные. Плохо масштабируется по числу состояний («логический ад» переходов). Идеален для крипа (Idle → Acquire → Chase → Attack → Retreat) и как каркас фаз босса. Даже F.E.A.R. под GOAP держал FSM всего из трёх состояний (GoTo, Animate, UseSmartObject) — планировщик решал «как», FSM исполнял.

**Behavior Trees (BT).** Индустриальный стандарт со времён Halo 2: в докладе Damian Isla «Handling Complexity in the Halo 2 AI» (GDC 2005) цель формулировалась как «a beautiful, clean and ultimately scalable brain architecture», реализованная как иерархическая машина состояний / дерево поведения. BT модульны, читаемы, хорошо авторятся в данных и визуально отлаживаются. Минусы: разрастаются в «спагетти-деревья», статичны, менее эмерджентны. Хороши для тактического, тестируемого поведения. Важная деталь из Halo: дерево на самом деле статично, impulses/stimulus-поведения не вставляются в рантайме, а проверяются каждый тик — но с оптимизацией, чтобы не гонять дорогие проверки впустую (событийная активация).

**Utility AI / IAUS (Infinite Axis Utility System, Dave Mark).** Каждое действие скорится набором considerations, каждая — через response curve, входы нормализованы. Выбирается максимум (или взвешенно-случайно). Плюсы: авторится «на естественном языке» дизайнера («под огнём — приоритет искать укрытие»), не хрупок, легко расширяется, масштабируется. IAUS давал «мозги» от NPC до армий и «даже неодушевлённых объектов». Минусы: тюнинг кривых требует чутья; «почему выбрал вот это» отлаживается хуже, чем ветка BT. Оптимизации стоимости: early-out на нулевом скоре, weight-ordered evaluation с отсечением, дешёвые оси раньше дорогих (LoS — последней), кэш переиспользуемых величин на цикл решения, скоринг «по интервалу», а не каждый кадр.

**GOAP (Goal-Oriented Action Planning, Jeff Orkin, F.E.A.R. 2005).** A\* по пространству world-states: действия с preconditions/effects, планировщик сам находит «маршрут» к цели. Плюс: эмерджентность, агент решает «как». Минусы: дороже BT, тонкая настройка представления состояния, теряется контроль над «весёлостью», трудно отлаживать. Окупается для немногих «умных» врагов, не для толп.

**HTN (Hierarchical Task Network).** Декомпозиция задач на подзадачи/методы; «золотая середина» между BT, GOAP и utility. Дороже реактивных схем, требует авторинга иерархии. Для арены избыточен.

**Стимул-реакция (stimulus/response) и threat/aggro-таблицы.** Дешёвые событийные механизмы. Aggro-таблица — де-факто стандарт таргетинга массовых юнитов: каждый враг держит «threat table» и бьёт того, кто наверху (WoW-style), либо использует простые правила приоритета цели (Dota 2 lane creeps). Идеально для крипа.

**AI Director (Left 4 Dead, Mike Booth, GDC 2009).** Отдельный слой режиссуры — не поведение юнита, а метаконтроль темпа/спавна. Построен как «слой предельно простых, тестируемых алгоритмов»: метрика emotional intensity, Active Area Set, Flow Distance по navmesh. Прямо релевантно волнам крипов: спавн и давление волн — это Director-слой поверх поведения отдельного крипа.

**Вердикт по пригодности:** массовый крип → HFSM + aggro-таблица + utility-скоринг цели/действия (дёшево); волна → Director-слой (спавн/давление); босс → HFSM-фазы в данных + каст-ротации с приоритетами/условиями + телеграфы.

### 2. Референсные игры: что скрипт, что дерево/utility, что планировщик

- **Dota 2 lane creeps** — простейший FSM + правила приоритета цели. Aggro-чек по дистанции: приказ атаки по вражескому герою в радиусе acquisition (по Dota 2 Wiki — «500 range for melee creeps, 600 range for ranged creeps and 800 range for siege creeps») переключает цель; иначе бьют ближайшего/по threat-приоритету. Никаких деревьев — чистые правила в данных. Siege creeps: здания в наивысшем приоритете. Это ровно та «достаточно умная, но не гениальная» модель, что нужна крипам Fluxus.
- **WC3/SC2 юниты** — приказ-ориентированные FSM (acquire/attack/move) внутри детерминированного lockstep; групповое движение SC2 — steering + flocking с flow fields.
- **MMO-боссы (WoW)** — скриптованные энкаунтеры: фазы по %HP, таймерам, event'ам; ротации способностей; enrage-таймеры; реакции на позиционирование. Threat-таблица для таргета с точными порогами переключения: по WoW Classic Threat Guide (Warcraft Tavern) — «To pull the target onto yourself you must exceed 110% of the leader's threat in melee or 130% at range», плюс taunt-механики. Это данные/скрипты, не планировщик.
- **Diablo/Path of Exile** — толпы монстров на дешёвых FSM/aggro; акцент на читаемости телеграфов.
- **Left 4 Dead** — AI Director как отдельный слой режиссуры (см. выше) поверх reactive path following и HFSM отдельных заражённых.
- **They Are Billions / RTS-волны** — спавн-волны как контентные таблицы + flow field к базе.
- **F.E.A.R.** — GOAP (планировщик) для небольшого числа солдат; эмерджентность из planning'а.
- **Guild Wars 2: Heart of Thorns** — IAUS + influence maps «at massive scale»: utility как формат, данными, дизайнер собирает уникальный AI-пакет быстро (по gameai.com про доклад Mark & Lewis, IAUS «enables designers to construct unique AI packages for their NPCs in as little as 7 minutes»).

### 3. ИИ внутри детерминированной lockstep/rollback-симуляции

Ключевые уроки из детерминированных движков напрямую диктуют, как Fluxus обязан исполнять NPC-ИИ:

- **Age of Empires (Bettner & Terrano, «1500 Archers on a 28.8», GDC 2001).** Full state-sync ограничил бы игру ~250 юнитами: «Just passing X and Y coordinates, status, action, facing and damage would have limited us to 250 moving units in the game at the most». Deterministic lockstep дал 1500 юнитов на 8 игроков. RNG сеян и синхронизирован — код обязан делать **одинаковое число вызовов random** в симуляции. Код не должен зависеть от локальных факторов (свободное время, железо, настройки): путь исполнения на всех машинах совпадает. Бюджет движка (Genie Engine) делился так: «a rough breakdown of processing tasks for the engine was: 30% graphic rendering, 30% AI and Pathing, and 30% running the simulation & maintenance». AI/pathing мог «раскачивать» длину игрового тика до 200 мс — это гасилось Speed Control (адаптивным удлинением тика), НЕ нарушением детерминизма.
- **StarCraft II.** Порядок исполнения действий юнитов рандомизируется по псевдослучайному алгоритму, seed которого — текущий tick, поэтому последовательность воспроизводима на всех клиентах без коммуникации. Фиксированная целочисленная (fixed-point) математика. Реплей = сохранённая последовательность команд, работает и после патчей благодаря разделению GUI/simulation/attributes.
- **Factorio (Wube, Friday Facts + Wiki).** 60 тиков/с → бюджет 16.667 мс/тик; по Factorio Wiki («Tutorial:Diagnosing performance issues»): «60 UPS is equivalent to 16.667ms per tick... 1ms of time costing you about 3.5 UPS. Anything above 1ms may be worth looking into, and anything above 5 is very significant». Path finder — отдельный time-sliced процессор: выделяет **фиксированное число шагов на биттера в тик**, хранит контекст расчёта между тиками, так что «все биттеры считают пути одновременно (хоть и не параллельно)». Один путь на группу, пути кэшируются, bidirectional A\*, дешёвый обход препятствий по прямой до фолбэка на A\*. Детерминизм чинили вплоть до «неоднозначного компаратора сортировки» (STL sort по-разному упорядочивает равные элементы на разных компиляторах) и кастомных реализаций тригонометрии для совпадения результатов на Win/OSX/Linux. Проверка: CRC карты каждый тик.

**Следствие для Fluxus:** ИИ NPC исполняется в `tick()` поверх сеяного RNG с именованным потоком (например, `npc-ai`), без wall-clock, с детерминированным порядком обхода сущностей (по entity id / стабильному индексу SoA). Стоимость мышления амортизируется, а не выносится из симуляции.

### 4. In-sim vs out-of-sim: критерии и вердикт по гипотезе

Наш **бот-игрок** справедливо вынесен out-of-sim: он полноценный участник матча (слот ростера, свой netclient, видит только FoW-снапшот, влияет только `InputFrame`, «человечность» — задержки/шум/джиттер). Стоимость его мышления не должна влиять на каденс тика — воркер идеален. Это правильный дизайн **для агента, имитирующего игрока**.

**Почему тот же приём НЕЛЬЗЯ по умолчанию тянуть на NPC:**

1. **Детерминизм и реплей.** Единственный вход симуляции — `tick(state, inputs)`. Если крип влияет на мир через `InputFrame`, эти вводы придётся **записывать в реплей** наравне с игроками, а мозг в воркере обязан быть побитово воспроизводимым и синхронным с тиком. Асинхронный воркер с собственным темпом — источник недетерминизма; чтобы сделать его детерминированным, придётся жёстко залокстепить его с тиком, что убивает главный плюс выноса (независимость от каденса).
2. **Стоимость канала на сотни юнитов.** Бот — единицы слотов. Крипы — десятки-сотни сущностей за волну. Гнать за каждого отдельный FoW-снапшот + `InputFrame` — это N-кратная сериализация/фильтрация тумана войны и раздувание записи вводов. Для NPC прямое чтение ECS и мутации через Command Buffer на порядки дешевле.
3. **FoW не нужен NPC.** Бот фильтруется туманом ради честности (он «как игрок»). Крип/босс — часть авторитетной симуляции; ему естественно читать мир напрямую (или через отдельную, дешёвую модель восприятия), а не через дорогой клиентский снапшот.
4. **Задержка реакции.** Для бота задержка — фича (человечность). Для крипа лишний round-trip воркер↔тик — паразитная латентность без выгоды.

**Прецеденты «NPC как игроки через input-канал».** Индустрия делает так для **бот-заполнителей мест игроков** (survivor-боты L4D, filler-боты в PvP) — там NPC буквально обязан быть неотличим от игрока. Но массовые юниты (крипы SC/AoE, биттеры Factorio, толпы UE5 Mass) управляются **системой внутри симуляции**, а не input-каналом. UE5 прямо разводит: ECS-Mass для крауда, «traditional AI» для геймплейно-важных NPC — «не пытайтесь сделать одну систему всем».

**Вердикт по гипотезе автора:** ❌ как основная архитектура. ✅ как **общий формат**: переиспользовать модель скоринга (considerations/curves/веса) и формат JSON-документа поведения, но исполнять NPC-мозг **внутри тика**. Это гибрид «общий словарь считалок/кривых как контент, разное исполнение и восприятие».

### 5. Data-driven авторинг для дизайнеров

Fluxus уже имеет всё нужное: universal evaluator, Expression/Action DSL (JsonLogic-совместимый), пространственные запросы (`withinRadius`/`nearestTo`/`limit`/`withTag`), способности с триггерами (input/event/always) и машину состояний каста в данных. Индустриальный принцип «mechanism in code / policy in data» (Jason Gregory, *Game Engine Architecture*): движок — универсальный исполнитель, всё, что тюнит дизайнер, — в JSON.

Форматы авторинга поведения в индустрии:
- **BT в JSON/asset** (Unreal BT, множество редакторов с экспортом в JSON) — узлы sequence/selector/decorator/task; читается и визуально отлаживается.
- **Utility как контент** (IAUS/Curvature-редакторы Dave Mark/apoch): базы considerations и кривых; дизайнер собирает AI-пакет за минуты, «core behaviors» переносятся между NPC.
- **Скриптовые ротации боссов как таблицы** (WoW-подобные энкаунтеры): фаза → список способностей с приоритетом, кулдауном, условием, телеграфом.
- **UE5 StateTree** — иерархические состояния как альтернатива per-entity BT, «прожорливым на масштабе»; для крауда триггерятся из Mass через signal-подсистему (событийно, не polling).

Отладка без программиста: визуальный дебаг-слой (как StateTree Debug Panel / ImGui-оверлеи Director'ов), показывающий текущую фазу, скоры considerations, выбранное действие, threat-таблицу. Для Fluxus — детерминизм это подарок: любой баг воспроизводится из записанных вводов побитово.

### 6. Что реально шарить между ботом и NPC

**Шарится (формат/механизм):**
- Модель скоринга: considerations → response curves → взвешенная сумма/выбор.
- Словарь кривых (linear, logistic, quadratic, step, …) как переиспользуемый контент.
- Формат JSON-документа поведения и его schema.
- Универсальный evaluator DSL (уже ядро Fluxus).

**Обязано разойтись:**
- **Восприятие:** бот — FoW-снапшот (transferable-буферы, воркер); NPC — прямое чтение ECS/SoA или отдельная дешёвая perception-модель внутри тика.
- **Канал влияния:** бот — `InputFrame`; NPC — Command Buffer.
- **Размещение/каденс:** бот — воркер вне потока сервера; NPC — система внутри `tick()`.
- **Случайность:** оба сеяны, но у NPC поток RNG — часть sim-состояния (`npc-ai`), у бота — свой изолированный.
- **«Человечность»:** только у бота (задержки/шум/джиттер); NPC такого не имитирует.

### 7. Движение масс при пустом pathfinding-шве

Иерархия стоимости: **A\* на каждого юнита** (дорого, N-кратно) → **flow field / vector field** (один расчёт поля на цель, разделяется всей волной; Supreme Commander 2, Elijah Emerson, Game AI Pro) → **steering behaviors** (локально: seek + separation + obstacle avoidance; Craig Reynolds). SC2 и SupCom2 комбинируют flow fields с flocking для сотен-тысяч юнитов.

**Минимально достаточно для арены (пока NavigationApi пуст):**
1. Shared flow field к текущей цели/герою (пересчёт при смене цели), либо — для открытой арены без лабиринтов — прямой seek к цели.
2. Локальный steering: separation (антитолкучка) + простое обход статичных препятствий.
3. «Атака в контакте»: при входе в attack-range переход HFSM Chase → Attack, стоп движения.

Всё это — целочисленно (Q16.16), детерминированно, без внешнего A\*. Flow field отлично ложится на туман-дефенс/волновую геометрию (как tower-defense: одно поле, вся волна рероутится). Полноценный A\*/HPA\* за `NavigationApi` откладывается до появления сложной геометрии.

### 8. Боссы с фазами

Паттерн, проверенный WoW/Impossible Bosses, ложится на Fluxus DSL:

- **Фазы — HFSM в данных.** Переходы по %HP (порогам), таймерам, событиям (умер add, разрушена колонна). Impossible Bosses: energy-pool → ultimate при заполнении (инвула + 3 с задержки), counterable-абилки (F-контр останавливает конкретный каст), phase-переходы под %HP (birdform <20%).
- **Каст-ротации.** В каждой фазе — список способностей с приоритетом, кулдауном, условием (JsonLogic), целевым правилом (nearestTo/withinRadius/withTag), и телеграфом (windup-фаза каста уже есть в spec).
- **Телеграфирование.** Читаемый windup/tell перед атакой — фундамент честного боя (Game Developer, ARPG readability). В Fluxus это фаза каста (машина состояний) + событие для визуала/звука на клиенте.
- **Приоритеты атаки / threat.** Threat-таблица (как MMO): накопление угрозы от урона/хила, taunt-переопределение, переключение по порогу. Плюс правила «босс бьёт дальнего кастера / бьёт по позиционированию».
- **Реакции на игроков.** Пространственные запросы: «если >3 героев в радиусе R — AoE-nuke»; «если никого в ближнем — gap-closer»; «раскидать по расстоянию».

Механизм (в коде): исполнитель HFSM/ротаций, вычисление условий, применение каста через Command Buffer, threat-таблица как компонент. Политика (в JSON): состав фаз, пороги, список/приоритеты/кулдауны способностей, кривые угрозы, телеграф-тайминги.

### 9. Производительность и аллокационная дисциплина

- **Бюджет.** При server-authoritative тике фиксированной частоты бюджет ИИ — доля тика (ориентир из AoE — ~30% на AI & pathing, но для арены цель — «≪1 мс на сотню NPC»). Factorio-правило «1 мс дорого, >5 мс — очень значимо» — хороший ментальный якорь.
- **Амортизация.** Staggered/round-robin: обновлять решения 1/N агентов в тик (Mat Buckland, *Programming Game AI by Example*: «не обязательно обновлять все компоненты каждый шаг; частота назначается по критичности/стоимости»). Движение — каждый тик; выбор цели/действия — по интервалу. Decision-budget: фиксированное число «дорогих» решений (смена цели, пересчёт поля) на тик, как time-sliced pathfinder Factorio.
- **LOD для ИИ.** Дальние/неактивные NPC — реже и дешевле (UE5 Mass LOD; CitySample: полный скелет вблизи, лёгкие Mass-entity вдали). Для арены — «спящие» до входа в активную зону.
- **UE5 Mass как ориентир по стоимости.** ECS-архетипы, contiguous fragments, cache-friendly итерация тысяч сущностей за кадр; StateTree будится через Mass Signal (событийно). Профиль CitySample (Epic Games Japan, CEDEC 2022): Mass-процессоры порядка 1.4–3.4 мс на кадр в тяжёлой краудовой сцене, GameThread-боттлнек растёт с числом агентов/трейтов — отсюда упор на LOD и async.
- **Аллокационная дисциплина Fluxus.** Горячий путь тика не аллоцирует пропорционально числу сущностей: SoA/TypedArrays, мутации только через Command Buffer, скоринг с переиспользованием буферов (scratch-массивы на систему, не на агента), threat/flow-field — предвыделенные структуры.

## Recommendations

**Этап 0 — фундамент формата (сейчас).** Зафиксировать общий JSON-формат поведения и словарь response curves как контент, разделяемый ботом и NPC. Вынести модель скоринга (considerations → curves → выбор) в переиспользуемый модуль ядра поверх существующего evaluator. Benchmark-порог: формат должен описывать и utility-выбор бота, и HFSM-фазу босса без расширения ядра.

**Этап 1 — крипы как система внутри тика.** Реализовать нативную `NpcBehaviorSystem` за интерфейсом `System`: HFSM (Idle/Acquire/Chase/Attack/Retreat) + threat/aggro-таблица как компонент + utility-скоринг цели/действия из JSON. Восприятие — прямое чтение ECS; влияние — Command Buffer; RNG-поток `npc-ai`. Движение — прямой seek + separation (без A\*). Порог перехода к flow field: когда на арене появляется статичная геометрия/хокпоинты, ломающие прямой seek.

**Этап 2 — волны как Director-слой.** Отдельная система-режиссёр (спавн/состав/давление волн) из контентных таблиц, поверх поведения отдельного крипа. Метрика давления опциональна (L4D-style), но начать со скриптованных волн. Порог усложнения: если бои монотонны — добавить intensity-метрику и адаптивный спавн.

**Этап 3 — боссы с фазами.** HFSM-фазы в данных (%HP/таймер/event) + каст-ротации (приоритет/кулдаун/условие/цель/телеграф) поверх существующей машины состояний каста. Телеграфы через фазу каста + событие визуалу. Реакции на позиционирование через пространственные запросы DSL.

**Этап 4 — движение масс (когда нужен pathfinding).** Реализовать shared flow field за `NavigationApi` (детерминированно, Q16.16). Полноценный A\*/HPA\* — только если геометрия арен станет лабиринтной.

**Сквозная дисциплина:** staggered-обновления (1/N в тик), decision-budget на дорогие пересчёты, LOD для «спящих» NPC, scratch-буферы на систему. Порог тревоги: ИИ-часть тика приближается к ~1 мс на сотню NPC — включать более агрессивный staggering/LOD.

**Что НЕ делать:** не вешать утилити-мозг бота в воркере на крипов; не гонять NPC через `InputFrame`/FoW-снапшот; не тащить GOAP/HTN на массовых юнитов.

## Caveats

- **Конкретные per-agent µs/мс для IAUS на масштабе** («Building a Better Centaur», GDC 2015) публично не выложены — абстракт говорит лишь «significantly less processing time» и «7 минут на AI-пакет»; точные цифры производительности за paywall GDC Vault. Вывод о масштабируемости utility опирается на этот доклад + практику UE5 Mass/StateTree.
- **Числа UE5 Mass (1.4–3.4 мс, CitySample)** — из вендорского профиля Epic Games Japan (CEDEC 2022) для крауда MetaHuman'ов, не для top-down арены; это ориентир порядка величины, не прямой перенос.
- **Детали tick-seeded RNG StarCraft II** — из уважаемого технического разбора (Medium/adequatesource), не из первичной документации Blizzard; трактовать как правдоподобную реконструкцию.
- **«30 секунд веселья» Bungie / time-slicing Halo** — задокументирована дизайн-модель, но конкретные per-frame бюджеты ИИ Bungie публично не приводит; любые «Halo при X мс» непроверяемы.
- **Impossible Bosses** — коммьюнити-карта WC3 без официального постмортема; описания механик — из вики/воркшопов фанатов, надёжны как геймплейный референс, но не как инженерный источник.
- **Fluxus-специфика.** Рекомендации приземлены на README/openspec репозитория (детерминизм, ECS-SoA, DSL, пустой NavigationApi, спека бота), но детальные интерфейсы (`System`, Command Buffer API) не читались построчно — при реализации сверяться с актуальными openspec-спеками.
