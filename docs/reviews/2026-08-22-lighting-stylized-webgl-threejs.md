# Освещение для Fluxus: лучшие практики стилизованного света в WebGL/three.js

## TL;DR
- **Гибридная схема «запечённый уровень + один реалтайм-directional на персонажей» — единственно верный путь.** Статичную геометрию из Blender запекайте в lightmap (второй UV, KTX2/UASTC, `lightMap`+`aoMap`), динамику (персонажи, снаряды, пропсы) освещайте одним общим directional-светом плюс дешёвый ambient/hemisphere/LightProbe для заполнения. Реалтайм-теней — минимум: одна CSM-каскадная тень от «солнца» либо blob-тени под персонажами.
- **Читаемость важнее реализма.** Следуйте гайдам Valve (Dota 2 Character Art Guide) и Riot (LoL VFX Style Guide): жёсткая структура тонов (тёмный низ → светлый верх у персонажей), сдержанный фон по значению, рим-свет для отделения силуэтов, team-color и bloom только на важных элементах. Dota 2 использует deferred-освещение — вам оно в WebGL недоступно и не нужно; имитируйте результат запеканием.
- **Бюджет для веба/Steam Deck жёсткий.** Держитесь forward-рендера three.js, ≤1–2 теневых источника, избегайте множества point/spot с тенями и дорогого постпроцессинга. Steam Deck — это 8 RDNA2 CU @ 1.6 ГГц (1.6 TFLOPs FP32, 6-нм AMD APU, экран 1280×800 60 Гц); по бенчмаркам сообщества это ~86% GTX 1050 и ~95% RX 560. Целитесь в 60 FPS на интегрированной графике. Свет должен оставаться чисто косметическим и никогда не касаться детерминированного симуляционного ядра (соответствует принципу однонаправленных зависимостей Fluxus).

## Ключевые выводы

### Привязка к архитектуре Fluxus
Репозиторий подтверждает разделение слоёв, критичное для освещения:
- `core-ts/` — детерминированное ECS-ядро, **нулевые рантайм-зависимости**, работает в Web Worker. Освещение НЕ должно попадать сюда ни при каких условиях.
- `render-ts/` — рендер на three.js, содержит модули **extractor, host, viewBuffer, models и их подсистемы**. Всё освещение живёт здесь.
- `assets-ts/` — реестр ассетов, загрузчики **MDX и PNG**, манифест; о three.js не знает (ASSET-5). Построение сцены — в `render-ts`.
- `content/visuals/` — манифест визуалов, модели, текстуры. ID ассета = путь в дереве (ASSET-2).
- Данные идут из ядра в воркере через канал поверх transferable-буферов (SHELL-1..7); `render-ts` их читает через extractor→host→viewBuffer.

**Важные следствия для освещения:**
1. Свет, тени, тонмаппинг, постпроцессинг — целиком в `render-ts`, за границей воркера. Это уже правильно архитектурно: освещение косметическое по определению и не нарушает детерминизм.
2. **Замечание по пайплайну:** README документирует загрузчики MDX и PNG в `assets-ts`, а НЕ glTF. Задача исходит из установленного Blender→glTF-пайплайна — если glTF-загрузчик ещё не в коде, его надо добавить в `render-ts` (там, где строится сцена), а не в `assets-ts`. Проверьте это в коде: от этого зависит, как запечённые lightmap попадут в движок.
3. Интерполяция между тиками для рендера в README не подтверждена — проверьте в `render-ts/src`. Для плавного света на движущихся персонажах интерполяция позиций желательна, но она уже относится к трансформациям, не к свету.

### Арт-дирекшн: как добиться вида Dota/Warcraft
Ключевой первоисточник — **Dota 2 Character Art Guide** от Valve (публичный PDF, зеркало на wiki.polycount.com, актуальная веб-версия на support.steampowered.com). Основные принципы, подтверждённые несколькими источниками:

- **Структура значений (value) — фундамент.** Общая тональность персонажа: темнее у ног, светлее к торсу и голове — глаз игрока притягивается к светлому верху, где лицо/оружие/иконография. Это буквальная рекомендация гайда Dota 2.
- **Компрессия значений.** Стилизация использует сжатый динамический диапазон с явными ступенями (тень/полутон/свет), а не непрерывный градиент фотореализма — именно это даёт читаемую «форму» света. [Nasty Rodent](https://nastyrodent.com/stylized-3d-characters-art-direction-principles/) Избегайте крайних 0% и 100% в палитре, работайте средним диапазоном.
- **Фон тише персонажей.** Держите значения фона чуть темнее, чтобы силуэты читались мгновенно — критично для быстрых боёв. [GamineAI](https://gamineai.com/blog/lighting-2d-action-game-silhouettes-rim-ambient-shader-basics-2026)
- **Рим-свет (backlight) для отделения силуэта.** Стилизованные проекты (Marmoset-воркфлоу, Arcadegeddon, LoL) используют яркий, часто цветной рим-свет позади персонажа, чтобы отделить его от фона [ArtStation](https://www.artstation.com/artwork/yJWbGx) и добавить объём. В three.js его дают либо второй directional-свет сзади-сверху, либо fresnel/rim в шейдере.
- **Трёхточечная схема как основа.** Key (главный, ~45° — самый читаемый угол), [Generalist Programmer](https://generalistprogrammer.com/tutorials/game-lighting-design-complete-visual-guide-2025) fill (мягкий, не даёт теням уйти в чёрное), rim (отделение). Fill не должен «сплющивать» — если видно всё одинаково, уменьшайте fill. [GamineAI](https://www.gamineai.com/blog/game-lighting-design-creating-atmosphere-and-mood-in-your-games)
- **Team-color и цвет.** Урок Warcraft III Reforged: провал читаемости произошёл из-за размытых/бледных team-color и переусложнённых моделей — игроки на форумах Blizzard прямо жаловались, что не различают юниты в бою («colors make me dizzy; I can't tell what's happening in battles»). Держите team-color насыщенными и на крупных, чистых участках; ограничивайте детализацию ради читаемости.
- **Bloom/emissive выборочно.** Гайд LoL VFX: illumination усиливает контраст и «магию» эффектов, но только на первичных элементах; вторичные — тише по value и saturation. Принцип Riot — «immediate clarity with minimal visual noise».
- **Верхне-левое освещение** — интуитивная конвенция (свет сверху), удобная для top-down.

### Освещение статичной геометрии: запекание в Blender
Поскольку Blender→glTF — установленный пайплайн, запекать свет уровня в Blender полностью оправдано (свет здесь «бесплатен» в рантайме):

1. **Второй UV-канал.** Основной UV (`uv`) — под тайловые текстуры; второй UV (`uv1`/в three.js становится `uv2`) — под lightmap, без наложений, весь остров в пределах 0–1. Используйте Smart UV Project или Lightmap Pack.
2. **Bake в Cycles.** Ставите свет в сцене → создаёте пустую текстуру → Bake типа «Combined» или отдельно диффуз+тень. Денойз обязателен (уменьшает семплы). Типовые значения из практики (tchayen, baked lighting in r3f): 2048–4096 текстура, 128 семплов, ≥4px margin (иначе bleeding на краях).
3. **Проверьте нормали** — Cycles беспощаден к вывернутым нормалям (чёрные пятна при запекании), тогда как во вьюпорте они прощаются.
4. **Экспорт glTF.** Blender-glTF экспортирует второй UV. Lightmap подключается в three.js вручную или через glTF; three.js ожидает `lightMap` на `uv2`.
5. **Формат.** Для lightmap-цвета three.js рекомендует `LinearSRGBColorSpace` и float-форматы (.exr/.hdr) для HDR-света; для LDR — KTX2/UASTC (качество как BC7, подходит и для данных) с Zstandard-суперкомпрессией. Не переусердствуйте с RDO — он ухудшает качество lightmap ради размера. Инструмент: `gltf-transform` / `toktx` (KhronosGroup/KTX-Software).

### Подключение в three.js
```js
// Статичная геометрия (уровень)
material.lightMap = lightmapTexture;      // на uv2
material.lightMap.colorSpace = THREE.LinearSRGBColorSpace;
material.lightMapIntensity = 1.0;
material.aoMap = aoTexture;                // тоже uv2, красный канал
material.aoMapIntensity = 1.0;
// ВАЖНО: geometry должна иметь attribute 'uv2' (в новых three.js — 'uv1').
// GLTFLoader создаёт второй UV автоматически при наличии в файле.
```
- **KTX2Loader** с `detectSupport(renderer)` для загрузки сжатых lightmap; транскодер basis из `three/addons/libs/basis/`.
- **Материалы:** для стилизованного вида `MeshLambertMaterial` дешевле и часто достаточен (per-fragment на новых версиях); `MeshStandardMaterial` даёт PBR и корректно работает с `envMap`/`lightMap`, но дороже. Для чисто hand-painted вида без PBR — `MeshBasicMaterial` + lightMap (свет полностью запечён, реалтайм-свет не влияет) или toon/matcap.

### Освещение динамических объектов
Персонажи, снаряды, физ-пропсы не могут иметь lightmap. Подход, подтверждённый документацией three.js и практикой:
- **Общий directional-свет** («солнце») — один на всю сцену, направление совпадает с направлением запечённого света уровня (иначе персонажи будут «наклеенными»).
- **Заполнение (fill/ambient):**
  - `HemisphereLight` (цвет неба сверху / цвет земли снизу) — очень дёшево, естественный уличный тон.
  - `AmbientLight` низкой интенсивности (0.1–0.5) — чтобы тени не уходили в чёрное.
  - **`LightProbe` (диффузные сферические гармоники)** — лучший вариант «под запечённый уровень». Функционально эквивалентен irradiance-карте; хранит свет, проходящий через точку пространства. Динамика, попадая в зону probe, получает отражённый/непрямой свет уровня. В three.js: `LightProbe` + `LightProbeGenerator.fromCubeRenderTarget()` из CubeCamera, размещённой в ключевых точках арены. Официальная позиция three.js (PR #16223, WestLangley): статику лучше лайтмапить, а динамику освещать через LightProbe — именно эта категоризация вам и нужна.
- **IBL/env map:** `scene.environment` из `PMREMGenerator.fromScene(RoomEnvironment())` (без файла) или из HDRI — даёт дешёвое общее освещение и корректные отражения на `MeshStandardMaterial`. `environmentIntensity`/`envMapIntensity` регулируют силу. Для стилизации держите интенсивность умеренной, чтобы не «замыливать» цвета.
- **Согласование запечённого и реалтайм-света:** совпадение направления, цветовой температуры и интенсивности между Blender-светом уровня и three.js directional-светом персонажей — главное условие, чтобы персонажи не выглядели наклеенными. Практический тест из арт-дирекшн: рендер каста при трёх условиях (key спереди, key сбоку, только rim) на 25% насыщенности — если силуэты сливаются, компрессия значений недостаточна. [Nasty Rodent](https://nastyrodent.com/stylized-3d-characters-art-direction-principles/)

### Тени
- **Реалтайм-теней — минимум.** Тени в three.js forward-рендере дороги, пересчитываются каждый кадр.
- **Вариант A — одна directional-тень с CSM.** Аддон three.js `CSM` (из `three/addons/csm/CSM.js`, оригинал StrandedKitty/three-csm; есть TS-порт alexnil/three-csm-typescript). Настройки: desktop `cascades: 4, shadowMapSize: 2048`, Steam Deck/слабое железо `cascades: 2, shadowMapSize: 512–1024`, `mode: 'practical'`, `fade: true`. `csm.setupMaterial(material)` обязателен. Для top-down арены каскады можно упростить — камера смотрит вниз, дальность ограничена.
- **Вариант B — blob-тени (рекомендуется как база).** Тёмный круг/декаль под персонажем. Очень дёшево, отлично читается позиция над землёй, широко применяется в мобильных/веб-играх. Подход Mario Odyssey: directional вниз для главного персонажа без двойной тени; либо декаль на несколько см ниже ног (трюк Yooka-Laylee). Можно запечь силуэт персонажа в текстуру blob. Blob-тени практически не имеют статистически доказанного проигрыша по восприятию против shadow map для платформеров (diva-portal), при огромной экономии.
- **Гибрид:** blob под всеми юнитами + одна CSM-тень от солнца только для крупной статики/боссов, если нужно.
- **Настройки shadow map при использовании:** `renderer.shadowMap.type = THREE.PCFSoftShadowMap`, `shadow.bias ≈ -0.0005`, вручную подгоняйте `shadow.camera` frustum под сцену (не оставляйте дефолт), `shadow.mapSize` минимально достаточный. Память shadow map растёт квадратично с размером.

### Тонмаппинг и цветокоррекция
- **Выбор оператора:**
  - `ACESFilmicToneMapping` — кинематографичный, но «вымывает» насыщенность и уводит яркие цвета к белому (canary yellow, яркие green/blue недостижимы — modelviewer.dev); для стилизованного яркого вида это минус.
  - `AgXToneMapping` — нейтральнее, но «сплющивает» изображение, теряет насыщенность и характер (по обсуждениям three.js discourse). Дефолт Blender 4.x — удобно для консистентности с Blender-запеканием.
  - `NeutralToneMapping` (Khronos PBR Neutral) — по официальному релизу Khronos (16 мая 2024) обеспечивает «faithful reproduction of a product's base color, hue and saturation... while eliminating HDR artifacts around highlights»; референс-реализация — всего 13 строк GLSL; уже поддержан three.js, Blender, Babylon.js, Filament. В Blender добавлен как view transform в версии 4.2.
  - **Рекомендация:** для Dota/Warcraft-вида начните с `NeutralToneMapping` или даже `Linear/NoToneMapping` при запечённом свете (диапазон уже под контролем художника) — они сохраняют насыщенность team-color. ACES берите только если нужен явный HDR-bloom и кинематографичность. Настраивайте `renderer.toneMappingExposure`.
  - `renderer.outputColorSpace = THREE.SRGBColorSpace` — обязательно.
- **Цветокоррекция через LUT.** `LUTPass` + `LUTCubeLoader`/`LUT3DLoader` (аддоны three.js, поддержка .cube/.3dl из Photoshop/DaVinci). Применять после основного рендера, до/после bloom по вкусу, в linear RGB. Один .cube LUT задаёт единый «look» всей игры дёшево — это стандартный приём цветового скриптинга. LUT можно интерполировать между двумя для смены настроения (день/ночь). Храните LUT в KTX2/сжатыми.

### Постпроцессинг
- **Bloom — выборочно.** `UnrealBloomPass` дорогой (жалобы на three.js discourse: ~90% GPU и 40 FPS на Core i7 при bloom на одном объекте). Используйте selective bloom по слоям (`layers`) или по emissive (`webgpu_postprocessing_bloom_emissive`-подход), чтобы светились только заклинания/emissive-детали, а не вся сцена. Для веба/Deck рассмотрите более дешёвый dual-bloom (ycw/three-dual-bloom).
- **AO — запекать, не считать в реалтайме.** SSAO/SAO в WebGL дороги. Запекайте AO в Blender в `aoMap` вместе с lightmap. Если нужен реалтайм — `SAOPass` дешевле полноценного SSAO, но для арены обычно не нужен.
- **emissive для «магии»:** glTF `KHR_materials_emissive_strength` (Blender 3.3+ поддерживает значения >1) [Khronos](https://www.khronos.org/blog/blender-gltf-i-o-support-for-gltf-pbr-material-extensions) + selective bloom даёт светящиеся заклинания/руны. three.js читает расширение; проверьте, что значения >1 доходят.
- **Порядок пассов:** RenderPass → (selective) bloom → LUT/tonemapping (OutputPass) → FXAA последним (FXAA требует sRGB-вход). MSAA/antialias: на Deck ограничьте `pixelRatio` до 2 и рассмотрите отключение AA — Dota 2 сама держит Anti-Aliasing Off на всех уровнях (по данным ProSettings.net, 43 про-игрока, март 2026: ~10% стоимости FPS, а стилизованный арт почти не страдает от алиасинга на 1080p+).

### Бюджет производительности (веб + Steam Deck)
- **Лимит источников света в forward-рендере three.js.** Каждый пиксель итерирует по всем источникам; лимит упирается в `MAX_FRAGMENT_UNIFORM_VECTORS`. По webgl2fundamentals минимум для фрагментного шейдера — **16 векторов** в WebGL1 (256 vertex / 224 fragment в WebGL2), и «если используете больше — код не заработает на машине с минимумом». SpotLight ест ~6 значений — на минимальном железе не влезает и 3 spot. Практика: 30 directional/point-источников уже роняют кадр или ломают рендер (сообщения о крахе на 13/30 источниках с тенями). **Deferred-рендеринг в WebGL непрактичен — не пытайтесь.** Отсюда — запекание как основная стратегия.
- **Целевое железо.** Steam Deck: 8 RDNA2 CU @ 1.6 ГГц, 1.6 TFLOPs FP32, 16 ГБ LPDDR5-5500, экран 1280×800 60 Гц (офиц. спеки Valve); ~86% GTX 1050 и ~95% RX 560 по расчётам сообщества. Бенчмарк Dota 2 на Deck (leaked dev-kit, Tom's Hardware): до 47 FPS на highest, 80 FPS на low в нативном 1280×800. Интегрированная графика и Deck делят память CPU/GPU → draw calls дороже (memory contention). Минимизируйте draw calls (батчинг, merge статики, InstancedMesh для повторяющихся пропсов/снарядов).
- **Electron/Steam-нюанс:** производительность в Electron/Chromium-обёртке может быть заметно ниже, чем в системном браузере (жалобы на Babylon-форуме о ~200% просадке); убедитесь, что WebGL использует дискретную GPU (`powerPreference: 'high-performance'`, но на многих системах атрибут игнорируется). На Steam Deck (Linux/Proton) встречаются проблемы с аппаратным ускорением WebGL (баг open-duelyst #248) — тестируйте на реальном устройстве рано. Steam Overlay не поддерживает браузерные игры на многих платформах.
- **Чек-лист «чего избегать»:** много теневых источников; SSAO/SSR; тяжёлый bloom на всю сцену; RectAreaLight (дорогой, только Standard/Physical); дефолтные frustum'ы теней; `pixelRatio` выше 2 на Deck.
- **Правило три.js:** ставьте `near` камеры выше, `far` ниже; `BufferGeometry` всегда; переиспользуйте материалы/геометрии; `dispose()` неиспользуемого; LOD для дальних объектов.

## Детали и рекомендуемая архитектура освещения

**Что запекать (offline, в Blender):**
- Непрямой свет + тени статичной геометрии уровня → `lightMap` (второй UV, KTX2/UASTC или EXR).
- Ambient occlusion статики → `aoMap` (второй UV).
- При желании — цветовой градиент/gradient mask на персонажах (трюк из гайда Dota, описан на polycount: запечь свет сверху в маску для эффекта тёмный-низ→светлый-верх).

**Что оставить реалтайм (в `render-ts`):**
- Один directional-свет («солнце») для всей динамики, направление = направлению света уровня.
- `HemisphereLight` + низкий `AmbientLight` ИЛИ сетка `LightProbe` для непрямого заполнения динамики.
- `scene.environment` (PMREM из RoomEnvironment или лёгкого HDRI) для отражений/IBL.
- Опционально: рим-directional сзади-сверху ИЛИ fresnel-rim в шейдере персонажей.
- Тени: blob под всеми юнитами; опционально одна CSM-тень от солнца.
- emissive + selective bloom для заклинаний/эффектов.

**Размещение LightProbe:** сетка probe по игровой плоскости арены (например, узлы 4–8 м), генерируйте через CubeCamera+`LightProbeGenerator` на этапе загрузки уровня, выбирайте ближайший probe (или интерполируйте) для каждого динамического объекта. Для одной небольшой арены с равномерным освещением может хватить одного probe + hemisphere. Для разных зон освещённости (свет/тень арены) нужны несколько.

**Порядок работы над светом уровня** (из level-design практики, leveldesignbook.com): глобальный свет → свет для навигации/читаемости → геймплейный свет (подсветка целей/интерактивного) → детали/настроение. После каждого прохода — проход оптимизации. [The Level Design Book](https://book.leveldesignbook.com/process/lighting)

## Рекомендации (поэтапно)

**Этап 1 — база (сделать сразу):**
1. Проверьте в `render-ts/src`: версия three.js, есть ли GLTFLoader, текущие камера/свет/материалы, есть ли интерполяция тиков. Если glTF-загрузки нет — добавьте GLTFLoader + KTX2Loader в `render-ts` (не в `assets-ts`, по ASSET-5).
2. Настройте рендерер: `outputColorSpace = SRGBColorSpace`, `toneMapping = NeutralToneMapping` (старт), `toneMappingExposure` под вкус, `shadowMap.enabled` только если используете CSM.
3. Освещение динамики: один directional + HemisphereLight + низкий Ambient. Blob-тени под юнитами.
4. Материалы уровня: `MeshLambertMaterial` или `MeshStandardMaterial` c `lightMap`+`aoMap`.

**Этап 2 — запекание и согласование:**
5. Настройте Blender-bake: второй UV (Lightmap Pack), Cycles, денойз, 2048–4096, ≥4px margin. Экспорт glTF со вторым UV.
6. Сожмите lightmap в KTX2/UASTC (gltf-transform/toktx), подключите через `lightMap` на uv2.
7. Согласуйте направление/цвет/интенсивность реалтайм-directional с запечённым светом. Прогоните тест «25% насыщенности / 3 условия света».

**Этап 3 — стилизация и полировка:**
8. Добавьте рим-свет (второй directional сзади-сверху или fresnel-шейдер) для отделения силуэтов.
9. Настройте team-color: насыщенные, на крупных участках, проверьте различимость в бою.
10. Selective bloom по слоям только для emissive-заклинаний. `KHR_materials_emissive_strength` для HDR-emissive.
11. LUT-цветокоррекция (`LUTPass` + .cube) для единого «look». FXAA последним.
12. LightProbe-сетка, если одного hemisphere мало для непрямого света динамики.

**Этап 4 — оптимизация под Deck/веб:**
13. Профилируйте на реальном Steam Deck и на интегрированной графике рано.
14. Батчинг/InstancedMesh для снарядов/пропсов; сокращайте draw calls.
15. Пресеты качества: Deck → `pixelRatio ≤ 2`, тени 512–1024 или blob-only, bloom off/дешёвый, AA off.
16. `powerPreference: 'high-performance'`; тестируйте WebGL-ускорение в Electron на Deck.

**Пороги, меняющие решения:**
- Если FPS < 60 на Deck → уберите CSM, оставьте только blob-тени; отключите bloom или замените на dual-bloom.
- Если персонажи выглядят «наклеенными» → сначала согласуйте направление/цвет directional со светом уровня, затем добавьте LightProbe.
- Если team-color сливаются (урок Reforged) → поднимите насыщенность, увеличьте площадь цвета, затемните фон.
- Если цвета «вымыты» → уйдите с ACES на Neutral/Linear.
- Если > ~2 теневых источников или много point с тенями → переносите в запекание.

## Оговорки
- **Детали `render-ts` не верифицированы на уровне кода.** Подтверждены модули extractor/host/viewBuffer/models из README, но точная версия three.js, существующие свет/камера/материалы, наличие интерполяции тиков и glTF-загрузчика не были доступны для проверки (глубокие пути репозитория не открывались инструментом). README упоминает загрузчики MDX и PNG, а не glTF — это расхождение с посылкой задачи; проверьте в коде, прежде чем строить пайплайн запекания.
- **Deferred-освещение Dota 2 в вебе невоспроизводимо.** Dota 2 использует deferred-модель с динамическим светом (Valve Developer Wiki); в WebGL forward-рендере это недоступно — целевой вид достигается запеканием + аккуратным реалтайм-заполнением, а не копированием их пайплайна.
- **Blob-тени vs shadow map — восприятие.** Академические данные (diva-portal) не смогли статистически доказать превосходство shadow map над blob для платформеров; для арены blob обычно достаточны и сильно дешевле, но финальное решение — за плейтестами читаемости.
- **KTX2 для lightmap.** UASTC годен, но у lightmap бывают артефакты компрессии на градиентах; сравните с EXR/RGBD-PNG перед финализацией. Отключайте RDO для максимального качества.
- **Оценки железа Steam Deck** (~86% GTX 1050 / ~95% RX 560) — приближения из бенчмарков сообщества, не официальные эквиваленты; официальны только сами спеки Valve (1.6 TFLOPs, 8 CU). Реальный FPS сильно зависит от оптимизации и должен измеряться на устройстве.
- **Тонмаппинг субъективен.** Рекомендация Neutral/Linear для стилизации — отправная точка; финальный выбор оператора и exposure делается художником на реальных ассетах.
- Часть источников — форумы (three.js discourse, Blender Artists) и сообщения разработчиков; API-детали three.js могут меняться между версиями (напр. `uv2`→`uv1`, `RGBELoader`→`HDRLoader` в новых ревизиях) — сверяйтесь с docs вашей версии.
