# Запас тика ядра под массовой нагрузкой: замеры и гэпы оптимизации — 2026-09-02

Не нормативный документ: цифры — с одной машины и с одного дня, нормой остаются спеки (`performance-budget`, `npc-behavior` NPC-9). Цель — ответить на два вопроса после чистки 2026-09-01: сколько сущностей тик держит сейчас и где в ядре остались резервы, не требующие ломать принципы (`CLAUDE.md`, «Неснимаемые принципы»).

## TL;DR

- **Тик масштабируется линейно по агентам.** Нагрузка `npc-stress` (196 массовых крипов, режиссёр, маршрут, двое героев) размножена ×2 и ×4 сдвигом позиций: 196 → 392 → 784 агентов стоят 1.72 → 2.9 → 4.9 мс/тик в debug-сборке и 1.02 → — → 2.94 мс в релизной (`NODE_ENV=production`). Стоимость агента падает с ростом толпы (7.5 → 6.1 мкс debug, 5.2 → 3.75 мкс release): квадратичных членов нет, сетка соседей с бюджетом осмотра (`EXAMINE_LIMIT`) и пересчёт расхождения по интервалу делают своё дело.
- **Запас при 60 Гц (16.7 мс на тик):** порядка 2 500 массовых агентов в debug и 4 000+ в релизе — на одном потоке, до учёта сети и рендера, которые в ядре не живут. Записанные матчи двух героев стоят 17–23 мкс/тик, то есть ничего.
- **Гейт и бенчи меряют debug-сборку.** `DEBUG = NODE_ENV !== 'production'`, и `vitest` его не переопределяет: каждое `add`/`mul`/чтение поля несёт assert. Релиз на 40 % дешевле, и профиль в нём другой — доминируют чтения ECS и командный буфер, а не арифметика.
- **Пять гэпов, по убыванию отдачи на единицу риска:** командный буфер по handle без объектов на команду (~15 % релизного тика), чтение полей в горячих циклах без пятикратной косвенности (~18 %), результат запроса без аллокации размером в мир (~5 % плюс GC), кэш запросов внутри тика (~5 %), быстрый путь `mul` для малых операндов (заметен только в debug). Всё — без изменения результата симуляции: эталоны golden и cost не двигаются, кроме счётчиков, которые эти правки и должны обнулить.

## Как мерилось

Скрипт вне репозитория собирает мир через `buildSimulation` и крутит `tick()` без снапшотов и сериализации — тем же циклом, что `prepareRecording` в `engine/integration-ts/test/benchLoad.ts`; `npm run sim` для замера не годится, потому что сериализует каждый тик (`encode` + запись в stdout — 40 % его времени). Размножение: каждая запись `Creep` документа `npc-stress.load.json` копируется k раз со сдвигом позиции на (0.29, 0.17) юнита, `capacity` поднята до 4096. Лучший из трёх прогонов по 200 тиков после прогрева. Профили — `node --cpu-prof`, самовремя по функциям.

Стоимость агента в релизе упала с 5.2 до 3.8 мкс при 196 агентах и с 3.75 до 2.85 при 784 — линейность сохранилась. Эталоны golden и cost при этом не сдвинулись ни на байт: правка меняет адресацию и контейнеры, а не правила.

## Что гэпом не является

Проверено по коду, а не предположено: сетка соседей (`systems/npc/grid.ts`) обходит кольцами наружу с бюджетом осмотра и выходит с заполнением буфера; расхождение пересчитывается раз в `separationIntervalTicks` со сдвигом по слоту и держится в компоненте (NPC-6, SNAP-1); корень — целочисленный Ньютон с сидом по длине двоичной записи (прежний двоичный поиск уже вычищен); dirty-трекинг покомпонентный; `TickResult` — живой view, не копия; в горячем пути нет ни float, ни libm, ни `BigInt` (`determinism-review/scripts/check.sh` чист, дифф ядра с базы чистки просмотрен построчно). Многопоточность тику не положена по построению (TICK-1, детерминизм), и это не гэп: рендер и сеть уже живут в другом потоке.

## Гэпы

Порядок — по отношению ожидаемой отдачи к риску. Оценки долей — из релизного профиля выше; ни один пункт не меняет результат симуляции, и golden-эталоны при них не двигаются.

### 1. Командный буфер: адресация по handle и хранение без объектов (~15 %) — СДЕЛАНО

Сейчас каждая `setField` — объект `{ kind, entity, component, field, value }` со строковыми именами компонента и поля (`ecs/commands.ts`, `enqueue`), который `validate()` проверяет по строкам через `Map` магазинов, а `applyCommand` разрешает те же строки второй раз (`world.setField` → `storeOf` → `fieldTypeOf`). На 784 агентах это ~4 000 команд и ~4 000 короткоживущих объектов на тик — ровно та аллокация, пропорциональная числу сущностей, которую дисциплина ядра запрещает в горячем пути.

Предложение: `commands.setFieldByHandle(entity, handle, value)` рядом с существующим строковым каналом (строки остаются для JSON-систем и валидации на загрузке); буфер хранит команды в параллельных типизированных массивах (`kind`, `entity`, `handle`, `value`), растущих раз и переиспользуемых между тиками; `validate` для handle-команд — проверка владения по таблице `FieldTable`, без строкового поиска. Семантика CMD-1..CMD-5 не меняется: порядок применения, отложенность, `peekField`, трейс DIAG-2/DIAG-5 (`commandData` собирает имена из таблицы handle'ов при записи трейса, не раньше). Спека: SYS-10 говорит про handle-путь чтения; писать через команды по handle — то же требование, дополненное одной фразой, TICK-3 не трогается (мутация по-прежнему только командой). Кто платит: платформа NPC (пять записей на агента за тик), физика (`Position`/`Velocity`), локомоушен.

### 2. Чтение полей в горячих циклах: колонка вместо пяти вызовов (~18 %) — СДЕЛАНО

`posX(ctx, handles, e)` → `ctx.getByHandle` (замыкание контекста) → `getFieldByHandle` → `toInternal` → `readByHandle` → `aliveIndexOf` (распаковка id: `%` и умножение на `GENERATION_LIMIT`) → `maskHas` → чтение из `Float64Array`. Для сущности, только что выданной запросом с этим компонентом в `all`, живость и владение доказаны построением, и семь шагов ради одного чтения — чистые накладные расходы.

Предложение: запрос выдаёт рядом с id и raw-индексы (второй буфер той же длины; QUERY-2 порядок тот же), а контекст даёт `ctx.column(handle)` — сам типизированный массив колонки. Горячий цикл читает `column[index]`. Тотальность ECS-7 не нарушается: колонка доступна только в паре с индексом из запроса, а запрос уже отсеял всех, кто компонентом не владеет; для остальных чтений остаётся `getByHandle`. Мягкая версия без изменения API — `readByHandle` с `index` вместо `entity` для вызовов внутри одного прохода по запросу. Спека: SYS-10 (handle-путь) — дополнить формой «чтение по индексу запроса»; ECS-7 без изменений.

### 3. Результат запроса без аллокации размером в мир (~5 % + GC) — СДЕЛАНО

`query()` на каждый вызов создаёт `new Float64Array(entities.aliveCount)` — на 784 агентах и десятке запросов за тик это ~10 буферов по 6 КБ на тик, и `collectMatches` при этом обходит ВСЕ слоты до `nextIndex`, проверяя маску каждого. Комментарий в `ecs/query.ts` обещает «без материализации массива живых», но выделение результата всё равно пропорционально миру.

Предложение: `ctx.queryInto(spec, out)` с буфером, которым владеет система (у платформы NPC уже есть `scratch`), либо буфер на спецификацию внутри контекста, переиспользуемый между тиками (спецификации систем — константы, `this.spec ??=`). Побочная выгода — исчезает `subarray` и GC-давление тика; 4 % сборщика мусора в релизном профиле — это в основном команды (гэп 1) и эти буферы.

Гэпы 1–3 закрыты изменением `core-tick-hot-path` (2026-09-02): команда `setFieldByHandle` и журнал команд в типизированных массивах; `ctx.queryInto` в буферы, которыми владеет система, плюс `ctx.getByIndex` — чтение по raw-индексу слота из этой же выборки. Колонку наружу при этом никто не отдал: SYS-10 уточнён так, что запрещённой остаётся изменяемая ссылка на колонку, а запись по handle — та же команда буфера (CMD-1). Переведены платформа NPC, физика, локомоушен и пересчёт видимости; JSON-системы и холодные нативные остались на строковом пути.

### 4. Кэш запросов внутри тика (~5 %)

Восемь систем платформы NPC и физика задают за тик десяток запросов, половина — с одинаковой спецификацией (`{ all: [NpcAgent, Position, Velocity] }` у поведения, движения и угрозы). Состав мира между `flush`'ами меняется только структурными командами (`spawn`/`destroy`/`addComponent`/`removeComponent`), и буфер знает, были ли они. Кэш «спецификация → результат», сбрасываемый на структурном `flush`, убирает повторные обходы слотов; при 30 JSON-системах сцены — где каждая начинается с запроса — выигрыш больше, чем на платформе NPC. Порядок QUERY-2 и семантика CMD-2 (следующая система видит спавны предыдущей) сохраняются по построению: кэш живёт ровно между структурными изменениями.

### 5. Быстрый путь `mul` для малых операндов (в debug ~4 %, в релизе ~1 %)

`|a|·|b| < 2^53` — а это все координаты до ±32 юнитов, умноженные на скорости и веса, — точно в двоичном контейнере: `Math.floor(|a·b| / 65536)` со знаком после даёт тот же результат, что hi/lo-разложение. Проверено на 2^20 случайных пар из этого диапазона — расхождений 0; микробенч в debug: 62 → 16 нс на операцию. В релизе `mul` стоит 2.4 % тика, так что отдача скромная, а FP-2 буквой требует именно hi/lo-эмуляцию в TS — путь нужен как названное применение исключения DET-2 (условие 2), то есть с дельтой FP-2. Делать после гэпов 1–4, если профиль всё ещё покажет.

### Наблюдения без предложения

- **`lengthOf` в расхождении** (7 %) — по одному корню на соседа. Формула вклада (`d · (1/|d| − 1/R)`) уже сведена к одному корню и одному делению; убрать корень целиком можно лишь другой формулой веса, а это правка NPC-6 и эталонов, не оптимизация.
- **Бенч-сентинелы стерегут debug.** Не дефект (PERF-5 требует порядок, не число), но стоит либо печатать `[bench]` в обоих режимах, либо хотя бы назвать режим в строке калибровки: 40 % разницы легко принять за регресс или за ускорение.
- **Контекст тика** собирается заново каждый тик с дюжиной замыканий — документировано в `sim/tick.ts`, стоит константу на тик, в профиле не виден.

## Как проверять

Любой из гэпов проверяется одинаково: golden-эталоны (`npm test` в `engine/core-ts`, `matchGolden.test.ts`) не двигаются, cost-эталоны меняются только там, где правка обнуляет счётчик (гэп 3 не трогает ни одного — счётчики считают работу симуляции, а не аллокации), сторожа `bench.test.ts` печатают новую цифру. Замер «до/после» — тот же скрипт масштабирования на ×1/×4 в обоих режимах сборки; заносить в этот документ строкой рядом с таблицей.
