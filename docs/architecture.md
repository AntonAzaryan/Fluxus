# Архитектурный обзор движка

> Требования переехали в `openspec/specs/` — это документ «как всё устроено целиком» и «в каком порядке строим». Нормативные формулировки живут только в спеках; здесь их дублировать нельзя.

## 1. Слои

```text
┌──────────────────────────────────────────────────┐
│  Blender + аддон — редактор level-дизайна        │
│  Расстановка, террейн, кривизна: кисти и превью  │
│  .blend → .glb → импортёр tools/blender-ts       │
└──────────────┬───────────────────────────────────┘
               │ импорт — операция слоя editor-core (BLND-5, ED-29):
               │ initial, decorations, ассет террейна, карта кривизны
┌──────────────▼───────────────────────────────────┐
│  Редактор (TypeScript, веб и десктоп)            │
│  Data-Driven логика: системы, схемы, prefabs,    │
│  манифест, триггеры; превью и правка сцены       │
│  Вьюпорт — та же реализация rendering + camera   │
└──────────────┬───────────────────────────────────┘
               │ sim-документы: компоненты, системы, prefabs, конфиг сцены
               │ presentation-документы: манифест визуалов, карта кривизны,
               │ парный presentation-слой сцены (ED-3, ED-19, ED-21)
┌──────────────▼───────────────────────────────────┐
│  Deterministic Core (TS, позже Rust)             │
│  ┌────────────────────────────────────────────┐  │
│  │ System Evaluator (JSON → pipeline)         │  │
│  │ Action Executor / Expression (JsonLogic)   │  │
│  │ ECS foundation + Query API                 │  │
│  │ Time / Tween / Snapshot / RNG              │  │
│  │ Visibility (система FoW на TS)             │  │
│  │ Abilities / Buffs (платформа на TS)        │  │
│  └────────────────────────────────────────────┘  │
│        ▲ DI        ▲ DI            ▲ DI          │
│    Math API   Physics API      Navigation API    │
│               (обяз. при FoW)  (NAV-7..NAV-10,   │
│                                systems/nav/)     │
└──────────────▲───────────────────────────────────┘
               │ worldInit: террейн (immutable) + стартовая расстановка
               │ tick(state, inputs) → TickResult
               │ DiagnosticsSink ← push во время тика (DIAG-1)
        ┌───────┴────────────────┐
        │  External Observers     │  ← аналитика / логи / звук
        │  Netcode snapshot filter│  ← per-client фильтрация (viewpoint)
        │  CLI (golden-file)      │  ← cross-language sync
        └───────┬─────────────────┘
               │ зависимость строго односторонняя (DI-3, NTR-1, ASSET-1)
┌──────────────▼───────────────────────────────────┐
│  Netcode transport (engine/net-ts)               │
│  MatchServer (чистый цикл) │ MatchClient         │
│  Protocol ─ Transport (loopback / WebSocket)     │
│  Session: авторитет (local/listen/dedicated)     │
│    × рандеву (in-process/адрес/инвайт) × лобби   │
├──────────────────────────────────────────────────┤
│  Presentation (assets-ts + render-ts)            │
│  assets: handle'ы, загрузчики, кэш, манифест     │
│    визуалов, карта кривизны, эффекты камеры      │
│  rendering: extractor → viewBuffer → подсистемы  │
│    (террейн и кривизна, модели, скины, пол)      │
│  camera: режимы → поза → стек эффектов           │
├──────────────────────────────────────────────────┤
│  Client shell (engine/client-ts)                 │
│  ядро в воркере, рендер в главном потоке,        │
│  transferable ping-pong + обратный канал ввода   │
├──────────────────────────────────────────────────┤
│  Игра (game/demo-ts) — потребитель оболочки:     │
│  сборка демо-арены, читает дерево контента       │
└──────────────────────────────────────────────────┘
```

Выходов из ядра два, и они разные. `TickResult` — отчёт о тике, читаемый observer'ами ПОСЛЕ него. `DiagnosticsSink` — push-канал, работающий ВО ВРЕМЯ тика: по нему идут нарушенные инварианты и трейс потока команд. Второй нужен именно потому, что первого не существует в момент, когда тик оборвался исключением. Подробности — capability `diagnostics`.

Из нижних четырёх секций независимых потребителей одного и того же выхода — три: транспорт, presentation и оболочка. Четвёртая, игра, стоит не рядом с ними, а поверх оболочки: `TickResult` она читает через неё, а собственного канала к ядру у неё нет. Presentation — такой же наблюдатель, как netcode и CLI: ассеты не влияют на симуляцию (ASSET-1), рендер читает `TickResult` и внутри себя волен считать во float (REND-1), камера — presentation-конвейер позы и в мир не пишет (CAM-1). Оболочка клиента разносит эту пару по потокам: ядро тикает в воркере, рендер и камера живут в главном, а границей между ними служит presentation-состояние (`client-shell` SHELL-1, SHELL-2). Вьюпорт редактора берёт ту же реализацию `rendering` и тот же конвейер `camera` — второго рендера не заводится (ED-1, ED-13), — а наполняться presentation-состояние умеет и не от тика, а от редактируемых документов (REND-11).

Внутри рендера у инстанса модели **два яруса представления**, и выбирает ярус запись манифеста визуалов, а не код (`rendering` REND-20, `assets` ASSET-13). **Батчевый** — умолчание: инстансы одной записи живут записями разделяемого `InstancedMesh`, скиннинг идёт на GPU по запечённым в текстуру матрицам костей (bone-VAT, ASSET-12), анимационное состояние инстанса — это индекс клипа и фаза, скин — индекс слоя в массиве текстур. Число draw calls растёт с числом ЗАПИСЕЙ манифеста, а не с числом инстансов, и пер-инстансных скелетов на CPU не остаётся. **Детальный** — прежнее пер-инстансное поддерево со своим скелетом и микшером; его получают записи с процедурным контролем костей (REND-5), записи, которым художник назначил его явно, и модели, у которых запечённых производных нет (деградация стоимости, а не отказ отрисовки). Наблюдаемое поведение у ярусов одно: машина состояний REND-4, поза, границы и picking считаются одним кодом — различается только носитель. Поверх ярусов работают отсечение по консервативным границам модели по всем её клипам (REND-21) и выбор уровня детализации по экранному размеру с порогами из записи (REND-22).

Верхний ярус с 2026-08-09 разделён по инструментам, а не по слоям. Поверхность level-дизайна — Blender: расстановка, террейн и кривизна авторятся там и приезжают одно-направленным импортом glTF (capability `blender-pipeline`); собственный редактор остаётся превью и инструментом data-driven-авторинга — системы, схемы, prefabs, манифест, — а level-дизайн-функциональность в нём не развивается. Второго пути правки при этом не появляется: импортёр — headless-потребитель слоя операций редактора и его канонического сохранения (BLND-5, ED-29, ED-21), поэтому валидация, сериализация и правила порядка у обоих инструментов одни.

## 3. Механизм против политики

Сквозное разделение, которое легко потерять при реализации:

| Механизм (core) | Политика (evaluator / геймплей) |
|---|---|
| Переходы WSM + `HistoryProvider.seekTo(tick)` | Ульта отката: глубина, cooldown, стоимость, автостоп |
| `TimeScaleModifiers.sources` + произведение с клампом | Как стакаются слоу: сильнейший / аддитив / мультипликатив |
| `VisionModifier.sources` | Правила баффов обзора |
| Фильтр снапшота с параметром `viewpoint` | Кто авторизован получать `viewpoint = ALL` |
| Хендшейк предъявляет пару версии и сверяет её | Что показать игроку на отказе, откуда качать обновление |

Правило: core никогда не знает баланса. Если в ядро просится число, которое может поменять геймдизайнер, — оно живёт в JSON.

С 2026-08-05 у правой колонки есть адрес: игровой контент живёт в дереве `content/` вне пакетов движка, и это проверяется механически (capability `game-content`, CONT-1). Тестовые фикстуры движка — golden-эталоны и сцены кросс-слойной сюиты — контентом не являются и остаются в `engine/` (CONT-4): основание границы — что именно пинает тест, и оно записано в самом требовании; здесь достаточно помнить, что golden-эталон фиксирует поведение движка, а не баланс игры.

## 4. LLM-friendly dev workflow

Не требования к системе, а следствие JSON-first архитектуры — почему она выбрана:

- JSON-first упрощает генерацию контента агентом.
- Строгие JSON-схемы → агент генерит валидные компоненты и системы.
- Документированные Action DSL и JsonLogic-операции — контекст для few-shot.
- Cross-language парность поддерживается агентом (генерация Rust-версии по TS-спецификации), включая системы на TS вроде `VisibilitySystem`; сверка — golden-файлами.

## 5. Roadmap

Фокус: полностью рабочий data-driven тик + детерминизм с самого начала. Единый интерфейс `System` появляется рано, чтобы подменяемость JSON↔код проверялась не в конце, а в момент появления evaluator'а.

Порядок подчинён приоритету «сначала гибкий редактор с системами, потом геймплей сверху». Редактор идёт сразу после минимума, который ему нужен (evaluator, формат данных, террейн), а не после всего ядра: он и есть проверка гипотезы, ради которой затевалась data-driven архитектура — что геймдизайнер собирает системы и арену без правки кода. Проверять её после того, как поверх формата написаны физика, netcode и FoW, поздно.

## 6. Открытые вопросы

Не противоречия ядра, а нерешённые дизайн/фичасибилити-вопросы. Каждый помечен слоем, на котором решается.

1. **Пейс глобальной перемотки** (геймплей). Механизм решён, но в FFA до 10 игроков перемотка одного игрока замораживает мир всем на до 7 с. Открыт баланс: как часто доступна ульта, не убивает ли динамику 20-минутного матча.
2. **Модель отзывчивости** (замер). Схема выбрана: server-auth без предсказания, клиент симуляцию не тикает (`netcode-transport` NTR-10). Lockstep-relay отклонён — размазывает авторитет вопреки NET-1 и потребовал бы писать сервер заново. Прототип есть (`engine/net-ts`), и он даёт число: «нажал→увидел» локально порядка 40–50 мс при 60/30/2. Открытым остаётся, достаточно ли этого на реальном канале и когда включать предсказание своей сущности (NET-2/4/5) — решается замером, а не заранее.
3. **Гранулярность dirty-tracking** (перф). Per-component или per-entity-per-component — по замерам на реальной сцене, этап 14.
4. **Суб-стримы RNG** (редактор). Дефолт — один стрим на систему по `name` (RNG-4). Нужны ли именованные суб-стримы — вопрос РЕШЁННЫЙ: формат имени задаёт RNG-7, а из данных они доступны полем `subStream` действий `random` и `randomBelow` (`data-driven-systems` ACT-1). Открыто только, как редактор показывает и объявляет состав суб-стримов системы, — по мере появления систем с несколькими независимыми источниками случайности. Живёт в `## Open Questions` спеки `rng`, здесь — указатель.
5. **Стоимость per-client фильтрации** (netcode/перф). 10 игроков × 30 Гц = до 10 фильтраций снапшота на тик, при delta — ещё и 10 baseline-diff'ов. Замерить; при упоре — снизить частоту рассылки или отложить per-client delta.
6. **Гранулярность видимости** (дизайн/перф). Сейчас — per-team битмаска. Per-entity потребует другой структуры и ломает дешёвый dirty. Решать только если потребует дизайн.
7. **Кто получает `viewpoint = ALL`** (netcode). Для локального прогона решено: полный поток идёт только соединению, объявленному наблюдателем в конфиге матча, и игровому слоту не выдаётся ни при каких условиях (`netcode-transport` NTR-9). Точка зрения игрового слота при этом нормирована целиком: это команда его сущности в мире матча, она обязана лежать в диапазоне `[0, 31]` (`fog-of-war` FOW-2), а сентинель полного потока в этой роли отвергается сборкой матча (NTR-9) — `VIEWPOINT_ALL` не въезжает игроку опечаткой в конфиге. Граница доверия теперь названа по режимам сессии (`net-session` SES-7): в `dedicated` нефильтрованного состояния нет ни у кого из играющих, в `listen` оно по построению лежит в памяти хоста, и режим объявлен пригодным только для доверенных сторон. Открытой остаётся продакшн-авторизация выделенного режима: сетевой аутентификации пока нет (инвайт — допуск, а не удостоверение, SES-5), и матч с недоверенными участниками непригоден в любом режиме, пока её нет.
8. **Политика видимости событий и снарядов** (геймплей). Точная политика при разной видимости источника и цели: открыт геймплейный выбор, а не механизм — предикат называется именем из закрытого набора в документе матча (`any-referenced` против `all-referenced`, NET-13), и смена его правкой движка не является. Отдельно: видны ли снаряды/VFX от невидимой сущности — у снаряда может быть своя видимость, независимая от кастера.
9. **LoS-обрезка тумана в рендере** (рендер) — закрыт: `FOW-9` требует круг эффективного радиуса, обрезанный по линии взгляда (2D shadow-casting), с тенями, направленными по высоте (ребро обрыва затеняет, только если его верхний уровень строго выше уровня наблюдателя, `PHYS-13`, `FOW-5`). Круга-radius без обрезки норма не допускает: он засвечивал бы область, которую симуляция считает невидимой.
10. **FoW × глобальный rewind** (геймдизайн/netcode). Во время перемотки, инициированной одним игроком: все видят мир глазами инициатора или каждый свою историческую видимость?
11. **Политика арены** (геймплей). Механизм решён (`arena`: граница, события `LeftArena` и `FellThroughFloor`, сужение радиуса командой), политика — нет: что бывает за выход за край, по какому расписанию сужается арена, какова судьба провалившегося сквозь пол. Политика — свойство конкретной арены, а не игры: продуктовая рамка — песочница арен-потасовок (one-pager), и каждая сцена задаёт свой свод правил своими JSON-системами. Описывается после этапа 8. Узкие вопросы модели террейна, которые здесь когда-то числились открытыми, закрыты все три и остались в `## Open Questions` спеки `terrain` записями о том, чем именно: связность сетки — 4-связная (`pathfinding` NAV-7), обрезка reveal-круга — по линии взгляда с тенями, направленными по высоте (`fog-of-war` FOW-9), символы флагового слоя (`.`, `^`, `_`) зафиксированы в TERR-3. Там же закрыта ширина рампы (TERR-7); сторона флага рампы стала нормой позже (TERR-5, этап 46).

12. **Направленный обзор с высоты** (геймдизайн/рендер). Нормативная часть закрыта: FOW-5 приведён к реальному рельефу — обрыв несёт оба тега блокировки (TERR-5), поэтому LoS отсекает пару раньше правила высоты, и сценарий «наблюдатель сверху» переписан под это. Открытым остаётся дизайн-вопрос: нужен ли отдельный направленный алгоритм обзора вниз (в пределах видимой сверху зоны, а не «всё, что не за обрывом»). Указателя в `fog-of-war` под него нет и не нужно: там открыта только гранулярность видимости (пункт 6), а этот вопрос не про механизм, а про желаемый дизайн обзора — и живёт здесь.
13. **Апдейт-гейт на клиенте** (клиент/продукт). Хендшейк появился: пара версии предъявляется в `Hello`, обе половины сверяются до того, как о матче сообщено что-либо, отказ называет разошедшуюся половину, а хеш `worldInit` сверяется отдельным исходом «разошлись данные матча» (`netcode-transport` NTR-5). Механизм закрыт. Открытым остаётся продуктовая часть: что клиент показывает игроку на отказе и откуда тянет обновление. Канал обновления сервером матча не является — эту границу проводит NET-16 (раздел «Обновление»), и здесь она только упоминается. — *клиент.*

14. **Хранение байтов художественных ассетов** (инфраструктура). Выбор свободен: спека уже фиксирует всё, что делает его свободным — отсутствующий presentation-ассет не меняет ни байта `TickResult` и не входит в `worldInit` (`assets` ASSET-1), ID ассета есть путь от корня дерева, а не адрес хранилища (ASSET-2, `game-content` CONT-2), тесты движка проходят в срезе репозитория без дерева контента (CONT-4), а доставка есть свойство оболочки (CONT-5). Поэтому вариант хранилища намеренно не нормативен: требование вида «бинарники хранятся в LFS» сузило бы выбор, ничего не защитив. Открыт сам выбор — обычный git (сейчас; дерево контента весит порядка сотни килобайт), Git LFS или контент-адресуемое хранилище с манифестом и скриптом выкачки. У вопроса есть срок: переезд с обычного git переписывает историю и ломает все существующие клоны, поэтому решать его нужно до того, как бинарники наберут вес, а не после. Триггер — суммарный вес художественных ассетов около гигабайта либо переход ре-экспортов в регулярные; до него делать нечего. Текущий наклон — LFS, как прозрачный и не требующий своего тулинга; аргумент против него (трафик, который жёг бы CI) снимается тем же CONT-4 — сборке ассеты не нужны, и клонировать она может, не выкачивая их.

## 7. Технические риски

- **Time-манипуляции + сетевой реалтайм-синк на таймингах** — наиболее рискованная связка (риск из one-pager). Механизм заложен через глобальный `Rewinding` и авторитетный сервер, но пейс и ощущение проверяются только прототипом.
