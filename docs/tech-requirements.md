# Технические требования к игровому движку

## 1. Обзор архитектуры

Многослойная архитектура с детерминированным ядром, data-driven описанием систем и визуальным редактором геймплея.

```text
┌─────────────────────────────────────────────────┐
│  Редактор (Compose Multiplatform)                │
│  Визуальные триггеры / Data-Driven логика        │
└───────────────┬──────────────────────────────────┘
                │ генерирует JSON (компоненты, системы, prefabs)
┌───────────────▼──────────────────────────────────┐
│  Deterministic Core (TS, позже Rust)             │
│  ┌────────────────────────────────────────────┐  │
│  │ System Evaluator (JSON → pipeline)         │  │
│  │ Action Executor / Expression (JsonLogic)   │  │
│  │ ECS foundation + Query API                 │  │
│  │ Time / Tween / Snapshot / RNG              │  │
│  └────────────────────────────────────────────┘  │
│           ▲ DI              ▲ DI                 │
│      Math API          Physics API (опц.)        │
└───────────────▲──────────────────────────────────┘
                │ tick(state, inputs) → TickResult
        ┌───────┴────────────────┐
        │  External Observers     │  ← аналитика / логи / звук / рендер (§2.6)
        │  CLI (golden-file)      │  ← cross-language sync
        └─────────────────────────┘
```

**Основные принципы:**
- **Детерминизм first-class**: единственный вход в симуляцию — `tick(state, inputs) → TickResult`
- **Data-driven**: системы и геймплей описываются JSON, ядро — универсальный evaluator
- **Единый интерфейс System**: JSON-система и нативная TS-система взаимозаменяемы за одним контрактом (§4.2) — оптимизация переписыванием в код без изменений вокруг
- **Мультиязычность**: MVP на TS, задел на Rust (общая спецификация поведения)
- **Server-authoritative netcode** с предсказанием своего игрока + интерполяцией чужих (reconciliation ограничен своей сущностью, не всем миром) — архитектура заложена с самого начала
- **Наблюдаемость без side-effect'ов**: симуляция ничего не отправляет наружу; внешние потребители читают `TickResult` после тика (§2.6)

## 2. Детерминированное ядро (Core Engine)

### 2.1 Детерминизм
- **DET-1**: Полная воспроизводимость: `(seed + inputs[]) → identical state`
- **DET-2**: Собственная **fixed-point арифметика** (не FP, не готовые либы) для гарантии кросс-платформенности
- **DET-3**: Фиксированный порядок выполнения систем (детерминированный scheduler)
- **DET-4**: Детерминированный ГПСЧ (см. §7)
- **DET-5**: Отсутствие зависимостей от wall-clock **внутри симуляции**; только tick-based fixed timestep (60 Hz базово). Wall-clock допустим лишь как внешний триггер «когда продвигать тик» (см. TICK-2) и не влияет на содержимое `state`
- **DET-6**: Все ID генерируются детерминированно (см. §8)
- **DET-7**: Все мутации ECS — через Command Buffer в детерминированном порядке (см. §9)

### 2.2 Языки реализации
- **CORE-1**: MVP — только **TypeScript**
- **CORE-2**: Задел на **Rust** (fallback: вторая реализация тоже на TS)
- **CORE-3**: Формальная спецификация поведения — источник истины для всех реализаций
- **CORE-4**: **Никаких WASM-мостов** в MVP

### 2.3 Инверсия зависимостей
- **DI-1**: Ядро зависит от **интерфейсов** Math API и Physics API
- **DI-2**: **Math API** — обязательный (fixed-point операции, векторы, матрицы)
- **DI-3**: **Physics API** — опциональный (может быть отключён)

### 2.4 Модель тика (tick-based, prediction/reconciliation-friendly)
- **TICK-1**: Единственный способ прогресса симуляции — `tick(state, inputs[]) → TickResult` (чистая функция; `TickResult.state` = новый `state'`, см. §2.6)
- **TICK-2**: Внешние воздействия — **InputFrame на (игрока, тик)** (не дискретные события; для непрерывного WASD-движения сэмплим состояние ввода каждый тик):
  ```json
  { "tick": 1234, "playerId": "p1", "seq": 42,
    "move": { "x": "fixed", "y": "fixed" }, "aimDir": "fixed", "buttons": "u16 bitmask" }
  ```
  Дискретные действия (касты) — биты в `buttons`; edge-detection делает `InputSystem`.
  Буферизация: тик N исполняется, когда пришли фреймы всех игроков **или** по таймауту → predicted-фрейм (повтор последнего).
  Клиенты не обязаны ждать сервер (предсказывают своё — §15); TICK-2 описывает серверную буферизацию и генерацию канонического потока инпутов. **Таймаут — wall-clock только для решения «пора продвинуть тик» (DET-5)**; сам `inputs[]` (включая predicted-фреймы) записывается как канонический, поэтому `(seed + inputs[]) → state` побитово воспроизводим при реплее, reconciliation и rewind.
- **TICK-3**: Никаких side-channel API — нельзя менять мир вне тика. Симуляция не инициирует внешних side-effect'ов; наблюдаемость наружу — только через `TickResult` (§2.6)
- **TICK-4**: Внутри симуляции инпуты обрабатываются системами (например, `InputSystem` конвертирует их в компоненты/события)

### 2.5 Fixed-point спецификация
- **FP-1**: Формат **Q16.16**, signed, контейнер **i32**. Диапазон ±32768, точность 1/65536 — с запасом для арены. Q32.32/i64 — escape-hatch при упоре в диапазон/точность (по замерам).
- **FP-2**: Умножение: `(i64(a) * i64(b)) >> 16`. В TS промежуток 64-бит через эмуляцию hi/lo (не float — произведение i32 вылетает за 53-битный safe-int; не BigInt в hot-path).
- **FP-3**: Округление — **truncate toward zero**, идентично зашито в mul/div всех реализаций.
- **FP-4**: Overflow — **wrapping (2's complement)** + assert в debug-сборке (матчит Rust `wrapping_*`).

### 2.6 External Observers (наблюдаемость наружу)

Ядро экспонирует **read-only наблюдаемость** результата тика. Ядро не знает про конкретных потребителей (аналитика, логи, звук, рендер) — они сами извлекают нужное. Это держит TICK-3/DET-5: симуляция остаётся чистой, все внешние side-effect'ы живут во внешнем слое **после** `tick()`.

- **OBS-1**: `tick()` возвращает `TickResult` — read-only отчёт о тике:
  ```ts
  interface TickResult {
    readonly state: WorldState;        // новый state' (идёт в следующий тик)
    readonly tick: number;
    readonly mode: WorldMode;          // Running | Paused | Rewinding (§11)
    readonly isReplay: boolean;        // первый честный проход тика или rewind/reconciliation
    readonly events: ReadonlyEventLog; // события этого тика, read-only view
    readonly changes: ChangeSet;       // per-component dirty-tracking, read-only view
  }
  ```
- **OBS-2**: Внешние потребители реализуют `TickObserver.onTick(result)`; вызываются внешним слоем **после** `tick()`. Аналитика, логи, звук, рендер — частные случаи одного контракта:
  ```ts
  interface TickObserver {
    readonly name: string;
    onTick(result: TickResult): void; // side-effect'ы легальны ТОЛЬКО здесь
  }
  ```
- **OBS-3**: `TickResult` — **read-only view на данные ядра, без копирования**. Валиден только синхронно в рамках `dispatch()` сразу после `tick()`. Потребитель **не сохраняет** ссылки на view; если данные нужно пережить тик (async-отправка) — потребитель **сам копирует только необходимое** (не ядро). Тот же lifecycle-контракт, что у QUERY-3.
- **OBS-4**: Категоризация/фильтрация событий (что интересно потребителю) — **в потребителе**, не в ядре. Событие описывает **доменный факт** (`DamageDealt`, `UltimateCast`), а не адресата. Никаких маркеров вроде `analytics: true` в ядре.
- **OBS-5**: Дедуп против повторной обработки при rewind/replay — **в потребителе**, по `mode`/`isReplay`. Дедуп-стейт живёт вне детерминированного ядра. Пример: аналитика реагирует только при `mode === "Running" && !isReplay`; логгер реплеев — наоборот.
- **OBS-6**: `TickResult.changes` — view на **единый** per-component dirty-tracking. Один источник dirty-данных → три потребителя без дублирования: SNAP-5 (копирование dirty TypedArray в снапшот), NET-8 (delta против last-acked), внешние observer'ы (что поменялось). Dirty-tracking считается один раз за тик.

## 3. ECS Foundation

- **ECS-1**: Использовать готовую библиотеку:
  - TS: **bitecs** (SoA, TypedArray)
  - Rust: `bevy_ecs` / `hecs` (при появлении второй реализации)
- **ECS-2**: Общая спецификация поведения ECS для парности реализаций
- **ECS-3**: Компоненты описываются JSON-схемами (тип, поля, defaults)
- **ECS-4**: Сущности собираются из JSON prefabs / archetypes
- **ECS-5**: Валидация JSON-конфигов на загрузке (JSON Schema)

### Query API
- **QUERY-1**: Декларативные запросы:
  - `all: [ComponentA, ComponentB]` — сущности со всеми компонентами
  - `any: [...]`, `not: [...]` — базовая логика
  - `withinRadius: [center, radius]` — пространственный
  - `withTag: "..."` — по тегам
- **QUERY-2**: Порядок обхода детерминирован
- **QUERY-3**: Query возвращают снапшот на момент начала системы; мутации отложены

## 4. Data-Driven Systems

Системы описываются JSON, ядро — универсальный evaluator.

### 4.1 Три уровня DSL

| Уровень | Описывает | Пример |
|---|---|---|
| **System** | Что и когда исполнять | `{query, forEach, order}` |
| **Action** | Побочные эффекты | `modifyComponent`, `spawnEntity`, `forEach`, `if`, `let` |
| **Expression** | Чистые вычисления | JsonLogic |

### 4.2 System Evaluator + единый интерфейс System

Ключевое проектное решение: **система — чёрный ящик за единым интерфейсом**. И JSON-система (`EvaluatedSystem`), и нативная TS-система реализуют один контракт `System`; scheduler и tick-loop не знают, какая перед ними. Это делает возможным флоу: «сделал систему в редакторе (JSON) → потом переписал её кодом ради скорости → вставил без изменений вокруг».

- **SYS-1**: Система — JSON-описание с полями: `name`, `order`, `query`, `forEach`/`do`
- **SYS-2**: Scheduler упорядочивает системы по `order` детерминированно (DET-3)
- **SYS-3**: Данные-компоненты и системы регистрируются на старте, валидируются
- **SYS-4**: Единый интерфейс `System` для любой реализации:
  ```ts
  interface System {
    readonly name: string;   // = имя RNG-стрима (§7), ключ в реестре для подмены
    readonly order: number;  // DET-3/SYS-2
    execute(ctx: SystemContext): void;
  }
  ```
- **SYS-5**: `SystemContext` — **контракт границы core↔геймплей** (публичный API, проектируется аккуратно с самого начала):
  ```ts
  interface SystemContext {
    readonly world: WorldView;        // QUERY-3: снапшот на начало системы, read-only
    readonly commands: CommandBuffer; // CMD-1..4: единственный канал мутаций
    readonly events: EventBus;        // EVT-1..3
    readonly rng: { stream(sub?: string): RngStream }; // RNG-4: стрим по name системы
    readonly time: TimeContext;       // TIME-1..3: tick, globalDelta
  }
  ```
- **SYS-6**: Обе реализации живут за одним контрактом:
  - `EvaluatedSystem` — исполняет JSON-описание через Action Executor + Expression Evaluator;
  - нативная TS-система — считает напрямую (например, ради оптимизации).
    Границы поведения идентичны: обе читают через `WorldView` и пишут только в `CommandBuffer` — у нативной системы физически нет способа обойти TICK-3/CMD-4.
- **SYS-7**: `SystemRegistry` — реестр систем по `name`; подмена реализации через `override(system)` с тем же `name`/`order` не затрагивает scheduler, Command Buffer, события, RNG-стримы:
  ```ts
  registry.registerFromJson(dashSystemJson); // из редактора
  registry.override(new NativeDashSystem()); // оптимизированная версия, тот же name/order
  // вокруг — ноль изменений
  ```
- **SYS-8**: Golden-file тест (§14) не меняется при переписывании системы в код; расхождение снапшота нативной и JSON-версии = красный тест (страховка детерминизма при оптимизации).

### 4.3 Action Executor
- **ACT-1**: Набор actions:
  - `modifyComponent`, `addComponent`, `removeComponent`
  - `spawnEntity`, `destroyEntity`
  - `emitEvent`
  - `forEach { query, do }` — итерация с телом-actions
  - `if { cond, then, else }`
  - `let { bindings, do }` — локальные переменные
  - `addTween`, `addModifier` (см. §5, §6)
- **ACT-2**: Все actions, меняющие ECS, работают через Command Buffer. В частности, `addTween` и `addModifier` (§5, §6) тоже создают commands (создание/модификация компонентов `Tween`/модификаторов), не мутируют ECS напрямую
- **ACT-3**: Порядок применения commands детерминирован

### 4.4 Expression Evaluator
- **EXPR-1**: MVP — **JsonLogic** через либу; выражения хранятся как JSON-AST
- **EXPR-2**: Собственные расширения:
  - Fixed-point арифметика вместо float
  - `getComponent`, `hasComponent`
  - Векторная математика через Math API
- **EXPR-3**: Sandboxed — никаких side-effects
- **EXPR-4**: Абстракция за интерфейсом `ExpressionEvaluator` для последующей замены на собственный AST. Внутри `EvaluatedSystem` — отдельная точка абстракции; нативной системе не нужен (считает напрямую).
- **EXPR-5**: Циклы **не поддерживаются** в expressions (только в actions через `forEach`)

### 4.5 Event Bus
- **EVT-1**: Детерминированная очередь событий
- **EVT-2**: События потребляются системами в порядке публикации
- **EVT-3**: События — часть snapshot (для rewind/rollback)

**Разграничение с Command Buffer (§9):** EventBus несёт **факт** («что-то произошло», broadcast нескольким системам-подписчикам), Command Buffer несёт **мутацию** (адресное изменение ECS). Событие само по себе мир не меняет — реакция систем-слушателей проводит мутации через Command Buffer. События снапшотятся (могут пережить границу тика, EVT-3), команды — нет (flush per-система, буфер пуст на границе тика, CMD-2).

## 5. Time System

### 5.1 Модель
- **TIME-1**: Tick rate фиксирован (60 Hz базово), **не** меняется от time scale
- **TIME-2**: `TimeScale { value: fixed }` — компонент, влияющий на симуляционную скорость сущности внутри тика
- **TIME-3**: `getEffectiveDelta(entity, globalDelta)` = `globalDelta * TimeScale.value` (default: 1.0)

### 5.2 Opt-in per-system
- **TIME-4**: Системы **явно** выбирают, учитывать ли TimeScale — не глобальный override
- **TIME-5**: Типичное применение TimeScale:
  - ✅ движение снарядов, физика, LifetimeSystem (по решению автора)
  - ❌ Cooldowns, глобальные таймеры, animation speed
- **TIME-6**: Замедление персонажа делается через **параметры** (`MoveSpeedModifier`, `AttackSpeedModifier` и т.п.) — это уже геймплейный слой, не core

### 5.3 Стакинг
- **TIME-7**: `TimeScaleModifiers { sources: [{id, value}] }`. Core-контракт:
  - reducer = **произведение** всех `sources[].value`;
  - **clamp итога в `[0.05, 4.0]`** — техническая защита от деления на ~0 в `getEffectiveDelta` (не балансный кап);
  - композиционная политика (стак / «берём сильнейший» / аддитив) — **вне core**, на геймплейном слое, через управление списком `sources`. Пример: «сильнейший слоу» = система-владелец держит в `sources` один источник с минимальным `value`; core перемножает список из одного элемента.
- **TIME-8**: Источники добавляются/снимаются системами (например, `TimeDomeSystem`)

### 5.4 Взаимодействие с rewind
- **TIME-9**: Во время `Rewinding` компоненты TimeScale игнорируются, темп задаёт rewind-механизм (следствие REW-4: обычные системы, включая обработку TimeScale, выключены во время Rewinding)

## 6. Tween System (hardcoded)

- **TWEEN-1**: Компонент `Tween { target, from, to, duration, elapsed, easing, onComplete }`
- **TWEEN-2**: Easing: минимум `linear`, `instant`; расширяемо
- **TWEEN-3**: `target` — путь к полю компонента (например, `"Health.value"`)
- **TWEEN-4**: `onComplete` — action, исполняется по завершении
- **TWEEN-5**: Твины создаются через action `addTween`
- **TWEEN-6**: TweenSystem тикает нативно, не через JSON
- **TWEEN-7**: Учёт TimeScale — настраиваемо per-tween

## 7. RNG

- **RNG-1**: Собственная реализация PRNG (кандидаты: xorshift128, PCG, splitmix64) — побитово одинаковая в TS и Rust
- **RNG-2**: **Множественные именованные стримы**, по одному на систему (или логический контекст). Один общий генератор детерминирован, но привязывает случайность каждой системы к глобальному порядку вызовов — хрупко к правкам (лишний `next()` сдвигает все последующие) и несовместимо с частичным реплеем в netcode (NET-4). Отдельные стримы развязывают эту связь.
- **RNG-3**: Каждый стрим seeded от главного world seed + имени стрима: `seed = hash(worldSeed, streamName)`
- **RNG-4**: Стрим привязан к **`name` системы** (SYS-4). `ctx.rng.stream()` без аргумента = основной стрим системы (`hash(worldSeed, name)`); опциональный суб-стрим `stream("crits")` = `hash(worldSeed, "Name/crits")`. Единообразие: нативная система с тем же `name` автоматически получает тот же стрим, что и её JSON-версия → reconciliation и golden-file совпадают без ручной синхронизации имён.
- **RNG-5**: Состояние всех стримов — часть snapshot
- **RNG-6**: В expressions RNG не вызывается напрямую; система "тянет" значение и передаёт через `let`
- **RNG-7**: Формат имени суб-стрима — строгая конкатенация `"{systemName}/{subStream}"` (разделитель `/`, UTF-8 без BOM). Хеш-функция и порядок байт (endianness) зафиксированы одинаково во всех реализациях ядра. Любое расхождение = красный cross-language тест (CLI-6).

## 8. Entity IDs

- **ID-1**: Generational IDs: `{ index: u32, generation: u32 }` (реализация по возможностям bitecs)
- **ID-2**: Монотонный счётчик в world state; increment при спавне
- **ID-3**: При удалении сущности `generation` инкрементится — старые ссылки становятся невалидными
- **ID-4**: Счётчик и generations — часть snapshot; откатываются при rewind
- **ID-5**: Одинаковый алгоритм генерации во всех реализациях ядра

## 9. Command Buffer (mutations)

- **CMD-1**: Все мутации ECS во время итерации — deferred, через Command Buffer
- **CMD-2**: Команды применяются **в конце каждой системы** (flush per-system, не per-tick): внутри системы мутации deferred (стабильная итерация), между системами — видимы. Иначе цепочки систем в одном тике не видят структурных изменений (напр. `SpawnSystem` → `MoveSystem`).
- **CMD-3**: Порядок применения детерминирован (порядок создания)
- **CMD-4**: В action DSL операции `spawnEntity`, `destroyEntity`, `addComponent`, `removeComponent` создают commands, не мутируют напрямую
- **CMD-5**: Query внутри системы видит состояние на начало системы, не с учётом отложенных команд. «Начало системы» = состояние мира **после flush предыдущей системы** (CMD-2), не начало тика.

**Разграничение с Event Bus (§4.5):** Command Buffer — адресная мутация ECS без «подписчиков», применяется внутри тика (flush per-система). Event Bus — broadcast факта нескольким системам, снапшотится и может пережить границу тика (EVT-3). Слить в один нельзя: событие не должно мутировать world напрямую (сломает детерминированный flush), команда не имеет подписчиков.

## 10. Snapshot System / Rewind

### 10.1 Snapshot infrastructure
- **SNAP-1**: Snapshot = полное состояние world (ECS + event bus + RNG state + counters + world state machine)
- **SNAP-2**: Интерфейс `HistoryProvider` — rewind-механика и rollback netcode могут иметь разные реализации
- **SNAP-3**: Storage — ring buffer

### 10.2 Rewind как игровая механика

**Слои (важно):** core даёт **механизм** — WSM-переходы (§11, WSM-5) + `HistoryProvider.seekTo(tick)` (применить snapshot@T: ECS + event bus + RNG + counters + WSM). Конкретная **ульта** (глубина, кто инициирует, cooldown, HP/mana-стоимость, автостоп) — **геймплейная система в evaluator** (JSON) поверх механизма, а не хардкод в core. Ниже: REW-3/REW-4/REW-10 — механизм (core); REW-1/REW-5/REW-7/REW-8/REW-9 — политика (evaluator, приведены как ориентир).

- **REW-1**: Глубина: **7 секунд** (420 тиков при 60 Hz) — *политика ульты; core ограничен лишь размером ring buffer (§10.3)*
- **REW-2**: Rewind = восстановление **полного** снапшота@target (SNAP-1) → откатывается **весь мир** (REW-3): позиции, HP/mana, event bus, RNG, counters. **Нет per-entity фильтра записи** (пишем весь мир целиком, экономия — через SNAP-5 structural sharing, а не отбрасыванием сущностей на записи). На **откате** единственное исключение — явный **exempt-список** (REW-9); никаких пометок сущностей на записи. Вне exempt-списка — всё возвращается к целевому тику (детерминизм на выходе, REW-10).
- **REW-3**: Rewind — **глобальный режим мира**, не эффект на отдельные сущности
- **REW-4**: Во время `Rewinding` — все обычные системы выключены; активна только rewind-логика
- **REW-5**: Инпуты игроков во время rewind не влияют на симуляцию, кроме управления самим rewind
- **REW-6**: Синхронизирован по сети через авторитетный сервер
- **REW-7**: Инициатор — игрок, прожавший скилл; момент остановки выбирает он же (или автостоп на 7 сек)
- **REW-8**: Rewind внутри Rewind — запрещён
- **REW-9**: Cooldown ульты rewind должен пережить откат — попадает в **exempt-список** (что не откатывается при перемотке), обрабатывается отдельно от общего восстановления снапшота. Формат: exempt-список ссылается на конкретные поля вида `[{ entity, "Cooldown.rewind" }]` (или через выделенный компонент-маркер, который сам не подлежит откату) — точечное исключение на восстановлении снапшота, не механизм фильтрации записи (REW-2). Иначе — бесконечный rewind-луп.
- **REW-10**: Event bus **снапшотится вместе с миром** (EVT-3/SNAP-1), откатывается на целевой тик, **не очищается**. На выходе `Rewinding → Running` шина = состояние целевого тика. Очистка сломала бы детерминизм vs честный реплей с того же тика.

### 10.3 Оптимизации
- **SNAP-4**: MVP — full copy → MessagePack, **без компрессии**. Порог для решения: 420 снапшотов × N сущностей, замер RAM/времени копирования на реальной сцене.
- **SNAP-5**: Порядок оптимизаций (по замерам): **1)** structural sharing по компонент-массивам (bitecs SoA — копируем только dirty TypedArray, `HistoryProvider` с per-component dirty-tracking, единым с NET-8 и OBS-6); **2)** downsampling дальнего прошлого; **3)** delta-компрессия.
- **SNAP-6**: Размер ring buffer (SNAP-3, дублируется как серверный буфер в NET-10) ≥ глубины rewind-политики (REW-1, сейчас 420 тиков/7с). Это связь механизм↔политика: при изменении баланса ульты (глубина отката) — пересмотреть размер буфера здесь и в NET-10.

## 11. World State Machine

- **WSM-1**: Состояния: `Running`, `Paused`, `Rewinding`
- **WSM-2**: Разрешённые переходы:
  - `Running ↔ Paused`
  - `Paused → Rewinding` — начать скраб из замороженного мира
  - `Rewinding → Paused` — остановиться на выбранном тике (можно перевыбрать точку)
  - `Paused → Running` — продолжить с текущего (в т.ч. перемотанного) тика

  Единственный флоу перемотки: `Running → Paused → Rewinding → Paused → Running` (заморозил мир → отмотал к точке → продолжил). Прямой переход `Running → Rewinding` **не допускается** — вход в Rewinding всегда проходит через Paused.
- **WSM-3**: Вложенные состояния запрещены
- **WSM-4**: Расширяется по мере появления геймплейных требований
- **WSM-5**: Переходы дёргаются **core-API** (`pause()`, `beginRewind()`, `seekTo(tick)`, `resume()`). «Ульта отката» (инициатор, cooldown, стоимость, глубина, автостоп) — **геймплейная система в evaluator** поверх этих переходов, не хардкод в core. Core = механизм, evaluator = политика (см. §10.2). `Paused` в сетевой игре — авторитарное состояние сервера (синкается всем); правила «кто и когда паузит» — тоже политика evaluator
- **WSM-6**: Текущий `mode` (`Running`/`Paused`/`Rewinding`) и признак `isReplay` (тик исполняется впервые vs повторно при rewind/reconciliation) прокидываются в `TickResult` (§2.6, OBS-1) — внешние потребители используют их для дедупа (OBS-5)

## 15. Netcode

Модель: **server-authoritative + предсказание своего игрока (client-side prediction, own entity only) + интерполяция чужих сущностей**. Полного отката всего мира на клиенте нет — reconciliation ограничен своей сущностью.

> **Прототип отзывчивости:** на старте допустим упрощённый режим — **lockstep через тупой relay-сервер** (инпут-only, input-delay буфер), чтобы руками замерить, насколько вялы дэши. Норм по ощущению — можно остаться на нём; вяло — включаем предсказание своего игрока (NET-2..NET-6). Детерминированное ядро общее для обоих режимов, ядро от выбора не зависит.

- **NET-1**: **Авторитарный сервер** — единственный источник истины симуляции. Клиенты предсказывают и рендерят, но не авторитетны.
- **NET-2**: **Предсказание — только своей сущности.** Клиент тикает локально свой `InputFrame` (движение, дэш, локальные эффекты своих действий), не дожидаясь сервера → свои действия мгновенны. **Чужие сущности клиент не предсказывает.**
- **NET-3**: **Чужие сущности и остальной мир — интерполируются**: рендерятся с небольшим отставанием (interpolation buffer, старт ~100 мс) между двумя authoritative-снапшотами. Плавно, без предсказания и без скачков.
- **NET-4**: **Reconciliation своей сущности.** При расхождении предсказанного своего состояния с authoritative@T: клиент выставляет свою сущность = authoritative@T и **реплеит только свои** `InputFrame` T+1..now. Ре-симулируется **своя сущность** (+её локальные взаимодействия), **не весь мир** → дёшево; снимает риск ре-симуляции всей сцены на интерпретируемом ядре.
- **NET-5**: **Сглаживание коррекций — требование, не «оптимизация потом».** Reconciliation и приход authoritative-стейта не должны давать видимых рывков: визуальный blend позиции/состояния за несколько кадров. Особенно на исходах способностей (УТП = тайминг-комбо).
- **NET-6**: **Коммит исходов чужих способностей — по authoritative-подтверждению.** Замах/каст чужого показывается локально-визуально, но **payoff** (луч родился, комбо залетело/сорвано) резолвится по серверу → клиент не «переигрывает» неверный исход.
- **NET-7**: Сеть = транспорт **inputs** (клиент → сервер) и **authoritative state/deltas** (сервер → клиенты).
- **NET-8**: Формат server → client — **MVP: полные authoritative-снапшоты, MessagePack, без компрессии**, частота старт **30 Гц** (клиент интерполирует), поднять до 60 при запасе bandwidth. Первая оптимизация — **delta против last-acked клиентом тика** (per-component dirty, см. §10.3 и §2.6 OBS-6 — единый dirty-tracking).
- **NET-9**: Клиент хранит свои `InputFrame` в ring **~120 тиков (2 с)** — для reconciliation своей сущности (реплей T+1..now).
- **NET-10**: **Буферы:**
  - server-side snapshot **ring 420 тиков (7 с)** — для rewind-механики (§10.2) и авторитетных реплеев;
  - client-side — свой input ring (~120 тиков) + короткая история своей предсказанной сущности для reconciliation.

  Полноценного отката **всего мира** на клиенте нет (отличие от «rollback-everything»-модели файтингов).
- **NET-11**: Rewind-механика (игровая ульта) синхронизируется через сервер: клиент шлёт инпут → сервер авторитетно решает, входит в `Rewinding` и рассылает состояния всем; клиенты синхронно следуют (во время `Rewinding` клиент рендерит серверные состояния, локальное предсказание приостановлено).

## 19. Открытые вопросы (к проработке)

Не противоречия ядра, а нерешённые дизайн/фичасибилити-вопросы. Каждый помечен слоем.

1. **Пейс глобальной перемотки (дизайн/баланс).** Механизм решён (§10.2/§11: `Paused → Rewinding → Running`, глобальный режим). Но в FFA до 10 игроков перемотка одного игрока замораживает мир **всем** (REW-3/REW-4) на до 7 с. Открыт баланс: как часто доступна ульта, не убивает ли динамику 20-минутного матча (one-pager риск «time-механики в мультиплеере»). → *геймплейный слой.*
2. **Модель отзывчивости — решается прототипом.** Ядро детерминированное → работают обе схемы: (a) lockstep-relay + input-delay (проще), (b) server-auth + предсказание своего + интерполяция чужих (§15). Выбор зависит от того, насколько вялы дэши при input-delay — замерить руками на этапе netcode-прототипа. → *решение по факту прототипа, не блокер спеки; ядро от выбора не зависит.*
3. **Гранулярность dirty-tracking (перф).** Единый dirty-tracking (§2.6 OBS-6) обслуживает SNAP-5, NET-8 и `TickResult.changes`. Открыто: per-component или per-entity-per-component — зависит от замеров на реальной сцене (шаг 9). → *решение по замерам.*
4. **Суб-стримы RNG (контент/эргономика).** Дефолт — один стрим на систему по `name` (§7 RNG-4). Нужны ли именованные суб-стримы (`stream("crits")`) и как их объявлять в редакторе — по мере появления систем с несколькими независимыми источниками случайности. → *геймплейный/редакторный слой.*
