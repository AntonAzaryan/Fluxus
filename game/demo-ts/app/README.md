# Демо-арена

Демо воркер-сборки клиента (capability `client-shell`): симуляция идёт в
воркере, главный поток рисует доставленное состояние и шлёт ввод.

```sh
npm run demo                        # dev-сервер vite + стенд матча
npm run demo:lan                    # то же, но слушая все интерфейсы — для игры вдвоём
npm run demo:build -w @fluxus/demo
```

Режим страницы выбирается один раз, при старте (SHELL-8):

| адрес | что поднимается |
| --- | --- |
| `/` | матч против бота на сетевом стеке: сервер вкладки плюс тонкий клиент |
| `/?server=` | тонкий клиент против стенда на хосте самой страницы |
| `/?server=ws://…` | тот же клиент против стенда по явному адресу |
| `/?solo` | одиночная симуляция в воркере — с паузой и отладочной перемоткой |
| `/?observer` | наблюдение за матчем стенда: слота нет, поток без фильтрации (NTR-9, NTR-21) |

## Игра вдвоём

Матч двух людей — это два процесса: страницу отдаёт vite, матч держит стенд
(`bin/demo-serve.mjs`, `net-session` SES-1, режим `dedicated`). Второй из них
поднимает dev-сервер сам (`demoStand.ts`), поэтому запускать его руками не
нужно — а можно: занятый порт плагин уступает уже поднятому стенду.

```sh
npm run demo:lan     # печатает ссылку, которую надо отдать второму игроку
```

Ссылка вида `http://<хост>:5173/?server=` — пустой параметр означает «адрес
стенда выводится из страницы» (`mode.ts`), поэтому обе стороны идут на один и
тот же стенд, и вписывать в неё адрес руками не надо. Первый пришедший занимает
`p1`, второй — `p2` (design D4).

Незанятый слот через `--bot-fill-ms` (по умолчанию 5 с после первого
претендента) забирает бот (BOT-7) — второму игроку столько на открытие ссылки
может не хватить. Отсрочка задаётся переменной среды:

```sh
DEMO_BOT_FILL_MS=60000 npm run demo:lan   # минута на то, чтобы подключиться
DEMO_STAND=off npm run demo:lan           # не поднимать стенд: он запущен своими флагами
```

Страница по `https` требует стенда за `wss://` — адрес выводится вместе со
схемой, потому что `ws://` со страницы по `https` браузер блокирует как mixed
content. Своего TLS у стенда нет: в LAN он не нужен, а в интернет стенд выходит
туннелем, и TLS терминирует туннель.

### Через интернет — туннелем

```sh
npm run demo:tunnel   # dev-сервер + стенд + quick-туннель cloudflared
```

То же, что `demo:lan`, но ссылка второму игроку ведёт через quick-туннель
Cloudflare — работает из любой сети, без аренды сервера, проброса портов и
установки чего-либо у гостя. Хосту нужен бинарь `cloudflared` (ставится один
раз: `brew install cloudflared` / `winget install Cloudflare.cloudflared`);
отсутствие бинаря плагин называет подсказкой установки, а не трассой.

Туннель один на оба потока: страницу отдаёт dev-сервер, а WebSocket стенда едет
через его же прокси-путь `/stand` (`vite.config.ts`), поэтому ссылка имеет вид
`https://<случайное>.trycloudflare.com/?server=wss://<то же>/stand` — явный
`?server=`, потому что вывод адреса из страницы целится в порт стенда, которого
снаружи туннеля нет (`tunnel.ts`). Адрес случаен и живёт до остановки
dev-сервера; трафик идёт через edge Cloudflare, то есть пинг длиннее прямого —
это стенд «позвать друга», а не выделенный сервер интернет-матча
(`server-control`).

Канал гостя ломается двумя разными способами, и по счётчикам слота они выглядят
по-разному. УЗКИЙ канал — тот, который не тянет поток состояний: у соединения
растёт очередь отправки, и хост перестаёт слать ему каждый снапшот, считая
пропуски отдельно (NTR-22). Картинка у гостя при этом остаётся живой, просто
приходит реже: снапшот несёт свой тик и самодостаточен (NTR-2, NTR-10),
следующий заменяет пропущенный целиком, а неровный интервал между состояниями
переживает буфер интерполяции (NET-3). Растущая очередь без пропусков была бы
хуже: состояния приезжали бы всё позже, и вслед за ними опаздывал бы ввод.
ДЛИННЫЙ канал виден иначе — пропусков нет, зато у гостя растёт запас разметки
ввода (NTR-7), а по слоту идут predicted-кадры, пока запас догоняет круг.
Сколько круга матч вытягивает, решает документ матча
(`content/matches/duel.match.json`): `inputWindow` 60 даёт потолок запаса 56
тиков — около 0,93 с при 60 Гц, — а `silenceSeconds` 300 оставляет
выравнивателю время дорасти, не уронив слот по молчанию (NTR-6). Круг длиннее
этого запас уже не лечит: он упирается в потолок, и помогает только дорога
короче.

### На десктопе — кнопкой

В десктоп-контейнере (`desktop-shell`) стенд поднимает сам контейнер: профиль
игры объявляет его сервисом (DSK-7), и кнопка режима становится «поднять стенд и
играть по сети». Страница при этом называет контейнеру ОДНО имя объявленного
сервиса — ни файла, ни аргументов она не передаёт, — получает адрес и уходит в
обычный сетевой режим по нему (`desktopStand.ts`, SES-3 «опубликовать сессию»).
Стенд не переживает окно, а бот-заполнитель там отодвинут на минуту: кнопка
существует ради «позвать друга», и слот должен дождаться человека.

В вебе этой кнопки нет и быть не может — страница процессов не поднимает; бандл
при этом один и тот же, а признаком служит наличие моста в странице (DSK-1).

## Арена

Контент арены — `content/scenes/duel.scene.json`: сетка 48×48 по клетке,
играбельный пол — диск радиуса 22 вокруг центра `(24, 24)`, клетки вне его
без пола (`_`), и шаг за кромку — провал в пустоту. По квадрантам стоят четыре
ОДНОУРОВНЕВЫХ плато (уровень 1); к каждому ведёт рампа шириной четыре клетки со
стороны центра — подъёмы оспариваются из середины. Рампа — одна полоса клеток
уровня плато с флагом `^`: перепад в единицу через клетку-рампу проходим по
построению (TERR-5), и подъём занимает ровно одну ступень. Весь остальной
периметр плато — обрыв в единицу БЕЗ рампы: ПЕШКОМ он непроходим, но плато
одноуровневые, а прыжок открывает допуск подъёма ровно в единицу на время
полёта (`Locomotion.jumpHeight` = 1, LOC-5, PHYS-11), — значит кромка берётся
прыжком в ЛЮБОМ месте. Рампа даёт путь без прыжка, а не единственный вход;
это осознанное свойство карты, и оно пиннится тестом демо-сцены.
Герои матча спавнятся симметрично:
`p1` в `(8,5; 24,5)`, `p2` в `(39,5; 24,5)`.

## Управление

| клавиши | действие |
| --- | --- |
| `WASD` / стрелки | движение героя |
| `Shift` | уклон; дважды подряд — перекат (`locomotion` LOC-3, LOC-4) |
| `Space` | прыжок |
| `ЛКМ` | фаербол: удержание копит заряд, отпускание открывает прицеливание |
| `ПКМ` | подтвердить шаг прицеливания — выстрел фаербола, захват снаряда |
| `Q` | отменить начатый каст: кулдаун возвращается целиком |
| `F` | купол замедления: чужие снаряды внутри летят впятеро медленнее |
| `R` | захват снаряда: нажатие показывает конус, `ПКМ` ловит |
| `E` | щит: пузырь на секунду, чужие снаряды от него отскакивают |
| `X` | ульта отката: мир отматывается на 7 с; стартует ВЗВЕДЁННОЙ — первые 20 с её нет |
| `K` | смерть героя (отладка); через 10 с он возвращается на свой спавн |
| `T` | сменить скин steel/ember (`rendering` REND-6) |
| `C` | центрировать камеру на герое; удержание — держать в центре |
| `Y` | режим слежения (follow) |
| `V` | режим облёта: `WASD` двигают камеру, `Q`/`Z` — вверх/вниз, `ПКМ` — осмотр |
| `[` / `]` | наблюдение: предыдущий/следующий участник матча (`camera` CAM-10) |
| `\` | снять наблюдение — камера возвращается к своему герою |
| `P` | снимок кадра: PNG без HUD и без тряски камеры |
| стрелки, край экрана, `СКМ`, колесо | панорама и зум камеры (`camera` CAM-1..3) |

Тач и геймпад работают по тем же биндингам — раскладка устройств лежит в
`bindings.json` (`input-devices` INP-4), а смысл битов кнопок — в `sim.ts`
(`ACTION_BITS`), то есть в контенте демо, а не в движке.

Панорама краем экрана в этой сборке работает ТОЛЬКО в free-RTS (`cameraInput.ts`).
Причина — мышь: `ЛКМ` бьёт в точку под курсором, а захват и заряд каста целятся
ею всё время удержания, поэтому игрок, целящийся к кромке арены, держит курсор в
краевой полосе постоянно. Край здесь — тот ДВУСМЫСЛЕННЫЙ источник панорамы,
который CAM-2 разрешает освободить от открепления: без гейта прицел в край
срывал бы слежение за героем — камера «сама» уезжала от него. Стрелки, drag
средней кнопкой и клик миникарты открепляют по-прежнему: они однозначны, и
однозначный источник открепления сборка обязана сохранить. Открепившуюся камеру возвращает `Y`
(залипающий follow) или `C` (разовое центрирование) — и `V` тоже: выход из
облёта садится в free-RTS, а не в follow.

## Наблюдение и снимок кадра

`[` и `]` перебирают участников матча (CAM-10): камера ведёт выбранную сущность
тем же follow, каким вела героя, — со сглаживанием, порогом рывка (CAM-5) и
высотой по поверхности (CAM-2). Кандидатами считаются доставленные сущности со
статом слота (`STATS.slot`), то есть участники; порядок — по возрастанию
идентификатора, перебор цикличен в обе стороны. Наблюдаемый, исчезнувший из
доставки (вышел из матча), уступает следующему по порядку; перемотка выбор не
меняет. `\` снимает наблюдение — камера возвращается к своему герою. Подпись
наблюдаемого висит сверху по центру: это показание СТРАНИЦЫ о её режиме
просмотра, а не виджет HUD (в композицию HUD-4 оно не входит, как и выбор
качества).

Зритель, которому доставлены все сущности, — режим сетевого слоя, а не камеры:
полный поток без фильтрации получает соединение-наблюдатель (`netcode-transport`
NTR-9). В обычном матче кандидатами будут те, кого игроку видно.

Страница `/?observer` — это он и есть (NTR-21): соединение к тому же стенду, что
и `?server=`, но без игрового слота. Ввод оттуда не уходит, камера ведёт
участника перебором (`[`, `]`), а HUD собирается без виджетов своего героя —
кулдаунов, портрета и полосы здоровья: своей сущности у наблюдателя нет, а
показывать чужие кулдауны значило бы выдать чужое намерение (HUD-4, NET-12).

Стенд пускает наблюдателя только по флагу запуска — сетевой аутентификации нет
вовсе, и полный поток открывается решением человека, а не по умолчанию (NTR-9):

```sh
npm run demo:serve -- --observer     # стенд руками
DEMO_OBSERVER=on npm run demo        # стенд, который поднимает dev-сервер страницы
```

Без разрешения страница `?observer` показывает названный отказ
(`observer-not-allowed`), а не пустой экран.

`P` снимает кадр в PNG. HUD — отдельный DOM-слой (HUD-3), и снимок просто не
показывает его; эффекты камеры на этот кадр заморожены (REND-25) — трясущийся
снимок показывает движение, которого в мире нет. `preserveDrawingBuffer` при
этом НЕ включается: он стоит памяти каждому кадру матча ради одного кадра
снимка, поэтому канвас снимается тем же тактом, что и рисуется. Файл отдаётся
ссылкой с `download` — ни сервера, ни сети для этого не нужно.

## Качество картинки

Переключатель в правом нижнем углу (`render-quality` QUAL-1): три уровня —
производительность, баланс, ультра. Уровни — ДАННЫЕ этого приложения
(`app/presets/*.json`), движок знает только объявленные подсистемами ручки, а
имён пресетов не знает вовсе; четвёртый уровень — новый документ и подпись к
нему, без правок движка. Смена идёт в рантайме, пересборки рендера нет.

Дефолт — `balanced`: из авторских значений он ограничивает сверху только тени —
режим не выше `hybrid` и карту не крупнее 1024. Сегодняшнего кадра это не
меняет ни на пиксель: секции `lighting` у сцен ещё нет, действующий режим —
`none`, и потолок его не поднимает. `performance` ограничивает сверху
разрешение маски тумана (4 против сценных 8, FOW-10) и плотность разбиения
террейна, огрубляет уровни детализации, вдвое снижает плотность частиц и
выключает тени совсем. `ultra` потолков не ставит вовсе: авторские значения
сцены и манифеста действуют как написаны — сцене с режимом `full` он его и
оставит. Выбор запоминается в браузере и переживает перезагрузку; на симуляцию
и на то, что игроку видно, пресет не влияет ничем (QUAL-2, NET-12).

## Способности

Все живут ОПРЕДЕЛЕНИЯМИ конфига сцены (`ability-system` ABIL-2): триггер, фазы
каста, цепочка шагов прицеливания и эффекты списками действий того же DSL, что у
JSON-систем. Числа — выражения определений, то есть балансная политика, а не код
(mechanism vs policy); плоских god-компонентов `AbilityConfig` и `Cooldowns` у
сцены больше нет, а состояние каста и остаток кулдауна живут на СУЩНОСТЯХ-слотах
героя (ABIL-1, ABIL-7). Уникальные взаимодействия — перехват снаряда щитом,
удержание пойманного, возрождение — платформой не поглощены и остались
JSON-системами сцены (ABIL-9).
Купол, захват и щит работают ПРОТИВ соперника, поэтому в `?solo` (герой один)
они инертны: купол ставится и висит, но замедлять ему нечего — чужих снарядов в
мире нет, — захват не находит цели и потому даже кулдауна не тратит, а щит
встаёт пузырём, от которого нечему отскакивать (свой снаряд он пропускает
намеренно). Смотреть их надо в матче с ботом (адрес `/`) или по сети.

**Фаербол** (`ЛКМ`, перезарядка 1 с). Снаряд — круглый коллайдер в половину
героического (радиус 0,15 против 0,3), летит быстро (0,625 клетки за тик) и
низко над полом: дуга полёта в манифесте (`verticalOffset.flightArc`) прижата
к земле. Заряженный `HeavyFireball` бьёт по своей картинке: его коллайдер —
0,3, то есть ровно вдвое больше и ровно тот радиус, которым он нарисован.
Попал в ЧУЖОГО героя — снимает ему свой урон (`Projectile.damage`, базовый
100) и исчезает; попал в подъём обрыва плато или в стену — взрывается там же
(со стороны спуска обрыв его пропускает, см. ниже). Оба случая
приходят из физики событиями `Overlap` и `Collision` (PHYS-12, PHYS-8), которые
разбирает блок доставки определения (`projectile.onHit`, ABIL-9): попадание в
героя и удар о статику — две ветки одного списка действий, и вторая пропускает
снаряд, развёрнутый щитом на этом же тике. Свой снаряд владельца не задевает
(сравниваются `Owner.slot` и `Player.slot`). Долетевший до конца жизни снаряд
просто взрывается списком затухания (`projectile.onFade`) — пол он больше НЕ
выбивает; саму сущность после затухания снимает платформа.

Урон одного тика СКЛАДЫВАЕТСЯ: два снаряда, попавших в героя одним тиком,
снимают 200, а передержка вместе с попаданием — 350. Система `DamageApply`
стоит на order 320 — ПОЗЖЕ разбора попаданий (`ProjectileSystem`, 300): событие
урона публикуется там, и системе на прежних 128 оно было бы невидимо (EVT-2).
Обходит она не события, а ЦЕЛИ: на цель приходится одно чтение здоровья, сумма всех
адресованных ей `Damage` этого тика и одна запись. Иначе команды буфера
(последняя-побеждает на поле, CMD-3) оставили бы от N попаданий одно.

**Две честные границы попадания.** Первая — сенсор физики строится как ОБЪЕДИНЕНИЕ
границ снаряда до и после хода тика (`physics.ts`, помечено `ponytail`), то есть
как прямоугольник, описанный вокруг всего шага. По осям это точно: прямоугольник
шага и есть заметённый объём. По диагонали — нет: на скорости 0,625 клетки за
тик выстрел под 45° засчитывает попадание примерно в 1,9 раза дальше от своей
геометрии, чем следует, и герой рядом с траекторией ловит снаряд, который в него
не летел. Контент этого не чинит и чинить не может — числа скорости и коллайдера
тут ни при чём; чинится это заметающей (swept) проверкой в ядре, и она отложена
до профилировки на реальной сцене, как и прочие `ponytail`-компромиссы.

Вторая — снаряд останавливает только ПОДЪЁМ обрыва. В коллайдере снаряда стоит
`cliffRise: -1`, то есть направленный гейт обрыва (PHYS-11) с нулевым допуском
подъёма: выстрел в плато снизу детонирует о его кромку, а выстрел С плато вниз
эту же кромку пролетает и летит дальше над землёй — снаряд ведёт себя как
летящий, а не как пешеход. Рампы не останавливают ничего: перепад в единицу
через клетку-рампу проходим по построению (TERR-5), статики там нет вовсе, и
гейт на ней даже не спрашивают. Клетки без пола снаряду тоже не помеха: провал в
пустоту вешает `FallStart` только на носителей `FallConfig` (герои), а у снаряда
его нет — над ямой он просто летит дальше, пока не кончится жизнь.

**Заряд, прицеливание, выпуск.** Каст трёхтактный (ABIL-4): нажатие `ЛКМ`
начинает фазу заряда — перед кастером появляется оранжевый шар, — отпускание
переводит в фазу ПРИЦЕЛИВАНИЯ, а выстрел даёт `ПКМ`, подтверждающий шаг. Пока
идёт прицеливание, под курсором лежит контур будущего выстрела: его рисует
подсистема превью рендера по ТОЙ ЖЕ записи фигуры, по которой решает симуляция
(REND-28, ABIL-5), — второго описания способности у клиента нет. Не подтвердил
за полсекунды — шар уходит по направлению взгляда сам (`timeout: commit` фазы):
цепочка прицеливания добавляет игроку выбор, а не отнимает выстрел.
Окно роста заряда — 60 тиков, но тик НАЖАТИЯ в него не входит, и
полный заряд набирается 61-м тиком с кнопкой вниз (самый быстрый тап,
отпущенный на следующем тике, обязан дать обычный шар). Урон растёт как КВАДРАТ
размера — двойной шар бьёт на 400. Во время заряда ходьба свободна, а манёвры
(уклон, перекат, прыжок) заперты тем же селективным локом `ActionLock`
(`locomotion` LOC-7), что и пойманный снаряд; захват на это время недоступен.
Лок снимается на выходе из фазы заряда: прицеливаться игрок вправе на ходу.
Купол замедления (`F`) при этом остаётся доступен, но начатый каст ОБРЫВАЕТ —
старт другой способности того же владельца прерывает идущую (`supersede`,
ABIL-6), и это отличие от досмиграционной сцены, где купол под собственный заряд
ставился безнаказанно.
Передержка — 300 мс (18 тиков) сверх максимума, то есть 79 тиков заряда, —
выражена ИСХОДОМ таймаута фазы (`timeout: {then: cancel}`) и списком `onCancel`,
который различает источник по полю `lastInterrupt` слота: взрыв идёт В САМОМ
кастере — 250 урона всем в радиусе 3 клетки, включая его самого (свои промахи
должны стоить), кулдаун списывается, шар исчезает. Кулдаун в 60 тиков ставится и
на выстрел, и на передержку; отмена (`Q`) возвращает его целиком.

Шар заряда рисуется записью `effects.byState.Charging` манифеста по маркеру
сцены, который вешает фаза заряда (design Decision 7): он виден КАЖДОМУ, чья
сущность в фазе, а не только своему герою — заряжаемый шар противника обязан
быть виден, потому что он уже часть мира. Рукописных шаров главного потока
больше нет: РОСТ по ходу заряда и вынос перед кастером задаёт сама запись
(`radiusFromStat` по доставленному стату `charge` и `offset` по доставленному
прицелу, REND-23), а порог тяжёлого снаряда и мигание передержки — её же поля
`colorAt` и `blink`. Ушло с рукописным шаром одно — доворот торса на заряде:
направление выстрела до подтверждения шага не решено вовсе, и доворачивать было
бы не на что. У УЛЕТЕВШЕГО снаряда размер
меняется ступенькой: заряд от полутора размеров и выше рождает prefab
`HeavyFireball` (тот же тег `Fireball` для систем, свой визуальный тип для
манифеста), и плавного роста в полёте нет — это известная граница механизма, а
не недосмотр. С того же порога шар заряда перекрашивается в цвет тяжёлого
снаряда: цвет на выстреле не должен меняться сюрпризом, а «тяжёлый уже сейчас» —
единственная подсказка, которую игрок успевает прочитать.

**Купол замедления** (`F`, перезарядка 5 с, живёт 3 с). Ставится на месте
героя радиусом 10 радиусов его коллайдера (3 клетки) и разложен на две
независимые части (BUFF-7): сама зона — сущность с компонентом длительности
платформы (ABIL-9), которая тикает и по исчерпании снимает себя сама, а
замедление — ДЕБАФФ, который зона выдаёт вошедшим. Выдаёт его аура: слот со
способностью-триггером `always` живёт на самой зоне (её выдаёт та же
JSON-система сцены, что раздаёт слоты героям), каждый тик обходит чужие снаряды
внутри радиуса и накладывает бафф политикой `refresh` с длительностью в два
тика. Отсюда и снятие: вышедший из купола снаряд просто перестаёт получать
продление, и бафф гаснет сам — «следить за выходом» некому и не нужно.
Статовую правку бафф ставит в существующий список источников (`TimeScaleModifiers`,
BUFF-4, TIME-7): множитель 0,20 сводится `TimeScaleSystem`, а шаг снаряду
умножает физика (TIME-3) — сама скорость в компоненте не трогается, поэтому
выход из купола восстанавливает полёт точно. Свои снаряды купол не замедляет —
на этом и держится связка с захватом. Радиус купола в манифесте
(`effects.byKind.SlowDome.radius`, 3) — РУЧНОЕ зеркало произведения
`Collider.radius × domeRadiusMul` из определения: оболочка эффекта числами
симуляции не питается, и ретюнить их надо вместе.

**Захват снаряда** (`R`, перезарядка 2 с за ПОЙМАННЫЙ снаряд). Нажатие открывает
фазу подтверждения, и пока она идёт, под курсором лежит конус зоны — его рисует
та же подсистема превью, что и лану выстрела, по ФИГУРЕ ШАГА определения
(REND-28): круг радиуса `captureRadius`, срезанный клином `captureHalfAngle`. Ни
второго описания зоны, ни рукописного `capturePreview.ts` у сборки больше нет —
превью и проверка читают одну запись. `ПКМ` подтверждает шаг: платформа берёт
БЛИЖАЙШИЙ К ТОЧКЕ ПРИЦЕЛА чужой снаряд, прошедший предикат шага (тег снаряда,
не свой владелец, попадание в раствор) и дальность (ABIL-5) — прежнее «ближайший
к самому ловцу» стало «ближайший к тому, куда игрок целится». Кулдаун списывается
ТОЛЬКО за пойманный снаряд, и держится это не веткой контента, а умолчанием
платформы: пустой шаг проваливает проверку на подтверждении, источник
`targetLost` возвращает кулдаун (ABIL-6). Промах не стоит игроку ничего и
разрешает повторить попытку следующим же тиком. Пойманный снаряд замирает у
держателя, каст на это время заблокирован, а манёвры — локом `ActionLock`;
ходьба остаётся. Бросок — `ЛКМ` тем же прицелом: снаряд уходит по `aimDir`, и
ЕГО ВЛАДЕЛЕЦ СТАНОВИТСЯ БРОСИВШИМ, поэтому свой купол его больше не замедляет,
а купол прежнего хозяина — да; накопленный урон снаряд при этом сохраняет.
Не выброшенный за 2 с (окно броска — 120 тиков после тика захвата) снаряд
взрывается в руках и снимает держателю 250 hp общим путём урона сцены
(`Damage` → `DamageApply` → `HealthDeath`).

Каст и подтверждение ловят ФРОНТ кнопки, а конец фазы заряда — её отсутствие на
фоне прошлого тика, и поэтому по сети они ведут себя по-разному. Пропавший пакет
ввода сервер замещает повторением последнего кадра (`tick-loop` TICK-2): для
фронта это безобидно (нажатие просто приедет позже), а для отпускания означает,
что кнопка «остаётся зажатой» лишний тик — потеря пакета может добавить снаряду
каплю заряда, но не выдумать выстрел и не потерять его. У самой границы
передержки цена этого лишнего тика не капля: отпускание на 79-м тике, пакет
которого пропал, превращается в разрыв заряда в собственном кастере — 250 урона
себе вместо выстрела. Своевременный выстрел — часть риска способности, и по сети
этот риск на один тик шире, чем локально.

**Щит** (`E`, перезарядка 2,5 с, живёт 1 с). Каст-и-забыл: фронт клавиши вешает
на героя маркер `Shielded` и спавнит инстанс баффа, который этот маркер и снимет
по истечении (`onExpire`, BUFF-6) — маркерный компонент остался узором КОНТЕНТА,
а не полем определения (design Decision 7), поэтому `ShieldRicochet` и
`HoldingGuard` спрашивают `hasComponent(e, "Shielded")`, ничего не зная о
баффах, и биты состояний рендера не переписывались. Вокруг героя на секунду
встаёт синий
полупрозрачный пузырь радиусом 2,6 коллайдера героя (0,78 клетки против 0,3) —
круг, который ЕЗДИТ с героем, а не стоит на месте, как купол. Ставить щит
нельзя во время заряда каста и с пойманным снарядом в руках — те же две
блокировки, что у захвата; сам щит при этом не запирает ни манёвры, ни касты:
`ActionLock` (LOC-7) он не вешает вовсе. Одно исключение появилось миграцией:
подтвердить захват и нажать `E` ОДНИМ тиком — значит получить и снаряд в руках,
и пузырь. Прежде очередь решала шкала `order` (щит на 39 видел `Holding`,
поставленный захватом на 38), а теперь обе способности — слоты одной системы
(`CastPhaseSystem`), и её команды мир видит только после flush (CMD-2), поэтому
предикат щита читает мир без ещё не применённого `Holding`. На всех последующих
тиках блокировка держит.

Смерть снимает щит ТЕМ ЖЕ тиком — все три пути (`KillSwitch`, `FallDeath`,
`HealthDeath`) убирают `Shielded` рядом с `Dead`. Иначе труп до 59 тиков носил бы
синюю сферу, которая ничего не защищает: `ShieldRicochet` мёртвых исключает
запросом, и оставленный компонент был бы чистым обещанием игроку.

**Рикошет.** Пока пузырь стоит, ЧУЖОЙ снаряд, попавший в него, не бьёт хозяина,
а отскакивает: скорость отражается через нормаль контакта (`v' = v − 2(v·n)n`),
а ВЛАДЕЛЬЦЕМ снаряда становится хозяин щита. Смена владельца — не украшение, а
то, чем держится вся связка: свой снаряд владельца не задевает (разбор попаданий
идёт после рикошета и читает уже нового), купол прежнего хозяина начинает его
замедлять, а купол нового — перестаёт, и поймать его захватом теперь может
прежний стрелок. Урон и размер снаряд сохраняет: тяжёлый шар возвращается
стрелку теми же 400.

Геометрия рикошета живёт в JSON, а не в физике: снаряд героев не таранит
(`blockMask` у него — только статика обрывов), поэтому события `Collision` с
честной нормалью PHYS-9 тут не возникает, и нормаль система считает сама — по
ЛИНИИ ЦЕНТРОВ от героя к снаряду, ровно так, как PHYS-9 её и определяет для
круглого препятствия. Физическим путём (дать щиту блокирующий слой) это не
делается по одной причине: маски владельца не знают, а вынос выстрела (0,45
клетки) МЕНЬШЕ полуширины щита с полуосью снаряда (0,93) — щит запирал бы своего
хозяина, отражая в него его же выстрелы. Проверка `Owner.slot ≠ Player.slot` в
JSON-системе решает это одной строкой.

**Членство и нормаль считаются РАЗНОЙ геометрией, и это намеренно.** Попал ли
снаряд в щит — вопрос ОСЕВОГО бокса: `|dx| ≤ shieldR + halfX` и `|dy| ≤ shieldR
+ halfY`. Причина в том, откуда берётся урон: ветка попадания растёт из события
`Overlap` физики, а оно — пересечение ОГИБАЮЩИХ (PHYS-12), то есть бокс со
стороной «полуось героя + полуось снаряда», и по диагонали урон достаёт до
0,45·√2 = 0,636 клетки. Круг, вписанный в бокс членства, этот угол накрывает не
всегда: на прежнем множителе 1,3× полоса щита равнялась 0,54, то есть была
КОРОЧЕ диагонали урона, и снаряд, пришедший в лунку между 0,54 и 0,636, снимал
хозяину щита сотню без единого рикошета — та самая регрессия, ради которой
членство и переехало на бокс (тест «диагональный подлёт не течёт»).

На нынешних 2,6× лунки нет и у круга: полоса 0,93 сама длиннее 0,636, и бокс
щита строго СОДЕРЖИТ бокс урона — по каждой оси он шире ровно на `shieldR`.
Боксовым членство остаётся именно поэтому — по причине СОДЕРЖАНИЯ, а не потому,
что круг сегодня не дотягивается: содержание держится на `shieldR > halfX`
героя, то есть при любом множителе больше единицы, а «круг длиннее диагонали» —
на конкретных 2,6×, и ретюн вниз тихо вернул бы лунку. Щит обязан накрывать
ровно ту фигуру, которой бьют. Нормаль при этом
осталась КРУГОВОЙ, по линии центров: она описывает не «где щит кончается», а от
чего снаряд отскакивает, а отскакивает он от круглого пузыря (PHYS-9). Бокс
здесь — конверт физики, круг — форма поверхности; смешивать их было бы удобно и
неверно в обе стороны.

Держится это на двух неравенствах чисел prefab'а (пиннятся тестом): радиус щита
(0,78) БОЛЬШЕ полуоси героя (0,30) — бокс щита строго содержит бокс урона по
каждой оси; и полная ширина щита `2·(shieldR + halfX)` = 1,86 БОЛЬШЕ самого
длинного шага снаряда (0,625) — свип тика не может перешагнуть бокс насквозь,
оставив обе точки хода снаружи.

Плата честная и известная: по углу бокс достаёт до 0,93·√2 = 1,32 клетки, и там
снаряд отскочит, будучи заметно снаружи нарисованной сферы (0,78). Это ровно то
же искажение, которое уже есть у УРОНА — его бокс по углу достаёт до 0,636 при
нарисованном герое в 0,30, — и щит теперь врёт в ту же сторону и не больше, чем
хитбокс, который он закрывает. Выбор между «щит совпадает с картинкой» и «щит
совпадает с уроном» решён в пользу второго: расхождение с картинкой игрок видит
как щедрый блок, расхождение с уроном — как пробитый щит.

Рикошет считается ПО СНАРЯДУ: система обходит снаряды и для каждого берёт
БЛИЖАЙШИЙ подходящий щит (`nearestTo`, ACT-5) — членство решает бокс, а «кто из
двоих» решает расстояние, — поэтому за тик снаряд отражается ровно один раз,
сколько бы пузырей его ни накрыло, а один щит успевает отбить сколько угодно
снарядов. Пойманный снаряд (`Held`) щит не трогает — он в руках, а не в полёте.
Жизнь снаряда рикошет НЕ продлевает (в отличие от переброса): поэтому пинг-понг
двух щитов кончается сам собой, когда истекают те же 50 тиков полёта.
Вырожденный случай «снаряд ровно в центре героя» тоже определён: линии центров
там нет, и снаряд разворачивается назад по своему же курсу.

Обрыв в тике рикошета проигрывает пузырю: ветка удара о статику
(`projectile.onHit`, разбирается на order 300) пропускает снаряд, у которого в
этом же тике был `ShieldRicochet` (order 108). Столкновение со статикой
физика посчитала ДО отскока (разрешение движения — order 100), то есть
принадлежит уже стёртой траектории; без этой оговорки один тик показывал бы
разом вспышку рикошета и взрыв о край плато, а снаряд, который щит только что
отбил внутрь арены, исчезал бы.

Нормаль считается по УВЕЛИЧЕННОЙ в 64 раза разности центров (множитель живёт
именованной привязкой `normScale` — в JSON комментария не поставить, а голое
`4194304` в теле системы не читается; так же назван и разворот `minusOne`):
нормализация в Q16.16 на коротких векторах теряет точность (квадрат длины
разности в сотые доли клетки округляется до сотен единиц), и «единичная» нормаль
выходила бы длиннее единицы на процент — снаряд разгонялся бы с каждым отскоком.
С увеличением модуль скорости сохраняется до единиц Q16.16.

У множителя есть ПОТОЛОК, и он ограничивает ретюн. `vec.lengthSq` увеличенной
разности считает скалярное произведение в Q16.16, и `(64·d)²` обязана влезть в
i32: расстояние контакта `d` должно быть меньше 2,828 клетки (2√2, сырое 185364)
— дальше сумма переполняется молча, нормаль выходит мусорной, а скорость с ней.
Членство боксовое, и самая дальняя точка бокса — его угол, `band·√2`, поэтому
потолок на сам `band = shieldR + halfX` вдвое строже: меньше 2 клеток. Сейчас
там 0,93 — запас чуть больше двукратного, но `shieldRadiusMul` рекламируется тюнимым, а
соседний `domeRadiusMul` уже 10× (на нём эта нормализация переполнилась бы).
Неравенство пиннится тестом рядом с остальными зеркалами.

Один тик пузырь ВИЗУАЛЬНО протекает, и это цена расписания, а не дефект: снаряд
двигается на order 100, а скорость разворачивается на 108 — тик, в котором
случился рикошет, рисуется с шаром уже внутри сферы. На следующем он снаружи и
уходит обратно. Двигать шаг физики после рикошета значило бы решать, куда летит
снаряд, до того, как известно, летит ли он вообще.

## Смерть и возрождение

Смерть в этой сцене не терминальна: через 10 с (600 тиков, число системы
`Respawn`) герой возвращается В СВОЮ точку спавна целым.
Путей смерти по-прежнему три (`KillSwitch`, `FallDeath`, `HealthDeath`), и все
три обнуляют скорость рядом с `Dead`: труп не едет. Для провала это отдельная
оговорка — вход в падение (`FallStart`) скорость как раз СОХРАНЯЕТ, чтобы герой
уходил за кромку по дуге, — но в тик смерти импульс гасится, иначе тело все
десять секунд окна ехало бы прочь, и возрождение читалось бы телепортом с
другого конца карты.

След смерти при этом у каждого пути свой, поэтому возрождение (`Respawn`,
order 140) чистит каждый: снимает `Dead`, `Falling` и `LevelOverride` (след провала в пустоту),
`Shielded`, `ActionLock`, `Charging`, `Holding` (следы способностей), обнуляет
скорость и машину манёвров `LocomotionState`, возвращает `Collider.cliffRise` в
ноль (его открывает прыжок, и смерть в полёте оставила бы его открытым) и
ставит здоровье в `hpMax`.

Управление возвращается `addComponent`'ом: смерть снимает с героя `Locomotion`
целиком — это и есть механизм «труп не ходит», — а `addComponent` заполняет ВСЕ
поля схемы, поэтому числа локомоушена выписаны в системе второй раз. Это
единственная копия балансных чисел в сцене, и держит её в согласии с prefab'ом
зеркальный тест демо; расходиться им нельзя — воскресший герой поехал бы с
другой скоростью.

Точку возрождения запоминает `SpawnAnchor` (order 1): первым же тиком он вешает
на каждого героя компонент `Spawn` с его НАЧАЛЬНОЙ позицией. Отдельная система,
а не поле prefab'а, потому что расстановка — дело конфига матча
(`duel.match.json`, `initial`) и тестов, а не prefab'а: числа спавна лежат в
одном месте, и второй их записи не заводится.

Перезарядки способностей возрождение обнуляет — десять секунд ожидания уже
заплачены, и добирать поверх них секунды кулдауна незачем. Обнуляет их обход
сущностей-слотов героя (остаток кулдауна живёт там, ABIL-1), и слот ульты отката
из обхода исключён поимённо: обнулять его смертью значило бы сделать смерть
способом сбросить ульту.

Сам слот ульты стартует ВЗВЕДЁННЫМ — с полными 1200 тиками, — и это не баланс, а
анти-луп. Кулдаун ульты переживает откат (exempt-компонент `AbilityCooldown`,
REW-9), но exempt защищает ПОЛЕ, а не существование его владельца: слоты
выдаются JSON-системой на первом тике мира, поэтому в снапшоте тика 0 их нет, и
откат в тик 0 удалил бы сущность слота вместе с кулдауном — `GrantSlots` выдала
бы её заново с нулём, и ульта вернула бы саму себя. Инвариант, который это
закрывает: **стартовый кулдаун ульты не меньше её глубины отката**, а её
собственный кулдаун (1200) глубину (420) превышает — значит цель любого каста
лежит позже тика выдачи слотов. Ретюнить глубину и кулдаун порознь нельзя; обе
половины инварианта пиннит тест демо.

При СЕГОДНЯШНИХ числах этот сброс ничего не меняет: `CooldownSystem` тикает и у
трупа, а самый долгий максимум (300) вдвое короче окна возрождения, — то есть к
воскрешению всё и так по нулям. Сброс оставлен защитой на ретюн: инвариант
«воскресший кастует сразу» не должен зависеть ни от того, что кулдауны короче
`respawnTicks`, ни от того, что у мёртвого они вообще тикают. Разыгран ретюн
тестом — сцена с перезарядкой щита длиннее окна смерти, — иначе строка сброса
осталась бы непроверяемым обещанием.

Пойманный трупом снаряд разрешается раньше возрождения САМ: окно `holdTicks`
(121 тик) короче `respawnTicks` (600), поэтому `HeldPin` успевает взорвать его в
руках мертвеца, а не живого. Неравенство пиннится тестом, и держать его надо
именно в эту сторону: `respawnTicks ≤ holdTicks` означал бы взрыв пойманного
снаряда в руках уже ЖИВОГО героя — 250 урона за смерть, случившуюся до
возрождения.

Известная острая кромка: окна неуязвимости у точки возрождения нет. Герой
появляется на своём спавне целым, но открытым — соперник, стоящий рядом, бьёт
его первым же тиком, и спавн-кемп сцена ничем не наказывает. Это осознанный
пробел демо, а не дефект механизма: неуязвимость — такая же контентная политика
(компонент-маркер плюс гейт в системах урона), и заводится она вместе со счётом
матча, а не раньше.

## Что видно на экране

HUD собран из виджетов пакета `@fluxus/hud` по значению композиции
(`hud.ts`, `match-hud` HUD-4): рантайм-панель и статус матча слева сверху,
счётчики смертей сверху по центру, миникарта слева, портрет героя с полосой
здоровья слева снизу, способности с оверлеем перезарядки снизу по центру.

Полоса здоровья, счётчики смертей и оверлеи перезарядки читают ДОСТАВЛЕННЫЕ
статы (HUD-8). Здоровье и перезарядки каста, купола, захвата и щита в сцене есть
и едут значениями; счётчика смертей в ней по-прежнему нет, и его виджет показывает
пустое состояние — прочерк вместо выдуманного нуля; это ожидаемое поведение, а
не поломка. Кнопки `dodge` и `jump` слотов способностей не имеют вовсе — это
манёвры локомоушена (LOC-4, LOC-5), а не способности платформы, — и стата
перезарядки у них НЕТ: виджет показывает их всегда готовыми по тому же правилу
пустого состояния. Сами перезарядки читаются с сущностей-слотов героя слотовой
формой источника стата (`extractor.ts`), а имена статов (`<способность>.cd`) при
миграции не поменялись — HUD её не заметил.

Попадание фаербола по герою рождает событие `HeroHit`, на которое подвешен
короткий красный выброс частиц (`particles.byEvent`, REND-24; сам эмиттер —
`content/visuals/effects/blood-burst.effect.json`): брызги летят во все стороны
и падают — эмиттер сферический, и на частицы действует сила вниз. Взрыв
передержанного заряда рисуется растущей красной сферой
(`effects.byEvent.ChargeExploded`) и трясёт камеру сильнее обычного взрыва; его
конечный радиус — те же 3 клетки, которыми бьёт `overchargeRadius`. Вспышка
попадания снаряда (`FireballExploded`), наоборот, мелкая: урон у него
КОНТАКТНЫЙ, площади нет, и раздутый огненный шар обещал бы игроку взрыв, от
которого можно отойти.

Щит рисуется оболочкой СОСТОЯНИЯ (`effects.byState.Shielded`, REND-23): синяя
полупрозрачная сфера живёт ровно столько, сколько доставляется бит состояния
`Shielded` (`STATE_COMPONENTS` в `sim.ts` задаёт номера битов). Её радиус в
манифесте (0,78) — РУЧНОЕ зеркало произведения `Collider.radius ×
shieldRadiusMul` из `ShieldRicochet`, как и радиус купола: ретюнить их надо вместе,
иначе нарисованный пузырь перестанет совпадать с отражающим (отражающая фигура
при этом — БОКС этого радиуса плюс полуось снаряда, см. «Рикошет»: сфера рисует
её вписанной, по углам щедрее). Сфера гаснет на тик раньше, чем кончается
защита: состояние снимается с конца тика, а последний тик счётчика ещё отражает
— та же асимметрия, что у купола. Труп её не носит: смерть снимает `Shielded`
тем же тиком.
