# @game-mvp/net — сетевой слой

Транспортный слой поверх модели `netcode`: сервер матча, протокол, клиент,
транспорты и основание сессии. Нормативные требования —
`openspec/specs/netcode-transport/` (NTR-1..16), `netcode` (NET-1..17) и
`net-session` (SES-1..9); здесь только карта кода.

Зависимость на ядро односторонняя (NTR-1): `net-ts` импортирует `@game-mvp/core`,
обратного импорта нет и быть не может — ядро о сети не знает (DI-3). Проверяется
тестом `test/boundary.test.ts`, а не договорённостью.

## Что в MVP есть и чего нет

| Есть | Нет (и почему) |
|---|---|
| Авторитетный сервер, два и больше слотов | Предсказание своей сущности (NET-2/4/5) — сначала базовая линия для замера |
| Хендшейк со сверкой версии и `worldInit` | Матчмейкинг и аутентификация участников |
| Лобби и матч по инвайту, хост-игрок (`listen`) | Host migration — передача авторитета вместе с эпохой и логом (SES-8) |
| Полные снапшоты, per-client фильтрация | Delta-компрессия — NET-8 сам называет её оптимизацией потом |
| Loopback и WebSocket за одним интерфейсом | WebRTC DataChannel — новая реализация `Transport` и `Rendezvous`, без правок сервера и клиента |
| Канонический лог и парность с `runScenario` | Реконнект и подключение к идущему матчу |

## Карта

```text
src/
  protocol/   messages.ts — закрытый набор сообщений и разбор входящего (NTR-4)
              codec.ts    — MessagePack на проводе, JSON для дебага (NTR-13)
  transport/  transport.ts       — интерфейс (NTR-2)
              loopback.ts        — внутрипроцессный: сервер и клиенты в одном процессе
              webSocketServer.ts — слушающая сторона (Node), в т.ч. каналы на одном порту
              webSocketClient.ts — подключающаяся (Node и браузер)
              merged.ts          — несколько слушающих сторон за одной (нужно режиму listen)
  lobby/      messages.ts, codec.ts — свой закрытый набор сообщений (SES-4)
              lobbyServer.ts        — чистый цикл: сбор ростера и заморозка в MatchConfig
              host.ts, lobbyClient.ts, clientHost.ts
  session/    session.ts     — режим и фаза сессии, наблюдаемые (SES-1, SES-9)
              rendezvous.ts  — интерфейс «опубликовать / разрешить в транспорт» (SES-3)
              invite.ts      — значение инвайта: адресат и допуск (SES-5)
              rendezvous/    — inProcess.ts (тесты), webSocket.ts (LAN и проброс порта)
              hostSession.ts — режим listen: лобби, сервер и свой клиент рядом
              dedicatedSession.ts, joinSession.ts
  match/      world.ts    — подъём мира матча, общий для сервера и клиента
  server/     matchServer.ts — чистый цикл без I/O и часов (NTR-3)
              host.ts        — сокет, таймер, часы: всё, чего нет в сервере
  client/     matchClient.ts — чистый цикл, симуляцию не тикает (NTR-10)
              host.ts, inputRing.ts, interpolation.ts
  content/    pack.ts     — сцены по ссылке, хеш пака (NET-17)
  metrics.ts  — раздельные счётчики по причинам (NTR-11)
```

## Локальный матч на двух игроков

Три процесса. Сервер:

```sh
cd engine/net-ts
npm run serve ../../content/matches/duel.match.json -- --port 8080
```

Два клиента, каждый в своём терминале:

```sh
npm run play ../../content/matches/duel.match.json -- --player p1 --keys
npm run play ../../content/matches/duel.match.json -- --player p2 --keys
```

`--keys` — WASD и пробел. Терминал сообщает нажатие, но не отпускание, поэтому
клавиша задаёт направление на ~200 мс; для замера отклика этого достаточно.
Вместо клавиатуры можно подать сценарий: `--script inputs.json`, где
`[{ "tick": 20, "moveX": 0.25, "buttons": 1 }, …]`.

Прочие флаги: `--json` — JSON на проводе вместо MessagePack (поток читается
глазами), `--observer` на сервере разрешает подключение наблюдателя, на клиенте
— запрашивает его.

## Стенд демо-арены (выделенный сервер с ботом и авто-рестартом)

Тот же выделенный сервер, но настроенный на демо-арену `content/` и живущий
без присмотра. Из корня репозитория:

```sh
npm run demo:serve                       # ws://127.0.0.1:8080, дедлайн бота 5 с
npm run demo:serve -- --port 9000 --bot-fill-ms 0
```

Что добавляет обвязка (`bin/demo-serve.mjs`) к `serve.mjs`, не трогая ни
`MatchServer`, ни протокол (SES-2):

- **Матч из дерева контента.** `content/matches/duel.match.json` и его сцена —
  ровно то, что играет вкладка демо. Другой файл — `--match <path>`.
- **Бот-заполнитель слота (BOT-7).** Слот, не занятый человеком к дедлайну
  `--bot-fill-ms` (отсчёт от ПЕРВОГО подключения), получает бота — отдельным
  потоком (BOT-4), мозг `--brain`, профиль `--bot <profile.json>`. Друг, успевший
  раньше дедлайна, занимает слот штатным `Hello`, и бот в такой матч не входит:
  уступка — политика этой обвязки, сервер ботов от людей не отличает (BOT-1).
- **Авто-рестарт.** По `End` любой причины (включая молчание слота) поднимается
  следующий матч тем же конфигом; `--once` оставляет ровно один. Цикл живёт в
  обвязке — чистый тик сервера не трогается (NTR-3).

Вкладка демо подключается к стенду параметром `?server=ws://127.0.0.1:8080`
(кнопка «играть по сети» в углу ведёт на захардкоженный адрес сборки).

## Матч без выделенного сервера (режим `listen`)

Выделенного сервера нет — авторитетный цикл поднимает один из игроков, и он же
играет. Два процесса вместо трёх. Основатель:

```sh
cd engine/net-ts
npm run host ../../content/matches/duel.match.json -- --player p1 --port 8080 --keys
```

Запускалка печатает инвайт — одну строку, которую основатель пересылает
приглашённому целиком. Приглашённый:

```sh
npm run play ../../content/matches/duel.match.json -- --player p2 --invite fluxus1.… --keys
```

Матч стартует, когда займутся все слоты: лобби морозит ростер в `MatchConfig`, и
дальше это обычный матч — тот же `MatchServer`, тот же `MatchClient`, тот же
набор сообщений, что на выделенном сервере (SES-2). Собственный клиент
основателя подключён внутрипроцессно и привилегий не имеет: тот же хендшейк, тот
же персональный снапшот, тот же путь ввода (SES-6).

Две вещи, которые надо знать до того, как звать друга:

- **Слушать входящие соединения умеет процесс, а не вкладка браузера.** Поэтому
  хост здесь — Node или десктопная сборка, а приглашённый добирается по LAN
  либо через проброс порта (`--advertise внешний-хост:порт` кладёт в инвайт
  внешний адрес). Хост во вкладке — это WebRTC, и встанет он под тот же
  интерфейс `Rendezvous`, не трогая ни сервер, ни клиента, ни протокол.
- **`listen` — режим для доверенных сторон.** Процесс хоста держит
  нефильтрованный мир по построению: фильтр видимости (NET-12) защищает
  удалённых участников, а хоста от самого себя не защищает и не может. Против
  недоверенных участников держит только выделенный сервер (SES-7).

## Какие числа смотреть

Клиент печатает три величины, и они отвечают на три разных вопроса — в этом
весь смысл раздельного счёта (NTR-11):

- **нажал→увидел** — сколько прошло от отправки кадра до появления его `seq` в
  снапшоте. Это и есть отзывчивость: в неё входят дорога до сервера, буфер
  задержки ввода и темп рассылки. Локально — около 40–50 мс при 60/30/2.
- **буфер** — отставание интерполяции (NET-3), цель ~100 мс. Растёт — снапшоты
  приходят неровно.
- **отброшено** — снапшоты с устаревшим тиком. Не ноль — канал переупорядочивает.

Сервер печатает на слот **применено/предсказано/опоздало**. Предсказанных много
при живом игроке — ввод не доезжает к дедлайну, стоит поднять `inputDelay`.
Опоздавшие не ноль — канал медленнее, чем предполагает запас.

## Проверки

```sh
npm test        # 70 тестов
npm run typecheck
```

Главный из них — парность (`test/match.test.ts`, NTR-8): отыгранный матч
выгружается как сценарий и прогоняется через `runScenario` ядра, состояние
обязано совпасть побитово. Это единственное доказательство, что сетевой слой не
сломал детерминизм; расхождение здесь — дефект этого модуля, а не ядра.

## Известные ограничения

- **Контент-пак — ровно одна сцена.** `contentPackHash` — чистая функция одного
  конфига сцены (NET-17), а склейка хешей нескольких сцен не нормирована.
  Изобретать её здесь значило бы завести второй способ хеширования, что NET-17
  запрещает.
- **Оценка серверного тика не компенсирует половину круга.** Локально точна, на
  канале с плечом часть кадров начнёт опаздывать. Компенсация вводится по
  замеру `нажал→увидел` на реальном канале — то есть когда есть чем проверить,
  что она помогла.
- **bin-скрипты требуют `--experimental-transform-types`.** Ядро использует
  parameter property (`core-ts/src/systems/visibility.ts`), а strip-only режим
  Node их не поддерживает. Флаг зашит в npm-скрипты и shebang. Той же болезнью
  болеет `core-ts/bin/sim.mjs`, где флага нет, — это дефект ядра, не этого модуля.
