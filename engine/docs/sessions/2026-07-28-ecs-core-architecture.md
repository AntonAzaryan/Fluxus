# Разгон: Архитектура ядра игры (ECS, spec-driven, детерминизм, рендер)

## Дата
2026-07-28

## Тема / повод
Старт разработки сетевой игры (тип: MOBA/dota-like). Триггер — продумывание процесса разработки: детерминированный движок на ECS, spec-driven подход (компоненты/системы/конфиги описываются декларативно, код генерится генератором + LLM), мульти-язык (Rust-сервер, TS/Unity-клиент). Нужно было прояснить жизнеспособность подхода и спроектировать состав ядра.

## Что обсуждали
- **Spec-driven процесс** — компоненты/конфиги описываются в YAML → генератор кодит под язык/движок; системы генерятся LLM по контракту. Вывод: подход рабочий, но с оговорками (см. ниже).
- **Генерация систем через LLM** — тупик в чистом виде: LLM даёт нестабильный/неповторяемый код, что убивает детерминизм. Отброшено «генерить тело системы из псевдокода каждый раз». Принято: декларативный контракт систем (query/reads/writes/order) + тело как фиксируемый артефакт.
- **Детерминизм** — не создаётся тестами, а закладывается конструкцией: fixed-point математика везде (float запрещён в геймплее), фиксированный порядок итерации сущностей и систем. Тесты — страж, не источник.
- **Тестирование детерминизма** — голден-тесты (снапшот + хеш стейта по тикам), докер-матрица `{язык} × {ОС/arch}` (особенно ARM vs x86), три инварианта: кросс-платформа, повторный прогон, прогон-из-середины (снапшот). CLI над ядром = точка запуска тестов.
- **Мульти-язык** — обоснован архитектурой (Rust authoritative server + client-side prediction на TS/Unity), не блажь. Fixed-point обязателен, т.к. float не совпадает бит-в-бит между языками.
- **Три слоя ядра** — ECS-фреймворк (готовый) / общие «кубики» (Transform, Movement, Health, Cast...) / геймплей. Зависимости только вниз. Спека разбита: core/ common/ game/.
- **Различение компонент / система / конфиг** — компонент = состояние сущности (меняется, своё); система = логика (фикс. порядок); конфиг = статические справочники типов/способностей (грузятся в ресурс мира, только читаются). Критерий: «меняется в игре / своё у сущности → компонент; статично и общее для типа → конфиг».
- **Спор реген vs способность** — реген уехал в компонент (`HpRegen{rate}`, меняется предметами/аурами); параметры способности (range/cd/damage) остаются в конфиге (свойство способности, не юнита; много скиллов; дублирование = риск рассинхрона). Гибрид: компонент хранит ссылки (`ability_id`) + динамику (`cd_remaining`, `level`), конфиг — статику.
- **Кубики геймплея** — выделены из требований: Player/OwnedBy/Controllable; Position/Facing/Velocity (fixed-point); MovementMode (wasd+rmb = один enum-режим); AnimatedValue (tween свойства, армлет-кейс, ≠ баф); Stat/Health; Ability/Casting/CastRequest; targeting как enum-база (NoTarget/UnitTarget/Point/Vector/Cone/Points — покрывает пангольера/марси/щиты-конусы); AreaEffect.
- **2.5D / Z** — геймплей плоский XY (как дота), Z добавлен для прыжков/уворотов: вертикальный кинематик (гравитация, не физдвижок), XY-коллизии = круги, Z-коллизии = интервалы высот. Никаких 3D-collision-mesh. Targeting остаётся плоским XY (как варкрафт), Z только в разрешении попадания.
- **Prediction каста** — разведены три смысла: превью-прицел (рендер, не симуляция); локальный фидбек анимка/звук (рендер, всегда); предсказание эффекта (симуляция). Правило: свой юнит/движение (блинк, дэш, cast-lock) → предсказываем; чужие сущности/урон/хиты снарядов → server-authoritative. Флаг `predicted` на эффекте (в конфиге, не компонент), режим мира `Authoritative|Predicted` читает флаг, система одна.
- **Маркеры предсказания** — `predicted` = статические данные способности, НЕ компонент. Per-entity `Predicted`-тег нужен только при адресном откате; при полном rollback-снапшоте не нужен — не закладывать преждевременно.
- **Валидация спеки** — два уровня: JSON Schema (структура, автокомплит в IDE) + семантический линтер (несуществующие компоненты в reads/writes, циклы в порядке, нарушение слоёв, протечка float в геймплей). Невалидная спека → генератор не запускается (pre-commit + CI).
- **Визуальные редакторы ECS** — тупик: Unreal Blueprints / Unity Visual Scripting не про ECS и плохо совместимы с детерминизмом. Flecs Explorer — только просмотр рантайма. Вывод: сама спека (YAML + JSON Schema) = твой «редактор», версионируемый и диффаемый. Свой веб-редактор — overengineering до наличия игры.
- **Связка core ↔ рендер** — односторонняя (рендер читает ядро). Фикс. тик ≠ кадр → интерполяция между двумя тиками (float, в рендере). Непрерывное (позиция) = интерполяция; дискретное (каст/смерть/хит) = события из ядра. Rollback: рендер держит свою сглаженную визуальную позицию, прячет коррекции prediction. Ядро оперирует id, клиент мапит id→ассеты; слово «mesh» в ядре не встречается.
- **Выбор рендера (веб vs Unity)** — тупик «Unity в вебе + TS-ядро»: WebGL-билд тяжёлый, интероп JS↔Unity-C# болезненный, Unity силён только когда вся игра в C#. Отброшено на текущем этапе.

## К чему пришли
- Spec-driven подход принят: декларативны данные и структура (компоненты, конфиг-схемы, контракты систем); логика систем — фиксируемый код (LLM помогает, но артефакт стабилен), верификация тестами → ADR-0001
- Детерминизм закладывается конструкцией (fixed-point + фикс. порядок), не тестами → ADR-0002
- Fixed-point математика обязательна во всём геймплее, float запрещён (линтер-правило) → ADR-0003
- Трёхслойная структура ядра (framework / common-кубики / game) и spec-разбивка core/common/game → правка core-engine.md §структура
- Модель различения компонент/система/конфиг + критерий развилки → правка core-engine.md §модель-данных
- Гибрид «способность = компонент-ссылки + динамика, конфиг = статика» → правка core-engine.md §abilities
- 2.5D модель: XY-геймплей + Z-кинематик, XY-круги + Z-интервалы, targeting плоский → ADR-0004
- Prediction-политика: свой юнит предсказываем, чужие/урон = server-authoritative; флаг `predicted` в конфиге эффекта → ADR-0005
- Валидация спеки в два уровня (JSON Schema + семантический линтер), gate на pre-commit/CI → правка core-engine.md §validation
- Связка ядро↔рендер (интерполяция + события, id-маппинг, smoothing при rollback) → правка core-engine.md §render-bridge
- **Веб-first (TS ядро + TS рендер) для прощупывания геймплея, рендер — сменный слой.** Кандидаты: Babylon.js / PlayCanvas (ближе к движку, чем Three.js), Unity отложен → ADR-0006
- Рендер на этапе прототипа = дебаг-визуал (примитивы, отрисовка векторов/радиусов/Z), не вкладываться временем → решение принято

- [ ] Механизм хеша стейта мира (что включать, порядок, сериализация снапшота) — прототип для голден-тестов
- [ ] Нужны ли снаряды как отдельный `Projectile`-кубик сейчас (зависит от набора дальнобойных скиллов) — отложено
- [ ] Версионирование/хеширование конфига для сверки клиент↔сервер — детализировать
