## Context

Мотивация — proposal.md (Why). Исходное состояние: `render-ts/src/host.ts` — `RenderHost` реализует `TickObserver`, в `onTick` читает `WorldState` (`world.getField`/`hasTag`/`listAlive`) и копирует минимум в `TickView`; подсистемы потребляют `TickView` через `syncTick`/`updateFrame` и мира не касаются. Копия уже обязательна (OBS-3), точка конверсии Q16.16 → float уже одна (REND-1) — граница воркера кладётся на существующий шов, а не прорезает новый.

Ограничения: ядро без изменений и без зависимостей; в мультиплеере клиент сам не тикает (NTR-10), но десериализация снапшотов и будущее предсказание (этап 24, NET-2/4/5) — та же воркер-сторона; всё в этой capability — механизм клиентской оболочки, геймплейной политики здесь нет.

## Goals / Non-Goals

**Goals:**

- Разбиение `RenderHost` на Extractor (воркер) и ViewBuffer (main) без правок контракта `RenderSubsystem`.
- Транспорт-независимая плоская раскладка буфера состояния: апгрейд доставки до SAB — замена модуля, не архитектуры.
- Обе топологии из одного кода: однопоточная сборка (тесты, headless) и воркер-сборка.

**Non-Goals:**

- `SharedArrayBuffer`-доставка (заложен только формат под неё; включается по замеру, см. Open Questions).
- OffscreenCanvas / рендер в воркере — выбрана обратная топология.
- Предсказание своей сущности (этап 24) — оболочка лишь оставляет ему место в воркере.
- Изменения `core-ts` и `net-ts`.

## Decisions

**1. Граница по `TickView`, а не по `TickResult` и не по памяти мира.**
Альтернативы: (а) гнать сериализованный `TickResult` — тащит `WorldState` через границу, ломает OBS-3 по духу и требует полной сериализации мира на тик; (б) SoA-массивы мира в SAB с прямым чтением из main — main видит рваное состояние посреди тика (мир мутабелен, TICK-1), хранилище компонентов переаллоцируется при росте, рендер привязывается к непрозрачной внутренней раскладке `WorldState`. Выбрано: через границу идёт только presentation-копия, которую Extractor и так обязан сделать.

**2. Transferable ping-pong, а не structured clone и не SAB.**
Арифметика: ~500 сущностей × ~12 полей × 4 байта ≈ 24 КБ/тик, при 60 Гц ≈ 1.5 МБ/с — пропускная способность не проблема ни для одного варианта; вопрос в аллокациях и хвостах. Structured clone объектов — стабильный GC-прессинг в обоих потоках. SAB — mailbox бесплатно, но требует COOP/COEP (все ассеты с CORP-заголовками, встраивание ломается) — деплой-налог без доказанной нужды. Transfer — переход владения без копии, пул из 2–3 буферов замыкает цикл в ноль аллокаций.

**3. Раскладка буфера — SoA, транспорт-независимая.**
Заголовок (tick, mode, флаги snapAll/isReplay/freshEvents, счётчики) + колонки сущностей: id — колонка `Float64` (48-битный generational ID точен во f64; те же 8 байт, что пара u32, но без склейки/расклейки — решение уточнено при реализации), kind-индекс i32 (−1 — не рисуется; таблица строк едет дословарём в конвертах, SHELL-5), x/y/facingYaw/aimYaw — `Float32` (конверсия из Q16.16 в Extractor'е, 24 бит мантиссы для арены достаточно; NaN в facingYaw — «стоит», в aimYaw — «нет цели»), level/флаги — u8. Дельта пола — пары u32 (клетка, значение бита): значения, а не переключения, чтобы дельты сливались при conflation (later-wins). Раскладка версионируется константой в заголовке; писатель и читатель — один модуль (`codec.ts`), рассинхрон ловится roundtrip-тестом в одном потоке.

**4. События — structured clone в конверте того же сообщения.**
События мелкие, редкие и разноформенные (`Record<string, number>`); бинарный формат для них — сложность без выигрыша. Конверт сообщения: `{header, events, buffer}` с transfer только буфера. Reliable-семантика (SHELL-4): Extractor копит события с номерами тиков с прошлой отправки; отправка очищает аккумулятор.

**5. Conflation через ack, а не через очередь.**
Воркер шлёт следующую доставку только когда main вернул буфер (возврат = ack). Пока буфера нет — Extractor перезаписывает staging и копит события. Так очередь сообщений не растёт по определению, а «main дренирует очередь и берёт последнюю» не нужно вовсе. Плата — состояние доезжает не чаще, чем main читает; для рендера это и есть требуемая семантика.

**6. Extractor — это `onTick`-половина нынешнего `RenderHost`, выделенная в `render-ts`.**
Обход живых сущностей, `kindOf` по тегам (кэш `kinds` остаётся при нём), конверсия во float, `FloorMirror`, capture aim (нужны позиции целей из мира — только воркер-сторона). ViewBuffer — main-половина: prev/curr-скольжение, snap/teleport-порог, протухание aim по номеру тика, `frame(alpha)`. Обе половины живут в `render-ts` и не знают о воркере: их соединяет либо прямой вызов (однопоточная сборка), либо канал из `client-ts`. Это даёт Goals-пункт «обе топологии из одного кода» и сохраняет тестируемость без DOM/Worker.

**7. Часы: `lastTickAtMs` ставится в момент доставки по `performance.now()` главного потока.**
У воркера и main разные `performance.timeOrigin` — таймстемп воркера напрямую не годится. Джиттер доставки становится джиттером альфы (доли мс), существующий кламп [0..1] его съедает. Альтернатива — вычислить смещение origin'ов на handshake — отложена до замера (Open Questions).

**8. Тикер воркера — `setTimeout`-цикл с коррекцией дрейфа.**
Таймеры dedicated worker'ов троттлятся мягче main thread; точность единиц мс на тике 16–33 мс достаточна. `Atomics.wait`-таймер точнее, но требует SAB → COOP/COEP — противоречит Decision 2.

**9. Локальный сервер — второй воркер, транспорт поверх `MessageChannel`.**
`Transport` в `net-ts` уже абстрагирует loopback/WebSocket; третья реализация (`MessagePort`) встаёт без правок `MatchServer`/`MatchClient`. Механизм/политика: вся capability — механизм оболочки; что показывать в UI на паузе, когда разрешена перемотка — политика вне её.

## Risks / Trade-offs

- [Латентность «нажал→увидел» растёт на ~1 доставку в каждую сторону] → ожидаемо +1–3 мс к текущим 40–50 мс (открытый вопрос № 2 обзора); замерить на воркер-сборке до и после, порог тревоги — рост > 5 мс.
- [Раскладка буфера и её читатель разъезжаются молча] → писатель/читатель в одном модуле, версия раскладки в заголовке, тест «Extractor → буфер → ViewBuffer в одном потоке» сверяет с прямым вызовом без канала.
- [Conflation по ack: зависший main замораживает доставку, события копятся] → аккумулятор событий ограничен глубиной (старше N тиков — с пометкой «просрочено», звук/VFX не проигрываются пачкой после разморозки); состояние по определению последнее.
- [Рост числа сущностей требует перевыделения буферов] → перевыделение с запасом (×1.5) на воркер-стороне, разовое, вне горячего пути; пер-тиковая аллокация остаётся нулевой.
- [Две топологии — двойная поверхность тестирования] → однопоточная сборка остаётся канонической для всех существующих тестов; воркер-сборка покрывается интеграционным тестом канала и демо.

## Замеры (задача 4.5, Node 22, 2026-08-05)

- Кодек + `ViewBuffer.apply` на 500 сущностей: **~0.10 мс/тик**, буфер ~15 КБ (`test/bench.test.ts`, сторожевые пороги там же).
- Round-trip конверта через MessageChannel (доставка + ack, 500 сущностей, transfer): **p50 0.018 мс, p99 0.087 мс** — латентность канала в шуме относительно тика 16–33 мс.
- Smoke демо в Chromium (headless, статика без COOP/COEP): воркер тикает ~50–60 тик/с, ввод доезжает, ошибок консоли нет.
- Полный «нажал→увидел» до/после переезда в воркер требует браузерного стенда с реальным вводом — остаётся в открытом вопросе № 2 обзора; структурная добавка оболочки по замерам выше — ≪1 мс.

## Open Questions

- Нужен ли SAB-транспорт вообще — по замерам выше пока нет (p99 round-trip < 0.1 мс); пересматривать при хвостах доставки на целевой сцене в браузере. Формат буфера к SAB готов.
- Приведение часов воркер↔main через смещение `timeOrigin` — только если джиттер альфы окажется виден глазом.
- Коалесцировать ли ввод до частоты кадра или слать по событию — сейчас демо шлёт раз в кадр; пересматривать по замеру объёма сообщений, на семантику (SHELL-6) не влияет.
