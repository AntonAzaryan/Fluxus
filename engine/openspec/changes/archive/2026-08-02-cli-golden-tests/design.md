## Context

Этап 10. Есть загрузчик сцены и plain-форма мира (этап 9), нет способа прогнать сцену целиком и зафиксировать результат. Два потребителя: человек, воспроизводящий баг из матча (CLI-1), и CI, сверяющий эталон (CLI-5). Требование к обоим одно — прогон должен быть воспроизводим из файла, без кода вокруг.

## Goals / Non-Goals

**Goals:**

- Прогон сценария одной функцией и одной командой, без рендера и сети.
- Потиковый вывод, по которому виден первый разошедшийся тик.
- Набор сценариев, пригодный для второй реализации ядра как есть.

**Non-Goals:**

- Cross-language сверка (CLI-6): сверять пока не с чем.
- Читаемый «дамп по живым сущностям» для глаз: golden сверяется машиной, а сырая plain-форма обратима, в отличие от дампа.
- Ключи CLI сверх имени файла. Перенаправление вывода делает шелл.

## Decisions

### Начальное состояние — расстановка prefab'ов, а не дамп мира

`worldInit` в DET-1 — это стартовая расстановка сущностей. Формально её можно было бы задать той же plain-формой, в которой выгружается мир: тогда вход и выход CLI были бы одним форматом, и снятый снапшот подавался бы обратно без конверсии.

Отвергнуто: plain-форма — это `maskWords`, `freeList` и поля по raw-индексам. Написать её руками нельзя, прочитать в ревью нельзя, а сценарий пишет человек. Расстановка `[{prefab, overrides}]` читается, а детерминизм ID при этом не страдает: порядок спавнов задаёт ID однозначно (ID-2, DET-6).

Продолжение снапшота (вход = ранее снятый мир) понадобится для reproduce из матча — но вместе с восстановлением RNG и номера тика, то есть это `restoreSnapshot` в CLI, отдельная возможность, а не форма начального состояния.

### События входят в потиковую запись

CLI-3 говорит о снапшотах состояния. Состояние — мир и RNG; события живут один тик и в снапшот не входят. Но система, которая только эмитит (`emitEvent` без записи в мир), при сверке одного состояния становится невидимой: её можно удалить, и golden не покраснеет.

Поэтому запись тика — снапшот плюс события этого тика. Это не расширение снапшота: `Snapshot` не меняется, расширяется формат вывода CLI, у которого потребитель — диагностика и golden.

### Golden-файлы лежат вне реализации

`engine/tests/golden/` рядом с `engine/core-ts/`, а не внутри него. CLI-4 требует один набор проверок для всех реализаций; набор внутри `core-ts/test/` при появлении Rust-ядра пришлось бы либо копировать, либо тянуть через границу языка из чужого каталога тестов. `test/golden.test.ts` в `core-ts` — адаптер: находит `*.scenario.json`, прогоняет, сверяет с `*.golden.json`.

Эталон сверяется как строка целиком, а не как разобранный объект: сверка объектов простила бы и порядок ключей (SER-6), и форматирование, то есть ровно то, что должно быть стабильным для дифферентного чтения.

### Запуск без шага сборки

`bin/sim.mjs` регистрирует resolve-хук, переписывающий `./x.js` в `./x.ts`, и импортирует ядро напрямую: типы Node стрипает сам (>= 22.18), нативных зависимостей у ядра нет.

Альтернатива — `tsc` в `dist/` перед каждым прогоном: второй tsconfig, шаг сборки и артефакт, который может разойтись с исходником, ради инструмента, который тесты и так зовут функцией. Хук — десять строк в единственном файле, который вообще не участвует в тестовом пути.

Цена: `engines.node >= 22.18` и зависимость от `module.registerHooks` (стабилизируется отдельно). Если хук отвалится, замена — тот самый шаг сборки, локальная правка одного файла.

## Risks / Trade-offs

- **Инпуты и RNG не покрыты эталонами.** JSON-система не может ни прочитать `InputFrame`, ни дёрнуть стрим — в Expression DSL нет соответствующих операторов. Поэтому golden фиксирует движение, спавн, смерть, события и переиспользование слотов ID, но не реакцию на ввод и не последовательность случайных чисел. Это предел не CLI, а DSL: TICK-4 требует, чтобы инпуты обрабатывались системами, а data-driven-цель требует, чтобы это могла быть JSON-система. Закрывается отдельным change'ем на операторы доступа к вводу и RNG; до него — нативные системы и `rng.test.ts`.
- **Эталон обновляется командой, а не автоматически.** Дешёвый способ «починить» красный тест — перегенерировать эталон не глядя. Защита процессная: `npm run golden` меняет файлы, которые видно в диффе, — и ровно этот дифф является предметом ревью.
- **Сцена инлайнится в каждый сценарий.** Два сценария — две копии похожего JSON. Ссылка на внешний файл сцены появится, когда копий станет достаточно, чтобы они расходились; до тех пор один самодостаточный документ проще воспроизводить.

## Migration Plan

Не требуется: новый код, существующие API не меняются.
