## Context

Этап 8. На входе — evaluator (этап 6), executor (этап 7), `SystemRegistry` с сортировкой по `order` (этап 4) и `tick()`, который создаёт `SystemContext` и делает flush после каждой системы (этап 5). Не хватает одного: способа получить объект `System` из JSON.

## Goals / Non-Goals

**Goals:**

- JSON-система, неотличимая для scheduler'а от нативной (SYS-4, SYS-6).
- `override` по имени с сохранением `order` (SYS-7) и тест, доказывающий парность поведения (SYS-8).
- Валидация дерева на регистрации (SYS-3): ошибка на старте, а не в матче.
- Спека SYS-4/SYS-5 приведена к реализованному контракту.

**Non-Goals:**

- RNG в DSL — см. ниже.
- Статическая проверка типов выражений. Валидатор проверяет имена и связанность, но не то, что `and` получит булево: для этого нужен вывод типов по дереву, а рантайм-ошибка уже есть.
- Горячая перезагрузка систем из редактора. `override` — механизм подмены, а не событие «файл изменился»; всё, что нужно редактору, — вызвать его повторно.
- Кэширование/компиляция дерева в замыкания. Порог тот же, что заявлен на этапе 6: 5% бюджета тика.

## Decisions

### `query` в системе — сахар над действием `forEach`

SYS-1 требует поля `query` у системы. Реализовать его отдельным механизмом итерации значило бы иметь два цикла с разной семантикой области видимости. Вместо этого система с `query` разворачивается в тело из одного действия:

```
{name, order, query, as, do}  →  do: [{ forEach: {query, as, do} }]
```

Три строки в конструкторе, ноль нового поведения. Система без `query` исполняет `do` один раз — это форма для систем, работающих не поэлементно (тайминги, глобальные счётчики).

### Валидация обходит дерево по именам ключей, а не по таблице действий

Валидатору нужно знать, где в узле лежат вложенные действия, где выражения, а где имена компонентов. Очевидный способ — вторая таблица рядом с таблицей действий, с сигнатурой каждого. Отвергнут: добавление действия требовало бы правки в двух местах, и рассинхронизация этих двух мест — вопрос времени.

Вместо этого обход опирается на конвенцию имён аргументов, единую для всего Action DSL: `do`/`then`/`else` — списки действий, `values`/`data`/`bindings`/`overrides` — карты выражений, `entity`/`cond` — выражения, `component`/`prefab`/`as`/`type` — литералы. Конвенция и так соблюдается всеми действиями, потому что читаемость DSL этого требует; валидатор просто делает её обязательной.

Цена: действие с аргументом, не подходящим ни под одно из имён, пройдёт валидацию без проверки содержимого. Это осознанный предел — он ловится ревью нового действия, а не молчит в рантайме.

### Проверка переменных требует отслеживания области видимости

`{"var": "trget"}` — самая вероятная опечатка в редакторе, и без проверки она даёт ошибку в матче. Валидатор ведёт множество связанных имён: `as` в `forEach` и ключи `bindings` в `let` добавляют имена в область видимости тела. Начальное множество задаётся при регистрации — сейчас пустое, но параметризовано, потому что этап 9 добавит системам входные параметры.

### Что валидатор проверяет по миру

Существование компонента и поля — по схемам зарегистрированного мира, существование prefab'а — по его реестру. Это требует двух аксессоров в `world.ts` (схема по имени компонента, наличие prefab'а); оба тривиальны и просятся наружу и сами по себе.

Следствие для порядка старта: мир создаётся раньше систем. Так уже устроен `tick()`, который получает и `Simulation`, и `SimulationState`, поэтому нового ограничения тут нет.

### `override` требует совпадения name и order

SYS-7 говорит «с тем же `name`/`order`». Проверка обязана быть в коде, а не в договорённости: подмена, тихо сдвинувшая `order`, меняет порядок систем в тике — то есть меняет результат симуляции, ничего не сломав видимо. Это ровно тот класс ошибки, ради которого DET-3 запрещает равные `order`.

### RNG в DSL: решено не добавлять

Этап 7 отложил вопрос сюда. Решение — не добавлять, и вот почему это решение, а не ещё одна отсрочка. Случайность не может быть выражением: `next()` двигает состояние стрима, а EXPR-3 запрещает выражениям side-effect'ы. Значит, это действие, связывающее результат в область видимости, — и его форма зависит от того, чем решится открытый вопрос 4 в `docs/architecture.md` (нужны ли именованные суб-стримы и как геймдизайнер объявляет их в редакторе). Зафиксировать форму в JSON-описаниях сейчас — значит потом мигрировать сохранённый контент.

Триггер для возврата к вопросу: первая система, которой случайность нужна по геймдизайну. К этому моменту будет известно, один ей нужен источник или несколько, — то есть будет чем закрыть вопрос 4.

### Механизм против политики

Всё здесь — механизм: способ превратить данные в систему. Ни одной геймплейной системы этот этап не добавляет; первые JSON-системы появятся как контент, и появятся они в редакторе (этап 12).

## Risks / Trade-offs

- **Спека SYS-4/SYS-5 расходилась с кодом четыре этапа.** Значит, расхождение может накопиться снова. → Смягчение: блоки `ts` в этих требованиях теперь дословно совпадают с `src/types.ts`; расхождение видно при чтении спеки рядом с кодом. Автоматической сверки нет — она стоила бы дороже, чем ловит.
- **Валидация по конвенции имён неполна** (см. выше). → Смягчение: набор имён зафиксирован в SYS-3, то есть новое действие обязано ему следовать, а не может завести свой.
- **Парность JSON и нативной версии проверяется одним сценарием.** → Смягчение: на этапе 10 это станет golden-file suite с побитовой сверкой; здесь фиксируется сам инвариант и способ его проверять.
