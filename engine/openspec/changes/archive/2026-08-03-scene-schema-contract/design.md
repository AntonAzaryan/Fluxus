## Context

`schemas.ts` порождает опубликованные JSON Schema из тех же закрытых наборов ядра, по которым
валидирует загрузчик (SER-5). Дефект B4 (отчёт сверки `docs/spec-compliance-2026-08-03.md`):
`scene`/`scenario` объявлены с `additionalProperties: false`, но не перечисляют пять полей,
которые загрузчик реально читает — `scene.arena` (`sim/scene.ts:41`), `scene.timeScale` (:43),
`scene.tweens` (:45), `scene.fog` (:50), `scenario.visibility` (`sim/scenario.ts:54`). Оба
собственных golden-эталона (`arena-time.scenario.json`, `visibility.scenario.json`) используют
эти поля и не проходят свою же опубликованную схему.

Приёмка нового поведения нуждается в проверке «схема принимает golden», а в `core-ts/node_modules`
и `engine/node_modules` нет ни `ajv`, ни другого валидатора JSON Schema — транзитивно тоже не
пришло. SER-5 прямо запрещает ядру зависеть от валидатора JSON Schema.

## Goals / Non-Goals

**Goals:**
- Опубликованная схема `scene` принимает `arena`, `timeScale`, `tweens`, `fog`; `scenario` —
  `visibility`; форма каждого поля соответствует тому, что реально читает загрузчик.
- Тест, который явно проверяет это по golden-эталонам и краснеет при регрессии.

**Non-Goals:**
- Не нормируется порядок порождённых компонентов (`floor → arena → timeScale → tween → fow`) —
  это задача `modifier-slots-and-actions`.
- Не добавляется зависимость на валидатор JSON Schema.
- Не проверяются `type`/`pattern`/`minimum`/`enum`/`oneOf` — только структурные правила
  (`$ref`, `additionalProperties`, `required`): SER-5 уже устанавливает, что загрузчик строго
  строже опубликованной схемы, второй проверяльщик значений мог бы разойтись с ним.
- Golden-эталоны (`tests/golden/*.scenario.json`) не меняются по содержанию: только опубликованная
  схема и код валидации схем, runtime-логика загрузчика не трогается.

## Decisions

**Минимальный ручной обход вместо ajv.** Полноценный JSON Schema валидатор избыточен для цели
теста — доказать, что опубликованная схема не строже загрузчика по пяти конкретным полям. Нужны
ровно три структурных правила:
1. разрешение `$ref` в `$defs` (схемы вложены через `$ref`, без него обход не дойдёт до `scene`
   внутри `scenario`);
2. `additionalProperties: false` → неизвестное свойство объекта — ошибка;
3. `required` → отсутствующее обязательное поле — ошибка.

Правила значений (`type`, `pattern`, `minimum`, `enum`, `oneOf`) сознательно не реализуются: они
нигде не были источником дефекта B4 (тот целиком про «схема отвергает лишнее поле»), а полная их
реализация — это половина ajv, написанная вручную и обречённая разойтись с загрузчиком в частностях
(SER-5 отдаёт эту строгость загрузчику, а не схеме). Обход умещается в ~35 строк прямо в
тест-файле — не в `src/`, чтобы не создать соблазн звать его как рантайм-валидатор.

**Формы добавленных полей списаны с кода загрузчика, а не придуманы заново:**
- `scene.arena` — объект `{ center: Vec2, radius: integer }` (см. `ArenaDef` в `systems/arena.ts`,
  уже есть `$defs/vec2` в схеме сценария, добавляется и в схему сцены);
- `scene.timeScale` — `boolean` (`def.timeScale === true` в `sim/scene.ts:43`);
- `scene.tweens` — массив `{ target: string, onComplete?: Action[] }` (`TweenDef` в
  `systems/tween.ts`, `onComplete` переиспользует существующий `$defs/action`);
- `scene.fog` — `boolean` (`def.fog === true` в `sim/scene.ts:50`);
- `scenario.visibility` — объект `{ order?: integer }` (`VisibilityOptions` в
  `systems/visibility.ts:108`, та же форма, что уже есть у `scenario.physics`).

## Risks / Trade-offs

- [Ручной обход неполон по значениям и мог бы пропустить будущий дефект вида «поле есть, но
  неправильного типа»] → приемлемо: SER-5 явно возлагает эту строгость на загрузчик, а не на
  схему; в области ответственности этого теста (структура документа) обход полон.
- [Дублирование списка правил с будущими схемами, если появится новая раскладка] → правила три и
  общие для любой схемы этого репозитория (draft 2020-12, без `patternProperties`/`if-then-else`),
  расширять по мере необходимости в месте использования.
