# unify-terminology — design

## Context

Анализ 21 спеки выявил перегруженные слова (одно слово — несколько несвязанных смыслов) и синонимы (одно понятие — несколько написаний). Change чисто терминологический: ни одно требование не меняет поведения, форматов данных и чисел. Единственное изменение кода — имя метода `SystemRegistry`.

## Decisions

### Словарь после change'а

| Слово | Закреплённый смысл | Что вытеснено |
|---|---|---|
| снапшот | полное состояние мира (SNAP-1) и его производные (персональный снапшот, потиковая запись CLI) | «снапшот» как результат query (QUERY-3) → «материализованная выборка» |
| авторитетный | единственный настоящий мир/состояние сервера (NET-1, NET-12) | «канонический мир» |
| канонический | зафиксированная форма записи: канонический `inputs[]`, каноническое представление для хешей | — |
| фрейм | `InputFrame` в прозе | «кадр ввода», «predicted-кадр» |
| сообщение | единица протокола на транспорте (NTR-4, NTR-13) | «кадр» транспорта |
| кадр | только кадры рендера (NET-5) | — |
| эталон / эталонный тест | golden-артефакт и сверяющий его тест в прозе | «Golden-file тест», «golden-эталон» |
| golden-файл / golden-сценарий / golden-набор | имена артефактов на диске (`tests/golden/`) — остаются | — |
| жёсткий инвариант (`assertInvariant`) | проверка без детерминированного продолжения, бросает в обеих сборках (FP-4) | «жёсткая граница», «жёсткий assert» |
| плоская форма | plain-форма снапшота (SER-1, SER-6) | написание «plain-форма» |
| `LevelOverride` | компонент явного уровня (ARENA-6, TERR-4) | безымянный «компонент-override уровня» |
| `replace(system)` | подмена реализации системы в `SystemRegistry` (SYS-7) | `override(system)` |
| observer | `TickObserver` (OBS-2) в прозе | «наблюдатели» в NTR-3 |
| наблюдатель | спектейтор матча (NTR-9) и сущность с `Vision` (FoW) | — |

### Почему `replace`, а не квалификация

`overrides` у `spawn` (CMD-6) и `LevelOverride` — данные, они переживут любой рефакторинг; `override` у реестра — глагол API, третий смысл того же слова на одном экране кода. Метод переименовывается, потому что это единственный из трёх случаев, где слово выбираем мы, а не формат данных. Снапшоты, JSON-описания систем и эталоны имя метода не содержат — golden-файлы не перезаписываются.

### Почему `LevelOverride` берётся из кода, а не придумывается

Реализация и golden-сценарии уже используют `LevelOverride` (`LEVEL_OVERRIDE_COMPONENT`, `terrain.scenario.json`). Спека получает имя, которое уже является фактическим форматом данных; выдумывание другого имени перекрасило бы эталоны без выгоды.

### Что сознательно не переименовывается

- «слот» (игрока / модификатора / сущности) и «маска» — разводятся квалификацией в прозе, не переименованием: имена полей входят в плоскую форму снапшота.
- Purpose-блоки спек правятся напрямую в главных спеках (дельты OpenSpec несут только требования): `netcode-transport` «с опоздавшим кадром» → «с опоздавшим фреймом».
- Архивные change-документы не трогаются: это история.

## Risks / Trade-offs

- **BREAKING (локально)**: `registry.override` → `registry.replace`. Потребители — тесты core-ts и, возможно, net-ts; внешних потребителей у пакета нет. Смягчение: typecheck + полный прогон тестов.
- Правка 23 требований в 11 спеках руками несёт риск случайно изменить смысл. Смягчение: каждое требование в дельте — полная копия действующего текста с точечной заменой слов; `openspec validate --specs --strict` после sync; побитовая неизменность golden-эталонов подтверждает, что поведение не тронуто.

## Migration

- Код: `registry.override(...)` → `registry.replace(...)` — единственная правка вызывающих.
- Данные и сеть: миграции нет, форматы не меняются.
