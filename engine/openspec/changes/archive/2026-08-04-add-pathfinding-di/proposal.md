## Why

Поиск пути в движке рано или поздно появится — для нейтральных крипов и NPC (управление игроками прямое, им pathfinding не нужен). Сам алгоритм сейчас писать незачем: ни агентов, ни геймплейного масштаба в спецификации ещё нет. Но шов, через который навигация войдёт в ядро, должен быть зафиксирован сейчас — ровно по той же причине, по которой он зафиксирован для физики: место зависимости определяет, что попадает в снапшот, что в `worldInit`, и остаётся ли ядро собираемым без неё. Вставить опциональную зависимость в готовое ядро дороже, чем описать её до.

`terrain` TERR-7 уже держит формат под навигацию, архивный `add-terrain-elevation` прямо говорит, что «навигация ложится на DI-3 так же, как Physics», но ни контракта, ни требования об опциональности для неё в спеке нет — есть только упоминания в прозе.

## What Changes

- Вводится capability `pathfinding` (префикс требований `NAV-`): контракт Navigation API — форма запроса, детерминизм, тотальность, бюджет поиска, разделение механизма и политики (путь — данные, движение по нему — геймплейная система).
- Navigation API объявляется опциональной зависимостью ядра наравне с Physics API: ядро SHALL собираться и тикать без него. В отличие от физики, для данной игры он тоже необязателен — в MVP нет ни крипов, ни NPC.
- `SystemContext` получает поле `navigation?: NavigationApi` — расширение состава контракта, которое SYS-5 требует оформлять изменением требования, а не молчаливо.
- Алгоритм поиска пути, навигационные данные, их построение из террейна, связность сетки (4/8 — открытый вопрос `terrain`), поле сценария CLI и валидация `tileSize` против диаметра агента — **не входят**. Это change, который вводит шов, а не навигацию.
- TERR-7 уточняется: обязательство «добавить проверку `tileSize` против диаметра агента» привязывается к change'у, вводящему реализацию поиска пути, а не к вводу самого DI-шва — диаметр агента берётся из реализации и контента, которых здесь нет.

## Capabilities

### New Capabilities

- `pathfinding`: Navigation API как опциональная зависимость ядра — форма запроса пути, детерминизм и чистота запроса, тотальность и бюджет поиска, место навигационных данных в неизменяемой части сборки, граница механизма и политики. Реализация алгоритма в эту версию не входит.

### Modified Capabilities

- `determinism-core`: DI-1 перечисляет интерфейсы, от которых зависит ядро, — добавляется Navigation API; вводится DI-4 об опциональности Navigation API на уровне ядра (по образцу DI-3).
- `data-driven-systems`: SYS-5 — в состав `SystemContext` добавляется опциональное поле `navigation?: NavigationApi`.
- `terrain`: TERR-7 — обязательство валидировать `tileSize` против диаметра агента привязывается к change'у с реализацией поиска пути и ссылается на capability `pathfinding`.

## Impact

- Спеки: новая `openspec/specs/pathfinding/spec.md`; правки в `determinism-core`, `data-driven-systems`, `terrain`.
- `core-ts`: `src/types.ts` — типы `NavigationApi`, `PathRequest`, `PathResult` и поле `navigation?` в `SystemContext`; `src/sim/tick.ts` — проброс зависимости в контекст по образцу `physics`; `src/index.ts` — экспорт типов. Реализации Navigation API в ядре не появляется: собранная без неё сцена — штатный режим, и все существующие сценарии остаются такими.
- Golden-эталоны и схемы не меняются: поведение тика без Navigation API идентично текущему, в конфиг сцены и снапшот ничего не добавляется (SER-7).
- `docs/architecture.md`: карта спецификаций и схема слоёв — навигация встаёт третьей DI-стрелкой рядом с Math и Physics.
