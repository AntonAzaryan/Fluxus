# Data-Driven Systems Specification

## Purpose

Геймплейная логика описывается JSON, ядро — универсальный evaluator. Ключевое проектное решение: система — чёрный ящик за единым интерфейсом, поэтому JSON-система и нативная TS-система взаимозаменяемы, и переписывание системы в код ради скорости не требует изменений вокруг.

Три уровня DSL:

| Уровень | Описывает | Пример |
|---|---|---|
| **System** | Что и когда исполнять | `{query, forEach, order}` |
| **Action** | Побочные эффекты | `modifyComponent`, `spawnEntity`, `forEach`, `if`, `let` |
| **Expression** | Чистые вычисления | JsonLogic |
## Requirements

### Requirement: SYS-1 Система как JSON-описание

Система SHALL описываться JSON с полями `name`, `order`, `do` и необязательными `query`/`as`:

```json
{
  "name": "Burning",
  "order": 30,
  "query": { "all": ["Burning", "Health"] },
  "as": "target",
  "do": [ /* actions */ ]
}
```

`query` SHALL быть сахаром над действием `forEach` (ACT-1): описание с `query` эквивалентно телу из одного `forEach` с тем же `query`, `as` и `do`. Отдельного механизма итерации у системы MUST NOT быть — иначе в языке появятся два цикла с разной семантикой области видимости.

Описание без `query` SHALL исполнять `do` один раз за тик: не всякая система работает поэлементно.

#### Scenario: Создание системы в редакторе

- **WHEN** геймдизайнер собирает систему визуально
- **THEN** на выходе — валидный JSON с этими полями, готовый к регистрации в ядре

#### Scenario: Система без запроса

- **WHEN** система описана без `query`
- **THEN** её `do` исполняется один раз за тик, без привязки к сущности

### Requirement: SYS-2 Детерминированное упорядочивание scheduler'ом

Scheduler SHALL упорядочивать системы по `order` детерминированно.

#### Scenario: Регистрация в произвольном порядке

- **WHEN** системы регистрируются в порядке, отличном от их `order`
- **THEN** исполнение всё равно идёт по `order`

### Requirement: SYS-3 Регистрация и валидация на старте

Компоненты-данные и системы SHALL регистрироваться на старте и SHALL валидироваться при регистрации. Валидация JSON-системы SHALL проверять:

- форму узлов: ровно один ключ у действия и у выражения;
- имена действий и операторов — по закрытым наборам (ACT-1, EXPR-6);
- существование компонентов и их полей, а также prefab'ов — по зарегистрированному миру;
- связанность переменных: каждое имя в `var` SHALL быть введено объемлющим `as` или `bindings`.

Сообщение об ошибке SHALL называть путь до узла — иначе поиск опечатки в дереве из сотни узлов сам становится задачей.

Аргументы действий SHALL следовать единой конвенции имён, на которую опирается обход: `do`/`then`/`else` — списки действий, `values`/`data`/`bindings`/`overrides` — карты выражений, `entity`/`cond` — выражения, `component`/`field`/`prefab`/`type`/`as` — строковые литералы. Новое действие MUST NOT вводить аргумент с иным смыслом под этими именами.

Проверка типов значений (число / булево / вектор) в валидацию не входит: она остаётся ошибкой времени вычисления.

#### Scenario: Система ссылается на неизвестный компонент

- **WHEN** JSON-система запрашивает компонент, которого нет в реестре
- **THEN** регистрация падает на старте, а не в середине матча

#### Scenario: Опечатка в имени переменной

- **WHEN** выражение ссылается на `var`, не введённый ни одним объемлющим `as` или `bindings`
- **THEN** регистрация падает и называет имя и путь до узла

### Requirement: SYS-4 Единый интерфейс System

Любая реализация системы SHALL удовлетворять единому интерфейсу:

```ts
interface System {
  readonly name: string;   // = имя RNG-стрима, ключ в реестре для подмены
  readonly order: number;  // равные order недопустимы (DET-3)
  run(ctx: SystemContext): void;
}
```

#### Scenario: Scheduler исполняет систему

- **WHEN** приходит очередь системы в тике
- **THEN** scheduler вызывает `run(ctx)`, не зная, JSON-система это или нативная

### Requirement: SYS-5 SystemContext как контракт границы core↔геймплей

`SystemContext` SHALL быть публичным контрактом границы core↔геймплей:

```ts
interface SystemContext {
  readonly tick: number;
  readonly query: (spec: QuerySpec) => Float64Array; // материализован на момент вызова (QUERY-3)
  readonly get: (entity: EntityId, component: string, field: string) => number;
  readonly has: (entity: EntityId, component: string) => boolean;
  readonly isAlive: (entity: EntityId) => boolean;
  readonly commands: CommandBuffer;                  // единственный канал мутаций (CMD-1..4)
  readonly events: EventEmitter & ReadonlyEventLog;  // публикация и чтение шины тика (EVT-1..4)
  readonly rng: RngStreams;                          // стрим по name системы (RNG-4)
  readonly math: MathApi;                            // обязательная зависимость (DI-2)
  readonly physics?: PhysicsApi;                     // опциональная (DI-3), обязательна при FoW
  readonly navigation?: NavigationApi;               // опциональная (DI-4), поиск пути (NAV-1)
  readonly terrain?: TerrainApi;                     // опциональная (DI-3), есть при террейне в сцене (TERR-4)
  readonly arena?: ArenaApi;                         // опциональная (DI-3), есть при арене в сцене (ARENA-1)
  readonly modifiers?: ModifierRegistry;             // опциональная (DI-3), списки источников сцены (TIME-7, FOW-3)
  readonly inputs: readonly InputFrame[];            // канонические вводы тика (TICK-2)
  readonly getEffectiveDelta: (entity: EntityId, globalDelta: Fixed) => Fixed; // TIME-3, TIME-4
}
```

Чтение мира — плоские `query`/`get`/`has`/`isAlive`, а не объект-view: view пришлось бы либо копировать, либо держать валидным дольше вызова, и то и другое противоречит QUERY-3.

`events` SHALL быть одновременно публикацией и read-only-чтением шины текущего тика: система обязана и эмитить факт, и видеть факты, опубликованные до неё (EVT-2). Мутирующей части у чтения быть не должно — очистка и восстановление шины принадлежат тику и rewind (EVT-4, `snapshot-rewind` REW-10), а не системе.

Опциональные поля (`physics?`, `navigation?`, `terrain?`, `arena?`, `modifiers?`) SHALL следовать паттерну опциональной зависимости DI-3: поле присутствует ровно тогда, когда зависимость собрана или сцена содержит соответствующие данные, — `physics` при собранной физике (и обязательно при FoW, FOW-4), `navigation` при собранной навигации (DI-4, `pathfinding` NAV-1), `terrain` при террейне в сцене (TERR-4), `arena` при арене в сцене (ARENA-1), `modifiers` при списках источников-модификаторов сцены (TIME-7, FOW-3). Система, которой отсутствующее поле необходимо, SHALL падать с ошибкой, называющей зависимость, и MUST NOT молча становиться системой без эффекта: сцена без зависимости — конфигурационная ошибка, а не режим работы.

Отдельного `TimeContext` в контракте нет: номер тика — поле `tick`, а масштабированный шаг — `getEffectiveDelta(entity, globalDelta)` (TIME-3), и учитывать его или нет решает каждая система сама (TIME-4).

Расширение состава `SystemContext` SHALL быть изменением этого требования, а не молчаливым расширением: контракт границы описан здесь целиком, и поле, которого тут нет, из системы недоступно.

#### Scenario: Системе нужен доступ к чему-то вне контекста

- **WHEN** реализации системы требуется ресурс, отсутствующий в `SystemContext`
- **THEN** это изменение публичного контракта — оформляется явно, а не обходится через импорт модуля напрямую

#### Scenario: Сцена без опциональной зависимости

- **WHEN** система обращается к `physics`, `navigation`, `terrain`, `arena` или `modifiers` в сцене, где их нет
- **THEN** она падает с ошибкой, называющей отсутствующую зависимость, а не отрабатывает тик без эффекта

#### Scenario: Система читает события тика

- **WHEN** системе нужен факт, опубликованный системой с меньшим `order`
- **THEN** она читает его через `events` — тот же объект, через который эмитит, но записать в него можно только новое событие

### Requirement: SYS-6 Две реализации за одним контрактом

`EvaluatedSystem` (исполняет JSON через Action Executor + Expression Evaluator) и нативная TS-система SHALL иметь идентичные границы поведения: обе читают через `WorldView` и пишут только в `CommandBuffer`. У нативной системы физически нет способа обойти TICK-3/CMD-4.

Часть систем проектируется нативно сразу (перф-критичные, интенсивно работающие с Physics API) — например `VisibilitySystem` с raycast-LoS каждый тик.

#### Scenario: Нативная система оптимизирует горячий цикл

- **WHEN** система переписана на прямые вычисления ради скорости
- **THEN** она по-прежнему читает через `WorldView` и пишет через `CommandBuffer`, детерминизм не страдает

### Requirement: SYS-7 SystemRegistry и подмена по name

`SystemRegistry` SHALL хранить системы по `name` и SHALL позволять подменить реализацию через `override(system)` с тем же `name`/`order`, не затрагивая scheduler, Command Buffer, события и RNG-стримы.

```ts
registry.registerFromJson(dashSystemJson, world); // из редактора
registry.override(new NativeDashSystem());        // оптимизированная версия, тот же name/order
registry.register(new VisibilitySystem());        // сразу нативная, тот же контракт
```

`override` SHALL требовать, чтобы система с таким `name` уже была зарегистрирована, и чтобы `order` совпадал с прежним. Подмена, сдвигающая `order`, MUST NOT приниматься: она меняет порядок исполнения систем в тике, то есть результат симуляции, не ломая при этом ничего видимого.

#### Scenario: Оптимизация системы переписыванием в код

- **WHEN** JSON-система заменяется нативной с тем же `name` и `order`
- **THEN** вокруг не меняется ничего: ни scheduler, ни имя RNG-стрима, ни порядок команд

#### Scenario: Подмена с другим order

- **WHEN** `override` вызывается с системой, чей `order` отличается от зарегистрированного
- **THEN** вызов отвергается: это не подмена реализации, а другая система

### Requirement: SYS-8 Golden-file не меняется при переписывании системы

Golden-file тест SHALL оставаться неизменным при переписывании системы из JSON в код; расхождение снапшотов нативной и JSON-версии SHALL считаться красным тестом. Для изначально нативных систем golden-file фиксирует эталон напрямую.

#### Scenario: Оптимизация изменила поведение

- **WHEN** нативная версия системы даёт снапшот, отличный от JSON-версии
- **THEN** golden-file тест краснеет — оптимизация сломала детерминизм и не принимается

### Requirement: ACT-1 Набор actions

Узел действия SHALL быть объектом с ровно одним ключом — именем действия; аргументы SHALL быть именованными полями объекта-значения, а не позиционным массивом. Имена компонентов, полей, prefab'ов, типов событий и переменных SHALL быть строковыми литералами; значения полей и данных событий SHALL быть выражениями (EXPR-1), вычисляемыми в текущей области видимости.

Action DSL SHALL поддерживать набор действий:

- `modifyComponent`, `addComponent`, `removeComponent`
- `spawnEntity`, `destroyEntity`
- `emitEvent`
- `forEach { query, as, do }` — итерация с телом-actions
- `forEachEvent { type, as, do }` — итерация по событиям тика заданного типа (EVT-2) с телом-actions
- `if { cond, then, else }`
- `let { bindings, do }` — локальные переменные
- `random { as, subStream, do }` — равномерное значение в [0,1) как Q16.16, связанное с именем в теле
- `randomBelow { as, bound, subStream, do }` — равномерное целое в `[0, bound)`
- `addTween { entity, def, from, to, duration, easing, ignoreTimeScale }` — создание твина
  (`time-system` TWEEN-5); `def` — индекс определения в таблице сцены (TWEEN-1), `easing` и
  `ignoreTimeScale` необязательны и по умолчанию нулевые
- `addModifier { entity, component, id, value }` — постановка источника-модификатора в свободный или
  уже занятый этим `id` слот (`time-system` TIME-7, TIME-8)
- `removeModifier { entity, component, id }` — снятие источника; отсутствующий `id` не ошибка (TIME-8)

`let`, `forEach`, `forEachEvent`, `random` и `randomBelow` SHALL создавать вложенную область видимости: имя, объявленное внутри, перекрывает внешнее и перестаёт существовать за пределами тела.

`forEachEvent` SHALL обходить события шины текущего тика в порядке публикации (EVT-2), отбирая их по литеральному `type`. Фильтр по типу SHALL быть обязательным: набор полей события задаётся его типом, и обход без фильтра читал бы поля наугад. Имя, связанное `as`, SHALL быть ссылкой на событие, поля которого читаются оператором `eventField` (EXPR-2), и SHALL быть действительно только внутри тела: данные события в переменную DSL не помещаются (значение переменной — скаляр или вектор), а за границей тика ссылка теряет смысл, потому что шина чистится (EVT-4). Отдельного механизма подписки на событие MUST NOT появляться — по той же причине, по которой у системы нет своего механизма итерации помимо `forEach` (SYS-1): второй порядок исполнения рядом с `order` (SYS-2).

`random` и `randomBelow` SHALL тянуть значение из стрима своей системы (RNG-4) и SHALL быть единственным способом получить случайное значение в DSL: в выражениях RNG не вызывается (RNG-6). Вид значения SHALL задаваться именем действия, а не полем-перечислением: имена действий образуют закрытый набор, проверяемый на регистрации (SYS-3), тогда как ошибка в значении поля дожила бы до срабатывания ветки.

`bound` SHALL быть выражением в Q16.16 и приводиться к целому внутри действия; результат `randomBelow` SHALL быть сырым целым — как значение поля `i32`, и в fixed-point арифметике требует явного `fromInt` (EXPR-2). `bound` меньше единицы SHALL приводить к ошибке: пустой диапазон значения не имеет.

`subStream` — необязательный строковый литерал, дающий суб-стрим по RNG-7; вычисляемое имя суб-стрима MUST NOT поддерживаться, иначе состав стримов зависел бы от состояния мира.

Аргументы, адресующие поля `i32` (`def`, `easing`, `ignoreTimeScale` у `addTween`, `id` у
`addModifier`/`removeModifier`), SHALL быть сырыми целыми, а не Q16.16: та же конвенция, что у
значений полей `modifyComponent`, преобразования масштаба действие не делает. Аргумент `value` у
`addModifier` — множитель, то есть Q16.16.

`component` у `addModifier`/`removeModifier` SHALL быть строковым литералом и SHALL адресовать
список источников, подключённый конфигом сцены (`serialization` SER-7); отсутствие такого списка
SHALL быть ошибкой, а не действием без эффекта. Ограничение на имя компонента общее для всего DSL:
незарегистрированный компонент отвергается на регистрации системы (SYS-3).

Набор имён действий SHALL быть закрытым: неизвестное имя SHALL приводить к ошибке, а не к пропуску узла — то же правило, что для операторов выражений (EXPR-6), и по той же причине.

#### Scenario: Условный эффект способности

- **WHEN** способность бьёт сильнее по целям ниже 30% HP
- **THEN** это выражается через `if` с JsonLogic-условием, без написания кода

#### Scenario: Затенение переменной во вложенном теле

- **WHEN** `forEach` внутри `let` связывает имя, уже объявленное снаружи
- **THEN** внутри тела видно внутреннее значение, а после выхода из тела — снова внешнее

#### Scenario: Опечатка в имени действия

- **WHEN** JSON содержит действие, которого нет в наборе
- **THEN** исполнение падает с ошибкой, называющей действие

#### Scenario: Разброс урона в JSON-системе

- **WHEN** формуле урона нужен случайный множитель
- **THEN** система оборачивает расчёт в `random { as: "roll", do: [...] }`, а выражение внутри читает `roll` как обычную переменную

#### Scenario: Равномерное целое

- **WHEN** нужно выбрать одно из `n` направлений
- **THEN** используется `randomBelow` с `bound`, а не остаток от значения `random`: остаток даёт смещённое распределение

#### Scenario: Опечатка в имени случайного действия

- **WHEN** в системе написано имя, которого нет в наборе
- **THEN** регистрация системы падает, а не первое срабатывание ветки, в которой оно написано

#### Scenario: Замедление цели из JSON-системы

- **WHEN** JSON-система должна замедлить цель на время действия эффекта
- **THEN** она ставит источник через `addModifier` и снимает его через `removeModifier`, не обращаясь к TS-коду: управление списком `sources` (TIME-8) доступно из данных

#### Scenario: addModifier к списку, которого нет в сцене

- **WHEN** действие адресует список источников, не подключённый конфигом сцены
- **THEN** это ошибка, а не действие без эффекта

#### Scenario: Отскок снаряда из JSON-системы

- **WHEN** ядро эмитит `Collision` с нормалью (`physics` PHYS-9), а решение об отскоке — политика
- **THEN** JSON-система с `order` больше физики обходит события через `forEachEvent`, читает нормаль через `eventField` и ставит команды через `modifyComponent` — политика написуема из данных

#### Scenario: Ссылка на событие за пределами тела

- **WHEN** выражение вне тела `forEachEvent` ссылается на связанное им имя
- **THEN** регистрация системы падает как на любой несвязанной переменной (SYS-3): ссылка на событие живёт только внутри тела

### Requirement: ACT-2 Все ECS-меняющие actions через Command Buffer

Все actions, меняющие ECS, SHALL работать через Command Buffer. В частности `addTween` и `addModifier` тоже SHALL создавать команды (создание/модификация компонентов `Tween`/модификаторов), а не мутировать ECS напрямую.

#### Scenario: Твин, созданный внутри forEach

- **WHEN** `addTween` вызывается для каждой найденной сущности
- **THEN** создаются команды, применяемые на flush, — итерация остаётся стабильной

### Requirement: ACT-3 Детерминированный порядок commands

Порядок применения команд, созданных actions, SHALL быть детерминированным.

Действия внутри `do` SHALL исполняться в порядке перечисления. Внутри одного действия, задающего несколько полей (`values`, `overrides`, `data`), команды SHALL создаваться в порядке отсортированных имён полей, а не в порядке ключей объекта JSON: порядок ключей объекта зависит от их вида (целочисленные имена всплывают вперёд) и от сериализатора, поэтому опорой для детерминизма служить не может. Сортировка задаёт порядок, воспроизводимый и во второй реализации ядра.

Сортировка SHALL быть лексикографической по именам полей независимо от того, выглядит ли имя как целое число, и SHALL распространяться и на вычисление значений, и на создание команд. Реализация MUST NOT опираться на порядок перечисления ключей объекта ни на одном из этих шагов, в том числе и после того, как карта уже собрана в отсортированном порядке: в JS целочисленные имена всплывают вперёд и упорядочиваются численно, поэтому поля `"9"` и `"10"` перечислились бы в порядке, обратном лексикографическому, — и расхождение с этой нормой было бы молчаливым.

#### Scenario: Несколько actions меняют одну сущность

- **WHEN** внутри одной системы к сущности применяется несколько модификаций
- **THEN** итоговое состояние однозначно определяется порядком создания команд

#### Scenario: Одно действие задаёт несколько полей

- **WHEN** `modifyComponent` меняет три поля компонента
- **THEN** команды создаются в порядке отсортированных имён полей, независимо от порядка ключей в JSON

#### Scenario: Поля с целочисленными именами

- **WHEN** `modifyComponent` меняет поля с именами `"9"` и `"10"`
- **THEN** команды создаются в лексикографическом порядке — сначала `"10"`, затем `"9"`, — а не в численном порядке всплывших ключей объекта

#### Scenario: Два чтения одного поля внутри системы

- **WHEN** два `modifyComponent` подряд уменьшают одно и то же поле, читая его выражением
- **THEN** оба читают значение на начало системы (CMD-5), и итог равен последней записи, а не сумме уменьшений

### Requirement: EXPR-1 JsonLogic-совместимый JSON-AST

Expression Evaluator в MVP SHALL исполнять выражения, заданные JSON-AST в форме JsonLogic: узел — объект с ровно одним ключом-оператором, `{"op": [args]}`, аргументы — вложенные выражения или литералы. Выражения SHALL храниться как JSON-AST, а не как строка-код.

Реализация SHALL быть собственной, библиотека `json-logic-js` MUST NOT использоваться: её арифметика — встроенные операторы JavaScript над double, что несовместимо с DET-2, а расширение через `add_operation` — глобальная мутация модульного синглтона, что несовместимо с DI-1 (две симуляции в одном процессе делили бы реестр операторов).

Сохраняется именно форма AST — чтобы редактор, валидация и построчный дифф работали с общеизвестным форматом.

#### Scenario: Хранение формулы урона

- **WHEN** формула урона задана в редакторе
- **THEN** она сериализуется как JSON-AST, пригодный для валидации и диффа, а не как строка-код

#### Scenario: Умножение в выражении

- **WHEN** выражение перемножает два fixed-point значения
- **THEN** используется fixed-point умножение (`(a * b) >> 16`), а не оператор `*` языка-хоста

### Requirement: EXPR-2 Собственные расширения JsonLogic

Evaluator SHALL расширять JsonLogic: fixed-point арифметика вместо float, `getComponent`, `hasComponent`, векторная математика и тригонометрия `sin`/`cos` через Math API, проверка отдельного бита целочисленной маски `bitTest`, чтение поля данных события `eventField`.

Все числовые операторы SHALL работать в Q16.16. Числовые литералы в AST SHALL быть сырыми Q16.16-значениями (`1.0` записывается как `65536`) — редактор конвертирует при сохранении, чтобы в тике не выполнялось ни одной операции с плавающей точкой. Значение поля типа `i32` (ECS-3) SHALL приводиться к Q16.16 явным оператором `fromInt` перед участием в fixed-point арифметике: смешение масштабов без явного приведения даёт тихо неверный результат, а не ошибку.

`sin [angle]` и `cos [angle]` SHALL принимать угол в единице `fixed-point-math` FP-7 (полный оборот — 2^16 единиц, заворачивание маской) и возвращать Q16.16 по нормативной таблице FP-8. Семантику, точность и сведение к первой четверти задаёт спека `fixed-point-math`; таблица операторов лишь открывает их выражениям.

`bitTest [mask, index]` SHALL работать с сырым целым значением поля `i32`, без приведения к Q16.16, и возвращать булево: маска — не число в геймплейном смысле, и арифметика над ней не определена. Полный набор битовых операций в таблицу не входит — потребитель маски читает её по одному биту. Диапазон номера бита SHALL быть `[0, 31]`: оператор общий для любой `i32`-маски, а ширину конкретного поля задаёт его собственное требование.

`eventField [event, field]` SHALL читать поле данных события, на которое ссылается имя, связанное действием `forEachEvent` (ACT-1), где `field` — строковый литерал. Значение SHALL возвращаться как хранится, без преобразования масштаба, — как у `getComponent`: масштаб задаёт эмитент события, и `entity` в его данных такое же сырое целое, как `EntityId`. Отсутствие поля у события SHALL быть ошибкой вычисления, называющей тип события и поле, а не нулём: набор полей события нигде не зарегистрирован, поэтому опечатку не поймать на регистрации (SYS-3). Ссылка на событие MUST NOT давать выражению возможность публикации: из выражения видна только read-only-часть шины (EXPR-3).

#### Scenario: Расчёт дистанции в выражении

- **WHEN** выражение считает расстояние между двумя сущностями
- **THEN** расчёт идёт в fixed-point через Math API, результат детерминирован

#### Scenario: Направление из угла в выражении

- **WHEN** система-способность разворачивает угол прицеливания в единичный вектор направления
- **THEN** вектор собирается как `vec [cos(a), sin(a)]` из таблицы FP-8, без нативной системы и без float

#### Scenario: Целочисленное поле в арифметике

- **WHEN** выражение использует значение поля типа `i32` (счётчик зарядов, число целей)
- **THEN** оно приводится оператором `fromInt`; без приведения масштаб не совпадает, и это дефект выражения, а не поведение по умолчанию

#### Scenario: Детект фронта кнопки в JSON-системе

- **WHEN** система реагирует на нажатие способности, а не на удержание
- **THEN** условие выражается как `bitTest` по текущей маске и отрицание `bitTest` по предыдущей (TICK-4), без битовой арифметики

#### Scenario: Нормаль столкновения в выражении

- **WHEN** политика отскока читает нормаль события `Collision`
- **THEN** она берёт её оператором `eventField` из ссылки, связанной `forEachEvent`, и выражение остаётся чистым: писать в шину ему нечем

#### Scenario: Опечатка в имени поля события

- **WHEN** выражение читает поле, которого у события нет
- **THEN** вычисление падает с ошибкой, называющей тип события и поле, а не возвращает нуль

### Requirement: EXPR-3 Sandboxed выражения

Выражения SHALL быть sandboxed: никаких side-effects.

#### Scenario: Попытка изменить компонент из выражения

- **WHEN** выражение пытается что-то записать
- **THEN** такой операции в языке выражений нет — мутации доступны только actions

### Requirement: EXPR-4 Абстракция ExpressionEvaluator

Evaluator SHALL быть скрыт за интерфейсом `ExpressionEvaluator` — для последующей замены JsonLogic на собственный AST. Точка абстракции живёт внутри `EvaluatedSystem`; нативной системе она не нужна.

#### Scenario: Замена JsonLogic на собственный AST

- **WHEN** производительность JsonLogic перестаёт устраивать
- **THEN** меняется реализация за интерфейсом, JSON-описания систем и остальной код не трогаются

### Requirement: EXPR-5 Никаких циклов в выражениях

Циклы MUST NOT поддерживаться в expressions; итерация доступна только в actions через `forEach`.

#### Scenario: Нужна агрегация по набору сущностей

- **WHEN** требуется просуммировать значение по нескольким сущностям
- **THEN** это делается через action `forEach` с накоплением в `let`, а не циклом внутри выражения

### Requirement: EXPR-6 Закрытая таблица операторов

Набор операторов SHALL быть закрытой таблицей, задаваемой реализацией evaluator'а. Оператор, отсутствующий в таблице, SHALL приводить к ошибке в момент вычисления, а не к пропуску узла или к значению по умолчанию. Разрешение имени оператора MUST NOT обращаться к цепочке прототипов объекта AST — иначе `constructor` или `__proto__` в позиции оператора дотянулись бы до хост-объектов, что нарушило бы EXPR-3.

Обоснование: закрытая таблица — это одновременно и sandbox (за её пределы выражению не выйти), и точка, в которой позже вырастет статическая валидация AST на регистрации системы (SYS-3).

#### Scenario: Опечатка в имени оператора

- **WHEN** JSON-выражение содержит оператор, которого нет в таблице
- **THEN** вычисление падает с ошибкой, называющей оператор, а не возвращает молчаливый результат

#### Scenario: Имя из цепочки прототипов в позиции оператора

- **WHEN** в позиции оператора стоит `constructor`, `__proto__` или другое унаследованное имя
- **THEN** оно не разрешается как оператор и обрабатывается как неизвестное

### Requirement: EVT-1 Детерминированная очередь событий

Event Bus SHALL быть детерминированной очередью.

#### Scenario: Несколько систем эмитят события на одном тике

- **WHEN** события публикуются из разных систем
- **THEN** их порядок в очереди воспроизводится при каждом прогоне

### Requirement: EVT-2 Потребление в порядке публикации

События SHALL потребляться системами в порядке публикации.

`SystemContext.events` SHALL давать системе read-only-доступ к шине текущего тика (длина, обращение по индексу, обход в порядке публикации) наравне с публикацией (SYS-5), а Action DSL SHALL иметь узел итерации по событиям тика (`forEachEvent`, ACT-1). Без этого требование невыполнимо: потреблять было бы нечем, и единственным читателем событий остался бы внешний слой, который мир менять не может (`tick-loop` TICK-3).

Система SHALL видеть на тике ровно те события, которые опубликованы до её запуска системами с меньшим `order` (SYS-2) или её собственным телом раньше по тексту. Событий прошлых тиков в шине нет: она чистится на границе тика (EVT-4). Событий систем с большим `order` в ней ещё нет, и на следующем тике их тоже не будет — поэтому реакция на событие SHALL выражаться порядком `order`, а не ожиданием следующего тика.

Узел итерации SHALL обходить события, опубликованные до входа в узел, и MUST NOT подхватывать опубликованные его же телом: иначе реакция, эмитящая событие того же типа, зацикливалась бы, а число проходов зависело бы от тела. То же правило, что у `forEach` над результатом запроса (QUERY-3): набор материализован на момент входа.

Цепочка реакций SHALL выражаться порядком `order`, а не подпиской: система-реагент читает шину и ставит свои команды, а колбэков в ядре нет (EVT-4).

#### Scenario: Цепочка реакций

- **WHEN** система с меньшим `order` эмитит `DamageDealt`, а следующая по `order` в ответ эмитит `EntityDied`
- **THEN** вторая видит `DamageDealt` в шине этого же тика, а система с ещё большим `order` видит оба события в порядке публикации, а не в произвольном

#### Scenario: Событие системы с большим order

- **WHEN** система читает шину, а интересующее её событие эмитит система с большим `order`
- **THEN** на этом тике она его не видит, и на следующем тоже: шина к тому моменту очищена — порядок реакции задаётся `order`

#### Scenario: Реакция эмитит событие того же типа

- **WHEN** тело узла итерации по `Collision` само эмитит `Collision`
- **THEN** новое событие в текущем обходе не участвует; его увидят системы с большим `order`

### Requirement: EVT-3 События — часть snapshot

События SHALL входить в snapshot (для rewind/rollback).

#### Scenario: Rewind на тик с необработанными событиями

- **WHEN** мир откатывается на тик, где в шине лежали события
- **THEN** они восстанавливаются вместе с миром, и продолжение симуляции идентично честному реплею

### Requirement: EVT-4 Разграничение Event Bus и Command Buffer

> Источник: врезки «Разграничение с Command Buffer / Event Bus» из tech-requirements.md §4.5 и §9; выделено в отдельное требование при конвертации.

EventBus SHALL нести факт («что-то произошло», доступный всем системам тика), Command Buffer SHALL нести мутацию (адресное изменение ECS). Событие само по себе мир не меняет — реакция систем-читателей проводит мутации через Command Buffer. Слить их в один механизм MUST NOT быть допущено: событие не должно мутировать world напрямую (сломает детерминированный flush), команда не имеет читателей.

Broadcast SHALL быть реализован общим чтением одной шины, а не подпиской: событие получает каждая система, которая читает шину после его публикации (EVT-2). Механизма регистрации колбэков-подписчиков в ядре нет и MUST NOT вводиться — набор и порядок подписчиков стали бы вторым порядком исполнения рядом с `order` (SYS-2, DET-3), и число реакций на событие перестало бы читаться из текста систем.

Время жизни у механизмов разное, но «дольше» — не значит «до следующего тика». Шина SHALL чиститься на границе тика, поэтому система видит только события текущего тика. Факт события SHALL переживать границу тика только в снапшоте: шина входит в снапшот и откатывается вместе с миром (EVT-3, `snapshot-rewind` REW-10) — то есть переживает «до восстановления этого тика», а не «до следующего». Command Buffer в снапшот не входит вовсе: он вливается в конце каждой системы (CMD-2) и на границе тика пуст.

#### Scenario: Реакция нескольких систем на смерть сущности

- **WHEN** эмитится `EntityDied`
- **THEN** каждая система с большим `order` читает его из шины и реагирует своим набором команд; само событие мир не меняет

#### Scenario: Событие на границе тика

- **WHEN** тик закончился и начался следующий
- **THEN** шина очищена: события прошлого тика в ней нет — а в истории они остались в снапшоте того тика и вернутся при откате на него (REW-10)
