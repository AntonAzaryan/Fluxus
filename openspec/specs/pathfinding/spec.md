# Pathfinding Specification

## Purpose

Navigation API — шов, через который в ядро входит поиск пути для крипов и NPC. Здесь зафиксирован контракт границы: форма запроса, его детерминизм и чистота, место навигационных данных в сборке и граница между механизмом (ядро отвечает, куда можно пройти) и политикой (геймплейная система решает, идти ли и как). Алгоритм поиска в эту версию не входит.
## Requirements
### Requirement: NAV-1 Контракт Navigation API

Поиск пути SHALL входить в ядро единственным интерфейсом Navigation API, по образцу Physics API (`physics` PHYS-4):

```ts
interface NavigationApi {
  readonly findPath: (from: Vec2, to: Vec2, options?: PathRequestOptions) => PathResult;
}

interface PathRequestOptions {
  /** Радиус агента в fixed-point: путь шириной меньше него не возвращается. */
  readonly agentRadius?: Fixed;
}

interface PathResult {
  readonly status: 'found' | 'unreachable' | 'budgetExhausted';
  /** Промежуточные цели в мировых координатах; последняя — конечная точка запроса. */
  readonly waypoints: readonly Vec2[];
}
```

Путь SHALL быть последовательностью точек в мировых координатах fixed-point. Точка `from` в путь входить MUST NOT: агент уже в ней, и её включение сделало бы первый шаг движения нулевым. Последняя точка SHALL совпадать с конечной точкой запроса при `status: 'found'`. Единственное исключение — совпадение старта и цели: по NAV-5 оно даёт `found` с пустым списком, потому что единственной точкой такого пути была бы сама `from`, которую путь не содержит.

При `status`, отличном от `'found'`, список точек SHALL быть пустым. Частичный путь — «дойти как можно ближе» — MUST NOT возвращаться под видом найденного: выбор запасной цели при недостижимости — политика (NAV-4), и если она понадобится ядру, это расширение данного требования, а не свобода реализации.

Источник значения `agentRadius` SHALL быть контентом, а не константой ядра. Соотношение радиуса с размером клетки — предмет валидации ассета террейна (`terrain` TERR-7).

#### Scenario: Путь между двумя точками арены

- **WHEN** система запрашивает путь из точки A в отличную от неё точку B, между которыми есть проход
- **THEN** возвращается `status: 'found'` и непустая последовательность точек, последняя из которых — B, а A в ней отсутствует

#### Scenario: Цель за непроходимой границей

- **WHEN** цель отделена от старта обрывом без рампы
- **THEN** возвращается `status: 'unreachable'` с пустым списком точек, а не путь до ближайшей достижимой клетки

#### Scenario: Проход уже агента

- **WHEN** единственный проход к цели уже, чем диаметр агента из `agentRadius`
- **THEN** цель считается недостижимой для этого агента, хотя для агента меньшего радиуса тот же запрос вернул бы путь

### Requirement: NAV-2 Запрос детерминирован и чист

`findPath` SHALL быть детерминированным и считаться в fixed-point: одинаковые аргументы при одной и той же неизменяемой части сборки SHALL давать побитово одинаковый результат — в пределах прогона, между прогонами и между реализациями ядра (`determinism-core` CORE-2).

Запрос SHALL быть чистой функцией аргументов и неизменяемой части сборки. Он MUST NOT читать ГПСЧ (`rng` RNG-1), изменяемое состояние мира или номер тика, MUST NOT зависеть от порядка и числа предыдущих вызовов. Кеширование допустимо ровно постольку, поскольку оно не наблюдаемо в результате: кеш, меняющий исход запроса, — расхождение детерминизма.

Разрешение неоднозначностей поиска — равные по стоимости пути, порядок раскрытия узлов с равным приоритетом — SHALL быть нормативным правилом, а не свободой реализации: change, вводящий реализацию, SHALL зафиксировать правило tie-break в спеке, как это сделано для порядка hit'ов raycast (`physics` PHYS-7).

#### Scenario: Повторный запрос того же пути

- **WHEN** тот же запрос повторяется на другом тике и в другой реализации ядра
- **THEN** возвращается побитово тот же путь

#### Scenario: Два пути равной стоимости

- **WHEN** до цели есть два маршрута одинаковой стоимости
- **THEN** выбор между ними определён нормативным правилом, а не порядком обхода структуры данных конкретной реализации

#### Scenario: Попытка внести случайность в поиск

- **WHEN** реализация хочет разнообразить маршруты агентов через ГПСЧ внутри `findPath`
- **THEN** это отклоняется: разброс маршрутов — политика, задающая разные цели, а не недетерминированный запрос

### Requirement: NAV-3 Навигационные данные — часть неизменяемой сборки

Навигационные данные SHALL быть производными от карты уровней и жить в неизменяемой части сборки наравне со статическими коллайдерами (`physics` PHYS-10) и террейном (`terrain` TERR-6). В снапшот они входить MUST NOT и при перемотке не восстанавливаются и не пересобираются: они производны от иммутабельных данных, а восстановление — источник расхождения реализаций.

Запрос MUST NOT учитывать динамические сущности. Индекс динамики, снятый в начале тика, к моменту запроса из другой системы может не соответствовать миру (`physics` PHYS-5), а обход движущихся тел — локальное избегание — политика геймплейной системы, а не свойство статичной геометрии.

#### Scenario: Перемотка матча

- **WHEN** мир откатывается на предыдущий тик
- **THEN** навигационные данные не восстанавливаются и не пересобираются: снапшот их не содержит

#### Scenario: Агент упёрся в другого агента

- **WHEN** по найденному пути стоит другая сущность
- **THEN** путь остаётся прежним: разойтись с ней — задача геймплейной системы, а не `findPath`

### Requirement: NAV-4 Путь — данные, движение по нему — политика

`findPath` SHALL быть запросом, а не командой: он MUST NOT писать в мир, эмитить события и заводить состояние агента. Ядро MUST NOT двигать сущность по найденному пути.

Следование пути — хранение текущей точки, переход к следующей, перепланирование при смене цели или застревании — SHALL быть геймплейной системой, пишущей `Position` через Command Buffer на общих основаниях (`determinism-core` DET-7, `ecs-foundation` CMD-4). Компонента пути, поля «идти сюда» и встроенного поведения преследования в ядре MUST NOT быть: это ровно та политика, которая в `physics` PHYS-9 оставлена геймплейной системе для столкновений.

#### Scenario: Крипу задана цель

- **WHEN** геймплейная система ведёт крипа к цели
- **THEN** она сама запрашивает путь, хранит прогресс по нему в своих компонентах и двигает сущность через Command Buffer

#### Scenario: Предложение встроить движение по пути в ядро

- **WHEN** возникает идея дать API команду «вести сущность по пути»
- **THEN** она отклоняется: это состояние агента и политика движения, а не механизм поиска

### Requirement: NAV-5 Тотальность и бюджет поиска

`findPath` SHALL быть тотальным: исключение посреди тика останавливает матч, поэтому невалидный запрос — точка за пределами сетки, старт внутри непроходимой геометрии, совпадение старта и цели — SHALL давать результат, а не ошибку. Точка за пределами сетки SHALL трактоваться так же, как в запросе уровня (`terrain` TERR-4) — по ближайшей клетке; совпадение старта и цели SHALL давать `status: 'found'` с пустым списком точек.

Объём поиска SHALL быть ограничен бюджетом — предельным числом раскрытых узлов. Бюджет SHALL быть параметром сборки Navigation API, а не константой ядра: это число, которое настраивает геймдизайнер под размер арены и цену тика. Бюджет SHALL измеряться в единицах работы, а не во времени: измерение времени внутри симуляции запрещено (`determinism-core` DET-5), и лимит по времени сделал бы исход поиска зависящим от машины.

Исчерпание бюджета SHALL быть отличимо от недостижимости (`status: 'budgetExhausted'` против `'unreachable'`): первое — сигнал о неверно подобранном лимите или слишком большой арене, второе — штатный ответ о геометрии, и политика реагирует на них по-разному.

#### Scenario: Запрос из точки за краем сетки

- **WHEN** сущность оказалась за пределами сетки террейна и для неё запрашивается путь
- **THEN** запрос отвечает по ближайшей клетке, а не бросает исключение посреди тика

#### Scenario: Поиск упёрся в лимит

- **WHEN** число раскрытых узлов достигает бюджета до того, как цель найдена
- **THEN** возвращается `status: 'budgetExhausted'`, и этот исход отличим от `unreachable`

#### Scenario: Лимит по времени вместо лимита по узлам

- **WHEN** реализация хочет прерывать поиск по истечении миллисекунд
- **THEN** это отклоняется: результат стал бы зависеть от скорости машины

### Requirement: NAV-6 Алгоритм и представление — за реализацией

Контракт MUST NOT фиксировать способ поиска: сетка с A\*, навигационная сетка, flow field и любое другое представление SHALL быть заменимы без изменения Navigation API и без изменения кода систем-потребителей (`determinism-core` DI-1).

Связность сетки (4- или 8-связная) — открытый вопрос `terrain` — здесь фиксироваться MUST NOT: она свойство конкретного представления, а не границы. Change, вводящий реализацию, SHALL закрыть этот вопрос и зафиксировать выбор нормативно.

Сцена без навигации SHALL тикать штатно (`determinism-core` DI-4), а система, которой Navigation API необходим, SHALL падать с ошибкой, называющей зависимость (`data-driven-systems` SYS-5).

#### Scenario: Замена представления навигации

- **WHEN** поиск по клеткам заменяется поиском по навигационной сетке
- **THEN** код систем-потребителей не меняется: у них тот же `findPath`

#### Scenario: Сцена без навигации

- **WHEN** ядро собрано без Navigation API и ни одна система его не требует
- **THEN** `tick()` отрабатывает штатно
