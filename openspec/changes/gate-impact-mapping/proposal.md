# Proposal: gate-impact-mapping

## Why

Единственные ворота репозитория — клиентский `npm run check` перед пушем в `main` — стоят 439 с (7:19) на зелёном дереве, и половина этой цены — не проверки, а расписание и дублирование: пятнадцать последовательных `tsc --noEmit` типизируют исходники ядра по десять раз, потому что пакеты резолвят друг друга исходником (93 с); пятнадцать последовательных стартов vitest грузят модули дольше, чем исполняют тесты (transform 88 с + import 231 с против tests 222 с); четверть коммитов без слияний (41 из 171) меняет только `openspec/`, `docs/` и `*.md` — и платит те же 439 с за проверки, которые физически не могут покраснеть. Гейт при этом нигде не нормирован: `cli-testing` описывает прогоны, эталоны и guard-проверки (CLI-4..CLI-9), но не состав ворот, не их инвариант и не то, что они охраняют, — ускорять его нечем сверить.

Замер показал и то, чего делать нельзя. Файловый выбор тестов по графу модулей (`vitest related`) дырявый ровно там, где репозиторий data-driven: правка `content/scenes/duel.scene.json` выбирает 15 тестовых файлов из 27 зависящих — 20 читают сцену через `fs` по строке пути, — а правка эталона `engine/tests/golden/*.golden.json` не выбирает ни одного, потому что `golden.test.ts` ходит `readdirSync`. Пакетное замыкание по `package.json` течёт тоже: тесты `desktop/shell-ts` проверяют пути в четырёх пакетах, от которых контейнер не зависит ни одной строкой манифеста, а boundary-тесты `integration-ts` сканируют всё дерево. Выборочный прогон возможен только с явной картой, механическим сторожем её полноты — и только не как ворота `main`.

## What Changes

- **Гейт репозитория нормируется (CLI-13).** Состав `npm run check` — статический анализ всех пакетов, линт графа спек, тесты всех пакетов гейта — и инвариант: вердикт ворот MUST NOT зависеть от порядка и параллельности стадий, ни одна стадия не пишет того, что читает другая (регенерация эталонов и схем — отдельные явные команды, CLI-5). Это лицензия на расписание: `typecheck` — параллельно по числу ядер вместо `--workspaces` последовательно (93 → 40 с, замерено), `npm test` — один корневой пул vitest с проектами вместо пятнадцати стартов (218 → 184 с, замерено), список проектов общий с конфигом покрытия. Объём проверок не меняется ни на файл. Стоимость стадий гейта становится командой, а не ощущением.
- **Выборочный прогон — `npm run check:impact` (CLI-14).** По диффу от базы (общий предок с `main` плюс рабочее дерево): изменённые пути → пакеты → обратное замыкание по объявленным `@fluxus/*`-зависимостям **плюс объявленные тест-рёбра** (кто читает чужое дерево мимо манифеста) → проверка типов, линт и тесты только этих пакетов. Гранулярность — пакет, не файл: `fs`-рёбра внутри пакета потеряться не могут. Глобальные по природе проверки — knip, jscpd, depcruise, `spec-graph check` — всегда целиком (22 с суммарно). Интеграционная суита CLI-9 — в любой непустой выборке кода: её boundary-тесты сканируют всё дерево.
- **Широкие ворота и fail-closed.** Правка в `content/**`, `engine/tests/**`, `engine/schemas/**`, `scripts/**`, `.claude/hooks/**`, корневых конфигах, любом `tsconfig*.json`, манифестах и `package-lock.json` — полный гейт. Путь, не подошедший ни под одно правило карты, — полный гейт. Документный быстрый путь: дифф только из `openspec/**`, `docs/**`, `*.md` → `spec-graph check` плюс тесты, читающие дерево спек (сегодня один — `specGraph.test.ts`), ~5 с вместо 439.
- **Карта — данные, её полнота — сторож.** Широкие ворота, тест-рёбра и правила принадлежности путей живут в самом скрипте, и их правка обязана попадать в дифф на ревью (образец — списки CLI-8). Тест-сторож в `integration-ts`: каждый workspace корневого манифеста и каждый tracked-корень дерева назван правилом; AST-скан строковых литералов путей в `test/` и `bin/` каждого пакета (машинерия `engine/tests/guard/scanner.ts`, комментарии не считаются) — литерал чужого дерева, не покрытый ни тест-ребром, ни широкими воротами, краснит обычный прогон тестов с файлом и строкой. Новый пакет или новое чтение чужого дерева не выпадает из выборки молча. Выбор объясним: `--explain` называет правило, выбравшее каждый пакет.
- **Выборочный прогон MUST NOT охранять `main`.** `scripts/git-hooks/pre-push` перед пушем в `main` по-прежнему гонит полный `npm run check` — не меняется ни строкой. Выборка — внутренний цикл: фичевые ветки (сегодня не гейтятся вовсе) и агентский цикл (шаг «targeted package tests» у `implementer`, подтверждение находок у `reviewer`). Дыра карты тогда стоит лишнего полного прогона, а не пропущенного регресса.

## Capabilities

### New Capabilities

Нет: гейт и его выборка — тестовая инфраструктура, то есть `cli-testing` (CLI-8 уже нормирует guard-проверки «в обычном прогоне тестов», CLI-9 — интеграционную суиту).

### Modified Capabilities

- `cli-testing`: CLI-13 — состав и инвариант гейта репозитория, стоимость стадий как диагностика; CLI-14 — выборочный прогон по карте влияния: пакетная гранулярность, широкие ворота, fail-closed, механический сторож полноты карты, объяснимость выбора, запрет быть воротами основной ветки.

## Impact

Корневой `package.json` (скрипты `typecheck`, `test`, `check:impact`, `check:timings`; `check` — та же цепочка, что сейчас), `scripts/typecheck.mjs` (параллельный раннер), `scripts/impact.mjs` (карта, выборка, исполнение плана, `--explain`/`--dry-run`/`--full`), `vitest.projects.ts` + `vitest.gate.config.ts` (имя намеренно неканоническое — по той же причине, что у `vitest.coverage.config.ts`: корневой `vitest.config.*` перехватил бы попакетные прогоны), `vitest.coverage.config.ts` берёт список проектов оттуда. Тесты: `engine/integration-ts/test/impactMap.test.ts` (сторож полноты) и `impact.test.ts` (классификация, замыкание, сценарии спеки на фикстурных диффах). Документы: CLAUDE.md (блок команд), `.claude/agents/implementer.md` и `reviewer.md` (targeted-шаг), `docs/architecture.md` (строка roadmap). `scripts/git-hooks/pre-push` — без изменений. Ни один существующий тест, эталон, схема или документ контента не правится; симуляция, сеть, рендер, контент — не затрагиваются.

## Notes

**Замер (2026-09-02, 4 ядра, 15 ГБ, Node 22, чистое дерево):** сквозной `npm run check` — 439 с, rc=0. Постадийно: тесты 218,4 с (15 последовательных прогонов, 5796 тестов в 331 файле), eslint 133,4 с, typecheck 93,0 с, depcruise 15,0 с, knip 5,8 с, jscpd 0,7 с, `spec-graph check` 0,6 с. Единый пул vitest по 14 проектам — 180 с (transform 88 с, import 231 с, tests 222 с). Параллельный typecheck по 4 — 40 с. eslint `--cache` — 133 → 3 с на повторе, но кэш инвалидируется содержимым файла и не перелинчивает зависимых при правке типов: для типизированных правил это дыра, в гейт не входит, во внутреннем цикле — на усмотрение разработчика.

**Пробы выборки по графу модулей** (`vitest related`, база 320 файлов / 180 с): `engine/core-ts/src/math/fixed.ts` → 258 файлов, 127 с (−30 %: ядро в основании графа); `editor/ui-ts/src/areas/assetCameraEffects.ts` → 24 файла, 14 с (−92 %); `content/scenes/duel.scene.json` → 15 файлов, все в `@fluxus/demo`, 20 зависящих в восьми пакетах не выбраны; `engine/tests/golden/match-walk.golden.json` → 0 файлов.

**Резервация номеров (сверена 2026-09-02).** CLI-13 и CLI-14: main занят по CLI-12, открытые change'и CLI-номеров не резервируют.

**За пределами change (отложено осознанно):**
- Файловая гранулярность выборки с картой ресурсов «глоб → тесты»: браться, когда измерено, что пакетная выборка упирается в размер пакета (`demo` 54 с, `editor/ui` 25 с, `integration` 24 с), а не в широкие ворота.
- Project references TypeScript (`composite` + `emitDeclarationOnly`) убрали бы саму причину дублирования типизации, но это шаг сборки и артефакты там, где пакеты резолвятся исходником; параллельный раннер берёт большую часть выигрыша без этой цены.
- Кэш задач (turbo/nx): входы всё равно объявляются руками — та же карта, но с вендором и оркестратором сборки; цифры его не окупают.
- Гейт фичевых веток: сегодня их pre-push не проверяет ничего; подключать ли туда `check:impact` — отдельное решение владельца, этот change хук не трогает.
