# Design: gate-impact-mapping

## Context

Мотивация и замеры — `proposal.md` (Why, Notes). Что есть и что ограничивает подход:

- Гейт — `npm run check` = `lint:all && spec-graph check && test`, где `lint:all` = `typecheck && lint && lint:dead && lint:dup && lint:arch`; `typecheck` и `test` — `npm run … --workspaces`, то есть пятнадцать последовательных процессов каждый. Охраняет `main` клиентский `scripts/git-hooks/pre-push`. Спеки у гейта нет — только описание в CLAUDE.md.
- Пакеты резолвят друг друга исходником (`"main": "./src/index.ts"`, ни одного `composite`/`references`), поэтому `tsc --noEmit` каждого пакета типизирует исходники зависимостей заново, а типизированный eslint через `projectService` строит те же программы третий раз. Один `tsc` пакета — 5,8–10,4 с; все пятнадцать — 93 с последовательно, 40 с по четыре параллельно (замерено).
- vitest: пакеты гоняют `vitest run` без конфига; корневой конфиг покрытия носит неканоническое имя `vitest.coverage.config.ts` намеренно — корневой `vitest.config.*` vitest нашёл бы вверх по дереву из любого пакета и перехватил бы попакетные прогоны. Он перечисляет 14 проектов без `desktop/shell-ts` (контейнер вне охвата покрытия, DSK-6), тогда как `npm test --workspaces` юнит-тесты десктопа гоняет.
- Рёбра, невидимые графу модулей: 73 тестовых файла читают с диска, 68 спавнят процессы. Литералы путей чужих деревьев в строках кода (не в комментариях) тестов и бинов: `engine/integration-ts` → `editor/core-ts`, `editor/ui-ts`, `engine/core-ts`, `game/demo-ts`, `tools/blender-ts` (boundary-тесты сканируют дерево); `desktop/shell-ts` → `editor/ui-ts`, `game/demo-ts`, `game/server-agent-ts`, `game/server-manager-ts` (профили приложений проверяют пути бандлов и бинов — при нулевых зависимостях в манифесте); `game/server-agent-ts` → `game/demo-ts`; `engine/core-ts` → `engine/tests` (широкие ворота); `editor/ui-ts` → `engine/core-ts` (объявленная зависимость).
- Готовая машинерия: `engine/tests/guard/scanner.ts` — обход исходников через TypeScript Compiler API, где строки и комментарии различимы (CLI-8); `scripts/spec-graph.mjs` — stateless-CLI без кэша с экспортами для тестов; `engine/integration-ts/test/specGraph.test.ts` — образец теста для CLI из `scripts/`.
- Профиль правок: `engine/core-ts` — самый правимый пакет и основание графа (его правка тянет всё при любой гранулярности); 24 % коммитов без слияний — только документы.

## Goals / Non-Goals

**Goals:**

- Вердикт `npm run check` не меняется ни на одну находку; меняется расписание — и это доказуемо (CLI-13: стадии не общаются через ФС).
- Выборочный прогон, который не может пропустить регресс молча: пакетная гранулярность, широкие ворота, fail-closed, сторож полноты карты в обычном прогоне тестов.
- Объяснимость: каждый выбранный пакет назван вместе с правилом, его выбравшим.
- Стоимость гейта — команда с секундами по стадиям.

**Non-Goals:**

- Файловая гранулярность выборки и карта ресурсов «глоб → тесты» (отложено, proposal Notes).
- Project references и любой шаг сборки; кэш задач (turbo/nx); `--cache` eslint в гейте.
- Гейт фичевых веток — pre-push не трогается ни в какую сторону.
- Правка любого существующего теста: тесты — потребители выборки, не её часть.

## Decisions

**D1. Параллельный typecheck — свой раннер, не project references.** `scripts/typecheck.mjs` читает `workspaces` корневого манифеста, спавнит `tsc --noEmit` в каждом пакете с параллельностью `--jobs` (по умолчанию — число ядер), печатает вывод с префиксом пакета, возвращает ненулевой код, если красен хоть один. `npm run typecheck` переключается на него; `npm run typecheck -w <pkg>` работает как прежде. Раннер принимает список пакетов — им же пользуется выборка (D3). Альтернатива `tsc -b` с `composite`/`emitDeclarationOnly` убрала бы дублирование в корне, но добавила бы шаг сборки и `.d.ts`-артефакты туда, где пакеты резолвятся исходником, — цена выше выигрыша над 40 с. Лицензия на параллельность — инвариант CLI-13: типизация ничего не пишет.

**D2. Один пул vitest — общий список проектов, неканонические имена.** `vitest.projects.ts` экспортирует список пятнадцати проектов (включая `desktop/shell-ts`: его юнит-тесты гейт гоняет и сегодня). `vitest.gate.config.ts` = `projects` из этого списка; `npm test` → `vitest run --config vitest.gate.config.ts`. `vitest.coverage.config.ts` берёт тот же список без десктопа плюс `coverage` — охват отчёта не меняется. Имя `gate` неканоническое по той же причине, что `coverage`. Попакетный `npm test -w <pkg>` не меняется: разработчик и агент гоняют пакет как раньше. Выигрыш ограничен: единый пул даёт 180 с против 215 с — transform и import модулей насыщают четыре ядра, и это ровно то, что выборка режет дальше. Изоляция: `projects` даёт каждому проекту свой корень, 320 файлов в одном пуле зелёные (замерено); десктоп подтверждается при реализации.

**D3. Выборка — stateless-скрипт по образцу spec-graph, карта — его данные.** `scripts/impact.mjs`:

- *База и дифф.* `--base <ref>`, по умолчанию `merge-base(HEAD, origin/main)` (без `origin/main` — `main`; не разрешается — предупреждение и полный гейт). Дифф = изменённые от базы ∪ staged ∪ unstaged ∪ untracked (`git status --porcelain`): рабочее дерево проверяется таким, каким его видит разработчик, а не каким закоммитил.
- *Классификация путей — правила по порядку, первое подходящее:* (1) широкие ворота → `full`; (2) документы (`openspec/**`, `docs/**`, `**/*.md`) → `docs`; (3) путь внутри workspace-пакета → `pkg:<name>`; (4) ничего не подошло → `full`. Итог диффа — `full`, если хоть один путь дал `full`; иначе объединение пакетов, а `docs` без пакетов — документный план.
- *Замыкание.* Обратные зависимости считаются из манифестов workspace (`@fluxus/*` в `dependencies`/`devDependencies`/`peerDependencies`) — не переписываются руками, новое ребро манифеста попадает в замыкание само. К ним — таблица `TEST_EDGES` («читающий ← читаемые»): `desktop/shell-ts ← editor/ui-ts, game/demo-ts, game/server-agent-ts, game/server-manager-ts`; `game/server-agent-ts ← game/demo-ts`. `engine/integration-ts` — в любой непустой выборке кода (CLI-9, boundary-тесты). Пакет с обратным замыканием «все» (сегодня `engine/core-ts`) — это не особый случай, а результат: выборка совпадёт с полным гейтом, и `--explain` это покажет.
- *План и исполнение.* План — `{typecheck: [pkgs], lint: [dirs], test: [projects], global: true|false, docs: true|false}`. Исполнение: `scripts/typecheck.mjs <pkgs>`; `eslint <dirs> --max-warnings 0` (типизированные правила берут программу из tsconfig пакета — ограничение по каталогам не отключает типы); `vitest run --config vitest.gate.config.ts --project <name>…`; `knip`, `jscpd`, `depcruise`, `spec-graph check` — целиком всегда; документный план — `spec-graph check` + `--project @fluxus/integration` с фильтром `specGraph`. Флаги: `--dry-run` (план JSON, без запуска), `--explain` (путь → правило, пакет → кем выбран), `--full` (принудительно полный план), `--timings` (секунды по стадиям). `npm run check:impact` = `node scripts/impact.mjs`; `npm run check:timings` = `node scripts/impact.mjs --full --timings`. `npm run check` остаётся той же npm-цепочкой, что сейчас, — главные ворота не прячутся за скриптом.
- Альтернатива «`vitest --changed`» отклонена замером (proposal Notes): граф модулей не видит `fs` и спавн. Альтернатива «замыкание только по манифестам» отклонена тем же замером: у `desktop/shell-ts` ноль зависимостей и четыре читаемых пакета.

**D4. Сторож полноты — в обычном прогоне тестов, по AST.** `engine/integration-ts/test/impactMap.test.ts` (`scripts/impact.mjs` экспортирует карту, `classify` и `closure`, как spec-graph экспортирует `buildModel`):

1. каждый `workspaces`-пакет корневого манифеста известен карте, и каждый отслеживаемый корень дерева (`git ls-files` до первого `/`) подходит под правило;
2. скан строковых литералов в `test/**` и `bin/**` каждого пакета той же машинерией, что guard-сканер CLI-8 (TypeScript Compiler API: `StringLiteral` и `NoSubstitutionTemplateLiteral`, комментарии не видны по построению): литерал, начинающийся с `(../)*(engine|editor|game|tools|desktop)/<имя>` и адресующий другой пакет или дерево, обязан быть покрыт `TEST_EDGES`, широкими воротами или объявленной зависимостью манифеста; иначе — находка с файлом и строкой;
3. точечные исключения с причиной по образцу `GuardException` — для литералов, которые путями не являются (например, ожидаемый текст сообщения).

Переаппроксимация безопасна: лишнее ребро — лишний прогон, а не пропуск. `impact.test.ts` рядом — юнит-тесты классификации и замыкания на фикстурных диффах: по сценарию спеки на каждый.

**D5. Ворота `main` не трогаются, выборка встраивается в цикл.** `scripts/git-hooks/pre-push` — без диффа. `.claude/agents/implementer.md` шаг 7: «targeted package tests» → `npm run check:impact`, затем полный `npm run check` как и сейчас; `reviewer.md` — `check:impact` как способ подтвердить находку. CLAUDE.md — команды и одна фраза: выборка не ворота `main`. Вывод команды сам называет себя выборочным прогоном.

**D6. Стоимость стадий — тот же скрипт, флаг `--timings`.** Ортогональный флаг исполнения плана: на любом плане печатает секунды по стадиям таблицей. Отдельного скрипта не нужно, а `check:timings` = полный план + флаг даёт ровно тот замер, с которого начался этот change. Ни порогов, ни влияния на код выхода (PERF-5).

## Risks / Trade-offs

- [Память параллельного `tsc`: четыре процесса по ~1–2 ГБ] → `--jobs` с умолчанием по числу ядер; на 15 ГБ замерено без проблем; на слабой машине — `--jobs 2`.
- [Единый пул меняет изоляцию: тест, полагающийся на `cwd` пакета] → `projects` даёт каждому проекту свой `root`; 320 файлов зелёные одним пулом (замерено), десктоп — при реализации; красный тест здесь — дефект теста, а не повод вернуть пятнадцать стартов.
- [Карта устаревает молча] → сторож D4 в `npm run check` плюс fail-closed на неизвестный путь: устаревание либо краснит гейт, либо расширяет выборку до полной.
- [Ложные срабатывания скана литералов: строка, похожая на путь, но не чтение] → переаппроксимация безопасна; точечное исключение с причиной, попадающее в дифф на ревью.
- [`origin/main` не подтянут — база протухла] → предупреждение в выводе; дифф от устаревшей базы шире, не уже (лишние пути, не пропущенные); неразрешимая база — полный гейт.
- [Ложная уверенность от зелёной выборки] → D5: выборка не ворота, вывод называет себя выборочным, pre-push на `main` гонит полный гейт.
- [eslint по каталогам медленнее ожидаемого: `projectService` строит программы зависимостей всё равно] → приемлемо: объём меньше, типизация не теряется; замер в `--timings` покажет, стоит ли ограничивать сильнее.

## Migration Plan

Миграции нет: `npm run check` — та же цепочка команд с тем же вердиктом, `npm test -w <pkg>` и `npm run typecheck -w <pkg>` не меняются. Откат — возврат корневых скриптов к `--workspaces` и удаление `scripts/impact.mjs`, `scripts/typecheck.mjs`, конфигов проектов; ни один тест и эталон от этого не зависит.

## Open Questions

- Подключать ли `npm run check:impact` к pre-push фичевых веток (сегодня там нет проверок вовсе)? Решение владельца после того, как выборка поживёт во внутреннем цикле; на спеки, подход и задачи не влияет — хук этот change не трогает.
