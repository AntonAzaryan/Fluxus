## 2. Сервер: эпоха и рассылка

- [x] 2.1 `engine/net-ts/src/server/matchServer.ts`: пара `(эпоха, тик)` последнего известного состояния — тик обновляется на каждом исполненном тике и на каждом восстановлении, а рассылки суть сэмплы этой последовательности; увеличение эпохи ровно там, где формируется рассылка, по правилу «тик меньше предыдущего» (NTR-16) — одно место, а не наблюдение за переходами WSM
- [x] 2.2 Рассылка авторитетного состояния по факту восстановления во время `Rewinding` (мимо расписания `snapshotRate`), с персональной фильтрацией по видимости целевого тика (NTR-9, REW-11)
- [x] 2.3 Штамповка эпохи в `Snapshot` каждому клиенту
- [ ] 2.4 Оттуда же — штамповка эпохи в `Events` (NTR-15), если поток событий уже есть: эпоха выводится в одном месте, и все исходящие сообщения матча берут её из него, а не считают заново

## 3. Сервер: приём ввода

- [x] 3.1 Проверка эпохи входящего `Input`: расхождение — отброс и счётчик вышедших за окно (NTR-11), нового счётчика не заводить
- [x] 3.2 Сброс накопленного неприменённого ввода всех слотов при смене эпохи
- [x] 3.3 Верхняя граница окна: `tick > currentTick + inputWindow` — отброс и тот же счётчик; проверить, что буфер неприменённого ввода на слот ограничен конфигом
- [x] 3.4 Нижняя граница: тик, уже исполненный в текущей эпохе, — отброс и счётчик опозданий (обоснование переформулировано, правило прежнее)
- [x] 3.5 Дедуп «первый выигрывает» по паре (слот, тик) в пределах эпохи; отброшенный повтор молча и без счётчиков
- [x] 3.6 Predicted-фрейм после смены эпохи повторяет фрейм, применённый на тике восстановления, а не последний полученный сервером

- [x] 4.2 Матч без перемотки даёт ровно один сегмент; проверить, что существующая запись и её потребители не изменились
