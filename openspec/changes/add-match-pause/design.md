# design: пауза матча в духе Dota

## Context

Мотивация — proposal.md, нормы — дельты specs/ (NTR-4, новое NTR-20, новое HUD-9). Текущее состояние:

- Ядро уже умеет заморозку: WSM-1/WSM-2 (`Running ↔ Paused`), в `Paused` живых тиков нет (REW-4). `MatchServer` пользуется этим для машины перемотки (`pause()` → `beginRewind()` → … → `resume()`, REW-12/REW-13).
- Реконнект и заместитель в main (NTR-17/NTR-18, BOT-14); политика разрыва стенда — `--on-disconnect bot|hold`.
- Протокол: закрытый набор NTR-4, сериализация обеих форм (`SER-3`), сообщения в `engine/net-ts/src/protocol/messages.ts`.
- Клиент одноразовый (`matchClient.ts`), HUD — наблюдатель доставленного состояния (HUD-1), пауза как понятие в канале оболочки отсутствует.

## Goals / Non-Goals

**Goals:**

- Пауза целиком в сетевом слое и выше: ядро (`engine/core-ts`) не меняется ни строкой.
- Один механизм на три источника: игрок (`PauseRequest`), политика стенда (авто-пауза при разрыве), админ (`server-control` SRV-5).
- Правила паузы — данные документа матча; в сервере ни одной балансной константы.

**Non-Goals:**

- Пауза локального одиночного режима (worker-шелл без сервера) — отдельная, куда более простая задача; здесь не решается.
- Догонка пропущенного после возобновления (слоу-мо, реплей паузы) — состояние абсолютно, матч продолжается с замороженного тика.
- Голосование за паузу и прочие командные ритуалы — выражаются политикой позже, механизм их не знает.

## Decisions

**D1. Пауза — состояние хоста матча поверх существующего WSM, ядро нетронуто.** `MatchServer` получает понятие «пауза матча»: причина (`match-pause`) хранится рядом с WSM-состоянием, и хост различает свою заморозку и служебный `Paused` машины перемотки. Вход — тот же `pause()` ядра, что у перемотки; выход — `resume()` по истечении отсчёта. Альтернатива — четвёртое состояние WSM в ядре — отвергнута: ядру нечего делать по-новому (не тикать оно уже умеет), а расширение WSM тронуло бы снапшоты и спеку ядра ради знания, которое целиком принадлежит хосту.

**D2. Отсчёт возобновления — wall-clock хоста, доставляемый длительностью.** Тики заморожены, поэтому отсчёт не может быть тиковым. Сервер объявляет `Pause{resuming, ms}` и по своим часам проводит `resume()`; клиенты ведут визуальный отсчёт от доставленной длительности (HUD-9) и не обязаны сходиться миллисекунда в миллисекунду — авторитетен момент фактического возобновления (первый живой снапшот). В запись матча wall-clock не попадает (NTR-8, CLI-11).

**D3. Политика — секция документа матча, решает сервер.** `pause: { budgetPerPlayer, opponentUnpauseAfterMs, resumeCountdownMs, onOwnerDetach }` — раскладку задаёт `matchConfigOf` наравне с `tickRate` (NTR-14 тут ни при чём — на сборку мира политика не влияет, в хеш `worldInit` не входит). Решения «допустить запрос» принимает сервер по этим данным: бюджеты и права — его учёт вне мира. Альтернатива — решает стенд-обвязка — отвергнута: запрос приходит игровым протоколом прямо в сервер, и выносить учёт наружу значило бы гонять каждый `PauseRequest` через колбэк.

**D4. Отказ запроса — адресный `Pause` с причиной, не `Reject`.** `Reject` в этом протоколе рвёт соединение (NTR-4/NTR-5) — для законного «нельзя сейчас» это неприемлемо. Ответ тем же типом `Pause` с неизменённым состоянием и полем причины сохраняет набор закрытым и даёт HUD что показать (HUD-9).

**D5. Ввод в заморозке отбрасывается на сервере молча и без штрафа.** Клиент продолжает слать `Input` по своему темпу (его останавливать необязательно — меньше ветвлений в клиенте); сервер в паузе не учитывает такие фреймы ни в применённых, ни в опоздавших (NTR-11 не искажается паузой). Окно приёма продолжается от возобновления; оценка тика клиента чинится первым живым снапшотом штатно.

**D6. Авто-пауза при разрыве — расширение политики стенда.** Существующий наблюдатель отвязки (реконнект-обвязка стенда, D7 change'а `add-player-reconnect`) получает третий вариант поведения: `--on-disconnect pause` (и поле политики в документе матча) — вызов серверного API паузы вместо/до посадки заместителя. Комбинация «pause затем bot по таймауту» — тоже политика стенда, механизм её не знает.

**D7. Доставка состояния паузы клиенту — поле канала оболочки.** `matchClient` принимает `Pause` и кладёт состояние паузы в плоскую форму канала (SHELL-2, сторона воркера); HUD-виджет читает его как любое другое доставленное поле (HUD-1). Раскладка канала — внутренность оболочки, спеки `client-shell` не меняются (тот же класс изменений, что «поле, нужное HUD, добавляется в плоскую форму»).

**D8. Реконнект в паузу.** Хендшейк NTR-17 не зависит от WSM-состояния; после `Start` вернувшемуся шлётся текущий (замороженный) снапшот и `Pause` с текущим состоянием — порядок фиксирован, чтобы HUD не мигал «боем» до прихода паузы. Заместитель, севший в паузу, получает то же самое.

**D9. Боты — без спец-логики, закреплено тестом.** Бот — обычный клиент: в паузе ему не приходят живые снапшоты, его `Input` отбрасывается (D5). `Pause` бот разбирает и игнорирует. Тест фиксирует, что мозг не зацикливается и не копит очередь на длинной паузе.

## Risks / Trade-offs

- [Спам `PauseRequest` дёргает рассылку адресных отказов] → отказ шлётся только запросившему; частота запросов на соединение ограничивается тем же порогом, что и прочий входящий трафик (граница входа, security baseline исследования).
- [Пауза на неопределённо долго вешает матч и слоты стенда] → политика демо задаёт максимальную длительность одной паузы (по её истечении сервер сам объявляет возобновление) — число в документе матча, не в сервере; порог молчания (NTR-6) в заморозке не тикает, иначе длинная пауза убивала бы матч.
- [Два источника «Paused» (матч и перемотка) — риск перепутать в хосте] → причина хранится одним полем хоста с исчерпывающим перечнем; тесты на оба перекрёстных случая (NTR-20, сценарий «Пауза во время перемотки»).
- [Клиентские отсчёты разъезжаются с сервером на джиттере] → авторитетен факт возобновления (первый живой снапшот); визуальный отсчёт — ориентир, HUD-9 обязывает его сходиться к доставляемым обновлениям.
- [BREAKING набора сообщений: старые клиенты не войдут в новый матч] → штатно по NET-16: смена набора — смена сборки, несовпадение называется на хендшейке (NTR-5).

## Migration Plan

Изменение протокола — BREAKING по построению (NTR-4), мигрируется сменой сборки: старые записи матчей остаются валидными (лог паузы не знает), golden-эталоны не двигаются. Правки `add-server-manager` (SRV-5/MGR-3 — операции паузы) идут в его собственных дельтах; реализация админ-паузы зависит от NTR-20, порядок реализации — сначала этот change, затем админ-операции.
