# Proposal: presentation-scene-layer

## Why

По ED-19 decorations существуют только в presentation-слое: парный к сцене документ расстановки, не входящий в `worldInit`, снапшоты и сетевой трафик. Обязанность редактора вести слой нормирована (`editor` ED-16, ED-19), формата документа нет. Целевая модель — разделение Warcraft-типа: decorations — инструмент левел-дизайна без геймплейного влияния, props — сим-сущности арены (разрушаемые объекты), уже полностью выраженные существующими механизмами (prefab + запись манифеста + SER-8).

## What Changes

- **Типы декораций — секция манифеста визуалов** (`assets` ASSET-6): таблица «тип декорации → модель, скины, параметры наклона» по образцу секции сущностей. Запись расстановки ссылается на тип по ключу — настройки визуала не дублируются на каждую копию.
- **Парный presentation-документ сцены** (`assets` ASSET-9): расстановка decorations — упорядоченный список записей «ключ типа + позиция/поворот/масштаб + необязательные скин/клип», каждая запись с устойчивой идентичностью размещения (ключ инстанса, REND-11). Место в дереве — presentation-поддерево: `visuals/scenes/<имя>.decorations.json`, привязка к сим-сцене по имени; конфиг сцены на документ MUST NOT ссылаться (направление ссылок ASSET-6/CONT-2). Загрузка модулем ассетов через реестр загрузчиков, по образцу карты кривизны ASSET-7: типизированный handle, «правка не меняет `worldInit`, снапшоты и golden».
- **Слой декораций рендера** (`rendering` REND-14; REND-12 и REND-13 уже заняты): decorations — статичный слой сцены, наполняемый документом при инициализации подсистемы (как террейн-грид и карта кривизны), а **не** третий продюсер presentation-состояния. Взаимоисключение продюсеров REND-11 не трогаем — оно про сим-объекты. Слой один для игрового режима и редактора (ED-15: автору то же изображение, что игроку); в редакторе он декларативно обновляется правкой документа, в игре — read-only. Посадка по нормали (REND-10) и кривизна (REND-9) применяются per-type через параметры записи манифеста.
- **Перечисление presentation-контента** (`game-content` CONT-2): парный документ сцены добавляется в состав presentation-поддерева наравне с манифестом, моделями и текстурами.
- **Props — без новых требований**: граница и авторинг нормированы ED-19; разрушаемость — политика контента (JSON-системы), не спеки.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `assets`: секция типов декораций в манифесте (правка ASSET-6) и парный документ сцены — ASSET-9.
- `rendering`: слой декораций — REND-14; при необходимости — согласование формулировки REND-11 (упоминание парного документа среди входов документного источника), чтобы у decorations был один путь в обоих режимах.
- `game-content`: пополнение перечисления presentation-контента в CONT-2.

## Impact

Пакеты `assets-ts`, `render-ts`; `content/visuals/`. Симуляция не затрагивается; конфиг сцены не меняется. Инвариант — тестом: сцена с decorations и без даёт байт-в-байт одинаковые golden и hash `worldInit`.

## Notes

Решено (2026-08-08): место документа — `visuals/scenes/`; запись ссылается на тип из манифеста; в игре decorations — статичный слой, REND-11 не расширяется; props без новых требований; посадка REND-10 — per-type из манифеста; golden-инвариант обязателен.

Решить в design: точный формат ключа идентичности размещения; как слой получает документ (параметр инициализации подсистемы vs handle ассета внутри); нужна ли правка формулировки REND-11; поведение при неизвестном ключе типа (ожидаемо: предупреждение и пропуск записи, по образцу ASSET-8). Продолжение — `/opsx:continue presentation-scene-layer` (design → specs → tasks). Блокирует реализацию ED-16/ED-19 в части decorations; спеку `editor` не блокирует.
