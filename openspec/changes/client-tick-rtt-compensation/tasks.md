## 1. Эмулятор канала и воспроизведение бага

- [x] 1.1 Эмулятор канала в виртуальном времени (design D6): планировщик для `loopbackPair` с очередью «доставить на шаге N», шаг двигает тест-харнесс тем же `step()`, что и матч; профиль канала — данные (задержка в тиках, джиттер, потери), джиттер и потери — от сидированного xorshift ядра; проверка — два прогона одного профиля дают побитово одинаковую последовательность доставок.
- [x] 1.2 Красный тест-воспроизведение бага туннеля: профиль «туннель» (круг заметно больше `inputDelay` тиков), константная разметка `inputDelay: 2` — слот живёт на predicted, `applied` не растёт; тест фиксирует сегодняшнее поведение и перевернётся задачей 2.3.

## 2. Контроллер lead в клиенте

- [x] 2.1 Завести в `MatchClient` состояние `lead` (старт `inputDelay` из `Welcome.pacing`, границы `[inputDelay, inputWindow]`) и разметку `pushInput` через него вместо константы; проверка — существующие тесты клиента зелёные на loopback (lead не растёт без сигнала, разметка совпадает с прежней).
- [x] 2.2 Детектор опоздания по эху `seq` в ТИКОВОЙ шкале (design D1): `behind` = «тик снапшота − тик подтверждённого кадра» по тем тикам серии, которые клиент РАЗМЕТИЛ, допуск серии повторов, срок эха до первого подтверждения при живом канале состояний, нечувствительность к молчанию игрока и редкому вводу, к заморозке, к смене эпохи, к потере снапшотов и к разъехавшимся часам клиента в ОБЕ стороны; проверка — юнит-тест детектора на синтетической последовательности отправок/подтверждений без таймеров плюс матчи с часами клиента быстрее и медленнее серверных.
- [x] 2.3 Контроллер (design D2): подъём на период рассылки по сигналу до потолка (`inputWindow` за вычетом запаса оценки тика), спуск на 1 тик с чистого окна стабильности до `inputDelay`, память о значении, оказавшемся малым, с удвоением окна пробы; проверка — тест 1.2 переворачивается (predicted у слота прекращаются после подъёма), спуск после выправления медленнее подъёма, установившийся режим не отъедает управление пробами; константы контроллера подобраны прогоном профилей эмулятора и зафиксированы в тестах.
- [x] 2.4 Смена эпохи не сбрасывает `lead` (дельта NTR-7); проверка — тест: перемотка посреди адаптированного состояния, `lead` прежний, фреймы новой эпохи успевают.
- [x] 2.5 Снять оба `ponytail` в `advance()`/`resyncTick()` с обоснованием design D5 (компенсация живёт в разметке); проверка — `grep ponytail engine/net-ts/src/client/matchClient.ts` пуст по этим двум местам.

## 5. Интеграционная проверка

- [x] 5.1 Интеграционный тест net-ts: матч на эмуляторе канала с профилями «LAN» (круг ≤ `inputDelay`, lead не растёт, поведение прежнее) и «туннель» с джиттером — `applied` растёт, доля `predicted` в установившемся режиме падает, `lead` держится в одном тике; прогоны идут по несколько окон стабильности, иначе установившийся режим не наблюдается вовсе. Рядом — заморозка матча, удержанный скраб перемотки, часы клиента быстрее и медленнее серверных, рвущийся и оборванный downlink при живом uplink, перезапуск наблюдения на смене эпохи и длинный канал при ШТАТНОМ пороге молчания (NTR-6) вместе с границей, за которой окно шире требует и порога шире. Golden-базлайны не трогаются (канонический лог меняется только составом фреймов конкретного прогона, записанные матчи перегенерации не требуют — проверить `npm run golden` дифом, диф пустой).
- [x] 5.2 `npm run check` на node 22 (`.nvmrc`) — целиком зелёный; на node 24.19 известен пре-существующий краш CLI-тестов `journal.mjs` (libuv assert, вне этого изменения).
- [ ] 5.3 Ручная проверка через `npm run demo:tunnel` вдвоём: второй игрок управляем, `inputLead` у него поднялся и стабилен.
