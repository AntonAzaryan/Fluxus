## Context

Мотивация — proposal.md «Why»; нормы — дельта `specs/data-driven-systems/spec.md` (ACT-4, ACT-5, MODIFIED ACT-1/EXPR-2/EXPR-5/EXPR-8). Существенные для подхода факты реализации:

- Исполнитель действий (`dsl/actions.ts`) передаёт область видимости как plain-объект `vars` и на каждом вложенном теле копирует его спредом (`{ ...vars, [as]: entity }`). Значение привязки — `ExprValue` (number | boolean | Vec2).
- `forEach` материализует результат `ctx.query` (QUERY-3) и обходит его как отдано — в порядке QUERY-2. `withinRadius` читает `POSITION_COMPONENT` тотально (ECS-7).
- Окружение выражений (`dsl/expr.ts`) — срез `SystemContext`: `tick | get | has | isAlive | math | terrain`. `physics` в `SystemContext` опционален (`physics?: PhysicsApi`), сигнатура `raycast(from, to, {mask?, ignore?}) → RaycastHit | null`, `RaycastHit = { entity?, point }`.
- Валидация дерева на регистрации (SYS-3, `evaluatedSystem.ts`) уже знает набор действий (`actionNames`, `requiredArgs`), связанность переменных и арности операторов.
- Схемы `engine/schemas/*.json` и каталог блоков редактора порождаются из ядра.

## Goals / Non-Goals

**Goals:**

- Три примитива ровно в той форме, что в дельте спеки; ни одного нового понятия сверх неё.
- Валидация максимума ошибок на регистрации (SYS-3): неизвестные имена, арность, вид связывания для `set` — статически.
- Нулевые аллокации, пропорциональные числу сущностей, сверх уже существующей материализации запроса; никакого нового состояния, переживающего тик.

**Non-Goals:**

- Изменение Query API (`ecs-foundation`) и формы `PhysicsApi` (`physics`) — примитивы строятся над ними. Единственная правка `physics` — нормирование краевого случая, который таблица EXPR-8 ей и адресует: маска луча необязательна, и её отсутствие означает пересечение по всем коллайдерам (дельта PHYS-6).
- Кэширование повторных лучей внутри выражения: `raycastHit` + `raycastEntity` по одному отрезку — два вызова `physics.raycast`. Выражения чисты, детерминизм не страдает; стоимость — на авторе контента, оптимизация — по профилю (ponytail-дисциплина).
- Компоненты HP/урона, пайплайн урона, пакеты переиспользуемых систем — контент и отдельные изменения.

## Decisions

**D1. Свёртка = изменяемый `let` + действие `set`, а не отдельное действие `fold`.**
EXPR-5 уже обещает «накопление в `let`»; `set` закрывает обещание минимальной формой и покрывает не только свёртку (условное накопление, argmin с двумя привязками, флаг «нашёлся хоть один»). `fold { query, init, step }` был бы вторым механизмом итерации рядом с `forEach` — ровно то, от чего ACT-1 отказывается в вопросе подписки на события. Альтернатива «читать назад из Command Buffer» отвергнута: ломает CMD-5 (мир до flush не меняется) и превращает буфер в side-channel.

**D2. Представление изменяемой привязки — ячейка, а не значение в объекте scope.**
Сегодняшний спред `{ ...vars }` копирует значения: присваивание из вложенного тела не было бы видно снаружи. Привязки `let` заворачиваются в ячейку (`{ value: ExprValue }`), общую для всех вложенных областей; `var` разворачивает ячейку при чтении, `set` пишет в неё. Привязки `as` остаются голыми значениями — это и есть механическая форма запрета `set` на них (плюс статическая проверка на регистрации: валидатор уже знает, каким действием связано каждое имя). Альтернатива — единый мутируемый объект scope без копий — отвергнута: сломала бы затенение (сценарий ACT-1 «затенение переменной во вложенном теле»).

**D3. `nearestTo`/`limit` — аргументы `forEach`, сортировка поверх материализованного результата.**
Query API не трогаем: упорядочивание — потребность DSL-итерации, а не запросов ядра (нативные системы сортируют сами, как `VisibilitySystem`). Реализация: материализованный массив копируется в переиспользуемый буфер исполнителя (аллокация не per-tick; буфер — по одному на уровень вложенности `forEach`, потому что инстанса у исполнителя нет, а внутренний обход не должен портить внешний), сортируется вставками по ключу `(distSq, rawIndex)`. Вставками, а не `Array.prototype.sort`: стабильность и порядок сравнений заданы алгоритмом, а не реализацией JS-движка — то, чего требует нормативный тай-брейк для парности с Rust-портом. `distSq` считается той же функцией `distSqLe`-семейства, что `withinRadius` (одна арифметика — одно требование QUERY-1): сравнение точное, 64-битное, поэтому предела дальности у порядка нет, а приближение Q16.16 (`mul` над смещениями) отвергнуто — оно заворачивается за ~181 единицей и схлопывает различимые расстояния в тай-брейк.

**D4. Raycast — три оператора-выражения, а не действие со связыванием.**
Прецедент — `hasFloorAt`: пространственный запрос открыт выражению, семантика — у владеющей capability. Действие `raycast { as, do }` со ссылкой-hit и оператором `hitField` (по образцу `forEachEvent`/`eventField`) дало бы один луч на три чтения, но вводит второй reference-тип и действие ради чтения — тяжелее языка, который расширяем таблицей. Результаты разложены по типам EXPR-7: `bool` / `number` (entity, `-1` как «ссылки нет» по ECS-6) / `vec2` (точка; без попадания — `to`, тотальность вместо сигнальных значений). Окружение выражений получает `physics?`; отсутствие — ошибка вычисления по образцу `hasFloorAt` без террейна.

**D5. Арность «3 или 4» с необязательным `mask` последним.**
`ignore` обязателен: PHYS-6 требует, чтобы исключение источника было выразимо в вызове, а типичный луч геймплея идёт от сущности. «Не живая сущность — не исключает никого» делает аргумент тотальным: луч «из точки» пишется с `-1`. `mask` — литеральное имя (как имена компонентов), потому что состав тегов известен статически, а вычисляемый тег сделал бы фильтр зависимым от значения — незачем.

**D6. Голдены и схемы.**
Существующие эталоны не трогаются (старые сцены не используют новых имён). Новые: golden-сценарии на свёртку (сумма по радиусу), `nearestTo` с равноудалёнными сущностями (тай-брейк наблюдаем в эталоне), `limit`, каждый raycast-оператор с попаданием в сущность/статику/пустоту. `npm run schemas` регенерирует `engine/schemas`; каталог блоков редактора подхватывает новые имена из ядра, добавить строки-подсказки ru/en (ED-27/ED-28).

## Risks / Trade-offs

- [Сортировка в `forEach` на большой выборке — O(n²) вставками, и каждое сравнение — точная 64-битная арифметика квадратов] → арены малы (десятки сущностей), а вставки на почти отсортированном по rawIndex входе дёшевы; переход на детерминированный merge sort или на предпосчитанные ключи — по профилю, не заранее.
- [Мутируемые привязки открывают «состояние в скоупе» — соблазн имитировать компонент] → нормировано в ACT-4: привязка не переживает тело `let`, снапшот её не видит; ревью контента ловит паттерн «let на всю систему как хранилище» — он и так бесполезен, скоуп умирает с тиком.
- [Три raycast-оператора по одному отрезку = до трёх лучей] → осознанный trade-off D4; профилировать на реальной сцене, кэш — только если покажет себя (ponytail).
- [Рост нормативной таблицы EXPR-8 увеличивает контракт Rust-порта] → краевые случаи выписаны в дельте полностью (нулевой луч, статика, «ссылки нет», `to` без попадания), парность проверяется теми же golden-сценариями.
- [`set` в глубоко вложенных телах усложняет статическую проверку связанности] → валидатор уже ведёт множество связанных имён по дереву; добавляется лишь вид связывания (let/as) — расширение существующего прохода, не новый.
