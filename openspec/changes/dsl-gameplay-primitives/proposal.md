## Why

Первые же игровые механики поверх ядра (HP, пайплайн урона, таргетинг) упираются в три отсутствующих примитива DSL, и ни один не выражается контентом:

1. **Свёртки нет.** EXPR-5 обещает агрегацию «через action `forEach` с накоплением в `let`», но накопления в языке не существует: `bindings` у `let` вычисляются один раз на входе, действия переприсваивания нет, а `modifyComponent` внутри тика не читается назад (CMD-1, CMD-5). Сумма урона по площади, счёт врагов рядом, argmin — не записываются вообще.
2. **Выборки «ближайший / N ближайших» нет.** `forEach` + `withinRadius` даёт множество в порядке raw-индекса (QUERY-2) без упорядочивания по расстоянию; любой таргетинг сводится к argmin и упирается в отсутствие свёртки, а argmin через свёртку — ещё и в отсутствие детерминированного тай-брейка как нормы.
3. **Raycast недоступен выражениям.** `PhysicsApi` даёт детерминированный raycast (PHYS-6, PHYS-7), нативная `VisibilitySystem` им пользуется, но в таблице операторов (EXPR-8) из пространственных запросов есть только `hasFloorAt`. LoS-проверка перед уроном, hitscan, конус ближней атаки из JSON не пишутся.

Это блокеры этапа «геймплейные механики поверх ядра»: без них политика урона и таргетинга не выражается данными и просочилась бы в нативные системы — против mechanism-vs-policy.

## What Changes

- **Свёртка (аккумулятор) в Action DSL** — механизм накопления скалярного/векторного значения по итерации `forEach` / `forEachEvent`: изменяемая привязка `let` и действие присваивания (точная форма — в design.md). Закрывает сценарий EXPR-5 реальным механизмом.
- **Детерминированная выборка ближайших** — упорядочивание результата запроса `forEach` по расстоянию с нормативным тай-брейком (порядок QUERY-2 как вторичный ключ) и ограничением количества; сравнение по квадратам расстояний, как в QUERY-1.
- **Raycast в языке выражений** — оператор(ы) таблицы EXPR-8 поверх существующего `PhysicsApi` (PHYS-6, PHYS-7): проверка LoS и/или первая перекрытая сущность; форма результата ограничена моделью типов EXPR-7 (`number`/`bool`/`vec2`).
- Обновление таблицы EXPR-8, набора действий ACT-1 и, где нужно, схем/каталогов, порождаемых из ядра (`npm run schemas`).

Вне скоупа: фазы/приоритеты систем — уже нормированы (SYS-2, DET-3, DET-9); overlap-запрос — уже есть (`withinRadius`, QUERY-1); пакеты переиспользуемых систем между сценами — отдельное изменение.

## Capabilities

### New Capabilities

Нет: все три примитива — расширение существующего data-driven-слоя.

### Modified Capabilities

- `data-driven-systems`: ACT-1 — новые действия (аккумулятор/присваивание, упорядоченная выборка в `forEach`); EXPR-8 — новые строки таблицы операторов (raycast); EXPR-5 — сценарий агрегации ссылается на реальный механизм. Query API (`ecs-foundation` QUERY-1..3) и `PhysicsApi` (`physics` PHYS-6, PHYS-7) не меняются — примитивы строятся над ними.

## Impact

- `engine/core-ts/src/dsl/actions.ts` — новые действия, `requiredArgs`, валидация на регистрации (SYS-3).
- `engine/core-ts/src/dsl/expr.ts` — операторы raycast; доступ к `PhysicsApi` из окружения выражений (расширение среды `EvalEnv`).
- `engine/core-ts/src/dsl/schemas.ts`, `engine/schemas/*.json` — регенерация (`npm run schemas`).
- `editor/core-ts` — каталог блоков DSL производен от каталогов ядра, подхватит новые имена; проверить строки-подсказки (ED-27/ED-28).
- Golden-эталоны: существующие не меняются (поведение старых сцен не затронуто); новые примитивы получают свои сценарии в `engine/tests/golden/`.
- Rust-порт (этап 20): новые строки EXPR-8 и семантика действий — часть контракта побитовой парности, поэтому краевое поведение нормируется в спеке, не в коде.
