# Четыре нормы ECS и DSL, читающиеся против работающего движка

## Why

Валидация спек против кода (2026-09-01, `docs/reviews/spec-validation-2026-09-01/02-ecs-dsl.md`) прошла
`ecs-foundation` и `data-driven-systems` целиком. Кода-дефектов она не нашла: движок делает правильное.
Нашла она четыре места, где нормативный текст описывает не тот движок, который работает, — и каждое из них
читатель второй реализации ядра выполнил бы иначе, чем выполнено здесь.

- **ECS-5 требует того, что соседняя спека запрещает следующей же строкой.** ECS-5: «Все JSON-конфиги SHALL
  валидироваться JSON Schema на загрузке». SER-5: «Точкой контроля в ядре JSON Schema при этом MUST NOT
  быть, и ядро MUST NOT зависеть от валидатора JSON Schema. Контроль выполняет загрузчик, и он строго
  строже». Реализовано второе — сторонних библиотек у `engine/core-ts` нет ни одной, а строгость несут
  проверки загрузчика (`ecs/worldSchema.ts`, `dsl/evaluatedSystem.ts`, `sim/scenario.ts`). На один вопрос
  «чем проверяются конфиги» спека отвечает двумя взаимоисключающими способами.
- **QUERY-1 обещает терпимость, которой у систем-данных нет, и обосновывает `any` неверно.** Норма
  «неизвестное имя компонента в запросе MUST NOT быть ошибкой прогона» выполнена ядром буквально, но
  JSON-система с таким именем до запроса не доживает: её отвергает регистрация (SYS-3). Обещание «одна и та
  же система работает на сцене, где её опционального компонента нет» поэтому действует только для систем,
  написанных на TypeScript. Отдельно: обоснование пустого результата у `any` («требования, которое не может
  выполнить ни одна сущность, достаточно, чтобы выборка была пустой») для дизъюнкции неверно, и вторая
  реализация, читающая обоснование, а не букву, разошлась бы с первой.
- **SYS-9 объявляет перечень жёстких ошибок закрытым, а он неполон.** Ядро обрывает тик как минимум ещё в
  пяти ситуациях, которых в перечне нет, причём каждую требуют другие требования тех же спек: луч в сцене
  без Physics API (EXPR-2), отрицательный `limit` (ACT-5), непредставимое значение поля (ECS-3), занятость
  всех слотов источников и нулевой id источника (TIME-7), исчерпание ёмкости мира (ID-1). Реализация,
  собравшая поведение строго по перечню, продолжила бы матч там, где мы его обрываем.
- **EXPR-4 нормирует абстракцию, которой нет и которая не нужна.** Интерфейс `ExpressionEvaluator` объявлен
  и рядом лежит его единственный экземпляр, но через него не проходит ничего: исполнитель действий зовёт
  функцию напрямую, `EvaluatedSystem` слова `ExpressionEvaluator` не содержит вовсе — то есть «точки
  абстракции внутри `EvaluatedSystem`», которую называет требование, физически не существует. Вдобавок
  выражения контента вычисляет и нативная платформа способностей, а требование говорит «нативной системе
  она не нужна». Замена, ради которой требование написано (JsonLogic → собственный AST), давно произошла:
  библиотеки в ядре нет, обход AST свой.

## What Changes

- **ECS-5:** нормативная фраза переписана в терминах «загрузчик отвергает». Точка контроля — загрузчик;
  схемы публикуются как контракт и воротами загрузки MUST NOT быть; полное разделение держит SER-5, и
  повторяться здесь запрещено. Сценарий с опечаткой в имени поля остаётся; добавлен сценарий «реализация
  подключает валидатор схем как ворота загрузки».
- **QUERY-1:** обоснование пустого результата у `any` заменено на верное — отбросить невыполнимый вариант
  дизъюнкции нельзя, потому что пустой `any` по правилу выше не сужает выборку вовсе, и фильтр «никто»
  превратился бы в фильтр «все». Терпимость Query API названа нормой ТОТАЛЬНОЙ ОПЕРАЦИИ ядра, а не
  разрешением писать такие имена в тексте системы: имя компонента в запросе JSON-системы отвергает
  регистрация (SYS-3), и это тот же порядок «тотальная операция внизу, строгий загрузчик над ней», что у
  SER-5. Дописано следствие для контента: одна система на двух сценах работает тогда, когда компонент
  объявлен в обеих. Новые сценарии: неизвестное имя в `any`, JSON-система с неизвестным именем в запросе.
- **SYS-9:** перечень класса 3 пополнен пятью пунктами, каждый со ссылкой на требование, которое его
  вводит; пункт об опциональной зависимости сборки назван общим правилом и перечисляет физику наравне с
  террейном и списками источников. Добавлено правило пополнения: требование, вводящее новую ошибку
  вычисления, SHALL вносить её в перечень тем же изменением. Новый сценарий — луч в сцене без физики.
- **EXPR-4:** требование переписано на то, что действительно держит подменяемость и проверяется: вход
  вычисления в ядре ровно один, второй реализации вычисления в ядре нет, и им пользуются одинаково
  исполнитель действий, нативные системы и валидация на регистрации. Точка подмены — модуль вычислителя;
  внедряемый экземпляр отвергнут явно (модульный синглтон запрещён DI-1, поле в контракте границы — правка
  SYS-5 ради подмены, которой в тике никто не делает). Заголовок требования переименован: «Абстракция
  `ExpressionEvaluator`» → «Единственный вход вычисления выражения».
- **Код:** мёртвая абстракция снята — интерфейс `ExpressionEvaluator` и его экземпляр `evaluator` удалены
  из `engine/core-ts/src/dsl/expr.ts` и из публичной поверхности `engine/core-ts/src/index.ts`; на их месте
  комментарий, называющий единственный вход по EXPR-4. Поведение ядра не меняется.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `ecs-foundation`: ECS-5 — загрузчик как точка контроля; QUERY-1 — верное обоснование `any` и граница
  между терпимостью Query API и строгостью регистрации.
- `data-driven-systems`: SYS-9 — полный перечень жёстких ошибок и правило его пополнения; EXPR-4 —
  единственный вход вычисления вместо неиспользуемого интерфейса.

## Impact

- Симуляция не меняется: golden- и cost-эталоны остаются прежними, схемы `engine/schemas/` не
  перегенерируются.
- `engine/core-ts/src/dsl/expr.ts`, `engine/core-ts/src/index.ts` — удаление неиспользуемой абстракции и
  комментарий на её месте.
- Новых номеров требований не заводится: четыре существующих приводятся в соответствие с работающим
  движком.
