# Design: npc-grid-optimization

## Context

Числа «до» (release `NODE_ENV=production`, Node 22, медиана 11–12 прогонов `npc-stress.load.json`, 24 тика, 196 крипов; замерная машина — контейнер сессии):

- Медиана тика: **2.04–2.10 мс** (два независимых стенда замера).
- Self-time профиля (v8 `--cpu-prof`, 120 прогонов): `npc/grid.ts` **27.8%** (`collectCell` 23.4%, `sweepCell` 1.9%, `sweepRing` 0.75%), `distSqCompare`+`distSqLe` **~15.1%**, `lengthOf` **6.5%**. Скан соседей с его арифметикой — **~43–49% тика**.
- Изоляция расхождения (`separationWeight=0` — запросы расхождения глушатся до сетки): тик **1.32 мс** против 2.04 мс, осмотры `npcNeighbors` **3802** против **8960**/тик. Расхождение ≈ **723 мкс/тик (35%)** и ≈ **5160 осмотров/тик (58%)**.
- Осмотры эталона подтверждены: `npc-stress.cost.json` несёт 215042/24 = 8960/тик — замер и гейт видят одну и ту же величину (PERF-3).

Расхождение платят все агенты каждый тик (NPC-6), окно решения каденса (NPC-4) его не амортизирует. Perception-запросы уже амортизированы каденсом решений и вдвое дешевле.

Урок change'а `component-handle-api` соблюдён: профиль снят самостоятельно ДО proposal, гипотеза «что горячее» подтверждена изолирующим прогоном, а не чужими числами.

## Goals / Non-Goals

**Goals:**

- Минус 20–30% медианы тика на `npc-stress` за счёт каденса пересчёта расхождения; ожидание при K=3: ~2/3 × 723 ≈ **−470–490 мкс ≈ −23%** (проверяется замером «после» тем же стендом).
- Детерминизм и перемотка без оговорок: окно пересчёта — функция состояния мира, держимый вектор — снапшотируемое состояние.
- Ноль правок контента: умолчание нормативно, существующие документы поведения не трогаются.

**Non-Goals:**

- Общая сетка на тик, подбор размера ячейки, ленивые строки ассертов — отклонены профилем (D4).
- Ускорение perception-запросов и `distSqCompare` как таковых — отдельная работа, если профиль после этого change'а всё ещё покажет их доминантой.
- Изменение семантики словарей документа, лимитов осмотра и кольцевого порядка NPC-6 — не трогаются.

## Decisions

**D1. Каденс пересчёта расхождения — параметр документа с нормативным умолчанием 3.** Вектор расхождения агента пересчитывается в окне `(tick + slot) % K === 0`, где `slot` — стабильное место агента в обходе выборки (QUERY-2), K — `separationIntervalTicks` документа поведения. Тот же приём, что окно решений (NPC-4, D4 архивного `npc-behavior`): функция состояния мира и только его — ни машины, ни нагрузки, ни «свободного времени». Умолчание 3 — нормативное число требования (паттерн NPC-2): молчание документа обязано значить одно и то же у двух реализаций ядра (CLI-6). Документ, которому нужен потиковый пересчёт (босс, дуэльная арена), называет 1 — валидация принимает K ≥ 1, ноль — находка.

**D2. Держимый вектор — поля компонента агента, не кэш системы.** Между пересчётами применяется последний вектор — значит, он влияет на будущие тики и ЕСТЬ состояние симуляции: перемотка и реплей обязаны возвращать его вместе с миром (SNAP-1, REW-2), иначе прогон с отката разошёлся бы с живым. Поля `sepX`/`sepY` (`fixed`, умолчание 0) живут на `NpcAgent` — компонент есть у каждого агента, префабы сцен не трогаются (новый обязательный компонент потребовал бы правки всех расстановок). Запись — через Command Buffer в окне пересчёта; в самом окне свежий вектор применяется из полей системы (мир до flush команду не видит, CMD-5 — тот же приём, что `stateEnteredTick` решателя). Альтернатива «кэш в полях системы» отклонена: структура платформы вне мира, переживающая тик, — ровно то, что NPC-6 запрещает сетке, и по той же причине (перемотка её не вернёт).

**D3. Пересчёт — исполнение, не решение.** Каденс расхождения НЕ входит в decision-budget и не сдвигает окна решений (NPC-4): это каденс свежести уже принятого решения, как и сам потиковый seek. Сетка движения по-прежнему наполняется каждый тик внутри одного прогона одной системы (NPC-6 в этой части не меняется): в каждом тике есть агенты своего окна, и им нужны соседи по текущему миру.

**D4. Что отклонено профилем и почему — фиксируется, чтобы не перерешивать.**
- *Общая сетка на тик (ленивое наполнение первым потребителем).* Стоимость обоих построений — ~2% тика (`rebuild` восприятия 0.77% self + циклы `add`); выигрыш не окупает правку несущей нормы NPC-6 «наполняется и опрашивается внутри одного прогона одной системы» и семантический риск: популяции сеток разные (восприятие — все сущности со стороной и позицией, движение — живые агенты), а герои двигаются локомоцией МЕЖДУ прогонами двух систем — общая сетка вернула бы ровно тот класс устаревания, от которого NPC-6 и заведён.
- *Подбор размера ячейки.* Меняет состав и порядок осмотренного (лимиты NPC-6 наблюдаемы) — то есть траектории; оценка площадей развёртки для радиусов сцены (расхождение 1.5, чувство 6 при ячейке 2) выигрыша не обещает, профиль подтвердить его не может. Не берём без собственного профиля на реальной плотности.
- *Ленивые строки ассертов `checkBounds`.* Release-профиль их не видит вовсе — выигрыш только debug-сборки, цель change'а release-тик.

## Acceptance criteria

- Замер «до»/«после» одним стендом на одной машине (медиана ≥10 прогонов, release): «после» в пределах −20–30% медианы тика; числа обоих замеров — в отчёт и в сообщение коммита.
- `*.golden.json` — ноль диффа (golden-тесты зелёные БЕЗ регенерации).
- Дифф `npc-stress.cost.json` принят осознанно через `npm run golden:cost` и входит в коммит: `npcNeighbors` падает, `commandsApplied` растёт на записи вектора (~+130/тик при K=3 на 196 агентах).
- Два прогона нагрузки побитово равны (`npcStress.test.ts`); демо-тесты босса зелёные; полный `npm run check` зелёный.

## Risks / Trade-offs

- [Вектор черствеет до K−1 тиков — толпа «дышит» реже] → K=3 при потиковом движении — черствость ≤2 тиков; визуально расхождение — низкочастотная сила, документ с плотной толпой вправе назвать 1–2. Совпавшие агенты (COINCIDENT) держат детерминированное направление по порядку обхода — расходятся за окно, как раньше за тик.
- [Свежепоставленный агент до первого окна идёт без расхождения] → умолчания полей — ноль, до K−1 тиков нулевой вектор; на спавне волны агенты выходят из одной точки с разными slot'ами — окна размазаны, задержка незаметна.
- [Смерть агента сдвигает slot'ы живых → окна пересчёта сдвигаются] → сдвиг детерминирован (функция состояния мира), воспроизводимость не страдает; семантика документа не меняется (NPC-4: каденс влияет только на свежесть).
- [+2 setField на агента в окне — рост flush] → ~+130 команд/тик против ~920 базовых; чистый выигрыш замером «после» это уже учитывает (критерий приёмки).

## Migration Plan

Один шаг: документ (умолчание нормативно) + компонент + окно в `movement.ts` + регенерация схем и cost-эталона. Существующий контент не трогается; откат — revert коммита.

## Open Questions

Нет. Величина K для конкретных сцен — политика контента и тюнится дизайнером после; спека фиксирует только нормативное умолчание.
