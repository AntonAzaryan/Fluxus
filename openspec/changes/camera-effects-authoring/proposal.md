## Why

Второй абзац ED-14 не реализован целиком: редактора таблиц «событие тика → импульсный эффект» и «состояние сущности → длящийся эффект» нет, и завести его сегодня не из чего. ED-14 требует брать набор типов эффектов «из описания, предоставленного кодом камеры, а не из захардкоженного списка» — а кода, который такое описание предоставляет, в репозитории нет: `CameraEffectsDirector` (`engine/render-ts/src/camera/director.ts`) сравнивает `def.effect` с литералами `'shake'` и `'sway'`, а имена и умолчания параметров (`amplitude`, `radius`, `frequency`, `maxOffset`, `maxRoll`, `decay`, `rollAmp`, `yawAmp`, `fovAmp`, `fadeSeconds`) рассыпаны по вызовам `num(def, …, fallback)` в трёх методах. Единственное, что редактор мог бы прочитать машинно, — это исходник диспетчера.

Отсюда обе половины пробела. Со стороны камеры: набор типов существует только как ветвление в коде, поэтому «новый тип эффекта появляется в редакторе сам» невыполнимо в принципе, а добавление типа сегодня правит диспетчер в трёх местах — это же противоречит клаузе CAM-6 «Добавление нового вида эффекта MUST NOT требовать правок режимов и других эффектов». Со стороны редактора: секции нет ни в интерфейсе, ни в слое операций (`assetVisuals.ts` — три операции по записи сущности и ни одной по секции эффектов), а `validateManifest` проверяет секцию только структурно — «`effect` есть и это непустая строка, остальные поля — конечные числа», — то есть ни неизвестный тип, ни параметр вне диапазона, которых ED-14 требует в реальном времени, поймать не может.

Сама секция при этом уже нормативна (ASSET-8), уже есть в формате (`engine/assets-ts/src/manifest.ts`) и уже используется контентом (`content/visuals/manifest.json`, `FireballExploded → shake`) — правится она сегодня только руками в JSON, чего ED-14 не допускает.

## What Changes

- **Код камеры начинает описывать свои типы эффектов машинно.** Появляется описание: для каждого типа — его идентификатор (значение `effect` в записи манифеста), вид (импульсный или длящийся), список параметров с именем, умолчанием и допустимым диапазоном; плюс параметры самой привязки, общие для всех записей вида (`amplitude` и `radius` у импульсных). Описание — тот же источник, из которого слой эффектов строит эффекты по записям манифеста: ветвления по типу в диспетчере не остаётся, второго списка типов не заводится (те же основания, что у `editor` ED-30).
- **Валидация манифеста становится способной проверять секцию по описанию.** Описание передаётся валидации входом: получив его, она различает неизвестный тип и незаявленный параметр (предупреждение — запись переживает код, ASSET-8) и значение вне объявленного диапазона (ошибка на общих основаниях с прочими числовыми полями манифеста). Без описания проверяется только структура — модуль ассетов о типах эффектов не знает и знать не должен.
- **Редактор получает секцию.** Две таблицы строятся из описания, тип выбирается из него же, поля записи — параметры выбранного типа плюс параметры привязки; правка идёт зарегистрированными операциями (ED-29), обратима (ED-18) и исполнима без интерфейса; нарушения подсвечиваются в реальном времени (ED-8) через то же правило `assets.manifest`, которому теперь передаётся описание.
- Диапазоны в описании — границы осмысленности значения (амплитуда неотрицательна, частота положительна), а не окно вкуса: балансное число остаётся политикой манифеста, и код его не сужает.
- Правки спеки `editor` не требуется: ED-14 уже формулирует и требование, и оба сценария; невыполнимым его делало отсутствие описания в камере, а не текст требования.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `camera`: ADDED CAM-8 — машинное описание типов эффектов камеры (состав, единственность источника, независимость от графического контекста, отсутствие человекочитаемых формулировок); MODIFIED CAM-6 — построение эффекта по записи манифеста идёт через это описание, ветвления по типу в диспетчере MUST NOT быть.
- `assets`: MODIFIED ASSET-8 — набор типов и их параметров задаётся описанием CAM-8; валидация манифеста принимает описание входом и, получив его, проверяет записи секции по нему с разделением «предупреждение / ошибка».

## Impact

- `engine/render-ts/src/camera/effects.ts` — дескриптор рядом с каждым классом эффекта; `TraumaShake`/`SwayEffect` приводятся к контрактам импульсного и длящегося эффекта.
- `engine/render-ts/src/camera/effectTypes.ts` (новый) — собранное описание; экспорт из `engine/render-ts/src/index.ts`.
- `engine/render-ts/src/camera/director.ts` — диспетчер строит эффекты по описанию; литералов типов и списков параметров в нём не остаётся.
- `engine/assets-ts/src/manifest.ts` — тип описания (контракт формата секции), проверка секции по описанию, предупреждения в результате валидации; `engine/assets-ts/src/loaders/manifest.ts` и потребители — передача описания.
- `editor/core-ts/src/validation/engineRules.ts`, `adapters.ts` — описание доезжает до `validateManifest`, предупреждения — до находок важности `warning`.
- `editor/ui-ts/src/areas/assetCameraEffects.ts` (новый), `editor/ui-ts/src/areas/assets.ts`, `editor/ui-ts/app/assembly.ts` — операции секции, таблицы в области ассетов, регистрация вкладов.
- `editor/ui-ts/src/i18n/` — строки описаний типов и параметров в пространстве `cameraEffect.*` (ED-28) со своим гейтом «бандл ↔ описание».
- `content/visuals/manifest.json` — секция дополняется примером длящегося эффекта; правка presentation-данных, `worldInit`, снапшоты и golden-файлы не затрагиваются (ASSET-8).
- Симуляции изменение не касается вовсе: ни ядра, ни сети, ни golden-эталонов.
