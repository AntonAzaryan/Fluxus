## Context

Мотивация — в proposal.md. Состояние на входе: оболочка (`engine/client-ts`) доставляет в главный поток presentation-состояние и reliable-события (SHELL-2..5) и принимает ввод и команды обратным каналом (SHELL-6); демо держит ad-hoc HUD прямо в `demo/main.ts`; редакторский UI (`editor/ui-ts`) — vanilla DOM на токенах с собственной лёгкой абстракцией узлов, тестируемой без браузера. Идёт change `shell-modes`: SHELL-1/SHELL-6 переписываются под два режима оболочки, но место UI (главный поток) и контракт доставки не меняются.

## Goals / Non-Goals

**Goals:**

- Пакет HUD, в котором виджеты, композиция и оверлей-хост разделены так, что источник композиции заменяем (TS-значение → JSON-документ) без правки виджетов (HUD-4).
- Форма композиции JSON-сериализуема с первого дня — «шов под data-driven» существует как проверяемое свойство, а не намерение.
- Демо `client-ts` — первый потребитель: его ad-hoc HUD переезжает на пакет.

**Non-Goals:**

- JSON-документ HUD в `content/`, его schema и авторинг в редакторе — будущий change; сейчас только форма, которую он заполнит.
- World-anchored элементы (подсистема рендера) — будущий change; здесь только запретная граница (HUD-3).
- Визуальный язык игрового HUD (скины, темы, бренд арены) — первая версия ограничивается нейтральной минимальной стилизацией.
- Экраны вне матча.

## Decisions

**1. Отдельный пакет `engine/hud-ts` (`@game-mvp/hud`), а не модуль в `client-ts`.**
`client-shell` по назначению — граница потоков и канал; вешать на него виджеты значит размыть capability. Пакетная нарезка повторяет принятую (`render-ts`, `assets-ts` — потребители ядра, не его части). Зависимости пакета: `@game-mvp/client` (типы протокола и доставленного состояния) — и ничего больше; DOM-фреймворков нет. Альтернатива «модуль внутри client-ts» отклонена: спека `client-shell` сознательно не знает, что именно рисует главный поток.

**2. Vanilla DOM + лёгкая узловая абстракция по образцу `editor/ui-ts`, без переиспользования его кода.**
Прецедент репозитория: редакторский UI обходится без фреймворка, а тестируется через собственный слой узлов без jsdom. HUD заводит свой минимальный аналог (создание/обновление узлов, классы, текст) — общий пакет с редактором не выделяется: связывать игровой клиент с authoring-инструментом ради пары хелперов — сцепление дороже дублирования. Альтернатива Preact/React (внешняя рекомендация: скорость соло-итерации, LLM-генерация, `useSyncExternalStore`) рассмотрена и для матчевого HUD отклонена осознанно: виджетов мало, обновления горячих величин всё равно императивные (реактивный слой пришлось бы обходить — что рекомендация признаёт и сама), а гибкость достигается композицией-данными. Решение зафиксировано с границей: **vanilla — для матчевого HUD; Preact — кандидат для будущей capability меню/лобби**, где экранов много, горячего пути нет и итерация важнее нулевой зависимости. Интерфейс виджета (HUD-4) дверь не закрывает: виджет, отрисованный любым способом, реализует тот же контракт.

**3. Композиция ссылается на всё по именам — селекторы, действия и виды виджетов резолвятся из реестров.**
`HudComposition` — JSON-сериализуемое значение: список записей `{ widget: <вид>, zone: <зона>, params, bindings: { <слот>: <имя селектора> }, actions: { <слот>: <имя действия> } }`. Виды виджетов, именованные селекторы над доставленным состоянием и именованные действия регистрируются кодом (реестры — образец `systems/registry.ts` ядра). Именно ссылки-строки делают переезд на JSON тривиальным: JSON-документ десериализуется в ту же форму, реестры уже есть. Альтернатива «биндинги — замыкания в TS» отклонена: она делает композицию несериализуемой и превращает будущий переезд в переделку (нарушение HUD-4).

**4. Фасад действий с двумя адресатами: мир — через словарь биндингов, presentation — через контракт камеры.**
Демо уже держит биндинги-данные (`demo/bindings.json`, INP-4). Именованное мировое действие HUD — ссылка в тот же словарь семантических действий; фасад оборачивает отправителя обратного канала (`sender.ts`) и не знает, «кнопка это была или клавиша» — так HUD-2 («кнопка неотличима от клавиши») выполняется конструктивно. Presentation-действия (перевод камеры по миникарте, фокус на герое) — второй тип записей фасада: они вызывают контракт управления камерой в главном потоке и в канал не пишут. Адресат — часть объявления действия, а не решение виджета: виджет дёргает имя, куда оно ведёт — знает реестр.

**5. Оверлей-хост: `pointer-events: none` на корне, `auto` на интерактивных элементах.**
Механизм HUD-3: корневой слой прозрачен для указателя по умолчанию, перехват — только там, где виджет объявил интерактив. Зоны экрана (углы, кромки, центр) — фиксированный словарь хоста; композиция раскладывает виджеты по зонам, а не по абсолютным координатам — это и есть переносимость композиции между разрешениями.

**6. Обновление — подписка на доставку, события — отдельный поток с номерами тиков.**
HUD подписывается на ту же точку доставки главного потока, что подсистемы рендера (`remoteHost`): состояние — по каденсу доставки, reliable-события — списком с номерами тиков, признак разрыва — снап (HUD-5). Виджет получает уже отрезолвленные значения селекторов; сравнение «изменилось ли» и точечное обновление DOM — забота виджета, не хоста.

**7. Иконки — asset ID через тот же asset-слой, что у рендера.**
Изображения HUD (иконки способностей и предметов, портреты) — контент под `content/visuals/`; ссылки в композиции и данных виджетов — asset ID (ASSET-2), резолв — через `assets-ts`, которым главный поток уже пользуется для манифеста визуалов. Таблица «идентификатор из симуляции → asset ID иконки» — данные контента по образцу таблицы kind'ов handshake (SHELL-5): симуляция доставляет идентификатор, картинку знает контент. Альтернатива «URL в композиции» отклонена: минует манифест, ломает переносимость дерева контента.

**8. Портрет: второй WebGL-контекст по образцу просмотрщика ассетов редактора, не scissor главного canvas.**
Развилку «один контекст рендера и врезка scissor-прямоугольником против отдельного маленького контекста» редактор уже прошёл для просмотрщика (ED-20) и задокументировал в `editor/ui-ts/src/areas/assetModule.ts`: свой canvas, свой `WebGLRenderer`, свой цикл кадров, а общий — модуль ассетов (ASSET-2, один кэш на дерево). Портрет — третий кадр по тому же образцу: scissor-вариант потребовал бы синхронизировать layout DOM с прямоугольником главного рендера на каждый resize и сцепил бы проход арены с раскладкой HUD. Стенд портрета — изолированная мини-сцена (модель по kind из манифеста, idle-клип, своя камера), не камера в арену; невидимый портрет (виджета нет в композиции) не рисует ничего — как невидимая область редактора. Отдельный здесь только инстанс: движок один — `render-ts` (сборка модели, анимации, скины, модуль ассетов переиспользуются), второй лишь `WebGLRenderer` со своим canvas и циклом кадра; второй реализации рендера не появляется.

**9. Миникарта: canvas-2D виджет, представление маркеров — таблица данных.**
Миникарта — обычный виджет HUD (интерфейс тот же), внутри — один `<canvas>` с 2D-контекстом: сотни маркеров в канвасе дёшевы, DOM-узел на сущность был бы деградацией, второй проход рендера сцены — дорогим и стилистически неверным (миникарта — схема, не вид сверху). Фон — из террейна handshake, перерисовка фона — только по дельтам пола; маркеры — по доставленному состоянию на каждом обновлении. Таблица маркеров: `визуальный тип → { форма | имя отрисовщика, окраска (командная/фиксированная), размер, приоритет }` плюс политика для типа без записи (default-маркер или пропуск). Таблица — часть композиции (значение HUD-4), значит JSON-сериализуема и уедет в JSON-документ вместе с ней; именованные отрисовщики (иконка героя, пинг) — третий реестр рядом с виджетами и селекторами. Клик по миникарте — presentation-действие камеры (решение 4); приказы через миникарту в первую версию не входят.

## Risks / Trade-offs

- [Change `shell-modes` переписывает SHELL-1/SHELL-6, на которые ссылается спека HUD] → по смыслу ссылки инвариантны к режимам (место UI и обратный канал сохраняются в обоих); при архивации второго из двух change'ов сверить формулировки ссылок.
- [Реестр именованных селекторов может разрастись в неструктурированную кучу] → набор растёт только из потребностей реальных виджетов; каждое имя — с тестом; ревизия при переезде на JSON-документ.
- [Обновление DOM на каждую доставку может дёргать layout при росте числа виджетов] → виджеты обновляют только изменившиеся текст/атрибуты; профилирование — по факту на реальной сцене (дисциплина «ponytail», а не преждевременная оптимизация).
- [Двойная лёгкая DOM-абстракция (редактор и HUD) — осознанное дублирование] → цена согласия: пара сотен строк; сцепление игрового клиента с authoring-пакетом стоило бы дороже.
- [Данные видимости для миникарты могут отсутствовать в доставляемой плоской форме сегодня] → штатный механизм SHELL-2: поле добавляется в плоскую форму на стороне воркера; собственного канала миникарта не заводит.

## Migration Plan

1. Пакет `engine/hud-ts` входит в workspace; `npm run check` зелёный без потребителей.
2. Демо `client-ts` переводится на пакет (статусный виджет + панель действий героя) — ad-hoc HUD из `demo/main.ts` удаляется.
3. Отката как такового нет: до шага 2 пакет никого не затрагивает; откат шага 2 — возврат демо на предыдущую ревизию.

## Open Questions

- Строковые ресурсы HUD (локали ru/en по образцу ED-27): первой версии хватает строк из композиции; выносить ли в ресурсы — решится при переезде композиции на JSON.
- Подключение HUD к превью редактора (потребитель того же локального режима оболочки): возможно позже, спека этого не требует и не запрещает.

## Отложенные швы (зафиксировано, чтобы не потерять)

- **OffscreenCanvas для canvas-виджетов.** Сознательно не закладывается: DOM в воркер не переносится в принципе, сим-воркер растеризацией нагружать нельзя (каденс тика), третий поток потребовал бы fan-out канала доставки, а выигрыш на миникарте — доли миллисекунды. Если профилирование реальной сцены покажет обратное — это точечная правка HUD-1 («исполняется в главном потоке»); контракты данных и действий переезд переживут. Настоящий кандидат на OffscreenCanvas — сам 3D-рендер, и это тема `client-shell`, не HUD.
- **Геймпад и Steam Deck — наследство для capability меню/лобби.** Матчевый HUD контроллер-безопасен уже по HUD-2: «кнопка неотличима от клавиши» означает, что в бою фокус-навигация по HUD не нужна — действия жмутся забинженными кнопками (INP-4). Всё остальное — spatial navigation по DOM, **мульти-фокус** (свой фокус-курсор на каждый подключённый геймпад в лобби выбора персонажей — готовые библиотеки этого не покрывают), экранная клавиатура через Steamworks, читаемость текста на 800p — требования к будущей capability экранов вне матча; её спека должна начинаться с этого списка. Там же решается стек этих экранов (кандидат — Preact, см. решение 2) и десктоп-упаковка (Electron + steamworks.js — тема дистрибуции, не UI).
- **World-anchored слой (будущий change, граница в HUD-3).** Кандидат реализации при вводе: MSDF-текст (например troika-three-text) и инстансированные квады в подсистеме рендера — не DOM-проекция.
- **Проекция мир → экран через камеру для HUD.** Понадобится виджетам, вычисляющим screen-space представление из мировой точки: пинг-маркер, edge-индикатор «за кадром», стрелка к месту события. Это не нарушает границу HUD-3 (элемент остаётся screen-space; запрещена пер-кадровая привязка элемента к сущности). Форма — read-only проекционный контракт от камеры в главном потоке, потребляемый именованными селекторами. В первой версии потребителя нет, потому в нормативный текст не внесено; вносить вместе с первым таким виджетом. Преобразования «мир ↔ миникарта» (аффинное, внутри виджета) и «экран → мир» (picking, REND-15) — не этот шов и уже покрыты.
