# Design — add-particle-system

## Context

Мотивация и выбор библиотеки — proposal.md (исследование build/buy/fork: three.quarks против three-nebula/wawa-vfx/своего). Требования — дельты `specs/rendering` (REND-24, уточнение REND-23) и `specs/assets` (ASSET-14). Точка интеграции существует: рендер — упорядоченный список подсистем за контрактом `RenderSubsystem` (REND-8), подсистема транзиентных эффектов (`engine/render-ts/src/subsystems/effects.ts`) уже реализует ровно нужный мост sim→vfx — источники byKind/byState/byEvent над `TickView`, словарь битов состояний `stateComponents`, часы кадра, сброс по `snapAll`. Рендер — WebGLRenderer (WebGL2), three ^0.185.

## Goals / Non-Goals

**Goals**

- Универсальная подсистема частиц: дебафы/ауры (byState), типовые эффекты сущностей со следами (byKind + сокет), one-shot по событиям (byEvent), статика на арене (decoration-эмиттеры, расстановка в т.ч. из Blender прокси-объектами — существующим путём импорта).
- Авторинг без кода: эффект — JSON из внешнего редактора (quarks.art), подключение — запись манифеста.
- Один `BatchedRenderer` на сцену: draw calls растут с числом конвейеров, не эмиттеров.

**Non-Goals**

- Чтение вшитых эмиттеров MDX (`ParticleEmitter2`) — открытый вопрос закрывается в пользу манифеста; MDX-эмиттеры не рисуются никогда.
- GPU-симуляция, WebGPU, soft particles — не в этом изменении; CPU-пути three.quarks достаточно (потолок ~50k частиц много выше нужд).
- Детерминизм частиц: расхождение картинки между клиентами — норма (REND-24). Телеграфы урона частицами не делаются.
- Собственный UI авторинга эффектов в редакторе — не заводится; редактор только переподаёт манифест (REND-17, ED-15).

## Decisions

**D1. three.quarks как рантайм-зависимость `render-ts`, версия зафиксирована точно (без `^`).**
Альтернативы: своё (3–6 недель до паритета), three-nebula (мертва), wawa-vfx (нет нужных фич). Точный пин — потому что JSON-формат эффектов версионируется библиотекой: обновление версии = осознанная миграция контента, а не побочный эффект `npm install`. Зависимость только в `render-ts`; `assets-ts` парсит документ без three.quarks (см. D3). Bus factor 1 принимаем; план Б — вендоринг в `render-ts/vendor` без смены формата.

**D2. Подсистема `subsystems/particles.ts` — структурная копия effects.ts.**
Тот же скелет: `syncTick(view)` сводит эмиттеры-оболочки с доставленным состоянием и запускает one-shot'ы по свежим событиям; `updateFrame(dt)` зовёт `batchRenderer.update(dt)`; `applyManifest` пересводит оболочки единственным правилом сведения; `snapAll` гасит one-shot'ы и частицы. Словарь `stateComponents` переиспользуется как есть. Отдельная подсистема, а не ветка effects: у частиц свой рендер-пайплайн (батчи three.quarks) и свой ассет — общего с примитивами только источники.

**D3. Эмиттерный ассет — файл `*.effect.json`, загрузчик в `assets-ts` без зависимости от three.quarks.**
Реестр ASSET-3 различает форматы; суффикс `.effect.json` отделяет документ эффекта от прочего JSON контента. Загрузчик `assets-ts` проверяет форму корня (структурная валидация, headless) и отдаёт документ как иммутабельные данные; в three.quarks-объекты (`QuarksLoader`) его разворачивает подсистема рендера при первом использовании — так `assets-ts` остаётся рендер-агностичным (ASSET-5), а тесты валидации идут в Node. Кэш развёрнутых эффектов — в подсистеме, по идентичности документа.

**D4. Секция манифеста `particles` зеркалит секцию `effects`.**
Таблицы `byKind`/`byState`/`byEvent`; запись: `{ effect: <asset id>, socket?, scale? }`, состав закрыт. Эмиттерный decoration-вид — запись раздела decoration-видов с `effect` вместо `model`. Разрешение записи — по своей секции, без просмотра чужой (REND-23 в новой редакции).

**D5. Сокеты — по имени узла инстанса.**
`socket` — имя узла сцены модели (кость или empty, экспортируется glTF штатно); резолв через `getObjectByName`, кэш на оболочке ВМЕСТЕ С КОРНЕМ, из которого узел взят (пересборка инстанса заводит новый корень — узел ищется заново, иначе эмиттер замирает в отцепленном поддереве), поза снимается в мировых координатах каждый кадр. Нет узла — предупреждение один раз и позиция сущности (поведение effects). Дерево узлов есть только у детального яруса (REND-20): у батчевой записи его не существует, и это состояние отличается от «модель ещё едет» — первое даёт предупреждение сразу, второе молча ждёт следующего кадра.

**D6. One-shot'ы — пул инстансов на эффект, не clone-на-выстрел.**
`ParticleSystem.clone()` на каждое событие аллоцирует пропорционально событиям; вместо `setAutoDestroy` — возврат отыгравшего инстанса в пул своего эффекта (паттерн пула effects.ts). Первичное разворачивание документа — ленивое, при первом использовании записи.

Отсюда две поправки к тому, что отдаёт библиотека, обе — следствие «жизненным циклом владеет пул»: `autoDestroy` документа с ЭКЗЕМПЛЯРА снимается (иначе по концу проигрывания библиотека снимет систему с батча и отцепит эмиттер, и экземпляр в пуле мёртв навсегда), а суб-эмиттеры клона пере-связываются на его собственные системы (`EmitSubParticleSystem.clone()` копирует ссылки образца: суб-частицы не играют ни у одного экземпляра, а счётчик образца растёт неограниченно). Пере-связывание — публичным конструктором поведения и параллельным обходом образца и клона.

## Risks / Trade-offs

- [Bus factor three.quarks = 1, заброшенность] → точный пин версии; фикстурный тест «наш контент загружается» ловит дрейф формата; план вендоринга (MIT позволяет) без смены формата контента.
- [Несовместимость с three ^0.185 или будущим апгрейдом three] → three у quarks — peer; версия three апгрейдится только вместе с проверкой quarks; фикстурные тесты рендера.
- [Overdraw полупрозрачных билбордов на слабом GPU — главный производственный риск] → бюджет контента (размер/число крупных частиц, экономия trail'ов), аддитивный блендинг по умолчанию (не требует сортировки), мониторинг `renderer.info.render.calls`; смена библиотеки не помогает — фиксируем как правило контента, не кода.
- [Формат three.quarks JSON богаче, чем валидирует загрузчик] → валидация формы корня, не полная схема: документ старше кода легален, неизвестное внутри эффекта — зона библиотеки; отказ — только на не-документе.
- [Недетерминированный рандом в render-ts рядом с детерминированным ядром] → граница уже нормирована (REND-1, REND-24): частицы не читают симуляцию и не пишут в неё; ничего нового не открывается.

## Migration Plan

Миграции нет: секция `particles` и эмиттерные decoration-виды опциональны, манифест без них валиден и рендерится как раньше; существующий контент не меняется. Снятие открытого вопроса «Частицы» из `openspec/specs/rendering/spec.md` — при sync/archive изменения. Откат = удаление подсистемы и секции манифеста; формат контента других слоёв не затронут.

## Open Questions

- Численные бюджеты (частиц на эффект, эмиттеров на сцену) — выставить после профилирования демо-сцены на целевом железе; на спеки и разбиение задач не влияют.
- Нужен ли прокси-плейсхолдер эмиттера во вьюпорте Blender-аддона (превью «здесь огонь») — удобство авторинга, решается в blender-addon отдельно, импорт не трогает.
