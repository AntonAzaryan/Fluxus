# Design: entity-presentation-timescale

## Context

Мотивация — proposal.md «Why»; норма — дельта REND-37. Текущее устройство:

- Часы презентации считает `ViewBuffer.frame()` (`engine/render-ts/src/viewBuffer.ts`): один `dt` со знаком режима мира на весь кадр (REND-25). Персональной величины на сущность в `FrameTiming` нет и не появится — шкала едет per-entity в плоской форме.
- Плоская форма `ExtractedTick` (`extractor.ts`) — SoA-колонки, граница потоков (SHELL-2); кодек `client-ts/src/codec.ts` копирует f32-колонки подряд секцией (`F32_COLUMNS = 6`: x, y, facingYaw, aimYaw, motionPhase, flightPhase).
- Анимация: машина одна на оба яруса (REND-20, `model/animation.ts`), носители — `MixerAnimationBackend` (микшер идёт по модулю `dt`, направление живёт в `action.timeScale = ±1`) и `VatAnimationBackend` (фаза — скаляр, кроссфейд дренируется по модулю отдельно от фазы).
- Частицы: вся симуляция шагается одним `batchRenderer.update(dt > 0 ? dt : 0)` (`subsystems/particles.ts`); three.quarks `BatchedRenderer.update(delta)` — это цикл `ps.update(delta)` по всем системам плюс `batch.update()` по батчам. Персонального темпа у библиотеки нет: `ParticleSystem.update` в типах приватный (в рантайме — обычный метод), `IParticleSystem` его не объявляет, `speedFactor` — параметр шейдера stretched billboard, не времени.
- Симуляционная сторона готова: `TIME_SCALE_COMPONENT = 'TimeScale'`, поле `value` (Q16.16, сведено и клампнуто `TimeScaleSystem`, TIME-7). Компонент есть только у сущностей с `TimeScaleModifiers` — читать строго через `hasComponent`, иначе ноль вместо единицы.

## Goals / Non-Goals

**Goals**

- Донести `TimeScale.value` до кадра ровно одним новым каналом данных (колонка плоской формы → `EntityView.timeScale`) и применить его в двух потребителях: клипы моделей, эмиттеры частиц сущности.
- Не тронуть: направление хода (REND-25), дренаж кроссфейдов, батчирование частиц, поведенческие golden-эталоны.

**Non-Goals**

- Никакого масштабирования величин самого потока (`realDt`), HUD, камеры, tier-fade, доворота/наклона, decoration-эмиттеров, one-shot выстрелов по событию — REND-37 прямо выводит их из-под шкалы.
- Никакой альтернативной «плавности»: шкала применяется как есть на кадр; сглаживать её рендеру незачем — плавность даёт tween самой ауры.
- Не менять `time-system`: TIME-5 остаётся как есть, REND-37 — его реализация на стороне рендера.

## Decisions

### D1. Шкала — колонка плоской формы, а не отдельный канал

Новая `timeScale: Float32Array` в `ExtractedTick`; экстрактор заполняет через `hasComponent → getField / FIXED_ONE`, иначе 1. В `EntityRecord`/`EntityView` — поле `timeScale: number` (величина последнего доставленного тика, без интерполяционной пары: плавность обеспечивает tween ауры на стороне симуляции, а интерполяция пары дала бы то же с точностью до кадра доставки). Кодек: `F32_COLUMNS` 6 → 7, колонка в хвост f32-секции; handshake не меняется.

*Альтернатива — бит в `flags`*: отвергнута, колонка `flags` (u8) забита (2 бита + 6 состояний), и шкала — число, а не флаг.

### D2. Контракт бэкенда: `update(dt, pace)`

`AnimationBackend.update` получает второй аргумент `pace` (персональный темп, ≥ 0, по умолчанию 1). Разделение обязанностей то же, что у направления (REND-25):

- `MixerAnimationBackend`: `action.timeScale = direction * pace` (было — чистое направление), микшер по-прежнему идёт `mixer.update(|dt|)`. Часы микшера ведут конверты кроссфейдов — они и остаются немасштабированными; фазы клипов масштабирует `timeScale` действия. Перезапись `action.timeScale` — по изменению значения, как сейчас по изменению направления (шкала под твином ауры меняется каждый кадр — цикл по `actions` ограничен клипами модели, аллокаций нет).
- `VatAnimationBackend`: `advancePhase(clip, dt * pace)`, а `fadeLeft -= |dt|` без множителя — кроссфейд уже дренируется отдельно от фазы, разрез готовый.
- `models.ts` `poseRecord`: `record.controller?.update(dt, view.timeScale)`.

Развязки one-shot'ов (конец вперёд / начало назад) не трогаются: масштаб меняет скорость подхода к границе, не границу.

### D3. Частицы: по-эмиттерный шаг вместо глобального `BatchedRenderer.update`

`updateFrame` подсистемы частиц перестаёт звать `batchRenderer.update(dt)` и шагает сам:

1. оболочки сущностей (`shells`) — `dt_шкалы = max(dt, 0) * shell.view.timeScale`;
2. decoration-оболочки и выстрелы — `max(dt, 0)` без множителя;
3. затем один проход `batch.update()` по `batchRenderer.batches` (публичный API, `VFXBatch.update(): void`).

Шаг системы — вызов рантайм-метода `ParticleSystem.update(delta)`, в типах приватного. Обход инкапсулируется в ОДНОЙ функции в `particleEffects.ts` (`stepInstance(instance, delta)`) со структурным типом `{ update(delta: number): void }` и проверкой `typeof`; смена API при апгрейде библиотеки бьётся в этой точке тестом (см. Risks). `emit(delta, …)` из `IParticleSystem` — не замена: это внутренний шаг эмиссии, не полный тик системы.

*Альтернатива — несколько `BatchedRenderer` по темпам*: отвергнута, темп непрерывен (тьюн ауры), а батчирование обязано остаться по конвейерам (REND-24).
*Альтернатива — `system.paused` + выборочные вызовы `update`*: отвергнута, `update` сам выходит по `paused`.

Порядок внутри кадра сохраняется: позы → `updateMatrixWorld` → шаг систем → сбор выстрелов → батчи. Заморозка обратного хода (`dt < 0 → 0`) остаётся в силе для всех трёх групп.

### D4. Стоимость

Счётчики не меняют семантики: `particlesSystemsStepped` уже считает системы оболочек по-штучно, шаг стал явным — число то же. Новая работа экстрактора (одно `hasComponent` + `getField` на сущность) отдельного счётчика не заводит — она того же порядка, что чтение скорости. Ожидание: cost-эталоны не краснеют; если красный дифф всё же появится — это сигнал перепроверить реализацию, а `npm run golden:cost` — только после понимания причины.

## Risks / Trade-offs

- [Приватный в типах `ParticleSystem.update` меняется при апгрейде three.quarks] → обход в одной функции `particleEffects.ts` с рантайм-проверкой и предупреждением один раз; юнит-тест шага экземпляра (эмиссия/возраст частиц наблюдаемы через `instanceParticles`) падает при смене API, а не молчит.
- [Перебор: замаcштабировать и кроссфейд микшера] → конверты ведёт `mixer.update(|dt|)`, масштаб живёт только в `action.timeScale`; тест «кроссфейд завершается за штатную длительность при pace = 0.2».
- [Ловушка нуля: чтение шкалы без `hasComponent`] → тест «сущность без `TimeScale` анимируется с множителем 1»; в экстракторе — явный `hasComponent`, в колонке дефолт 1.
- [Регресс обратной перемотки] → существующие тесты REND-25 не трогаются; новый — «`Rewinding` + шкала: фаза идёт назад в персональном темпе».
- [Дельта-канал: рассинхрон формы и кодека] → `codec.test.ts` уже гоняет roundtrip всех колонок; колонка добавляется в фикстуры.

## Migration Plan

Чистое расширение: колонка с дефолтом 1 и второй аргумент с дефолтом 1 не меняют поведения сборок без `TimeScale`. Откат — revert коммита. Регенерация эталонов не планируется (см. D4); поведенческие golden не задеваются по построению (рендер в них не участвует).
