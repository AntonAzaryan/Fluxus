# Design: lighting-time-of-day

## Context

Мотивация — proposal.md «Why»; требования — дельта `specs/rendering/spec.md` (MODIFIED REND-29, ADDED REND-32). Отправное состояние кода:

- `LightingSubsystem` (`engine/render-ts/src/subsystems/lighting.ts`) уже принимает правку секции в рантайме (`applyConfig`) и трактует смену света как **событие** перерисовки кэша статических теней; в `hybrid` глобальный свет между событиями статичен по построению.
- Контракт подсистемы уже даёт кадровые часы: `updateFrame(dt, alpha, realDt)` (`types.ts`), освещение их сегодня игнорирует.
- Разрешение секции в плоскую действующую конфигурацию — `lighting/config.ts` (`resolveLightingConfig` + потолки пресета в `effective()`).
- Формат секции и её валидация — `PresentationLighting` в `engine/assets-ts`.

Всё в этом изменении — presentation-механизм рендера и данные документа; политика (какие фазы, какие цвета, сколько минут) — контент сцены. Ядра и evaluator'а изменение не касается вовсе.

## Goals / Non-Goals

**Goals:**

- Исполнение цикла внутри подсистемы: константная покадровая работа, событийный кэш статики вне переходов, согласованные тени на переходе.
- Формат подсекции цикла, который читается как список «стабильных обликов» арены и не ломает ни одной сцены без него.
- Демо-арена показывает круг суток без единой строки кода в демо.

**Non-Goals:**

- Геймплейное время суток (фаза в симуляции, эффекты на обзор) — отдельное будущее изменение, JSON-система поверх тика; здесь только картинка.
- Аффорданс редактора «пауза/перемотка цикла» при правке фазы — не в этом изменении (см. Open Questions).
- Цикл параметров тумана (`fog`) или иных секций — только свет.

## Decisions

### D1. Формат: стабильные фазы + один кроссфейд, не непрерывный дрейф

```jsonc
"lighting": {
  "ambient": { … }, "directional": { … }, "shadows": { … },   // как сегодня
  "cycle": {
    "transitionSeconds": 15,          // необязательное; документированное умолчание
    "phases": [
      { "name": "утро",  "seconds": 120, "ambient": { … }, "directional": { … } },
      …                                // ≥ 2 фаз; поля фазы необязательны — дыры
    ]                                  // закрывает статическая часть секции
  }
}
```

Фаза держит свой облик `seconds`, на границе — кроссфейд длиной `transitionSeconds` (глобальная для цикла). Альтернатива «фазы — ключевые кадры, свет дрейфует непрерывно» отвергнута: «день» тогда ни секунды не стабилен, автор теряет предсказуемый облик арены, а формат — расширяемость (пер-фазные переходы добавимы позже без слома). Параметры теней в фазе запрещены (REND-32): режим/сторона карты меняться по кругу не могут — смена режима пересобирает программы материалов, это событие, а не кадр.

Разрешение формата: `resolveLightingConfig` дополняется разрешением фаз — каждая фаза схлопывается в плоский набор значений света поверх статической части секции (те же правила дыр, что PRES-2). Потолки пресета (QUAL-1) касаются только теневых полей и к фазам не применяются — им нечего ограничивать.

### D2. Интерполяция на живых источниках, мимо `applyResolved`

Ход цикла живёт в `updateFrame`, а не в `applyConfig`: покадровый вызов `applyResolved` каждым кадром перехода объявлял бы событие перерисовки кэша и пересчитывал фрустумы. Вместо этого:

- При применении секции фазы разрешаются один раз в массив пар `THREE.Color`/чисел — на кадре ни парсинга `#rrggbb`, ни аллокаций (дисциплина REND-26).
- Установившаяся фаза: два сравнения (номер фазы, флаг перехода) — работа нулевая.
- Кадр перехода: lerp цветов (`Color.lerpColors` в предсозданные объекты), интенсивностей и направления; позиция/цель источников переставляются точечно. Фрустум теневой камеры от направления **не зависит** (он обтянут по арене — design D6 текущей подсистемы), поэтому `updateProjectionMatrix`, сторона карты и bias'ы на переходе не трогаются.
- Часы — `realDt`: длина суток — свойство картинки, и замедление времени симуляции (`time-system`) её не растягивает; связь sim→render здесь не нужна вовсе.

`applyConfig`/`applyQuality`/`applyGrid` остаются единственным событийным швом и сбрасывают цикл на начало первой фазы (REND-32).

### D3. Тени на переходе: перерисовка кэша только если движется направление

Покадровая работа со светом в `hybrid` сегодня запрещена текстом REND-30 («сцене с анимированным светом положен `full`»), поэтому кроссфейд требует оговорки в самом REND-30, а не только нового требования рядом: дельта изменения несёт её (запрет остаётся в силе вне перехода, на переходе подсистема обязана приводить тени покадрово, стоимость видна счётчиками PERF-3). Дальше — как именно она приводит.

Карта теней — глубина из точки источника: от **цвета и интенсивности она не зависит**, только от направления (позиции) и фрустума. Отсюда политика перехода в `hybrid`:

- направления соседних фаз равны → кэш статики не трогается вовсе; переход бесплатен для теней при любой длине;
- направление лерпится → каждый кадр перехода поднимает `staticStale`, то есть перерисовывает кэш статики (плюс обычная покадровая карта динамики); `lightingStaticRebuilds` и счётчики кастеров честно растут — это и есть «стоимость видна счётчиками» (PERF-3, REND-32). По окончании перехода — установившаяся фаза, кэш событиен как прежде.

В `full` переход ничего не меняет (карта и так покадровая), в `none` теней нет. Альтернатива «на время перехода временно сойти в full» отвергнута: смена числа источников — пересборка программ материалов, дважды за каждый переход; текущая пара с покадровым `needsUpdate` даёт то же качество без неё. Авторам документируется практика: держать направление общим у соседних фаз (солнце «прыгает» на кроссфейде цвета) либо принимать цену — выбор политики, не механизма.

### D4. Валидация — в assets-ts, как весь формат документа

`PresentationLighting` получает тип и проверку `cycle`: закрытый состав, ≥ 2 фаз, положительные `seconds`, неотрицательный `transitionSeconds`, запрет теневых полей в фазе — все находки адресные (`lighting.cycle.phases[2].seconds`), тексты на русском, как принято форматом. Редактор и импортёр получают проверку из того же места — второй реализации не появляется (по образцу остального формата PRES-2).

### D5. Отладка и стоимость

- `DebugLightingState` (RDBG-2) дополняется: номер и авторское имя текущей фазы, доля прожитого фазой, флаг и прогресс перехода — с живых источников/состояния цикла, без аллокаций на кадре.
- QUAL-3: новая работа кадра константна (D2), покадровые перерисовки кэша на переходе управляются существующими ручками `lighting.shadowMode`/`lighting.shadowMapSize` — новая ручка не нужна, константность объявляется в декларации качества словами.

### D6. Контент демо

`content/scenes/duel.presentation.json`: `cycle` из четырёх фаз по 120 с (утро — тёплый низкий свет, день — нейтральный высокий, закат — оранжевый низкий встречный, ночь — синий тусклый с приглушённым ambient), `transitionSeconds` порядка 15. Точные числа подбираются глазами через `npm run demo` — это данные, дифф ревьюится картинкой, не спекой. Направления фаз выбираем осознанно: где «солнце едет» — там принимаем стоимость перехода по D3 (у duel режим `full`, так что цена и так покадровая — витрина честная).

## Уточнения при реализации

Решения D1–D6 остались в силе; три места пришлось назвать точнее, чем они были написаны, — здесь записано, что именно и почему.

### У1. Кроссфейд — в ХВОСТЕ слота фазы, а не сверх него (уточняет D1)

D1 читался двояко: «фаза держит облик `seconds`, на границе — кроссфейд `transitionSeconds`» допускает и «слот = `seconds` + `transitionSeconds`». Взято первое: слот фазы равен `seconds`, и последние `transitionSeconds` слота — кроссфейд к следующей фазе. Основание нормативное: при втором прочтении круг демо-арены длился бы 4×120 + 4×15 = 9 минут, а сценарий REND-32 говорит «четыре фазы … за восемь минут». Побочные выгоды: последний кадр перехода приходится ровно на границу слота, поэтому возврат к первой фазе не даёт скачка, а начало круга показывает первую фазу точно (кроссфейд в голове слота смешивал бы её с фазой, которой сцена ещё не жила).

### У2. Переход, не оставляющий фазе облика, отвергается валидацией (уточняет D1, D4)

Следствие У1: переход не короче слота обнуляет держание облика, и цикл вырождается в непрерывный дрейф — ровно ту модель, которую D1 отверг. Молча укорачивать авторское число нельзя (состав документа держится на адресном отказе), поэтому:

- **Авторское** `transitionSeconds >= seconds` любой фазы — находка валидации, одна на цикл, адресованная длительности перехода и называющая самую короткую фазу: `lighting.cycle.transitionSeconds: переход 15 с не короче слота фазы phases[1] (12 с) — держать облик фазе тогда нечем`.
- **Умолчание** валидация не видит (умолчания — политика подсистемы, формату они неизвестны), а ловушка достижима именно им: сцена с фазами короче 15 с и без `transitionSeconds` попала бы в дрейф молча. Поэтому умолчание ограничено сверху половиной самого короткого слота — точкой, где держание и переход равны; авторское число этой границей не правится никогда.
- В `lighting/cycle.ts` `min(transition, seconds)` остаётся последним рубежом для конфигурации, собранной руками мимо документа: фаза целиком под кроссфейдом, но без скачка и без зависания.

### У3. Кадры перехода делятся между картами ярусов (уточняет D3)

D3 говорит «каждый кадр перехода поднимает `staticStale` … плюс обычная покадровая карта динамики». Обе карты в одном кадре механизм не рисует: `castShadow` — флаг объекта, общий на оба источника, поэтому за кадр обновляется РОВНО одна карта (это же свойство даёт «тень декорации кадром старше»). Буквальное прочтение D3 заморозило бы карту динамики на всю длину перехода — тени бойцов стояли бы 15 секунд, а REND-32 требует согласованных теней на каждом кадре. Поэтому кадры перехода делятся между ярусами через один: обе карты отстают не больше чем на кадр (за кадр направление проходит сотые доли дуги перехода), а установившаяся фаза добивает кэш точным направлением фазы.

Цена этого решения названа вслух в декларации качества (QUAL-3) и видна счётчикам (PERF-3): смена яруса переставляет флаги ОБОИМ реестрам кастеров, то есть на кадре перехода появляется работа по числу корней сцены. Кадр перехода поэтому платит счётчиком не только яруса, чью карту он рисовал, но и яруса, которому переставил флаги. Собственной ручки эта работа не заводит: `lighting.shadowMode` снимает её целиком (`none` — теней нет, `full` — карта одна, делить кадры не с чем).

## Risks / Trade-offs

- [Перерисовка кэша статики на кадрах перехода в `hybrid` при движущемся направлении] → длина перехода — данные (15 с из 120), кадры делятся между ярусами через один (У3), стоимость видна счётчиками и управляется потолком `lighting.shadowMode`; практика «общее направление соседних фаз» документируется.
- [Кросс-фейд и `staticShare`: доля статики фиксирована, а интенсивности лерпятся] → доля применяется к уже слерпленной суммарной интенсивности — инвариант «пара светит как один источник» сохраняется тождественно.
- [Дифф cost-эталонов (`*.cost.json`) от цикла в записанных матчах] → записи короче 120 с — переходов в окне матча нет, установившаяся фаза бесплатна; если дифф всё же всплывает, он принимается явно через `npm run golden:cost` отдельным коммит-решением (PERF-3/PERF-4).
- [Тождество кадров ED-22 при недетерминированном старте часов] → ход цикла — функция от момента применения секции (REND-32): сравнение кадров в тестах делается на нулевом смещении либо с подставными часами; сам контракт «один и тот же свет по построению» не ослабляется.
- [Автор правит фазу в редакторе, а цикл убегает] → правка перезапускает цикл с первой фазы (ED-15 + REND-32) — облик воспроизводим; удобство точечной подгонки фазы — Open Question.

## Open Questions

- Аффорданс редактора «остановить цикл / показать фазу N» при подгонке значений: не меняет ни спеки (перезапуск при применении уже нормирован), ни разбиение задач — отдельное изменение capability `editor`, когда дойдут руки.
