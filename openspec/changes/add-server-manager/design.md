# design: Fluxus Server Manager — агент хоста и приложение управления

## Context

Мотивация — proposal.md, нормы — дельты specs/ (SRV-1..8, MGR-1..5, правки DSK-5/DSK-7, NTR-11, новое NTR-19). Текущее состояние кода:

- Сервер матча — процесс `game/demo-ts/bin/demo-serve.mjs`: владеет `MatchServer` in-process, наблюдает лобби и разрывы снаружи (`BotSlotFiller`, политика `--on-disconnect`, NTR-17/NTR-18 уже в main), управляется только stdout и сигналами.
- Десктоп-контейнер `desktop/shell-ts`: профили `apps/*.app.json` (editor, game), сервисы DSK-7 умирают вместе с сессией, Electron-клей вне гейта (DSK-6), контрактный сьют — чистый Node.
- `engine/net-ts`: WebSocket-транспорт без измерения RTT; `MatchServer.disconnect()` есть, запирания слота нет; метрики хоста без длительности тика и broadcast lag.
- Production-контекст — `docs/reviews/2026-08-24-game-server-infra.md`: агент проектируется как будущий «тонкий allocator» (control plane VPS + process-per-match), матчмейкер — клиент его протокола.

## Goals / Non-Goals

**Goals:**

- Один агент и один управляющий протокол на оба сценария: локальная машина разработчика и удалённый VPS.
- Все админ-операции над игроками — через существующие механизмы сервера матча; игровой протокол (NTR-4) не расширяется.
- Наблюдаемость (RTT, tick p99, broadcast lag, статусы) — во внешнем слое, без влияния на матч и канонический лог.

**Non-Goals:**

- Матчмейкер, Steam-аутентификация, UDP-транспорт — протокол агента лишь обязан их не блокировать (SRV-2).
- Шифрование игрового трафика: граница доверия игрового порта остаётся как названа (SES-7, NTR-9); шифруется только управляющий канал.
- Роли и разграничение прав внутри управляющего канала: токен один — «админ»; multi-tenant не проектируем.
- Запуск агента сервисом ОС (автостарт) — свойство упаковки, вне спеки и этого change.

## Decisions

**D1. Агент — пакет `game/server-agent-ts`, процессы серверов — существующие стенды.** Агент спавнит процесс запускалки стенда (сегодня — `demo-serve.mjs`) с флагами из параметров запуска: процесс-на-сервер, изоляция крашей бесплатно, матчевый цикл стенда не переписывается. Альтернатива — встроить супервизию в стенд — отвергнута: стенд остаётся «одним сервером», умирающим целиком, а мультипроцессность и реестр — забота агента.

**D2. Агент ↔ процесс сервера — stdio JSON-линии.** Стенду добавляется control-адаптер: периодический отчёт (фаза, слоты со статусами, метрики) и приём команд (`disconnect-player`, `bar-slot`, `unbar-slot`, `stop`) по stdin/stdout JSON-линиями. Одна точка аутентификации и один порт наружу — у агента. Альтернатива — свой админ-эндпоинт в каждом процессе сервера — отвергнута: N портов, N точек auth, и агент всё равно нужен для запуска/крашей.

**D3. Управляющий протокол — wss + JSON-сообщения, закрытый набор, версия в рукопожатии.** Push-события по подписке (SRV-2), той же дисциплиной, что игровой протокол (NTR-4/NTR-5), но отдельным словарём — у него другой контрагент и другой ритм. JSON, а не msgpack: объёмы админ-канала ничтожны, читаемость в отладке дороже. REST отвергнут: нужны серверные события, а не опрос.

**D4. TLS и пейринг.** Агент при первом старте генерирует ключ и self-signed сертификат в свой каталог состояния; канал — только wss. Менеджер закрепляет отпечаток при первом подключении (TOFU), токены выдаются пейринг-кодом, показанным командой на агенте; выданные токены — файл состояния агента, отзыв — операция протокола. Генерация сертификата — малой зависимостью в пакете агента (слой игры; правило «ноль зависимостей» касается ядра). Альтернатива — своя PKI/CA — отвергнута: операционная цена без выигрыша для одного админа.

**D5. Каталог состояния агента.** Сертификат, токены, книга процессов (для переживших менеджер серверов), краш-материалы (SRV-6) — в каталоге состояния агента. На старте агент сверяет книгу с живыми процессами: записи без процесса помечаются `stopped` (перезагрузка хоста не воскрешает серверы — и не должна).

**D6. Отвязываемый сервис в контейнере.** Реализация DSK-7: процесс, объявленный `detached`, спавнится в собственной группе процессов и не убивается при завершении сессии; адрес пере-обнаруживается повторным запросом запуска (существующее правило «повторный запуск возвращает адрес работающего», расширенное через границу сессий — по адресному файлу в каталоге состояния сервиса). Контрактный сьют проверяет обе ветви на чистом Node (DSK-6). Kill-on-exit — политика менеджера (MGR-4): при включённом тумблере менеджер шлёт агенту stop-all и останавливает сервис явно, контейнер о тумблере не знает.

**D7. RTT — ping/pong несущего канала.** WebSocket-транспорт меряет круг штатными ping/pong-кадрами и отдаёт последнее значение по соединению; интерфейс транспорта получает необязательную наблюдаемую «RTT либо явное отсутствие» (NTR-11). Игровой протокол и метрика отклика не трогаются.

**D8. Запертый слот — API `MatchServer`.** `bar(slot)`/`unbar(slot)` + именованный исход отказа в словаре `RejectReason` (данные существующего сообщения `Reject`, не новое сообщение). Запирание живого владельца идёт существующим путём «исход + разрыв» (как вытеснение заместителя в NTR-18). Стенд транслирует команды control-адаптера в эти вызовы.

**D9. Метрики хоста.** Длительность тика и broadcast lag меряет `MatchHost` (цикл и рассылка живут там; `MatchServer` остаётся чистым тиком, NTR-3); event-loop delay — `perf_hooks` в процессе стенда; RSS процесса сообщает сам процесс в периодическом отчёте адаптера. Агрегация перцентилей — на стороне поставщика отчёта, канал несёт готовые величины.

**D10. Host bundle и раздача клиента.** Скрипт сборки в пакете агента собирает: агента, стенд, `vite build` клиентского приложения демо и контент-пак; версии соединяются один раз при сборке (NET-16/NTR-5 сходятся по построению — SRV-7). Страница игрока раздаётся по обычному HTTP: игровой транспорт сегодня — незашифрованный ws, и https-страница не смогла бы к нему подключиться (mixed content); граница доверия игрового порта уже названа (Non-Goals). Ссылка входа — страница агента с адресом сервера в параметре.

**D11. Менеджер — веб-приложение `game/server-manager-ts` + профиль контейнера.** Третий профиль `apps/server-manager.app.json`: оконная интеграция + один объявленный отвязываемый сервис (агент); дерева контента у профиля нет (DSK-5) — список документов матча для формы запуска менеджер получает от агента операцией протокола (у агента контент дистрибутива под рукой, и это тот же словарь, каким будет пользоваться матчмейкер). Книга хостов (адреса, отпечатки, токены) — в хранилище страницы менеджера; риск открытого хранения назван ниже. Лавовая тема редактора переиспользуется как стиль, нормой не является.

## Risks / Trade-offs

- [Токены и отпечатки в хранилище страницы менеджера лежат открыто] → приемлемо для админ-инструмента на своей машине; переход на шифрованное хранилище ОС — отдельное расширение моста контейнера, не смешиваем с этим change; риск назван в коде рядом с хранением.
- [Отвязанный процесс на Windows: семантика групп процессов отличается от POSIX] → ветвь покрывается контрактным сьютом DSK-7 на обеих платформах через опции spawn Node; поведение «пережил сессию» проверяется без Electron.
- [Поток логов через stdio-адаптер может заливать канал] → хвост лога ограничен кольцом на стороне агента, строки длиннее предела режутся с пометкой; управляющие сообщения и лог не смешиваются в одном направлении без маркировки.
- [Self-signed + TOFU уязвим к MITM на самом первом подключении] → окно ровно одно и требует активного атакующего в LAN в момент пейринга; смена отпечатка после — громкий отказ (SRV-3). Осознанная цена отказа от PKI.
- [Порт/адрес: два сервера на один порт, гонки занятости] → занятость порта — названный отказ запуска (MGR-2); выбор свободного порта агентом — параметр запуска «порт: авто», а не молчаливое переназначение явно заданного.
- [Метрики p99 в процессе стенда — лишняя работа в горячем цикле] → счётчики копятся кольцами фиксированного размера вне тика (OBS-2), отчёт раз в секунду; при выключенной подписке отчёт не собирается.

## Migration Plan

Ломающих миграций нет: DSK-7 расширяется свойством, которого ни один существующий профиль не объявляет; NTR-11 добавляет наблюдаемые, не меняя существующих; NTR-19 — новое поведение по явной админ-команде. Симуляция, протокол матча и golden-эталоны не затрагиваются — откат равен удалению новых пакетов и профиля.

## Open Questions

- Раскладка каталога состояния агента (пути, имена файлов) и умолчание порта управляющего эндпоинта — решаются при реализации, спек не меняют.
- Шифрованное хранилище для книги хостов менеджера (safeStorage контейнера) — отдельное расширение DSK-словаря, когда/если понадобится.
