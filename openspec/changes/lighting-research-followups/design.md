# Design: lighting-research-followups

## Context

Мотивация — proposal.md; требования — дельты REND-29/30/32/34 и ASSET-5 этой правки. Текущее состояние: подсистема освещения (`engine/render-ts/src/subsystems/lighting.ts`) несёт `AmbientLight` + двухъярусный `DirectionalLight` (sun/sunDynamic для hybrid-кэша теней), конфиг разбирает `lighting/config.ts`, цикл суток — `lighting/cycle.ts`; постпроцесс (`subsystems/postprocess.ts` + `postprocess/*`) держит bloom и tone mapping собственными проходами (bloom-пирамида и resolve-материал с чанками three), а маска тумана — финальный проход поверх (FOW-7). Валидация presentation-документа и типы секций живут в `engine/assets-ts` (`PresentationLighting`, `PresentationPostprocess`); нормализованный материал — `assets-ts/src/model.ts`, его потребитель — `render-ts/src/model/build.ts`. Все умолчания обязаны воспроизводить сегодняшний кадр байт-в-байт — это правило уже принято REND-29/34 и дельтами сохранено.

## Goals / Non-Goals

**Goals:**
- Пять независимых возможностей, каждая включается данными и по умолчанию выключена: hemisphere, rim, blob-тени, HDR-emissive, LUT.
- Ни одной новой покадровой стоимости без ручки качества или объявленной константности (QUAL-3); всё счётное — в сток стоимости (PERF-2/PERF-3).
- balanced-пресет не меняет сегодняшний кадр (принятое ранее Migration-решение остаётся в силе).

**Non-Goals:**
- Запечённые lightmap (второй UV, `lightMap`/`aoMap`) — отдельное архитектурное решение, конфликтующее с циклом суток; сюда не входит.
- LightProbe/IBL (`scene.environment`, PMREM) — отложено до появления lightmap.
- CSM — не нужен top-down-камере с фрустумом по арене.
- Изменение существующих сцен: `duel.presentation.json` трогаем отдельным контент-коммитом, не этой правкой.

## Decisions

**D1. Hemisphere — `THREE.HemisphereLight` в подсистеме, подсекция `hemisphere` секции `lighting`.** Поля: `skyColor`, `groundColor`, `intensity`. «Нет подсекции — нет источника», а не умолчания-числа: так сцены без подсекции гарантированно рисуются прежним кадром, и не появляется второй способ записать «выключено». Альтернатива — всегда держать источник с нулевой интенсивностью — отвергнута: нулевой источник всё равно участвует в шейдерных униформах и ломает «байт-в-байт».

**D2. Rim — второй `THREE.DirectionalLight` без теней, подсекция `rim`.** Поля: `color`, `intensity`, `direction` (та же семантика смещения от цели, что у главного источника). Фиксированный к камере rim (классический контровой) потребовал бы покадрового пересчёта направления от позиции камеры — оставляем мировое направление, как у солнца: для top-down-камеры с почти постоянным азимутом разница не видна, а стоимость нулевая. Fresnel-rim в шейдере персонажей отвергнут: это правка материалов всех ярусов (включая VAT-батчи), несопоставимая по объёму с одним источником.

**D3. Blob — инстансированные декали в подсистеме освещения, не в models.** Один `InstancedMesh` (круглая мягкая текстура, generated, не ассет) с ёмкостью по числу динамических инстансов; позиции пишутся из того же обхода, что уже питает динамический ярус кастеров — нового обхода инстансов не появляется. Размер пятна — из габарита вида в манифесте (тот же источник, что LOD/отсечение). Маска тумана скрывает пятно автоматически: пятно рисуется в основной проход сцены, до маски (FOW-7). Ранг режима — расширение существующего `PRESENTATION_SHADOW_MODES` (`none`,`blob`,`hybrid`,`full`): `shadowModeRank`/`minShadowMode` работают без правок. Альтернатива «blob как отдельный флаг рядом с режимом» отвергнута: два поля порождают бессмысленные комбинации (`full`+blob), а ранговая семантика потолка пресета ломается.

**D4. Emissive strength — поле `emissiveStrength` нормализованного материала (default 1).** Парсинг `extensions.KHR_materials_emissive_strength.emissiveStrength` в `loaders/gltf.ts`; MDX-загрузчик пишет 1. Потребитель (`model/build.ts`) кладёт его в `material.emissiveIntensity`. Кламп не делаем нигде — HDR-значение и есть смысл поля; порог bloom (threshold 1) остаётся местом, где решается «светится/не светится».

**D5. LUT — 3D-таблица в resolve-проходе постпроцесса, формат ассета — `.cube`.** Парсер `.cube` — новый загрузчик в `assets-ts` по реестру ASSET-3 (вид ассета «lut»; открытое множество видов — правок ядра модуля нет), результат — иммутабельный `Float32Array` + размер стороны: headless, тестируем в Node. `render-ts` строит из него `Data3DTexture` и сэмплирует в том же resolve-материале, где уже живёт tone mapping, — после оператора, до записи в кадр: отдельного полноэкранного прохода LUT не добавляет, стоимость — одна выборка на пиксель (константа, QUAL-3). `amount` — lerp исходного и скорректированного цвета. Ручка качества — потолок-выключатель `postprocess.lut` по образцу `postprocess.bloom`. Альтернатива — `LUTPass` из three/addons — отвергнута: наш постпроцесс не на EffectComposer, и лишний полноэкранный проход дороже одной выборки в существующем resolve.

**D6. Цикл суток и новые источники.** Фаза интерполирует hemisphere/rim теми же правилами дыр, что ambient/directional (дельта REND-32): `resolvePhase` расширяется полями, `cycle.ts` — интерполяцией. Наличие источника — свойство статической части; фаза меняет только числа. Это сознательно запрещает «rim только ночью» — включение/выключение источника на переходе потребовало бы семантики появления из ничего; автор достигает того же интенсивностью 0 в фазе.

**D7. Валидация.** Все новые поля — в закрытые составы секций `lighting`/`postprocess` в `assets-ts` (адресные отказы, PRES-2), схемы обновляются там же, где живут существующие. Blender-импортёр не трогаем: он переписывает только derived-слой, секции света под BLND-2 сохраняются байт-в-байт.

## Risks / Trade-offs

- [Blob-пятна поверх прозрачного/неровного террейна могут z-ファйтить] → декаль с `polygonOffset`/лёгким подъёмом над поверхностью по образцу существующих оверлеев; финальная высота — по виду на реальной арене.
- [`.cube`-файлы бывают большими (33³–65³ float)] → парсер ограничивает размер стороны (валидация с адресной причиной); хранение в контенте — текст, кэш ассета разделяем.
- [Расширение словаря `PRESENTATION_SHADOW_MODES` меняет схему presentation-документа] → `npm run schemas` не задет (схемы движка — из core), схема документа живёт в assets-ts и обновляется вместе с типами; старые документы валидны — новых обязательных полей нет.
- [Rim удорожает фрагментный шейдер всех материалов (третий источник в forward)] → источник один и без теней; бюджет forward-лимита уже съедают локальные источники (REND-33) с потолком — rim в потолок не входит, его стоимость константна и объявлена.
- [Cost-бейзлайны] → сцены бейзлайнов новых полей не несут — счётчики не сдвигаются; если демо-сцена включит blob/LUT позже, это отдельный `npm run golden:cost` с осознанным диффом.

## Migration Plan

Каждая возможность — независимый коммит с зелёным `npm run check`; порядок: D4 (assets) → D1/D2 (свет) → D3 (blob) → D5 (LUT) → D6 (цикл). Отката данных не требуется: старые документы валидны, новые поля необязательны.
