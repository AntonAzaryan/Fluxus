# Design: npc-behavior

## Context

Мотивация и вердикт архитектуры — `proposal.md` и `docs/reviews/2026-08-26-npc-ai-architecture.md`. Что уже есть и что ограничивает подход:

- Модель скоринга (considerations → кривые → композиция) реализована в `engine/bot-ts/src/brains/evaluated/scoring.ts` поверх формата `behavior.ts` — вне симуляции, поверх FoW-снапшота.
- Ядро: ноль зависимостей, единый `System`, Command Buffer, broad-phase сетка физики (PHYS-5), событийная шина (EVT-2), именованные потоки RNG (RNG-2), машина каста с триггерами `event`/`always` (ABIL-3/4/6).
- Шов `pathfinding` NAV-1..6 нормирован, реализации нет; сцена без навигации обязана тикать (DI-4).
- Гейт стоимости: `*.cost.json` (PERF-3/4), регенерация только `npm run golden:cost`.
- Аллокационная дисциплина ядра: горячий путь тика не аллоцирует пропорционально числу сущностей.

## Goals / Non-Goals

**Goals:**

- Платформа поведения NPC в ядре, готовая к 200–300 массовых агентов на арене при потиковом движении и распределённых решениях.
- Один код скоринга на бота и NPC; словарь форм кривых — один.
- Босс с фазами и волны — целиком контентом поверх этой платформы, без правок кода на новый энкаунтер.

**Non-Goals:**

- Реализация Navigation API (flow field/A*) — отдельный change, когда геометрия арен сломает прямой seek.
- Адаптивный Director (intensity-метрика L4D) — старт со скриптованных таблиц волн; усложнение по факту монотонности боёв.
- Рендер-масштаб (инстансинг, LOD хелсбаров) — отдельная работа по QUAL-3 в `render-ts`.
- Обученные/ML-мозги, GOAP/HTN — отвергнуты ресерчем для массовых агентов.

## Decisions

**D1. Нативная система в ядре, не JSON-система.** Горячий цикл по сотням агентов (threat, скоринг, staggering, seek/separation) — механизм с жёстким бюджетом; JSON-evaluator платил бы за интерпретацию на каждом агенте. Политика остаётся в документе (NPC-2), сцена может дополнять поведение обычными JSON-системами (глушить/включать NPC-систему конфигом сцены как любую систему). Альтернатива «всё JSON-системами» отклонена по стоимости; интерфейс `System` гарантирует, что снаружи разницы нет.

**D2. Скоринг переезжает в ядро одним модулем.** Композиция considerations/кривых из `bot-ts/.../scoring.ts` — чистый код без зависимостей, ему место в `engine/core-ts` (рядом с `dsl/`); `bot-ts` импортирует его из ядра. Направление зависимости легально (все пакеты зависят от ядра), zero-deps ядра не нарушается. Критерий рефакторинга: существующие тесты бота зелёные без правки ожиданий — решения evaluated-мозга не меняются побитово (паритет BOT-8).

**D3. Состояние NPC — SoA-компоненты фиксированной формы.** Состояние HFSM (id состояния, тик входа), tier и фаза каденса, threat-таблица top-K плоскими массивами (K — константа формы компонента, число небольшое; веса и пороги — документ), прогресс маршрута (индекс waypoint'а). Никаких объектов на агента; scratch-буферы скоринга — на систему, предвыделены под максимум сущностей.

**D4. Каденс: детерминированный round-robin по стабильному индексу.** Окно решения агента — функция его стабильного порядка обхода и интервала K из документа/tier'а; плюс decision-budget на тик (предел числа пересмотров). Никакого «свободного времени» и адаптивности от нагрузки — исход зависит только от состояния мира (NPC-4). Событийное исключение: смерть текущей цели/провокация форсируют пересмотр вне окна — это переход HFSM, не нарушение каденса.

**D5. Восприятие — прямые запросы, событийный threat.** Выбор цели — broad-phase соседи (PHYS-5) + threat; накопление threat — подписка на события урона/лечения/таунта шины, O(событий), не O(агентов²). FoW NPC не читает: он часть авторитетной симуляции (NPC-1); «честность» NPC не нужна.

**D6. Движение: waypoint-маршруты как сущности `initial` + seek/separation.** Маршрут — цепочка waypoint-сущностей с компонентами (без расширения схемы сцены, SER-7 не трогаем); движение пишет позицию через Command Buffer (NAV-4). Separation — по соседям сетки. Когда появится реализация за NAV-1, система переключается на `findPath` без изменения контента.

**D7. Босс: фазы — HFSM документа, касты — события шины.** Ротация фазы выбирает способность скорингом (приоритет/условие/цель) и публикует событие; определение способности в сцене объявляет триггер `event` этого типа (ABIL-3) — дальше работают штатные фазы, телеграф и прерывания (ABIL-4/6). Второго пути каста нет (NPC-7); NPC-система не знает имён способностей — связка «действие → тип события» лежит в документе поведения, «тип события → способность» в сцене.

**D8. Director — отдельная маленькая система.** Читает таблицу волн (контент), спавнит через Command Buffer префабами сцены, соблюдает cap сцены (NPC-8). Отделена от поведения крипа, чтобы состав волн тюнился независимо.

**D9. RNG-поток `npc-ai`.** Вся случайность решений (джиттер выбора при равных скорах, разброс точек) — из именованного потока; число вызовов детерминировано каденсом.

**D10. Гейт масштаба с первой итерации.** Синтетический стресс-сценарий (арена, сотни массовых крипов, N тиков) в `engine/tests/golden/` с cost-эталоном и bench-сентинелом (PERF-5). Существующие эталоны не меняются: текущие сцены NPC не содержат.

## Risks / Trade-offs

- [Inner-platform: документ поведения разрастается в язык программирования] → закрытые словари исполнителей/входов/кривых (NPC-2/NPC-3), композиция примитивов остаётся кодом — тот же барьер, что BOT-9.
- [Рефакторинг скоринга сдвинет решения бота] → критерий D2: тесты бота зелёные без правки ожиданий; перенос — код без изменения семантики, различия ловятся существующими тестами паритета.
- [Событийный форс-пересмотр (D4) размоет каденс и бюджет] → форс-переходы считаются в decision-budget тика; при исчерпании — пересмотр в следующее окно.
- [Seek без навигации застревает на геометрии] → порог включения flow field зафиксирован (Non-Goals): первая же арена со статикой, ломающей прямой seek; до неё — waypoint'ы обходят статику руками дизайнера.
- [Стоимость фильтра снапшотов и dirty-tracking на 300 сущностей вне NPC-системы] → стресс-эталон меряет весь тик, включая эти фазы; регрессия видна там же (NPC-9).

## Migration Plan

1. Вынос скоринга в ядро (D2) — чистый рефакторинг, бот зелёный.
2. Платформа NPC (D1, D3–D6, D9) + документ поведения + стресс-эталон (D10).
3. Director и таблицы волн (D8), демо-сцена с волной.
4. Босс-фазы (D7) на демо-сцене.

Отката не требуется: до появления NPC в сценах поведение движка не меняется.

## Open Questions

- Ёмкость threat-таблицы K и интервалы каденса по умолчанию — числа контента; стартовые значения подбираются на стресс-сценарии, спека их не фиксирует.
- Нужен ли massовым крипам собственный дешёвый «скоринг цели» отдельной формой или хватает общей модели с 1–2 considerations — решится профилем стресс-эталона.
