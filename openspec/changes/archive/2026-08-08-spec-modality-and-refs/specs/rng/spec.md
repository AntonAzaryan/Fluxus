## MODIFIED Requirements

### Requirement: RNG-6 RNG не вызывается из выражений

В expressions RNG MUST NOT вызываться напрямую; система «тянет» значение и передаёт его через связывание имени.

В JSON-системе этим механизмом SHALL быть действия `random` и `randomBelow` (ACT-1): они обращаются к стриму и связывают результат с именем в своём теле. Число обращений к генератору SHALL быть видно в тексте системы — столько, сколько раз написано действие: иначе оно зависело бы от того, какие ветки выражения вычислялись, то есть от деталей реализации evaluator'а, а состояние генератора входит в снапшот (RNG-5) и сверяется между реализациями (`cli-testing` CLI-6).

#### Scenario: Формула урона с разбросом

- **WHEN** формуле нужен случайный множитель
- **THEN** система получает значение из своего стрима и связывает его через `let`, а выражение остаётся чистым

#### Scenario: Попытка вычислить случайное внутри условия

- **WHEN** автор системы хочет случайное значение прямо в выражении
- **THEN** такого оператора в таблице нет: значение берётся действием `random` выше по дереву и читается как переменная

### Requirement: RNG-8 Формула nextFixed и nextBelow

Помимо сырого `next()` (RNG-1), стрим SHALL предоставлять два производных метода с дословно зафиксированным алгоритмом, одинаковым во всех реализациях ядра:

**`nextFixed()`** — равномерное значение в `[0, 1)` в формате Q16.16 (`fixed-point-math` FP-1): старшие 16 бит результата `next()`, то есть `next() >>> 16`.

**`nextBelow(bound)`** — равномерное целое в `[0, bound)` без float, методом Lemire (multiply-shift с отбраковкой):

```text
s = bound (как u32)
threshold = (2^32 - s) mod s
do:
  x = next()
  (hi, lo) = x * s  // точное 32×32→64 умножение
while lo < threshold
return hi
```

`bound` SHALL быть положительным целым; `bound < 1` — нарушение инварианта на границе рождения значения (`ecs-foundation` ID-1 задаёт тот же принцип для `EntityId`) и SHALL проверяться жёстким assert'ом (`fixed-point-math` FP-4), бросающим в обоих режимах сборки.

Число отбраковок (итераций цикла `do/while`) SHALL быть детерминированной функцией текущего состояния стрима и `bound`, а не фиксированным: это часть детерминированного контракта генератора — состояние стрима после `nextBelow` входит в snapshot (RNG-5) и сверяется между реализациями (`cli-testing` CLI-6). Любая реализация `nextBelow`, дающая то же распределение другим алгоритмом (например, без отбраковки или с другой формулой `threshold`), расходится по числу продвижений генератора и SHALL считаться некорректной, даже если статистически неотличима.

#### Scenario: nextFixed из известного состояния

- **WHEN** `next()` возвращает конкретное значение `w`
- **THEN** `nextFixed()` равно `w >>> 16`, побитово одинаково в TS и Rust

#### Scenario: nextBelow без отбраковки

- **WHEN** первый вызов `next()` внутри `nextBelow(bound)` даёт `lo >= threshold`
- **THEN** возвращается `hi` этого же вызова, генератор продвинулся ровно на один шаг

#### Scenario: nextBelow с отбраковкой

- **WHEN** первый вызов `next()` даёт `lo < threshold`
- **THEN** генератор делает дополнительный шаг `next()` и повторяет проверку, продвинувшись более чем на один шаг

#### Scenario: Отбраковка воспроизводится в снапшоте

- **WHEN** `nextBelow` потребовал несколько отбраковок, и состояние стрима сохраняется в snapshot, а затем восстанавливается
- **THEN** повторный вызов той же последовательности операций даёт то же количество отбраковок и тот же результат

#### Scenario: bound меньше единицы

- **WHEN** `nextBelow` вызван с `bound <= 0`
- **THEN** это жёсткая ошибка — исключение бросается и в debug-, и в release-сборке
