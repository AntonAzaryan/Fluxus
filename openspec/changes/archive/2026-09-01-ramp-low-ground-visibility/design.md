## Context

Мотивация — в proposal.md (## Why). Состояние кода: `VisibilitySystem` уже срезает кандидатов строго выше уровня наблюдателя и передаёт уровень в `raycast` (FOW-5, PHYS-13) — менять его не нужно; импортёр Blender уже помечает рампой нижнюю клетку пары (`tools/blender-ts/src/sculpt.ts:considerRamp`), а база визуальной поверхности рендера (`engine/render-ts/src/visualSurface.ts:cornerLevels`) построена на правиле «на верхней стороне рампа тянется вниз только к соседу без рампы». Конвенцию нарушает рукописный контент: `content/scenes/duel.scene.json` (16 клеток) и `engine/tests/golden/terrain.scenario.json` (2 клетки). Редактор валидирует террейн вызовом `createTerrainGrid` (`editor/core-ts/src/validation/engineRules.ts`), так что новая проверка ядра доезжает до него без кода (ED-29).

## Goals / Non-Goals

**Goals:**

- Наблюдаемое поведение «как в Warcraft 3»: на рампе сущность ещё внизу — видна снизу, не видит верхний уровень; полный обзор открывается на верхней клетке.
- Конвенция стороны флага — инвариант модели с загрузочной валидацией, а не устная договорённость: без неё поведение FoW зависит от стиля карты.
- Консервативность картинки: маска тумана не показывает открытым пол строго выше уровня наблюдателя (проём рампы).

**Non-Goals:**

- Частичное «подглядывание» верха с рампы (ограниченный радиус) — не реализуется; заготовка отдельным stub-change.
- Промежуточные уровни/наклон в симуляции — TERR-5 по-прежнему запрещает.
- Слияние/оптимизация cliff-геометрии, изменения физики и навигации — их не происходит по построению (см. D2).

## Decisions

**D1. Правило в модели террейна, а не спецслучай в FoW.** Альтернатива — оставить карты как есть и научить `VisibilitySystem` подменять уровень «на рампе бери минимум соседей». Отвергнута: это второй источник правды об уровне (TERR-4 прямо запрещает), расползание по потребителям (`levelOf` зовут физика, нав, доставка `currLevel` рендеру) и расхождение с уже существующей конвенцией импортёра и рендера. Нормируем сторону флага в TERR-5 — тогда существующий фильтр высоты FOW-5 даёт нужное поведение без единой строчки в FoW, а рендер сходится сам: `currLevel` доставляется из симуляции.

**D2. Контент чинится опусканием уровня клетки рампы, а не переносом флага.** Перенос `^` на соседнюю нижнюю клетку добавил бы cliff-отрезки на боковых границах нынешнего «выступа» (в `duel` заходы (19,12)→(19,13) стали бы обрывом) — сдвиг геометрии, новые коллайдеры, изменение навигации. Опускание уровня той же клетки (1→0, флаг на месте) оставляет предикат `terrainStepPassable` на всех парах прежним, значит cliff-геометрия и проходимость байт-в-байт те же; меняется только уровень сущности на рампе — ровно то, что нужно. Бонус: углы визуального склона (`cornerLevels`) из кривого `[0,0,0,1]` становятся чистым скатом `[1,0,0,1]`.

**D3. Форма валидации: клетка-рампа не имеет соседа по стороне с уровнем на единицу ниже без флага рампы.** Проверка рядом с `validateRampWidth` в `createTerrainGrid`, той же ценой O(клетки×4), с адресной ошибкой (клетка, сосед). Формула эквивалентна нормативному тексту TERR-5: пара «нижний сосед без рампы + верхняя рампа» — единственный способ открыть переход флагом с верхней стороны. Цепочки склона проходят: нижний сосед-рампа разрешён. Терраса `0-плоская | 1-рампа | 2-плоская` отвергается — её шаг 0→1 открыт с верхней стороны; автор обязан пометить рампой и клетку уровня 0.

**D4. Срез маски по уровню тайла — в цикле reveal, по сетке, которая у подсистемы уже есть.** `FogSubsystemOptions.grid` содержит `levels`; в `mask.reveal` тексель, чья клетка (`levelAt`-эквивалент по индексу тайла маски) строго выше `observer.level`, пропускается до вычисления градиента. Разрешение маски и сетки различаются — тексель относится к клетке по своему центру; на границе клеток возможна погрешность в тексель, она консервативна (сомнение — туман) в смысле FOW-9. Стоимость — одна выборка на тексель круга, константный множитель в тех же тексельных единицах бюджета FOW-11/PERF-3; вероятна перезапись `*.cost.json` (`npm run golden:cost`) — принятие роста стоимости остаётся отдельным решением. Отброшенные срезом тексели получают СВОЙ счётчик (`fogMaskTexelsCut`): по одной убыли `fogMaskTexelsWritten` срез не отличить ни от тени, ни от порядка наблюдателей, а гейт обязан видеть работу нового пути (PERF-3, PERF-4). Счётчик заодно и страж стенда: матчевый бенч (`benchLoad.ts`) — синтетическая арена под записанные позиции, и её вырождение (герой «внутри» столба либо арена без единой высоты) иначе прошло бы эталоном из нулей.

**D5. «Подглядывание» верха с рампы — stub-change, не требование.** Спека — источник правды (CORE-3): требование без реализации — дефект. Заготовка `openspec/changes/` c `proposal.md` + `## Notes` (репозиторий такие стабы допускает) фиксирует идею: ограниченный обзор верхнего уровня с рампы как политика поверх того же фильтра высоты.

**D6. REND-9 сужается вместе с TERR-5, а не остаётся общим.** Требование о базе визуальной поверхности обещает, что пары «рампа + плато» и «рампа + низина» смыкаются как прежде, — а вторая пара после нормирования стороны флага перестаёт существовать: клетка-рампа с нижним соседом без рампы отвергается при загрузке, и другого пути к сетке у рендера нет (редактор строит её тем же `createTerrainGrid`, `editor/ui-ts/src/areas/sceneDocuments.ts:terrainOf`). Оставить формулировку общей значило бы держать в спеке обещание о конфигурации, которой не бывает: проверить его нечем, а код (`cornerLevels`) хранил бы ветку, про которую спека утверждает больше, чем правда. Поэтому REND-9 идёт в change дельтой — абзац про углы рампы называет сторону флага и снимает обещание на «рампе + низине», сценарий «Одиночные рампы не меняются» перечисляет только существующую пару. Саму ветку притяжения вниз код сохраняет защитной (комментарий на месте) — удалять её вместе с обещанием значило бы менять поведение там, где менять его этот change не собирался.

## Risks / Trade-offs

- [Перезапись голденов маскирует нежелательные диффы] → сначала `npm run golden` только после зелёных юнитов ядра; в коммит идёт дифф базлайнов с объяснением: меняются `worldInit` (уровни клеток) и маски `Visibility`, cliff-отрезки меняться не должны — их изменение в диффе означает ошибку правки карты.
- [Существующие карты вне репозитория перестанут грузиться] → это и есть цель (BREAKING в proposal); ошибка валидации адресная и говорит, какую клетку опустить/пометить; редактор показывает её через существующий канал `core.terrain`.
- [Срез по уровню замедлит перестройку маски] → выборка из `Uint8Array` на тексель; сентинел-бенчи (PERF-5) и `bench:demo` — диагностика; при неприемлемом росте срез можно считать по строке тайлов, но не выключать (консервативность нормативна).
- [В `duel` сузится «боковой» заход на рампу? Нет] → D2 сохраняет проходимость байт-в-байт; проверяется тестом на равенство cliff-отрезков до/после правки карты (в терминах пар уровней/флагов).

## Migration Plan

0. Спека: дельты TERR-5, FOW-9 и REND-9 (D6).
1. Ядро: валидация TERR-5 + тесты (валидные/невалидные карты, цепочка, терраса).
2. Контент/фикстуры: `duel` (16 клеток 1→0), `terrain.scenario.json` (2 клетки), прочие inline-карты тестов — по красным тестам.
3. Рендер: срез маски по уровню + тесты маски.
4. `npm run golden`, при красном диффе стоимости — `npm run golden:cost`; `npm run check` целиком.
5. Stub-change «ramp-peek-vision» (D5).

Откат — revert коммита: формат ассетов не меняется, только их значения и валидация.
