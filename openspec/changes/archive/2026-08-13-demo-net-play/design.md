## Context

Мотивация — proposal.md «Why»; нормативный контракт — дельта `bot-player` (BOT-7). Текущее состояние:

- `engine/net-ts`: `MatchServer`/`MatchClient`, транспорты (loopback, WebSocket, `portTransport` в client-ts), сессии `local|listen|dedicated`, лобби, рандеву, CLI `bin/serve.mjs`/`host.mjs`/`play.mjs` — всё есть и тестировано, но ни одна браузерная сборка это не использует.
- `engine/client-ts`: `WorkerShell` (локальная симуляция) — единственный режим демо; `NetworkShell` (тонкий клиент, без `Simulation`) — только в тестах. SHELL-8: ровно два режима, выбираются при старте, не переключаются.
- `engine/bot-ts`: бот — обычный `MatchClient` (`BotSeat`, `BotHost`), браузерная и нодовая сборки воркера; никем не подключён. `MatchServer.disconnect()` освобождает слот только в фазе `lobby`; слот берётся `Hello` с тем же `playerId` (`config.players.indexOf`).
- Демо-сцена: `content/scenes/duel.scene.json` + `content/matches/duel.match.json` (`players: ["p1","p2"]`).

Ограничения: SES-1/SES-2 — режим является свойством сборки, ветвление по режиму в сервере/клиенте — дефект; BOT-1 — сервер ботов не различает; NTR-6 — после Start состав заморожен; SHELL-6 — в сетевом режиме ввод едет на сервер и локально не применяется.

## Goals / Non-Goals

**Goals**

- Демо по умолчанию — матч p1-человек против p2-бота, собранный из сетевого стека (сессия `local`: `MatchServer` в воркере, `NetworkShell` у главного потока, бот — отдельный воркер).
- Подключение к выделенному серверу по захардкоженному адресу; друг занимает слот p2 вместо бота (BOT-7, до заморозки).
- Выделенная сборка сервера демо-арены (Node) с бот-заполнителем и авто-рестартом матча.

**Non-Goals**

- Никаких изменений протокола, `MatchServer`, `MatchClient`, набора сообщений (SES-2 это прямо запрещает).
- Никакой замены бота человеком после старта (NTR-6; BOT-7 явно не вводит).
- Никакого лобби-UI, списка серверов, авторизации: адрес — константа сборки/URL-параметр; рандеву — прямой адрес (SES-3 уже допускает).
- Rewind/pause в сетевом демо: у тонкого клиента симуляции нет; отладочная перемотка остаётся в соло-режиме.

## Decisions

**D1. Дефолтное демо — сессия `local` из сетевых деталей, соло-режим остаётся под флагом.**
Дефолт: sim-воркер собирает `MatchServer` (конфиг `duel.match.json`, сцена демо-арены) + два клиентских места — p1 через `MessagePort`-транспорт к главному потоку (`NetworkShell`), p2 — бот (`bot-ts`, браузерный воркер, порт-пара к sim-воркеру). Кадр едет тем же `Serializer` (SES-1: у `local` нет второго пути исполнения). Старый одиночный `WorkerShell`-режим сохраняется за URL-параметром `?solo` — там живут rewind/pause и отладка; SHELL-8 соблюдён: режим выбирается при старте страницы, переключение = перезагрузка с другим параметром.
Альтернатива «оставить дефолтом одиночную симуляцию, сеть только по кнопке» отвергнута: цель фазы — чтобы каждый запуск демо гонял тот же код, что сетевой матч.

**D2. Уступка слота — отложенное подключение бота, а не отзыв.**
Сборка-основатель (и браузерная `local`, и выделенный сервер) подключает ботов к незанятым слотам только на дедлайне старта (заморозка ростера = момент, когда все слоты заняты). Человек, успевший раньше дедлайна, просто занимает слот штатным `Hello` — отзывать нечего, серверу нечего различать (BOT-1). В браузерном дефолте дедлайн эффективно нулевой (второго человека не ждут); у выделенного сервера — конфигурируемая пауза (`--bot-fill-ms`, дефолт ~5 с после первого человека). Это допустимая форма BOT-7 («подключение ботов к незанятым слотам только в момент заморозки»).
Альтернатива — бот садится сразу, при `Hello` человека сборка его отзывает — требует сигнала «человек хочет слот», которого у сборки нет: сервер отвергает `Hello` в занятый слот, не уведомляя владельца бота. Городить такой сигнал = ветвление по типу участника где-то рядом с сервером.

**D3. Выделенный сервер — новая обвязка поверх существующей `dedicated`-сборки.**
`engine/net-ts/bin/` получает запуск демо-арены (расширение `serve.mjs` флагами или тонкий `demo-serve.mjs` поверх тех же деталей): конфиг матча + сцена из `content/`, WebSocket-транспорт, бот-заполнитель по D2, и авто-рестарт — по завершении матча (`End`, включая silence) сервер поднимает следующий матч с тем же конфигом, чтобы демо-стенд жил без перезапусков. Рестарт — цикл в обвязке, не в `MatchServer` (чистый тик-цикл не трогаем, NTR-3).

**D4. Подключение из браузера — конфиг, не UI-поток.**
Адрес сервера: константа сборки демо, переопределяемая `?server=ws://…`. Кнопка в углу — DOM демо-приложения (как существующий `#help`, вне HUD-композиции): клик = переход на URL с `?server=…` (перезагрузка страницы = новый старт оболочки, SHELL-8 чист). `playerId`: пробуем слоты по порядку конфига (`p1`, при отказе `p2`) — первый пришедший получает первый слот; отказ обоих — сообщение «матч занят/идёт».
Порт/протокол по умолчанию согласованы с D3; mixed-content (https-страница → `ws://`) в юзкейсе LAN-стенда не мешает (страница едет по http c dev-сервера), но в тексте кнопки/ошибке это называется явно.

**D5. HUD в сетевом режиме деградирует явно.**
`match-status` прячет pause/rewind-кнопки, когда контракт оболочки их не даёт (тонкому клиенту нечего перематывать); остальные виджеты (миникарта, портрет, абилити-бар) работают от той же доставки SHELL-2..5, им всё равно, кто тикает.

## Risks / Trade-offs

- [Бот-воркер в браузере не поднимется (bundling/поддержка)] → у `bot-ts` есть нодовая сборка воркера; в крайнем случае браузерный дефолт держит бота в sim-воркере тем же `BotHost` без отдельного потока — BOT-4 требует «вне потока сервера» для честности тайминга, для демо-стенда это осознанная деградация сборки, помеченная в коде; спека не правится.
- [Два игрока за NAT не соединятся] → вне охвата: юзкейс — LAN/один хост; для интернета есть инвайты/рандеву (SES-3), подключаемые позже той же сборкой.
- [Гонка за слот p1 при одновременном заходе] → сервер разрешает её сам (`Hello` в занятый слот — отказ), клиент откатывается на следующий слот; тест на последовательность отказов.
- [Латентность/потери на реальной сети] → интерполяция клиента уже есть (NET-9/NTR-10); тюнинг вне охвата фазы.
- [`?solo` и сетевой дефолт разъезжаются по поведению] → «сим и контент один и тот же» — расхождение возможно только в оболочке; интеграционный тест гоняет обе сборки на одном сценарии.

## Migration Plan

Чистая сборка поверх нетронутого стека: протокол, сервер, клиент, симуляция не меняются; golden/match-эталоны не затрагиваются. Откат = вернуть дефолт демо на `WorkerShell`.
