# Design: desktop-shell

## Context

Мотивация — в proposal.md. Что уже есть и ограничивает решение:

- Шов среды редактора существует: `EnvironmentHost` (`editor/core-ts/src/host/`) с веб- (`editor/ui-ts/src/host/web.ts`), memory- и overlay-реализациями; десктопной нет, и комментарий `host/index.ts` прямо оставляет её оболочке.
- Игровой клиент — чистое веб-приложение: воркеры `new Worker(..., {type:'module'})`, ассеты через `fetch('/<id>')` (ASSET-2), канал SHELL-3 без COOP/COEP. Ему от контейнера нужна только раздача файлов.
- Сборки: `vite build` демо клиента (`engine/client-ts/demo/`) и редактора (`editor/ui-ts/app/`); у редакторной сборки нет листинга и записи — их обязан дать хост (ED-12).
- Гейт `npm run check` должен оставаться зелёным без Blender (BLND-7) — тот же принцип распространяем на Electron.

## Goals / Non-Goals

**Goals:**

- Один пакет контейнера, обслуживающий оба приложения через профили (DSK-1, DSK-5).
- Граница контейнера без предметной семантики, закреплённая тестом (DSK-2, DSK-3).
- Первая реализация — Electron; контракт позволяет заменить её без правок приложений (DSK-6).

**Non-Goals:**

- Изменения `client-shell`, `editor`, движка и контента — их нет по построению.
- Автообновление, подпись дистрибутивов, магазины — вопросы дистрибуции, не этого change.
- Сетевой режим клиента: WebSocket из страницы работает без участия контейнера — контейнер о сети не знает.
- Вторая реализация контейнера (Tauri/CEF) — контракт её допускает, но она не делается.

## Decisions

**D1. Electron как первая реализация.** Причина выбора — один встроенный Chromium на всех платформах: одинаковый WebGL/three.js-вьюпорт, воркеры и transferable-канал везде, ноль браузерного разброса. Альтернатива Tauri (системные WebView: WebKit на macOS, WebKitGTK на Linux) меньше по размеру, но возвращает разброс браузеров — ровно то, от чего уходим. Свойство «один Chromium» — свойство реализации, не контракта: смена реализации осознанно обменяет его на другие качества.

**D2. Пакет `desktop/shell-ts` (workspace-member вне `engine/`, `editor/`, `content/`).** Electron и упаковщик — devDependencies только этого пакета. Внутри три слоя:
- `src/host/` — чистый Node без Electron: файловые операции (list/read/write/watch в пределах объявленных корней, атомарная запись tmp+rename — файловый аналог операционной атомарности импортёра BLND-6), раздача бандла и контента. Тестируется vitest'ом — это и есть контрактный сьют DSK-6.
- `src/bridge/` — типы поверхности моста (пути/байты/события/диалоги/окно) и её схема профилей. Без зависимостей вообще — эти типы вправе импортировать приложения (типы границы, не движка; направление зависимости приложение → контракт, контейнер от приложений не зависит, DSK-3 не нарушается).
- `src/electron/` — тонкий клей: main-процесс, preload с `contextBridge`, protocol handler. Гейтом не покрывается: вне `npm run check` его проходит ТОТ ЖЕ контрактный сьют (`npm run contract:electron` — режим `--contract` главного процесса исполняет вызовы в странице) плюс smoke-прогон. Два прогона одного сьюта, а не второй набор утверждений: DSK-6 требует сьют от любой реализации, а от гейта — независимости от контейнера.

**D3. Раздача через custom protocol, а не локальный HTTP-сервер.** Protocol handler отдаёт бандл и дерево контента; базовый URL контента страница получает при старте (DSK-4), а не зашивает схему. Альтернатива — локальный HTTP-порт — проще переносится на «host-процесс + браузер», но открывает порт наружу и требует управления его жизненным циклом; для Electron protocol handler безопаснее и без гонок за порт. Контракт формулирует раздачу поведением, так что HTTP-вариант остаётся легальной реализацией для будущего контейнера.

**D4. Мост — fs-подобная поверхность, профиль как whitelist.** Preload экспортирует только операции, объявленные профилем; игра получает read-only контент или вообще пустой мост (раздачи protocol handler'ом ей достаточно). `contextIsolation: true`, `nodeIntegration: false` в обоих профилях. Widening на живой сессии отсутствует по построению: preload собирает поверхность один раз на старте окна.

**D5. Десктопный `EnvironmentHost` — адаптер в `editor/ui-ts` рядом с `web.ts`.** Контейнер не знает про `ContentTreeHost`/`ContentPicker`; адаптер маппит их на мост. Выбор entry (веб-хост против моста) — по признаку наличия моста в странице, кода редактора вне адаптера это не касается (ED-12).

**D6. Тест независимости — по образцу `contentBoundary.test.ts`.** Проверка, что `desktop/shell-ts` не импортирует `@game-mvp/*` (кроме собственного пакета типов моста, если он выделится), живёт в гейте (DSK-3). Плюс lint-ограничение на импорты как ранний сигнал.

## Risks / Trade-offs

- [Дрейф моста в предметность: «перезагрузи сцену», «покажи ошибку»] → Запрет DSK-2 плюс тест DSK-3; каждая новая ручка моста проходит ревью на выразимость через существующие примитивы.
- [Electron-клей не покрыт гейтом] → Клей держится механически тонким (маршрутизация вызовов в `src/host/`), логика — только в тестируемом Node-слое; smoke-прогон контейнера — отдельный скрипт.
- [Двойная раздача контента у редактора: protocol handler читает, мост пишет — риск рассогласования видимости изменений] → Один источник правды: оба слоя ходят в один `src/host/`-модуль с одним watcher'ом.
- [Размер дистрибутива Electron] → Принято осознанно в обмен на «один Chromium»; пересматривается только со сменой реализации по DSK-6.

## Open Questions

- Имя и иконки приложений, структура дистрибутивов (по одному приложению на дистрибутив или общий лаунчер) — решается при упаковке, контракт не меняет.
- Упаковщик (electron-builder против Forge) — выбор последнего шага, наружу не виден.
