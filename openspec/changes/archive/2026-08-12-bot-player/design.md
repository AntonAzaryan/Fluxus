## Context

Мотивация — в proposal.md. Швы, из которых собирается бот, уже существуют: `ClientHost` принимает источник ввода `InputSource = (tick) => InputSample | undefined` и отдаёт наблюдаемый выход `ClientStep` (`engine/net-ts/src/client/host.ts`), клиент работает без рендера (NTR-14), `PortTransport` гоняет протокол матча поверх пары портов и уже абстрагирует структурный минимум порта, общий для браузерного `MessagePort` и `worker_threads` (`engine/client-ts/src/portTransport.ts`, `protocol.ts`). Ядро, сервер и протокол не трогаются.

## Goals / Non-Goals

**Goals:**

- Контракт мозга, переживающий смену реализации classic → ML без правок хостинга (BOT-2).
- Хостинг бота, работающий в обоих окружениях (браузерный Worker и node `worker_threads`) из одного кода.
- Первый играбельный мозг стартовой арены: utility-решения + steering-микро, с профилями сложности в контенте.

**Non-Goals:**

- ML-мозг — только доказать заменимость контрактом (мок-мозг в тестах достаточен как «вторая реализация»).
- Pathfinding: арена открытая, боту хватает steering; `NavigationApi` — шов для крипов внутри симуляции, здесь не используется.
- Лобби/UI добавления ботов в матч — сборка тестов и dev-запуска; продуктовый UI отдельной работой.
- Командные комбо и обмен намерениями между ботами (BOT-3 его допускает) — до появления командного режима у ботов.

## Decisions

### D1. Новый пакет `engine/bot-ts` (`@game-mvp/bot`)

Хостинг бота, контракт мозга и классическая реализация — один пакет, peer к `client-ts`/`net-ts`. Альтернативы: внутрь `client-ts` (отклонено — это оболочка рендер+воркер, боту не нужен DOM и главный поток) и внутрь `net-ts` (отклонено — там протокол/сервер/клиент, бот — их потребитель, а зависимость Yuka не должна появиться у сетевого пакета).

### D2. Форма контракта мозга — два метода под два каденса

```ts
interface BotBrain {
  /** Каждый доставленный шаг клиента — наблюдение (BOT-3: только своё, фильтрованное). */
  observe(step: ClientStep): void;
  /** Синхронный съём намерения на тик; undefined — ввода нет (BOT-2). */
  sample(tick: number): InputSample | undefined;
  dispose?(): void;
}
type BotBrainFactory = (profile: BotProfile, self: { playerId: string }) => BotBrain;
```

`observe`/`sample` ложатся 1:1 на существующие швы `ClientHost` (выход `ClientStep` → observe; `InputSource` → sample), поэтому хостинг — тонкая склейка без своего цикла. Асинхронность мышления — внутреннее дело реализации: тяжёлый мозг кладёт решение в поле, `sample` его читает (BOT-2 «мозг задумался»). Альтернатива — мозг как отдельный message-loop со своим протоколом — отклонена: второй протокол и лишняя задержка ради изоляции, которую уже даёт воркер.

### D3. Хостинг рантайм-агностичен, entry-точки тонкие

`BotHost` — чистый TS: принимает `Transport`, фабрику мозга и профиль, поднимает `MatchClient`+`ClientHost`, соединяет швы. Worker-entry для браузера и для node — по тонкому файлу, оба через `PortTransport` (структурный минимум порта уже общий). Пару портов создаёт сборка (главный поток / запускалка сервера) и раздаёт концы серверному и бот-воркеру. Несколько ботов в одном хосте — несколько пар `MatchClient`+мозг (BOT-4).

### D4. Первый мозг — слоёный классический, Yuka как движок нижнего слоя

Три слоя: восприятие (модель мира из `ClientStep` + память «последнее виденное» под FoW), решения (utility-скоринг поведений, ~10 Гц — своя реализация, зрелых библиотек нет), микро (steering: seek/flee/orbit/avoidance, доджи по экстраполяции проджектайлов, «не стоять у края» — Yuka: `SteeringBehavior`, `Vision`/`MemorySystem`). Float внутри легален (BOT-5): на observe fixed → float, на sample намерение квантуется в домены INP-3. Yuka пиннится точной версией; используется узкий срез (steering-математика), при проблемах срез вендорится — see Risks.

### D5. Профили — JSON в `content/bots/`

Профиль — обычный документ дерева контента (CONT-1): задержка реакции, шум прицела, джиттер блока, агрессивность, веса utility. Валидирует его `bot-ts` на конструировании мозга (схемы `engine/schemas/` порождаются из ядра и профилей не касаются). Референсные профили (`easy`, `normal`) — часть change.

### D6. Проверка заменимости — мок-мозг в тестах

Тест BOT-2 собирает бот-хост с тривиальным скриптовым мозгом (например, «иди в центр») и с классическим — одинаковой сборкой, разной фабрикой. Это же даёт детерминированного бота для интеграционных прогонов: скриптовый мозг без wall-clock и случайности воспроизводим, классический — нет и в записываемые эталоны не входит (BOT-5: реплей от вводов, мозг при реплее не исполняется).

## Risks / Trade-offs

- [Yuka не развивается с ~2023] → пин точной версии; используем только steering/perception-примитивы, у которых нет внешних зависимостей; план Б — вендоринг нужных классов (математика тривиальна), контракт D2 не меняется.
- [Бот сверхчеловечен по умолчанию: точные координаты из снапшота] → человечность — обязательная часть первого мозга, не пост-тюнинг: задержка реакции как буфер наблюдений, шум прицела, джиттер таймингов — всё в профиле (BOT-6).
- [Таймер `ClientHost` в воркере: троттлинг фоновых вкладок браузера] → для node и dev-прогонов не существует; для браузерного listen-хоста бот живёт в том же жизненном цикле, что серверный воркер, и троттлится вместе с ним — отдельной проблемы бота нет, но проверить в задаче интеграции.
- [Соблазн «подсмотреть» мир сервера при in-process сборке] → граница держится конструированием (мозгу физически не передаётся ничего, кроме `ClientStep`) и тестом на listen-сборку (BOT-3).

## Open Questions

- Точный состав полей профиля за пределами референсных (веса utility по поведениям, per-арена overrides) — дорастёт с плейтестами, схему профиля версионируем с первого дня.
- Как боты попадают в продуктовое лобби (кнопка «добавить бота», автозаполнение слотов) — UI-работа вне этого change; здесь только программная сборка.
