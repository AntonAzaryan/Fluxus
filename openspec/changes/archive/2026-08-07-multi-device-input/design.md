## Context

Мотивация — см. proposal.md «Why». Текущее состояние: захват ввода зашит в `engine/client-ts/demo/main.ts` (DOM-листенеры, ad-hoc латчи `pendingCast`/`pendingDodge`/`pendingJump`, константы битов из `demo/sim.ts`), `heroMoveFromKeys` живёт в `engine/render-ts/src/camera/rig.ts`. Канонический путь ниже уже правильный и не меняется: `remote.sendInput(move, aimDir, buttons)` → воркер ставит `tick`/`seq` → `InputFrame` (TICK-2) → `InputSystem` (TICK-4). Ввод камеры (`camInput`) — отдельный несимуляционный канал (CAM-1), он остаётся per-device.

Ограничения: floats легальны в оболочке до единственной точки квантования (та же граница, что у `fixed.fromFloat` сегодня); слой целиком в главном потоке — граница потоков (SHELL-6) не меняется; определение смысла битов — у сцены/контента (LOC-3), не у оболочки.

## Goals / Non-Goals

**Goals:**

- Механизм источников ввода в `engine/client-ts` + референсная реализация клавиатура+мышь с переводом демо на неё.
- Тач (виртуальные стики/кнопки) и геймпад (Gamepad API) как вторая и третья реализации того же контракта, в порядке продуктового приоритета.
- Центральный сэмплер: латчинг фронтов, свёртка источников, квантование, отправка в канал.
- Биндинги как JSON-данные с валидацией.

**Non-Goals:**

- UI переназначения клавиш в рантайме (данные это уже позволяют — интерфейса нет).
- Жесты камеры на таче сверх минимума (pinch-зум и пан — отдельное изменение capability `camera`).
- Изменения `InputFrame`, протокола оболочки, неткода, ядра.
- Хаптика, key repeat, наборы раскладок под локали клавиатур.

## Decisions

**D1. Слой живёт в `engine/client-ts/src/input/`, не отдельным пакетом и не в render-ts.** Ввод — часть оболочки клиента (SHELL-1 «рендер, ввод и UI — в главном потоке»); render-ts остаётся про картинку и камеру. `heroMoveFromKeys` поглощается клавиатурным источником (в render-ts остаётся только камерное). Отдельный пакет — неоправданная воркспейс-возня для слоя из ~5 файлов.

**D2. Контракт источника: опрос непрерывного состояния + пуш фронтов.** Источник отдаёт по опросу непрерывное состояние (move-вектор в единичном круге, aim либо «нет мнения») и пушит фронты действий в сэмплер в момент возникновения. Альтернатива «источник сам копит фронты, сэмплер их забирает» размазывает латчинг по реализациям — а INP-2 требует латчинг в одном месте. Для опросных устройств (Gamepad API) фронты вычисляет прослойка в том же общем слое сравнением масок prev/current — источник не обязан быть событийным.

**D3. Действия — семантические имена, биты — данные двух уровней.** Источники и биндинги оперируют именами действий (`cast`, `dodge`, `jump`, …). Раскладка «физический орган → имя действия» — биндинги клиента (INP-4); соответствие «имя действия → бит `buttons`» — конфиг рядом с контентом, тот же источник правды, что параметры сцены вида `locomotion.dodgeButton`. Константы `CAST_BUTTON`/… из `demo/sim.ts` становятся этими данными. Альтернатива «биндинги сразу в биты» отвергнута: она дублирует знание о битах во всех раскладках всех платформ.

**D4. Свёртка источников (INP-5): действия — OR, непрерывные — последний активный.** «Активность» — ненулевое/изменившееся непрерывное состояние в этой выборке. Правило детерминировано и дешево; арбитраж по приоритетам устройств отвергнут — игрок с геймпадом и клавиатурой одновременно должен просто получать то, что трогал последним (стандарт индустрии).

**D5. Квантование — в сэмплере, последним шагом.** Единственная точка float → Q16.16 (INP-3): `fixed.fromFloat` для move, целочисленный угол (`TURN_UNITS`) для aim — хелпер `aimAngle` переезжает из демо в слой. Клампы (единичный круг, u16) — до квантования, тоже здесь.

**D6. Тач: источник владеет pointer-событиями зон, рисование — приложения.** `TouchSource` получает геометрию зон (стик движения, стик/тап прицела, кнопки действий) и обрабатывает pointer-события с capture по pointerId; отрисовка накладки — ответственность приложения (демо), не движка. Виртуальный стик — «плавающий» (центр — точка первого касания), это данные конфигурации зоны, не код.

**D7. Геймпад: дремлет до первого события.** Gamepad API опросный и требует пользовательского взаимодействия до появления устройств в `navigator.getGamepads()`; источник активируется по `gamepadconnected` и опрашивается сэмплером в общем такте. Отключение → источник объявляет себя неактивным → нейтраль (INP-5), без залипания.

**D8. Тестирование — headless-юниты на контракт, без браузерной автоматизации.** Сэмплер (латчинг, свёртка, клампы, квантование) и источники (на синтетических событиях) покрываются vitest в `client-ts/test` — так же, как сейчас тестируется канал (`channel.test.ts`). Сквозная проверка на живых устройствах — ручная через демо; e2e-автоматизация тача/геймпада в браузере — за пределами изменения.

## Risks / Trade-offs

- [Конфликт aim двух источников (мышь двигается, стик наклонён)] → правило «последний активный» из D4 применяется к aim отдельно от move; дёрганье возможно только если игрок реально трогает оба одновременно.
- [Фронт с опросного устройства короче интервала опроса (быстрый тап по кнопке геймпада между выборками) теоретически теряем] → опрос геймпада привязан к rAF-каденсу главного потока (~60 Гц ≥ частоты тика); практический риск ничтожен, зафиксирован как известное ограничение опросных устройств.
- [Биндинги-данные добавляют файл конфигурации, который можно сломать] → схема + валидация при загрузке с внятной ошибкой; дефолтные раскладки лежат рядом с кодом и покрыты тестом «дефолт валиден».
- [Перевод демо на новый слой может изменить поведение (порядок латчей, кламп диагонали)] → диагональ уже нормализуется в `heroMoveFromKeys`; поведенческий контракт закрепляется юнитами на сэмплер до миграции демо.

## Open Questions

- Точные дефолтные тач-зоны (размеры, отступы) — подберутся руками на устройстве при реализации `TouchSource`; на спеки и разбиение задач не влияют.
