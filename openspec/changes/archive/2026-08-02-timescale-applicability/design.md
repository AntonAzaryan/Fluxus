## Context

`tech-requirements.md` §5.2 фиксировал применимость TimeScale списком «✅ движение снарядов, физика, LifetimeSystem / ❌ cooldowns, глобальные таймеры, animation speed». При конвертации в OpenSpec список стал нормативным TIME-5 с модальностью `MUST NOT`. Дизайн просит эффект «купол, замедляющий в том числе перезарядку способностей» — под действующей формулировкой такой эффект нереализуем без правки core-спеки или обхода core.

Механизм при этом уже двухосевой:
- **per-system** — система явно опт-инится, беря `getEffectiveDelta` вместо `globalDelta` (TIME-4);
- **per-entity** — на сущности есть или нет источников в `TimeScaleModifiers.sources` (TIME-2/TIME-7).

## Goals / Non-Goals

**Goals:**
- Снять запрет по классу систем; оставить решение автору системы.
- Сохранить предсказуемость для дизайна: если решение свободно, оно обязано быть записано.
- Показать оба направления сценариями: купол, влияющий на кулдауны, и обычный слоу, не влияющий.

**Non-Goals:**
- Не менять сам механизм: `getEffectiveDelta`, reducer-произведение и клампы `[0.05, 4.0]` (TIME-3/TIME-7) не трогаем.
- Не вводить в core список «какие системы опт-ин» — это регистр политики, а не механизма.
- Не решать балансный вопрос «замедляется ли cooldown rewind-ульты» — он остаётся открытым.
- Не переопределять TIME-6: узкие модификаторы остаются предпочтительным инструментом точечного баланса.

## Decisions

**1. Убрать запрет по классу систем, а не расширить белый список.**
Альтернатива — добавить `CooldownSystem` в «✅»-список — оставляет ту же ошибку: core-спека перечисляет геймплейные системы. Перечень пришлось бы править под каждый новый эффект. Ось «кто опт-ин» — это политика, её место в документации конкретной системы.

**2. Взамен запрета — обязанность документировать.**
Свобода без записи даёт непредсказуемое поведение под time-манипуляциями: дизайн не знает, какие системы замедлятся. Требование «SHALL явно документировать своё решение» стоит дешевле реестра в core и проверяется ревью спеки системы.

**3. Animation speed остаётся вне TimeScale — но не как запрет системе.**
Это не «системе нельзя», а «этого слоя нет в симуляции»: анимация — презентация, рендер сам решает, как визуализировать замедленную сущность. Формулировка остаётся `SHALL`, потому что это граница симуляция/рендер (см. `tick-loop` OBS-*), а не выбор автора.

**4. REW-9 — только уточнение области действия.**
Exempt-список — про восстановление снапшота, не про темп течения кулдауна. После снятия запрета из TIME-5 два механизма стали пересекаться в голове читателя; одно предложение разводит их и отправляет балансный вопрос в Open Questions `time-system`. Текст самого исключения не меняется.

## Risks / Trade-offs

- **Дизайн опт-инит слишком много систем, всё «плывёт» под слоу** → TIME-6 сохранён и остаётся дефолтным инструментом: узкий `MoveSpeedModifier` вместо широкого TimeScale. TimeScale — для эффектов, где замедляется всё поведение сущности сразу.
- **«SHALL документировать» не проверяется автоматически** → проверяется ревью спеки системы; отдельного линтера не заводим, пока систем единицы.
- **Кулдаун под TimeScale × rewind-exempt даёт неочевидную комбинацию** → зафиксировано открытым вопросом в `time-system`, решается балансом, а не спекой ядра.
- **Отмена ранее принятого решения** → в спеке сохранён след: изменение оформлено отдельным change, а не «правкой заодно» в общем post-conversion fix.

## Migration Plan

Кода ядра ещё нет — миграции нет. При появлении `CooldownSystem` (roadmap, этап 11+) её спека обязана содержать строку «учитывает / игнорирует TimeScale».

## Open Questions
