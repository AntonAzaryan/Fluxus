## Context

Мотивация — proposal.md (Why); требования — делта `specs/bot-player/spec.md` (BOT-8..11, MODIFIED BOT-6). Сегодняшний классический мозг (`engine/bot-ts/src/brains/classic/`) уже слоёный: восприятие (`perception.ts`), выбор маршрута utility-скорингом (`utility.ts`: `scoreBehaviors` — четыре захардкоженные формулы полезности, `UtilityLayer` — каденс передумывания и гистерезис), геометрия действий (`planFor` + steering-хелперы), способности (`abilities.ts`), микро (`micro.ts`), сеяный шум (`random.ts` — wall-clock'а в мозге уже нет). Данные в документ выносит ровно один слой — формулы `scoreBehaviors`; всё остальное — механизм и остаётся кодом.

## Goals / Non-Goals

**Goals:**

- Evaluator-мозг `brains/evaluated/`, читающий политику выбора маршрута из документа поведения; классическая политика воспроизведена референсным документом (паритет), после чего `classic` удалён.
- Закрытые словари входов/кривых/исполнителей; валидация документа с находками ru/en по образцу профиля.
- Трасса решений и детерминизм evaluator'а (BOT-10, BOT-11).

**Non-Goals:**

- Слой способностей в документ поведения не переезжает: политика способностей остаётся профилем (cast-блоки BOT-6); её эволюция — смежное изменение `bot-ability-hints` и отдельная работа после него.
- Никакого генерального DSL выражений: никаких формул в документе, только «вход → кривая → вес» (защита от inner-platform, BOT-9).
- Инструмент визуализации трассы на стенде — вне изменения; трасса пишется файлом/колбэком, смотреть её первым временем можно глазами и jq.
- Компиляция документа в код — не сейчас; форма документа лишь не должна ей мешать (решение из proposal).

## Decisions

### D1. Evaluator замещает один слой, остальные переиспользует

`brains/evaluated/` строится из тех же `Perception`, `AbilityLayer`, `MicroLayer`, `planFor` и `brainRandom`, что классический мозг; заменяется только пара `scoreBehaviors`/`UtilityLayer` — на скоринг по документу с тем же каденсом передумывания из `profile.decision` и тем же умолчанием `retreat` при нулевых очках (умолчание — механизм, BOT-9). Слои переезжают из `brains/classic/` в нейтральное место (`brains/layers/`), `classicBrain.ts` и `utility.ts` после паритета удаляются. Альтернатива — писать evaluator с нуля — отклонена: perception/micро и есть исполнители, их дублирование сломало бы паритет.

### D2. Форма документа поведения

```json
{
  "schema": 1,
  "name": "classic",
  "actions": [
    { "executor": "pressure",
      "considerations": [
        { "input": "enemyDistance", "curve": { "type": "linear", "slope": -1, "intercept": 1 }, "weight": 0.8 }
      ] }
  ]
}
```

- Словарь исполнителей v1 — сегодняшние `BOT_BEHAVIORS` (`pressure`, `kite`, `retreat`, `dodge`): исполнитель = ветка `planFor`. В коде словарь называется `BOT_EXECUTORS` и живёт в модуле документа: BOT-9 называет эти имена ИСПОЛНИТЕЛЯМИ, и «поведение» осталось за документом целиком.
- Словарь входов v1 — ровно то, что читают сегодняшние формулы: `enemyDistance` (нормирован `engageRange` профиля), `enemyKnown`, `threatDistance`, `threatClosing`, `edgeProximity` (нормирован `edgeMargin`/радиусом арены), `abilityCooldownFraction` (доля оставшегося собственного кулдауна по слоту). Нормировка входов в [0, 1] — код словаря, не документ.
- Кривые v1: `linear`, `quadratic`, `logistic`, `constant`; параметры — поля кривой. Оценка клампится в [0, 1].
- Композиция — произведение оценок × `weight` действия… нет: `weight` живёт на consideration'е, полезность действия — произведение оценок consideration'ов (каждая уже с весом через кривую/вес, кламп после каждого шага). Компенсацию Дэйва Марка (штраф за число осей) в v1 не вводим — осей мало; форма позволяет добавить полем документа позже.
- `schema` и `name` обязательны (BOT-8): версия — чтобы документ прошлой формы отличался явно, имя — чтобы находки валидации адресовались документу, а не «документу поведения бота». Валидация — по образцу `profile.ts`: структура находок та же (и язык тот же — русский, как у профиля).
- **Уточнено имплементацией.** Дистанция боя профиля (`movement.engageRange`) — МАСШТАБ входов `enemyDistance`/`threatDistance`, поэтому валидация профиля требует её строго положительной: ноль отменяет шкалу, и кривая документа поверх неё считает не политику, а деление на ноль под клампом. Прежний код на нулевой дистанции боя обнулял все четыре полезности делением на ноль под клампом — поведение, которое никто не настраивал и выразить документом нельзя.
- **Уточнено имплементацией.** Вес consideration'а ограничен диапазоном [0, 1]: оценка оси — `clamp01(кривая) × вес`, полезность действия — их произведение, и вес больше единицы вывел бы произведение за диапазон, сохранять который требует BOT-9. Приоритет выражается ОТНОШЕНИЕМ весов, поэтому любую политику можно ужать в [0, 1], не поменяв ни одного решения: общий положительный множитель сравнений не трогает. Референсные документы этим и пользуются — веса профилей формы 2 поделены на 2 (`retreat` 1.2 → 0.6, `dodge` 1.3 → 0.65, `pressure` 0.6×1 → 0.3, `kite` 0.4×0.8 → 0.16); деление на степень двойки в double точно, поэтому паритет вышел не «по решениям», а побитовым.

### D3. Доставка документа — как профиль, связка — данными

Профиль получает поле `behavior` — путь документа поведения в дереве контента (соответствие бота документу — данные, BOT-8). Загружает и парсит документ та же сторона сборки, что сегодня читает профиль (fill/стенд/тесты — они читают контент законно), и передаёт его фабрике evaluator'а опцией конструирования — тем же путём, что `terrain` и `center` у классики. `bot-ts` документ с диска не читает (CONT-4 не ухудшается).

### D4. Паритет и удаление классики

Референсный документ `content/bots/behaviors/classic.json` переписывает четыре формулы `scoreBehaviors` в considerations один в один (агрессивность и веса `profile.utility` уезжают в него; профиль — schema 3, без `utility` и `aggression`). Паритет проверяется на решениях, не на битах float: тест кормит оба мозга одним потоком наблюдений с одним seed и сравнивает последовательности выбранных маршрутов и намерений; формулы алгебраически совпадают, поэтому ожидание — точное совпадение, но контракт теста — решения. После зелёного паритета: `brains/classic/classicBrain.ts` и `utility.ts` удаляются, сборки (fill, демо-стенд, botWorker, тесты) переключаются на `evaluatedBrain(...)`, паритетный тест умирает вместе с классикой (его роль — ворота, не регресс).

### D5. Трасса решений

Опция конструирования `onDecision(record)` — колбэк с разбором пересчёта (тик, оценки consideration'ов по действиям, победитель). Ноль стоимости при выключенной трассе (без колбэка записи не строятся). Потребители: тесты мозга и стендовый лог в файл. В голдены и трассы ядра не попадает по построению — это другой канал (BOT-10, CLI-7).

### D6. Детерминизм

Evaluator наследует дисциплину классики: единственная случайность — `brainRandom(seed)` из профиля, wall-clock отсутствует (BOT-11). Тест: два прогона evaluator'а на записанном потоке `ClientStep` → идентичные намерения.

## Risks / Trade-offs

- [Паритет по битам float хрупок при перестановке операций] → контракт теста — последовательность решений и намерений, а не биты; формулы референсного документа повторяют исходные алгебраически.
- [Ползучее расширение словарей «ещё один вход, ещё одна кривая»] → каждый новый элемент словаря — код с ревью и требованием BOT-9; документ его не introduces.
- [Профиль schema 3 ломает существующие документы] → контент наш и в одном дереве: профили и тесты мигрируются в этом же изменении, обратная совместимость не нужна (валидация версии отвергает старые явно, BOT-8/профильная конвенция).
- [Все действия с нулевой полезностью из-за ошибки кривых] → умолчание `retreat` — механизм (BOT-9), бот остаётся живым; трасса решений показывает нули.

## Migration Plan

Одно изменение, один PR: (1) словари+evaluator+валидация, (2) референсные документы и профили schema 3, (3) паритетные ворота, (4) удаление классики и переключение сборок, (5) `npm run check`. Отката по флагу нет — до паритета классика остаётся default в дереве, удаление — последний коммит изменения.
