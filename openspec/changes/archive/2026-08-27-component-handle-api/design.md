# Design: component-handle-api

## Context

Мотивация и замер — `proposal.md`. Существенное для подхода:

- Хранилище — SoA на TypedArray (`ecs/world.ts`); компонент → store, поле → массив; сегодня путь чтения `getField(state, entity, component: string, field: string)` резолвит оба имени словарями на каждый вызов и делает проверку владения (ECS-7: тотальное чтение — ноль + диагностика).
- Хранилище растёт (спавн), а на перемотке буферы подменяются восстановлением из снапшота — «сырой» указатель на колонку не переживает ни того, ни другого.
- `SystemContext` — нормативный контракт (SYS-5); расширение состава — правка требования, что этот change и делает.
- Потребители строкового пути: нативные системы (~120 call sites `ctx.get` по `systems/`), DSL-evaluator (имена — его природа, не мигрирует), тесты.

## Goals / Non-Goals

**Goals:**

- Убрать строковый поиск из горячих циклов нативных систем; целевой эффект измерим на `npc-stress` (сейчас ~3.5 мс/тик на 196 крипов, доминирует `ctx.get`).
- Побитовая неизменность поведения: golden-эталоны не пересчитываются вовсе.

**Non-Goals:**

- Депрекация строковых `get`/`has` — остаются для DSL и единичных чтений.
- Запись по handle — не существует по построению (TICK-3).
- Миграция DSL-evaluator'а — у него собственное разрешение имён на компиляции документа; отдельная тема.
- Изменение `query`/`QuerySpec` — форма запросов не трогается.

## Decisions

**D1. Handle — числовые id, не ссылки на массивы.** `FieldHandle`/`ComponentHandle` кодируют id компонента и индекс поля (упакованные числа или маленькие замороженные структуры, создаваемые на разрешении — вне тика, поэтому аллокация легальна). Чтение по handle: две индексации массивов вместо двух словарных поисков; сама функция чтения живёт рядом с `getField` и разделяет с ним проверку владения и диагностику ECS-7 — семантика одна по построению, а не по дисциплине.

**D2. Разрешение — на конструировании системы.** Нативные системы резолвят свои handle там же, где сегодня хранят имена компонентов (конструктор/фабрика при загрузке сцены). Ошибка на неизвестном имени — немедленно, находкой с именем (SYS-10).

**D3. Миграция горячих циклов, не всех call sites.** Первым — пакет NPC (behavior/movement/threat/perception/director — измеренное узкое место), затем physics, locomotion, abilities/runtime, visibility, tween тем же паттерном. Единичные чтения вне циклов могут остаться строковыми — критерий: чтение на каждую сущность каждый тик мигрирует, разовое — по вкусу.

**D4. Паритетный тест как ворота эквивалентности.** Тест гоняет один мир и сверяет `getByHandle` против `get` побитово по всем компонентам/полям/сущностям, включая случай отсутствия владения (ECS-7) и чтение после перемотки. Плюс нулевой дифф golden-эталонов как интеграционное доказательство.

**D5. Счётчики стоимости не меняются.** Cost-эталоны меряют единицы работы (PERF-3), не способ доступа — они обязаны не измениться; wall-time сентинелы (PERF-5) и `npc-stress` тайминги — диагностика улучшения.

## Risks / Trade-offs

- [Handle с protective-проверками съест выигрыш] → проверка владения — одна битовая маска, как в `getField`; выигрыш — отказ от двух словарных поисков, он остаётся. Мерить на `npc-stress` до/после.
- [Раскрытие внутренних id наружу пакета] → handle — opaque-тип на публичной границе (брендированный тип), содержимое не нормируется и не читается потребителем.
- [Два пути чтения разъезжаются семантикой] → одна общая внутренняя функция после разрешения имён (D1): строковый путь = резолв + handle-путь.
- [Миграция ~120 call sites внесёт опечатку] → побитовый golden-дифф нулевой по построению; паритетный тест D4; миграция посистемно, гейт после каждой.

## Migration Plan

1. Ядро: типы handle, резолверы, чтение по handle, паритетный тест (D4).
2. Миграция пакета NPC + замер `npc-stress` до/после.
3. Миграция остальных нативных систем (physics, locomotion, abilities, visibility, tween).
4. Полный гейт; golden и cost-эталоны обязаны быть нетронуты.

Отката не требуется: строковый путь не меняется, handle-путь добавляется рядом.

## Open Questions

- Форма handle (упакованное число vs замороженная структура) — деталь реализации за opaque-типом, выбирается по бенчу; спека не фиксирует.
