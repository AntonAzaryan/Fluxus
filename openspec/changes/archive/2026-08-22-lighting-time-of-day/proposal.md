# Proposal: lighting-time-of-day

## Why

Свет арены сегодня статичен: секция `lighting` парного presentation-документа (REND-29) описывает один набор значений, и сменить его в рантайме можно только правкой секции целиком (`applyConfig`, ED-15). Живая смена времени суток — утро, день, закат, ночь — делает арену заметно атмосфернее и является чисто presentation-возможностью: симуляция о ней не знает ни байтом (PRES-4). Демо-арена должна показывать цикл сразу и без ручного переключателя: полный круг за 8 минут, по 2 минуты на фазу.

## What Changes

- Секция `lighting` парного presentation-документа получает необязательную подсекцию цикла: упорядоченный список фаз, каждая — полный набор значений света (тон/интенсивность рассеянного и направленного, направление) плюс длительность фазы и длительность перехода. Имена фаз («утро», «ночь») — авторские данные, не словарь движка: механизм видит упорядоченный список, политика имён — у сцены.
- Подсистема освещения (`LightingSubsystem`, REND-29) исполняет цикл сама: продвигает фазы по кадровым часам рендера, плавно интерполирует значения света между фазами и зацикливает список. Потребители рендера (демо, вьюпорт редактора) не пишут ни собственного драйвера цикла, ни чисел света — тождество кадров ED-22 сохраняется по построению.
- Взаимодействие плавного перехода с тенями (REND-30): смена значений света перестаёт быть исключительно событием перерисовки кэша статики — на время перехода подсистема обязана держать корректные тени без покадровой перерисовки кэша статики в `hybrid`; политика — в design.
- Сцена без подсекции цикла ведёт себя байт-в-байт как сегодня: статическая секция, никаких переходов. Импорт Blender секцию по-прежнему не трогает (BLND-2 — уже гарантировано текстом PRES-2).
- Контент: `content/scenes/duel.presentation.json` получает цикл из четырёх фаз — утро, день, закат, ночь — по 120 секунд каждая, по кругу. Это правка данных, не спеки.
- Валидация: состав подсекции закрыт, неизвестный ключ отвергается адресно — по общему правилу PRES-2; вырожденные значения (пустой список фаз, нулевые длительности) отвергаются валидацией.

## Capabilities

### New Capabilities

Нет: возможность целиком ложится в существующую capability `rendering`.

### Modified Capabilities

- `rendering`: REND-29 — состав секции `lighting` расширяется подсекцией цикла времени суток (список фаз, длительности, переходы); REND-30 — оговорка о кроссфейде: запрет покадровой анимации света в `hybrid` остаётся в силе ВНЕ перехода фаз, а на время перехода подсистема обязана приводить тени к действующему свету покадрово, и стоимость этого видна счётчиками (PERF-3); новое требование REND-32 — исполнение цикла подсистемой: кадровые часы, плавная интерполяция, зацикливание, инвариант «на симуляцию и на снапшоты ни байтом», поведение теней на переходе (связь с REND-30), умолчания и совместимость сцен без цикла.

## Impact

- `engine/render-ts`: `subsystems/lighting.ts` — состояние цикла и интерполяция в `updateFrame`, политика теневых карт на переходе; `lighting/config.ts` — разрешение подсекции цикла в действующую конфигурацию. Отладочный источник освещения (RDBG) показывает текущую фазу и прогресс перехода.
- `engine/assets-ts`: формат `PresentationLighting` — тип и валидация подсекции цикла (закрытый состав, адресные находки).
- `editor/core-ts` / `editor/ui-ts`: без правок кода ожидаемо — валидация приходит из assets-ts, вьюпорт получает цикл той же подсистемой; проверить ED-15/ED-22 тестами.
- `game/demo-ts`: правка `content/scenes/duel.presentation.json` (цикл 4×120 с); кода демо не меняется — переключателя нет по замыслу.
- `performance-budget`: покадровая работа цикла обязана быть константной (QUAL-3 — объявить константную стоимость или ручку); cost-эталоны (`*.cost.json`) могут измениться от новой теневой политики перехода — принятие диффа через `npm run golden:cost` отдельным решением.
- Симуляция, сеть, golden-эталоны симуляции: не затронуты (PRES-4 — правка presentation-слоя не меняет ни `worldInit`, ни снапшоты).
