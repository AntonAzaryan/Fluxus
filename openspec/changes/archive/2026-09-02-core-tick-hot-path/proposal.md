# Горячий путь тика: адрес команды, чтение по индексу запроса и результат без аллокации

## Why

Замер запаса тика под массовой нагрузкой (`docs/reviews/2026-09-02-core-tick-headroom.md`) профилировал релизный тик на `npc-stress`, размноженной до 784 агентов, и назвал три верхних гэпа. Все три — про АДРЕСАЦИЮ и КОНТЕЙНЕРЫ, а не про правила симуляции: результат тика ни один из них не меняет.

- **Командный буфер — ~15 % релизного тика.** Каждая запись поля стоит объекта `{ kind, entity, component, field, value }` со строковыми именами, которые проход валидации разрешает по словарю, а проход применения — второй раз (`world.setField` → `storeOf` → `fieldTypeOf`). На 784 агентах это ~4 000 короткоживущих объектов на тик: ровно та аллокация, пропорциональная числу сущностей, которую аллокационная дисциплина ядра запрещает в горячем пути.
- **Чтение полей — ~18 %.** `posX(ctx, handles, e)` — это пять уровней косвенности до ячейки: замыкание контекста, `getFieldByHandle`, `readByHandle`, распаковка идентификатора и проверка маски. Для сущности, только что выданной запросом, перечислившим этот компонент в `all`, и живость, и владение доказаны построением, и пять шагов ради одного чтения — чистые накладные расходы.
- **Результат запроса — ~5 % плюс давление на сборщик мусора.** `query()` выделяет `new Float64Array(aliveCount)` на КАЖДЫЙ вызов: на 784 агентах и десятке запросов за тик это десяток буферов по шесть килобайт, живущих один тик.

Спека при этом двух вещей прямо не разрешает: SYS-10 говорит «Канала записи по handle MUST NOT существовать» (о ссылке на колонку, но читается шире), а QUERY-3 запрещает общий переиспользуемый буфер под результаты. Изменение делает границу точной: запрещённым остаётся то, ради чего запрет писался, — изменяемая ссылка на колонку хранилища и ОБЩИЙ буфер, — а адресация команды числом и СОБСТВЕННЫЙ буфер системы разрешаются явно.

## What Changes

- **`ecs-foundation` CMD-1:** адрес команды записи поля бывает двух видов — имя и handle (SYS-10), — и это ОДИН канал: порядок применения общий (CMD-3), точечное чтение видит обе (CMD-5), исход симуляции от способа адресации не зависит.
- **`ecs-foundation` CMD-5:** точечное чтение буфера отвечает о ПОЛЕ, а не о способе, которым команда была заказана.
- **`ecs-foundation` QUERY-3:** нативная система MAY передать запросу СВОИ буферы под результат; запрет ОБЩЕГО переиспользуемого буфера остаётся, а дисциплина вложенных запросов становится обязанностью системы. Форма `query` для JSON-систем (SYS-5) не меняется.
- **`data-driven-systems` SYS-5:** в контракт границы добавлены `queryInto` (выборка в буферы вызывающего) и `getByIndex` (чтение по raw-индексу слота из этой выборки).
- **`data-driven-systems` SYS-10:** запрет переформулирован — не существует изменяемой ССЫЛКИ НА КОЛОНКУ; запись по handle есть та же команда буфера (CMD-1, TICK-3 не трогается). Добавлена форма «чтение по индексу запроса» с условиями годности индекса.
- **Ядро:** `CommandBuffer.setFieldByHandle`, журнал команд в типизированных массивах (растут удвоением, переиспользуются между тиками), `ctx.queryInto`/`ctx.getByIndex`, буфер выборки, которым владеет система. Горячие нативные системы — платформа NPC, физика, локомоушен, пересчёт видимости — переведены на эти каналы; JSON-системы и холодные нативные остаются на строковом пути.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `ecs-foundation`: CMD-1 — адресация команды записи поля; CMD-5 — точечное чтение независимо от адресации; QUERY-3 — буфер результата, принадлежащий системе.
- `data-driven-systems`: SYS-5 — состав `SystemContext`; SYS-10 — граница запрета и чтение по индексу запроса.

## Impact

- `engine/core-ts/src/ecs/{commands,query,world,fieldTable}.ts`, `src/sim/tick.ts`, `src/types.ts`, новый `src/systems/queryBuffer.ts`; потребители — `src/systems/npc/*`, `src/systems/{physics,locomotion,visibility}.ts`.
- Golden- и cost-эталоны НЕ двигаются: ни правил, ни порядка, ни числа команд правка не меняет — `commandsApplied` считается ровно как считался. Трейс тоже не двигается: запись о команде, заказанной по handle, собирает имена из плоской таблицы полей мира и побайтово равна записи строковой команды.
- Требований не прибавляется: пять существующих уточняются, новых номеров ни в одном префиксе не заводится.
