# Design: editor-camera-seam

## Context

Мотивация — `proposal.md`, требования — дельты `specs/camera/spec.md` и `specs/editor/spec.md`. Здесь — только то, что не является требованием: состояние кода на момент change'а и объём правки.

Камера реализована полностью (`engine/render-ts/src/camera/`: `rig.ts`, `effects.ts`, `director.ts`) и почти целиком готова к второму потребителю — это видно по её собственному `design.md` (Decision 4), где редактор упомянут прямо: «в редакторе, где тикающей симуляции нет, та же пара реализуется поверх редактируемого документа террейна».

Проверка кода это подтверждает:

- `CameraRig.update(input, dt, target: FollowTarget | null)` — от `TickView` не зависит, follow-цель nullable.
- `CameraRigOptions` принимает `groundHeightAt(x, y)` и `bounds` инжекцией; `terrainGroundApi(grid, heightStep)` — лишь одна из их реализаций, поверх `TerrainGrid`.
- Слой эффектов уже опционален: демо ходит по ветке `director === null`.

То есть CAM-7 фиксирует свойство, которым код уже обладает, а не требует переделки. Незакрытым остаётся одно место.

## Goals / Non-Goals

**Goals:**

- Сделать переиспользование конвейера камеры редактором требованием, а не возможностью.
- Убрать единственное место, где редактору пришлось бы копировать код камеры.
- Закрыть авторинг манифеста визуалов, который не покрывала ни одна редакторская требование.

**Non-Goals:**

- Не делается редактор: ED-13 и ED-14 — требования к будущей реализации (этап 12 roadmap отложен).
- Не меняется поведение камеры в игровом клиенте: перенос функции не трогает ни одну формулу.
- Не проектируется UI редактора манифеста — ED-14 говорит, что должно редактироваться, а не как выглядит.

## Decisions

### 1. `applyPose` переезжает в `render-ts`

Сегодня применение позы к `THREE.PerspectiveCamera` — локальная функция `applyPose` в `engine/client-ts/demo/main.ts`: позиция, `lookAt` по yaw/pitch, `rotateZ` для roll, обновление `fov` с `updateProjectionMatrix`. Это и есть «ровно одна точка» из старой формулировки CAM-1 — но лежит она в демо, куда редактор не ходит.

Оставить как есть — значит гарантировать копипаст: редактор напишет свою такую же функцию, и дальше они разъедутся в мелочах (порядок roll и lookAt, сравнение fov перед пересчётом матрицы проекции), а разъедутся они как раз в кадре, ради совпадения которого всё и затевалось. Функция чистая и three.js-специфичная — её место рядом с rig'ом, в пакете, который ED-1 обязывает редактор использовать.

Альтернатива «вынести в `client-ts`» отвергнута: `client-ts` — оболочка веб-клиента (SHELL-1..7), редактор её берёт ради воркер-хоста превью, а не ради камеры; зависимость «вьюпорт → оболочка клиента» ради одной функции лишняя.

### 2. CAM-1 правится, CAM-7 добавляется — а не наоборот

CAM-1 начиналась со слов «чистым клиентским состоянием», и это ровно та привязка, которую надо снять: редактор — не клиент. Заводить вместо этого отдельное требование «а ещё конвейер годится редактору» значило бы оставить в CAM-1 неверное слово и приписать к нему исключение.

CAM-7 добавлено отдельно, потому что говорит о другом: не о том, чей это конвейер, а о том, что он не требует идущего матча — nullable follow-цель, инжектируемая поверхность, опциональные эффекты. Это проверяемые свойства реализации, каждому нужен свой сценарий.

### 3. Типы эффектов редактор берёт из описания, а не списком

ED-14 требует, чтобы набор типов эффектов камеры приезжал в редактор описанием, как component-схемы в ED-2. Причина та же: ASSET-8 делит мир на «типы эффектов — код камеры, привязка и числа — манифест», и захардкоженный список типов в редакторе сделал бы добавление эффекта правкой в двух местах. Форма описания — вопрос реализации этапа 12; сегодня в коде камеры типы известны `CameraEffectsDirector`, и описание естественно порождать оттуда, по образцу `npm run schemas` для ядра.

## Risks / Trade-offs

- **[Перенос `applyPose` ломает демо]** → функция чистая, вызов один, покрытие даёт существующий прогон `npm test` и `npm run typecheck` из корня; поведение проверяется тем же демо.
- **[ED-13 связывает редактор с камерой жёстче, чем нужно для разметки террейна]** → отклонения от игрового кадра разрешены явно, но как режимы конвейера (CAM-2 уже содержит fly), а не как второй способ считать позу.
- **[ED-14 — крупное требование для отложенного этапа]** → оно и раньше подразумевалось ED-3, просто не было записано; риск в том, чтобы забыть его к моменту реализации, а не в объёме.

## Migration Plan

Порядок: спеки (дельты + `## Purpose` капаbility `camera` напрямую), затем перенос функции с прогоном тестов, затем дрейф документов. Откат — обратный change; в рантайме к этому времени меняется одна функция, вызываемая из одного места.

## Open Questions

- Форма описания типов эффектов для редактора (генерируемая схема против рефлексии по реестру эффектов) — решается при реализации ED-14, требований не меняет.
