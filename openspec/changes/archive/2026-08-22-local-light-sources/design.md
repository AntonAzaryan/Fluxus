# Design: local-light-sources

## Context

Подсистема освещения (`engine/render-ts/src/subsystems/lighting.ts`) владеет глобальным светом: ambient + directional, пара источников в `hybrid`, цикл суток. Инстансами владеют подсистемы моделей и декораций; подсистема освещения уже держит порт `ShadowCasterSink`, в который те регистрируют корни кастеров, — направление порта задаёт порядок регистрации (REND-31: владелец порта регистрируется раньше). three.js — форвард-рендерер: число источников света входит в программу каждого освещаемого материала, смена числа перекомпилирует шейдеры.

## Goals / Non-Goals

**Goals:**

- Локальный свет как свойство записи манифеста, жизненный цикл — вместе с инстансом, для всех трёх источников инстансов (тики, документный набор, декорации).
- Константная стоимость переключения активных источников: без перекомпиляции шейдеров на кадре.
- Потолок и счётчики с первого дня (QUAL-3, PERF-3).

**Non-Goals:**

- Тени локальных источников (REND-30 — только directional).
- Анимация света (фликер факела) — отдельный чейндж поверх готового механизма.
- Свет в фазах цикла суток: цикл (REND-32) правит глобальный свет; локальные источники от фаз не зависят.
- Area-light, IES-профили, отражения.

## Decisions

- **D1. Порт носителей света по образцу `ShadowCasterSink`.** Подсистема освещения объявляет `LightCarrierSink`; подсистемы моделей и декораций регистрируют носителя при создании инстанса записи с блоком `light` (ключ записи, разобранный блок, провайдер трансформа инстанса) и снимают при исчезновении. Альтернатива — освещение само читает presentation-состояние — отвергнута: трансформы и жизненный цикл инстансов принадлежат их подсистемам, второй просмотр состояния дублировал бы их логику.
- **D2. Пул источников фиксированного размера = потолок ручки.** `THREE.PointLight`/`SpotLight` создаются один раз в число потолка; неактивный слот — `intensity = 0`, объект остаётся в сцене. Число источников в программе материалов константно → нет перекомпиляций при переключении активных. Смена потолка (applyQuality) пересоздаёт пул — событие, не кадровый путь.
- **D3. Отбор активных — по расстоянию до точки взгляда камеры.** Метрика: расстояние от опоры источника (с учётом `offset`) до look-at камеры минус `distance` источника; тай-брейк — устойчивый ключ носителя (ключ записи + порядковый индекс в его подсистеме), не рантайм-порядок создания. Повтор кадра даёт тот же отбор (ED-22, воспроизводимость). Жёсткое переключение без фейда — принятый компромисс MVP (см. Risks).
- **D4. Единицы авторских величин — конвенции репозитория.** Углы — доли оборота (как `yaw` PRES-2), длины — мировые единицы; конверсия в радианы/метры three.js — на границе разбора манифеста (`assets-ts`), в рендер блок приходит готовым. Умолчание `decay` — 2 (физическое затухание three.js), документируется в типе.
- **D5. Счётчики стоимости.** В сток кадра — `localLightCarriers` (носители в сцене) и `localLightsActive` (активные за кадр), посекционно по пресетам, как счётчики теней REND-30. Демо-бейзлайны потяжелеют от света `Torch` — принимается явно через `npm run golden:cost`.
- **D6. Снос.** Пул источников и реестр носителей освобождаются точкой освобождения подсистемы освещения (REND-31); носители снимают себя сносом своих подсистем — порядок обратной регистрации это гарантирует.

## Risks / Trade-offs

- [Попинг на границе отбора: источник у края потолка мигает при движении камеры] → потолок пресетов ставится щедрым к реальной сцене (носителей ≈ потолок), метрика D3 непрерывна; фейд интенсивности — дешёвый follow-up, механизм его не блокирует.
- [Форвард-рендер: стоимость шейдера растёт с потолком для всех материалов] → потолок и есть ручка этой стоимости; ultra-значение подбирается по `npm run bench:demo`, не умозрительно.
- [Дифф `*.cost.json` демо] → отдельный коммит `npm run golden:cost` с объяснением, по конвенции PERF-3.
- [Spot вниз по умолчанию бесполезен для настенных факелов] → `direction` авторский; умолчание «вниз» выбрано как самое частое для арен сверху и документировано.

## Open Questions

- Значения потолка в пресетах демо (`performance`/`balanced`/`ultra`) — подобрать на живом демо и бенче при имплементации; спеку и разбивку задач не меняют.
