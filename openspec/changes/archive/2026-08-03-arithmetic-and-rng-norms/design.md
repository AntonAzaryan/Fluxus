## Context

`engine/core-ts` уже реализует правильные значения (wrapping, насыщающее деление, `sqrt(<0) → 0`, Lemire-отбраковка), а нынешний единственный `assert()` в `src/debug.ts` бросает исключение в debug-сборке для всех этих мест без разбора. Это работает случайно: ни один golden-сценарий (`engine/tests/golden/`) не доводит вход до `wrap`-переполнения, `div(_, 0)` или `sqrt(<0)`, поэтому тесты зелёные, но норма не отличает «диагностика» от «граница инварианта» — а разница есть уже в самом коде (жёсткий `throw` при `allocate` сверх capacity vs мягкое предупреждение при переполнении `generation`).

Это change — только нормирование: возвращаемые значения нигде не меняются, меняется исключительно то, что происходит с диагностикой при нарушении.

## Goals / Non-Goals

**Goals:**

- Развести диагностику на «мягкую» (не бросает, не влияет на результат) и «жёсткую» (бросает всегда) — механически (core), не по вкусу вызывающего места.
- Зафиксировать словами то, что код уже делает верно (`FP-2` truncate toward zero через магнитуду+знак, `sqrt(<0) → 0`).
- Дать `nextFixed`/`nextBelow` дословную, воспроизводимую в Rust формулировку, включая то, что отбраковка — часть детерминированного контракта.
- Не тронуть golden-эталоны: поведение симуляции побитово то же самое.

**Non-Goals:**

- Не меняется ни один численный результат операции.
- Не добавляется новый способ конфигурировать assert из JSON/DSL — sink подключается только программно (для тестов и, возможно, будущего логирования на хосте).
- Rust-порт самих функций — вне этого change'я, здесь только норма, которую он обязан воспроизвести.

## Decisions

### Мягкое/жёсткое — таблица

| Место | Функция | Было (throw в debug) | Стало |
|---|---|---|---|
| `fixed.ts` `wrap` | `add/sub/mul/div/abs/sqrt` при переполнении | throw | мягкий `assert` |
| `fixed.ts` `div` | деление на 0 | throw | мягкий `assert` (результат уже был `INT32_MAX`/`MIN`/`0`) |
| `fixed.ts` `sqrt` | отрицательный операнд | throw | мягкий `assert` (результат уже был `0`) |
| `entityIndex.ts` `free` | переполнение `generation` | throw | мягкий `assert` (результат уже был wrap по модулю) |
| `componentMask.ts` `checkBounds` | index/componentId вне диапазона | throw | мягкий `assert` |
| `entityIndex.ts` `createEntityIndex` | недопустимая `capacity` | throw | `assertInvariant` (бросает как раньше — граница рождения) |
| `entityIndex.ts` `makeEntityId` | index/generation вне 24 бит | throw | `assertInvariant` |
| `entityIndex.ts` `allocate` | превышена capacity | throw | `assertInvariant` |
| `rng.ts` `nextBelow` | `bound < 1` | throw | `assertInvariant` |

Критерий разделения: если у операции есть детерминированное продолжение с уже вычисленным значением (wrap, насыщение, 0) — это диагностика (`assert`), она не должна прерывать симуляцию. Если продолжения нет (индекс за пределами structural-массива, id вне 24 бит, capacity исчерпана) — это `assertInvariant`, потому что дальше нечего детерминированно возвращать.

### Интерфейс sink

```ts
// src/debug.ts
export type AssertSink = (message: string) => void;

let sink: AssertSink = () => {};
export function setAssertSink(fn: AssertSink): void {
  sink = fn;
}

export function assert(condition: boolean, message: string): void {
  if (!condition) sink(`assertion failed: ${message}`);
}

export function assertInvariant(condition: boolean, message: string): void {
  if (!condition) throw new Error(`invariant violated: ${message}`);
}
```

По умолчанию sink — no-op (не `console.error`): в vitest под `DEBUG=true` каждый существующий тест на переполнение/деление-на-ноль/sqrt<0 иначе печатал бы в stdout при каждом прогоне, что шумит без пользы. Тесты, которым нужно проверить, что диагностика сработала, подставляют свой sink через `setAssertSink` и снимают его в `afterEach`.

Вызовы `assert`/`assertInvariant` остаются внутри `if (DEBUG)` там, где сегодня так — `assertInvariant` не зависит от `DEBUG` вообще (бросает в обеих сборках), поэтому вызовы `assertInvariant` пишутся без обёртки `if (DEBUG)`; мягкий `assert`, наоборот, вызывается только под `if (DEBUG)`, чтобы в release не было даже вызова функции на hot-path (совпадает с нынешним паттерном).

### `checkBounds` остаётся приватной, обёртку `if (DEBUG)` переносим внутрь неё

Сейчас `if (DEBUG) checkBounds(...)` дублируется в каждом вызывающем месте `componentMask.ts` (6 мест). Задача явно просит перенести `if (DEBUG)` внутрь самой функции — тогда вызывающий код зовёт `checkBounds(...)` безусловно, а функция сама решает, проверять ли (и не платит цену в release, потому что `assert` внутри неё — no-op по построению по мягкой ветке, а вызов `checkBounds` в release превращается в пустую функцию, вызов которой V8 инлайнит/элиминирует не хуже, чем нынешний `if` снаружи). Это не меняет наблюдаемое поведение, только убирает 6 копий одинакового условия.

### FP-2 — только формулировка, код не трогается

`mul`/`div` в `fixed.ts` уже считают магнитуду отдельно от знака (строки 52-69, 76-87) — ровно то, что теперь описывает `FP-2`. Изменение — исключительно текстовое (спека), никакого кода в этом файле для FP-2 менять не нужно.

## Risks / Trade-offs

- **Молчаливое поглощение реальных багов в release.** Мягкий `assert` в release теперь не бросает вообще (раньше в debug бросал, в release не вызывался — тот же итог, значение всегда было wrapping/saturating). Поведение не меняется, риск не новый.
- **No-op sink по умолчанию прячет диагностику, если её не подключить явно.** Осознанный выбор — подключение sink оставлено потребителю (например, CLI/логгеру на хосте), это не в объёме этого change'я.
- **`assertInvariant` без `if (DEBUG)` добавляет вызов функции в release.** Это те самые 3-4 места на некритичном для тика пути (создание индекса, аллокация), не hot-path вроде `mul`/`add` — цена пренебрежима.

## Migration Plan

Чисто внутреннее изменение диагностики, наблюдаемое поведение симуляции не меняется. Существующие тесты, ожидающие `toThrow()` на мягких местах, переписываются на проверку sink; тесты на жёсткие места остаются на `toThrow()` в обеих сборках.
