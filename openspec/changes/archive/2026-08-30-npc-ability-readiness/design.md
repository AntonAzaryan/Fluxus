# npc-ability-readiness — design

## Context

Мотивация — proposal.md «Why». Текущее состояние:

- Словари документа NPC закрыты и живут парой `model.ts` (наборы + коды) / `tables.ts` (таблицы «имя → код»); входы вычисляет `NpcDecider.inputValue` (`decide.ts`), форму consideration'а валидирует и компилирует `document.ts`, JSON Schema блока `npc` порождает `dsl/npcSchemas.ts` → `engine/schemas/*.json` (`npm run schemas`).
- `CompiledConsideration` — `{input, curve, weight}`; параметра у входа сейчас нет ни у одного. Прецедент параметризованного входа — бот: `BotConsideration.slot` для `abilityCooldownFraction` (`engine/bot-ts/src/behavior.ts`), поле осмысленно только у этого входа и отвергается у прочих.
- Слоты способностей — отдельные сущности с `AbilitySlot` (`owner`, `slotIndex`, `abilityId`, `phase`) и `AbilityCooldown.remaining`; гейт старта — `CastPhaseSystem.tryStart`: слот idle (`phase < 0`) и `cooldownRemaining(ctx, slot) === 0` (`abilities/phase.ts`, `abilities/runtime.ts`).
- Демо-босс держится на сенсоре `BossReady` (order −797) в `content/scenes/duel.scene.json`: busy-гейты (`BossDash.ticksLeft`, `BossHunt.bumped`, любая активная фаза), готовность слотов по `abilityId` 8/9/10, дистанционные пороги 327680 (5.0) и радиус 117963 (1.8), события `Boss{Slam,Strike,Charge}Ready`. Документ `arenaBoss` — состояния `hunt → slam|strike|charge` по этим событиям, назад по `elapsed 1`.
- `game/demo-ts/test/demoBoss.test.ts` закрепляет текущую структуру: наличие сенсора, состав переходов `hunt`, зеркала балансных чисел.
- Демо-сцена вне golden/cost-эталонов (CONT-4); правка `engine/core-ts` эталоны затронуть может — гейт `npm run check` целиком.

## Goals / Non-Goals

**Goals:**

- Вход `abilityReady` в закрытом словаре NPC, слот-адресуемый, с семантикой гейта триггера и единым предикатом кода.
- Босс демо-арены как потребитель-доказательство: сенсор снесён, ротация — оси скоринга документа.
- Детерминизм: значение входа не зависит от порядка обхода слотов и раскладки чужих агентов; арифметика Q16.16/целые.

**Non-Goals:**

- Условие перехода о готовности (см. дельту NPC-7 — MUST NOT, пока переход несёт одно условие).
- Обобщённые входы «читай любой компонент» и выражения DSL в документе поведения (задокументированный non-goal бота, та же граница у NPC).
- Изменения машины способностей: гейт, кулдауны, фазы не трогаются.
- Пере-баланс демо сверх необходимого для сноса сенсора (веса/кривые подбираются до осмысленного боя, не до идеала).

## Decisions

1. **Адресация — `slotIndex`, не `abilityId`.** Зеркало ботовского `abilityCooldownFraction` (ABIL-1: `slotIndex` — идентичность слота у владельца); `abilityId` — индекс таблицы `abilities` сцены, он у сенсора был вынужденным (сенсор искал слоты запросом по всем). Документ поведения и так принадлежит сцене — связь с её раскладкой слотов не новая зависимость. Альтернатива `abilityId` отклонена: два способа адресации в одном словаре хуже одного.

2. **Предикат — модуль abilities.** Экспортировать из `abilities/runtime.ts` функцию вида `slotIdleReady(ctx, handles, slot): boolean` (имя по вкусу реализации) — ровно `phase < 0 && cooldownRemaining === 0`, и `tryStart` обязан читать её же (или её слагаемые из одного места), чтобы вход и гейт не разошлись. NPC-модуль импортирует её, а не переписывает.

3. **Поиск слота агента — линейный обход выборки `AbilitySlot` текущего тика.** Слот с `owner === agent && slotIndex === N`; выборка запроса уже переиспользуется механизмом Query, счёт — O(слотов) на вычисление входа. Допустимо: вход считают решающие в этот тик агенты (каденс NPC-4 бюджетирует), слотов в сцене десятки. Альтернатива — индекс owner→slots на платформе — отклонена как преждевременная: это кэш с инвалидацией ради недоказанной экономии; если профиль на реальной сцене покажет — пометить `ponytail` и вернуться. Обход слотов обязан быть от одной выборки (детерминированный порядок), результат от порядка не зависит (первый совпавший `slotIndex` уникален у владельца).

4. **Форма документа.** `NpcConsiderationDef` получает опциональное `slot?: number` (целое ≥ 0); `CompiledConsideration` — `slot: number` с `-1` («не назван»). Валидация `document.ts`: у `abilityReady` поле обязательно, у прочих входов — находка (зеркало ботовской «лишнее поле — признак непонимания»). Схема `npcSchemas.ts` — условная ветка по входу; регенерация `npm run schemas`.

5. **Вычисление входа** — в `NpcDecider.inputValue`: новый код `INPUT_ABILITY_READY` в конце набора (порядок существующих кодов нормативен — не переставлять), значение `FIXED_ONE`/`0`. Handles полей `AbilitySlot`/`AbilityCooldown` — через существующий механизм handle'ов NPC (`handles.ts`), разрешение имён один раз.

6. **Документ босса.** Состояния `hunt/slam/strike/charge` сливаются в одно состояние ротации с действиями:
   - `seekTarget` — базовая ось `always` с умеренным весом;
   - `cast BossStrike` — `[abilityReady slot=strike, targetDistance с кривой-гейтом ≤5.0]`;
   - `cast BossSlam` — `[abilityReady slot=slam, targetDistance с гейтом ≤1.8]`;
   - `cast BossCharge` — `[abilityReady slot=charge, targetDistance с кривой в пользу >5.0]`.
   Приоритет — веса/кривые (полезность каста при готовности обязана превосходить seek). Фронт `cast`-исполнителя самовосстанавливается: каст → откат → ось в нуле → действие снимается → при готовности выбирается заново → новый фронт → новое событие. Пороговые числа берутся из сенсора (5.0 / 1.8), формы кривых — забота реализации.

7. **Busy-гейты сцены (`BossDash.ticksLeft`, `BossHunt.bumped`, «любой каст»)** — политика сцены, не словаря. Подавление каста во время даша/стаггера выражается средствами, которые уже есть: предикатами/фазами определений способностей или лёгкой JSON-системой сцены, если без неё бой деградирует. Разрешено и удалить подавление, если наблюдаемый бой (см. приёмку) не страдает: демо вне эталонов, это баланс. В словарь NPC входы про сценные компоненты не добавляются.

8. **Приёмка контента — `demoBoss.test.ts` + прогон `npm run demo:debug`.** Тест переписывается на новую структуру: сенсора нет, у cast-действий есть ось `abilityReady` с существующим `slotIndex` слота босса и дистанционные оси с зеркалами порогов; прогон debug-матча (боты в слотах) обязан показать касты всех трёх способностей и отсутствие спама событий готовности (их больше нет как класса).

## Risks / Trade-offs

- [Правка ядра может тронуть golden/схемы] → `npm run schemas` обязателен (словарь входов — часть схемы); `npm run check` целиком; расхождение golden — только если реально изменилось поведение существующих сцен, чего быть не должно (новый вход существующие документы не используют). Регенерация эталонов без объяснимой причины — красный флаг, не рутина.
- [Каст поверх каста: per-slot готовность не знает «владелец занят другим слотом»] → в один тик поведение публикует не более одного события `cast` (фронт), а во время активной фазы новый старт другого слота даёт `supersede`-прерывание — наблюдаемо в debug-прогоне; если бой деградирует, подавление — политикой сцены (Decision 7), не расширением словаря.
- [Слом баланса демо] → числа порогов переносятся из сенсора как есть; итог проверяется журналом debug-матча (частота кастов сопоставима с досенсорной: ~39 кастов за 3600 тиков — ориентир, не эталон).
- [O(слотов) на вход] → принято осознанно (Decision 3); при росте сцен — профиль и `ponytail`.

## Migration Plan

Один атомарный коммитless-переход внутри ветки: движок (словарь + предикат + тесты + схемы) и контент (документ босса + снос сенсора + demoBoss-тест) могут идти отдельными коммитами — старый контент валиден на новом движке, обратное неверно, поэтому движок первым. Отката как процедуры нет: до пуша всё локально, гейт — `npm run check`.

## Open Questions

Нет: адресация решена (Decision 1), busy-гейты — латитюд реализации в рамках Decision 7.
