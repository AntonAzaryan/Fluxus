# Design: perf-budget-bench

## Context

Мотивация — proposal.md «Why»; требования — дельта `performance-budget` (PERF-1..7). Что уже есть и что ограничивает решение:

- Симуляция детерминирована; записанные матчи `engine/tests/golden/match-*` (CLI-10) — готовая воспроизводимая нагрузка. Golden-культура и процедура регенерации (`npm run golden`, `npm run record`) отработаны.
- Прецедент wall-time бенча — `engine/client-ts/test/bench.test.ts`: warmup, `performance.now()`, печать `[bench] …`, ассерт только «на порядок». `syntheticTick(count)` оттуда строит `ExtractedTick` любого размера.
- Рендер headless-запускаем: пакет свободен от DOM (REND-19), рендерер в тестах — структурный спай (`FogRendererLike`), часы `ViewBuffer` инжектируются. GPU-время headless не видно в принципе.
- В ядре есть сток диагностики (`debug.ts`, DIAG-1..7): push во время тика, инертен (DIAG-4), детерминирован (DIAG-6), изнутри симуляции недостижим (DIAG-7).
- CI нет: гейт — локальный `npm run check` на разных по мощности машинах. Всё, что гейтит, обязано быть машинно-независимым.
- Прецедент регрессии: пересборка маски FoW в `syncTick` (CPU), ×16 работы прошло ревью незамеченным — целевой класс регрессий именно такой.

## Goals / Non-Goals

**Goals:**
- Точный, машинно-независимый гейт стоимости в `npm run check` без нового инструментария поверх vitest.
- Атрибуция: регрессия видна на уровне стадии конвейера и конкретного счётчика.
- Ручной браузерный бенч, отвечающий на вопрос «60 fps ещё сходится?» против профиля устройства.

**Non-Goals:**
- Не оптимизация: изменение строит линейку, а не ускоряет код (найденные им долги — отдельные changes).
- Не замер GPU-времени в гейте: headless его не видит; GPU-сторона — зона браузерного бенча.
- Не CI и не автодетект устройства.
- Не пресеты качества — это `render-quality-presets`, он строится поверх этого гейта.

## Decisions

### D1. Гейтят счётчики, не время

Гейт — детерминированные счётчики объёма работы, сверяемые с эталоном побитово. Wall-time в гейте только «на порядок». Альтернативы: жёсткие пороги времени (флаки между машинами — отвергнуто), A/B-прогон против базового коммита (честно, но медленно и требует жонглирования git-состоянием на каждый прогон — отвергнуто как гейт, остаётся возможным ручным приёмом).

### D2. Доставка счётчиков: ядро — DIAG-сток, рендер — свой инжектируемый сток

Ядро ничего нового не экспортирует: счётчики тика едут записями через существующий сток диагностики (уровень `systems` достаточен). Рендер получает зеркальный минимальный интерфейс `CostSink` (по образцу `debug.ts`) — плоская структура именованных счётчиков, инкременты в заранее созданные поля, ноль аллокаций; сток по умолчанию отсутствует, и учёт не исполняется. Механизм — интерфейс стока; политика — какие счётчики включены в эталон.

Стартовый набор счётчиков (расширяемый, фиксируется эталоном, а не спекой):
- ядро: исполненные команды Command Buffer, вычисления выражений DSL, пары broad-phase, рейкасты;
- рендер: тексели маски FoW, тесты сегментов (субсэмплы), вызовы рендерера (спай), байты загрузки текстур, инстансы, тронутые в `syncTick`/`frame`.

### D3. Дом гейта — `engine/integration-ts`, эталоны — `engine/tests/golden/*.cost.json`

Матчи уже разыгрываются в `integration-ts` (`matchGolden.test.ts`); бенч-тест стоимости прогоняет те же записи через ядро и через презентационный тракт (ViewBuffer → PresentationStage со спаем рендерера) и сверяет счётчики с `*.cost.json` рядом с парами матчей. Регенерация — `UPDATE_COST=1`, корневой скрипт `npm run golden:cost`; `npm run golden` его не вызывает (удорожание принимается отдельным осознанным жестом, не паровозом с поведенческими эталонами).

### D4. Декомпозиция по стадиям — двумя инструментами

Headless-счётчики тегируются стадией (tick / channel / syncTick / frame) по месту снятия — это атрибуция объёма работы. Время стадий меряет только браузерный бенч (лёгкий probe в странице демо вокруг тех же швов: тикер воркера, `remote.frame`, `fog.render`). Сводить обе картинки в один отчёт не требуется — у них разные вопросы.

### D5. Оси масштабирования — размеры S/L в одном эталоне

Бенч-нагрузка каждой оси (сущности, наблюдатели, сегменты укрытий, разрешение маски) гоняется на двух размерах; эталон хранит счётчики обоих. Квадратичность видна по отношению L/S без интерпретатора. Синтетика строится на `syntheticTick` и фикстурах render-ts, не на новых форматах.

### D6. Браузерный бенч — Playwright поверх демо-стенда

`npm run bench:demo`: поднимает демо (бот-соперник, фиксированный сид), катает N секунд, собирает тайминги кадров и стадий из probe, печатает p50/p99 против профиля. Профили устройств — JSON в `game/demo-ts/bench/profiles/` (сейчас `desktop-dev.json`; профиль среднего мобильного добавится, когда появится референс-устройство). В гейт не входит, Chromium в dev-окружении уже есть.

### D7. Wall-time сторожа рендера — зеркало client-ts

`engine/render-ts/test/bench.test.ts` по тем же конвенциям (warmup, `[bench]`-печать, ассерт «на порядок»). Оси — ровно те, по которым въехала FoW-регрессия: разрешение маски 4/8, число наблюдателей, число сегментов.

## Risks / Trade-offs

- [Счётчики не видят чужой работы: внутренности three.js (матрицы, аттрибуты) не инструментируются] → их константную стоимость страхуют wall-time сторожа и браузерный бенч; счётчики меряют только собственный код движка.
- [Эталоны стоимости зачастят в диффах при правках записанных матчей] → cost-эталоны привязаны к тем же `match-*`-записям: перезапись матчей (`npm run record`) и так осознанный жест; `golden:cost` идёт следом в том же коммите.
- [Соблазн читать счётчики из геймплея] → сток ядра — существующий DIAG: изнутри симуляции недостижим (DIAG-7), наружу — push-only.
- [Браузерный бенч шумит] → он не гейт (PERF-7); отчёт — перцентили по нескольким прогонам, вердикт против бюджета профиля, не против прошлого запуска.
- [Двойная бухгалтерия счётчиков и голденов поведения] → счётчики не пишутся в поведенческие эталоны (CLI-3 не меняется); отдельные файлы, отдельная команда.

## Migration Plan

Изменение аддитивно: новые тесты, новые файлы эталонов, новый скрипт. Отката как такового нет — удаление тестов и эталонов возвращает всё как было. Существующие golden-пары и их процедуры не меняются.

## Open Questions

- Точный состав счётчиков ядра (D2 — стартовый список): зафиксируется по первому прогону на записанных матчах — критерий «счётчик двигается от реальных правок», бесполезные нули в эталон не входят.
- Числа бюджетов профиля среднего мобильного устройства — до появления референс-устройства в руках; на механику не влияет.
