# perf-budget-bench

## Why

Правка рендера FoW (`0bb2619`: покрытие 2×2 субсэмплов вместо бинарного теста, разрешение маски 4 → 8 текселей/юнит) подняла CPU-стоимость пересборки маски примерно в 16 раз и обрушила FPS демо — и ни один рубеж этого не поймал: в спеках нет ни одного требования о производительности, в `npm run check` нет ни бенчмарка, ни бюджета, единственные «сторожевые числа» (`engine/client-ts/test/bench.test.ts`) стерегут только канал SHELL-3. Продуктовая цель при этом сформулирована: минимум 60 fps на машине разработчика сейчас и 60 fps на среднем мобильном устройстве при будущей поддержке мобильных и планшетов. Нужен формальный, воспроизводимый на любой машине способ увидеть удорожание рендера и ядра в момент коммита, а не в демо.

## What Changes

- **Новая capability `performance-budget` (префикс PERF)** — бюджеты производительности и механика бенчмарк-гейта:
  - бюджет кадра формулируется в перцентилях (p99 времени кадра), а не в среднем FPS, и проверяется против **референс-профилей устройств**, объявленных данными (профиль несёт свои бюджеты; появление планшета — новый профиль, а не новое требование);
  - бюджет декомпозируется по стадиям конвейера (тик в воркере → экстракция и канал → `syncTick` → `frame` → GPU), чтобы регрессия была атрибутируема к стадии;
  - **детерминированные счётчики стоимости** — объём работы (тексели маски, тесты сегментов, вызовы рендерера, байты аплоада, команды ядра), битово воспроизводимый на любой машине; инструментирование инертно: ноль аллокаций, ноль стоимости в выключенном виде, сток инжектируется (в ядре — существующий diagnostics-сток DIAG-1..7, тик не меняется);
  - **голден-гейт стоимости**: счётчики снимаются на записанных матчах (CLI-10) и сверяются с закоммиченным эталоном точно, как golden-пары ядра; гейт входит в `npm run check` и работает headless — ни браузера, ни GPU (по образцу BLND-7); удорожание принимается явной командой регенерации с диффом эталона в коммите;
  - **wall-time сторожа**: замеры времени печатаются при каждом прогоне, но ассертятся только против деградации на порядок; жёстче ассертить wall-time MUST NOT — числа между машинами несравнимы, жёсткий порог даёт флаки;
  - **оси масштабирования**: бенч-нагрузка гоняется на нескольких размерах по осям стоимости (число сущностей, наблюдателей FoW, сегментов укрытий, разрешение маски), чтобы суперлинейный рост был виден в эталоне;
  - **браузерный бенч** — ручная диагностика абсолютного FPS против бюджета профиля (реальный Chromium, демо-сцена); это инструмент по запросу, как `npm run coverage`, а не гейт.

### New Capabilities

- `performance-budget`: бюджеты производительности (перцентили кадра, декомпозиция по стадиям, референс-профили устройств как данные) и механика контроля — детерминированные счётчики стоимости, голден-гейт на записанных матчах, wall-time сторожа, браузерная диагностика абсолютного FPS.

### Modified Capabilities

(нет — счётчики ядра едут через существующий сток `diagnostics` без изменения его требований; вид golden-пары стоимости определяется новой спекой со ссылкой на `cli-testing` CLI-5/CLI-10, сами CLI-требования не меняются)

## Impact

- `engine/render-ts` — счётчики стоимости в маске FoW и сабсистемах (инжектируемый сток по образцу `debug.ts` ядра), учёт вызовов рендерера через существующий структурный контракт (`FogRendererLike` и спаи тестов); `test/bench.test.ts` со сторожевыми числами по образцу `client-ts`.
- `engine/core-ts` — счётчики объёма работы тика через diagnostics-сток; тик и его детерминизм не меняются, аллокаций в горячем пути не прибавляется.
- `engine/integration-ts` — прогон счётчиков на записанных матчах, golden-пары стоимости в `engine/tests/golden/` (`*.cost.json` рядом с парами матчей), регенерация явной командой по образцу `npm run golden`.
- `game/demo-ts` — ручной браузерный бенч демо-сцены (скрипт поверх Playwright/Chromium), замер p50/p99 кадра против бюджета профиля.
- Референс-профили устройств — файлы данных (дом уточняется в design); числа бюджетов в спеку не пишутся.
- Корневые скрипты: голден-гейт стоимости и сторожа — обычные vitest-тесты, попадают в `npm test`/`npm run check` без нового шага; браузерный бенч — отдельный `npm run bench:demo`, в гейт не входит.
