# Design: character-movement

## Context

Мотивация — в proposal.md (Why). Текущее состояние кода: `InputSystem` (TS, order −1000) раскладывает `InputFrame` в компонент `Input`; JSON-система `Movement` в `duel.scene.json` пишет `Velocity` мгновенно; `PhysicsSystem` (TS, order 100) разрешает `Velocity → Position` поосевым swept-AABB; `FireballFlight` интегрирует позицию снаряда сама, мимо физики; блокировка бинарна по тегу `blocksMovement`; TimeScale на перемещение не действует. Требования зафиксированы в дельтах: `locomotion` LOC-1..6, `physics` PHYS-2/8/11/12, `terrain` TERR-5.

## Goals / Non-Goals

**Goals:**

- Нативная `LocomotionSystem` между `InputSystem` и `PhysicsSystem` (order между −1000 и 100): разгон/торможение, машина Dodge/Roll/Airborne, все числа — из компонентов.
- Маски `layer`/`blockMask`/`hitMask` в `PhysicsSystem` и `StaticCollider`; sensor-события `Overlap`.
- TimeScale в точке интеграции; направленный cliff-гейт по `cliffRise`.
- Контент `duel.scene.json` переведён на новый конвейер; снаряд идёт через физику.

**Non-Goals:**

- Никакой непрерывной вертикали, дуг и «высоты» вне уровней террейна (PHYS-1).
- Никакого pathfinding/ИИ-движения — только запись `Velocity` политиками.
- Депенетрация, массы, импульсы (PHYS-5 неизменен).
- i-frames, урон, баланс манёвров — политика контента, не этот change.

## Decisions

**D1. Машина состояний — два компонента: конфиг и стейт.**
`Locomotion` (конфиг): `maxSpeed`, `accel`, `decel`, `dodgeSpeed`, `dodgeTicks`, `windowTicks`, `rollSpeed`, `rollTicks`, `jumpSpeed`, `jumpTicks`, `jumpHeight`, `dodgeButton`, `jumpButton`. `LocomotionState` (стейт): `state` (0=Normal, 1=Dodge, 2=Roll, 3=Airborne, 4=Window), `ticksLeft`, `dirX`, `dirY`. Разделение конфиг/стейт повторяет паттерн `ArenaState.support` наоборот: конфиг мутируем модификаторами (слоу — политика, TIME-6), стейт снапшотится и переживает rewind (SNAP-1). Альтернатива «один компонент» отвергнута: dirty-дельта помечала бы конфиг изменённым на каждом манёвре. Окно даблтапа — отдельное значение `state`, а не флаг: одно поле состояния исключает одновременные манёвры по построению (LOC-3).

**D2. Имена компонентов и биты кнопок — опции конструктора системы**, как у `InputSystem`/`PhysicsSystem` (LOC-1). Ядро не получает новых конвенций имён.

**D3. `cliffRise` — поле компонента коллайдера, не отдельный компонент.** Физика уже читает коллайдер движущегося; отдельный компонент — вторая выборка на горячем пути ради поля, которое семантически «как я прохожу через статику». Locomotion мутирует его через Command Buffer при входе/выходе из `Airborne`; буфер вливается в конце системы, `PhysicsSystem` (order выше) видит свежее значение в том же тике.

**D4. TimeScale применяется к шагу оси внутри `PhysicsSystem`**: `step = fixed.mul(velocity_axis, timeScale(entity))`, где timeScale — редукция `TimeScaleModifiers` (TIME-7) с дефолтом 1.0. Скорость в компоненте не мутируется — замедление не «прилипает» к состоянию. Альтернатива «Locomotion масштабирует Velocity» отвергнута: не покрыла бы снаряды и props, потребовала бы опт-ин каждой пишущей скорость системы (ровно то, что PHYS-8 теперь запрещает решать поштучно).

**D5. Маски — i32-поля.** Блокировка: `(obstacle.layer & mover.blockMask) ≠ 0` + cliff-гейт для обрывов. Сенсор: `(obstacle.layer & mover.hitMask) ≠ 0` по фактически исполненному свипу, одно событие на пару за тик, порядок статика→динамика по индексу (PHYS-12). Слой статики обрывов — параметр сборки `PhysicsSystem`/загрузчика сцены (PHYS-2). Тег `blocksMovement` из движения уходит; `blocksVision` остаётся механизмом обзора (raycast не трогаем).

**D6. Уровни сторон в `StaticCollider` обрыва** пишутся при выводе геометрии (`staticsFromTerrain`): `lowSide`/`highSide` неудобны — нужна привязка к геометрии, поэтому храним `levelNeg`/`levelPos` — уровень со стороны меньшей и большей координаты по нормали ребра. Сторона захода при гейте определяется знаком шага по оси, перпендикулярной ребру (ребро — вырожденный AABB, ось нормали очевидна из его нулевой толщины).

**D7. Снаряд через физику.** `Fireball` получает `Collider` (круг, `blockMask=0`, `hitMask=слой юнитов`) — летит насквозь, урон по `Overlap` решает политика; `FireballFlight` сокращается до декремента `Lifetime`. Пример «блокирующегося» снаряда остаётся вне MVP-сцены — механизм покрыт тестами.

**D8. Порядок систем**: Input (−1000) → Locomotion (10) → JSON-политики → Physics (100). Существующие тесты порядка не ломаются.

## Risks / Trade-offs

- [Golden-эталоны разойдутся: `Movement` JSON заменяется, физика масштабирует шаг] → это ожидаемое, спекой закреплённое изменение поведения; перегенерация `npm run golden` с диффом эталонов в коммите (процедура CLI-10).
- [`Overlap` каждый тик пересечения — спам событий при долгом контакте] → принято спекой (PHYS-12): память «уже задел» в механизме была бы состоянием вне снапшота или лишним компонентом; политика дедупит своим состоянием.
- [Маска по умолчанию 0 = «ничего не блокирует» — молчаливое прохождение сквозь стены при забытом поле] → значения по умолчанию задаёт контент в prefab'е; сцена без масок ведёт себя как «всё насквозь», что видно немедленно; схемы компонентов (`npm run schemas`) документируют поля.
- [Q16.16-диапазон при `fixed.mul(velocity, timeScale)`] → оба множителя малы (скорость ≤ единицы за тик, TimeScale ≤ 4.0 по TIME-7), произведение в диапазоне.
- [Рост ветвлений в горячем пути `PhysicsSystem`] → маски — битовые операции без аллокаций; cliff-гейт срабатывает только на статике-обрыве; аллокационная дисциплина сохраняется.

## Migration Plan

1. Ядро: terrain (уровни в отрезках) → physics (маски, TimeScale, гейт, `Overlap`) → locomotion (новая система) — в этом порядке, каждый слой со своими юнит-тестами.
2. Контент: `duel.scene.json` — новые компоненты, удаление JSON-`Movement`, снаряд через физику.
3. `npm run schemas` и `npm run golden` (перезапись матчей и эталонов), дифф эталонов в коммит.
4. Откат — revert коммита: снапшот-формат обратно совместим (новые компоненты — обычные данные сцены).
