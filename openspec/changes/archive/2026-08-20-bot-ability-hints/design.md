## Context

Мотивация — proposal.md (Why); требования — делта `specs/bot-player/spec.md` (BOT-12, BOT-13). Сегодня запись способности в профиле (`engine/bot-ts/src/profile.ts`, `BotAbilityProfile`/`BotAbilityCastProfile`) дублирует руками то, что уже сказано определением сцены (`ability-system` ABIL-2..5: бит триггера, фазы, шаги, кулдаун), и добавляет то, чего сцена не знает (цель `enemy|threat|cliff`, руки, прицелы шагов, числа сложности). Оба дерева законно читает только игровое приложение: `game/demo-ts/app/bots.ts` уже резолвит профиль и документ поведения от корня контента, `bin/demo-serve.mjs` читает дерево как игра. Демо-сцена — `content/scenes/duel.scene.json` (блок `abilities`, у дуэли шесть боевых определений), парный документ-прецедент — `duel.presentation.json`.

## Goals / Non-Goals

**Goals:**

- Документ `content/scenes/<база>.bots.json`: форма, валидация, аннотации всех боевых способностей дуэли.
- Один модуль вывода «сцена + аннотация → ожидаемая механика записи профиля», используемый и сверкой, и генерацией (BOT-13: второй реализации правил не появляется).
- Сверка как тест `game/demo-ts` (входит в `npm run check`), генерация как CLI `npm run bots:sync`.

**Non-Goals:**

- Механика способностей, схема сцены, ядро и `engine/bot-ts` не меняются; форма профиля остаётся schema 3 (поле `cooldownTicks` и все числа сложности живут как жили).
- Выбор «когда кастовать» и словарь considerations мозга не трогаются (это территория BOT-8/BOT-9).
- Редакторская поддержка документа аннотаций (превью, формы) — вне изменения.

## Decisions

### D1. Форма документа аннотаций

```json
{
  "schema": 1,
  "name": "duel",
  "abilities": {
    "cast": {
      "target": "enemy",
      "hands": "free",
      "steps": [ { "aim": "enemy" } ],
      "range": 12,
      "requiresMoving": false
    }
  }
}
```

Ключ — `id` определения сцены. Поля — ровно та семантика, которой нет в определении: `target`, `hands`, `requiresMoving`, `rise`, `range` (осмысленная дальность применения для мозга), `steps[].aim`, и `cooldownTicks` — обязательный только когда кулдаун определения выражение, а не литерал (BOT-13). Числа сложности в аннотации не живут — это профиль (BOT-6). Парность — по имени файла, как у презентации; валидация — по образцу `profile.ts` (структура находок, русский язык), но кодом `game/demo-ts`: движку документ не принадлежит (CONT-4, BOT-12).

### D2. Модуль вывода — один на сверку и генерацию

`game/demo-ts/app/botContract.ts` (имя уточнит имплементация): по определению сцены и аннотации строит ожидаемую запись `BotAbilityProfile` без чисел сложности. Правила вывода из определения: `trigger.input.bit` → `button`; биты подтверждения/отмены — из блока ввода сцены, которым они назначены (ABIL-3/INP-4: биты назначает контент; где именно они лежат в конфиге дуэли — смотреть на месте); фаза вида `release`/`commit` → `cast.commit`; `targeting.steps` → число и порядок шагов (их `aim` — из аннотации); длительность фазы удержания → `holdTicks`; кулдаун-литерал → нижняя граница `cooldownTicks` (выражение → число из аннотации). Сверка сравнивает выведенное с фактическим профилем по механике и семантике и отдельно проверяет кулдаун-инвариант `profile >= scene`; генерация пишет выведенное, сохраняя существующие числа сложности (merge по полям, не по записи целиком).

### D3. Сверка — тест демо-приложения

`game/demo-ts/test/botContract.test.ts`: для каждого профиля `content/bots/*.json`, чья сцена — дуэль, сверить все записи `abilities` с выводом D2. Находки — русским текстом с именем способности, полем и обоими значениями; тест перечисляет находки разом (а не падает на первой). Это и есть «проверочный гейт игрового приложения» BOT-13: `npm run check` гоняет тесты demo.

### D4. Генерация — CLI

`game/demo-ts/bin/bots-sync.mjs`, из корня `npm run bots:sync [-- --profile <path>]`: читает сцену, аннотацию и профили, обновляет механику/семантику записей, добавляет скелеты для способностей, которых в профиле нет (числа сложности скелета — нейтральные умолчания, помеченные на тюнинг), не трогает числа сложности существующих записей, пишет канонично отсортированный JSON тем же способом, каким записаны сегодняшние профили. Идемпотентность: второй запуск подряд — ноль изменений; это тест CLI.

- **Уточнено имплементацией.** Скелет заводится по ЯВНОМУ `--add`, а не по умолчанию. «В профиле этой способности нет» читается двояко — либо сцена только что её получила (сценарий BOT-13), либо этот уровень сложности ею не играет (состав способностей — решение дизайнера, BOT-6), — и различить их генерации нечем. Умолчание «добавлять» дописывало бы лёгкому профилю дуэли `throwHeld` и `capture`, которыми он не играет, причём молча: дописанные скелеты сверке не противоречат, и гейт остался бы зелёным. Настоящая страховка — не флаг, а тест: прогон команды без флагов по КОПИИ отгруженного `content/` обязан быть неподвижной точкой (`botsSync.test.ts`).
- **Уточнено имплементацией.** Числа профиля команда не правит ВОВСЕ — включая длительность удержания, выпавшую из окна фазы, и `cooldownTicks` ниже кулдауна сцены: BOT-13 запрещает перетирать их без оговорок, а «привести к сцене» и «перетереть» для числа, выставленного руками, — одно действие. Разошедшееся число она НАЗЫВАЕТ находкой (той же сверкой, что и гейт, по документу уже после правки механики) и выходит ненулевым кодом. Умолчания достаются только заводимому скелету — это создание записи, а не правка чужой.
- **Уточнено имплементацией.** «Тем же способом, каким записаны сегодняшние профили» на деле означает каноническую форму документа (`prettyJsonSerializer`, ED-21), а не рукописную вёрстку с однострочными объектами: файл БЕЗ правок не переписывается вовсе, но первая же правка переформатирует его целиком.

### D5. Ульта отката времени

В аннотации дуэли её нет — как нет и в профилях (профильный комментарий: бит ульты ведёт хост мира, бот, дёргающий его, останавливал бы матч). Отсутствие способности в аннотации = «боту её не описывали»; генерация скелет не создаёт, сверка записей по ней не ждёт. Это данные документа, не ветвление кода.

## Risks / Trade-offs

- [Правила вывода разойдутся с ядром при эволюции ABIL-*] → правила читают определение сцены как данные и живут в одном модуле; изменение формы определения ломает тест сверки явно, а не молча.
- [CLI перетирает ручной тюнинг] → merge по полям с явным списком «полей сложности», тест идемпотентности и тест «сложность не тронута» (сценарий BOT-13).
- [Дубль знания «какие биты назначены подтверждению/отмене»] → берётся из конфига сцены/ввода, не константой; если в конфиге дуэли биты назначает документ биндингов ввода (`game/demo-ts/app/bindings.json`) — читать его, он тоже дерево игры.
- [Тест сверки завязан на дуэль] → перечень «профиль → сцена» строится от поля `behavior`/структуры контента, новая сцена с ботами подхватывается данными, а не правкой теста.

## Migration Plan

Одно изменение: (1) документ+валидация, (2) модуль вывода, (3) тест сверки, (4) CLI, (5) `duel.bots.json` и выверенные профили, (6) `npm run check`. Существующие профили уже сходятся со сценой (проверено конвенцией «60→62» руками) — ожидание: сверка зелёная сразу; если нет, находка сверки и есть первый пойманный рассинхрон, чинится профилем.
