## Context

Конвертация 522-строчного `tech-requirements.md` в 14 capability прошла машинно-однообразно: каждый буллет `**ID**: текст` стал `### Requirement: ID` с модальностью `SHALL`. Там, где оригинал был мягким («(Опц.)», «по необходимости»), однообразие исказило смысл. Плюс потерялись части, не имевшие формы требования: §20 «Открытые вопросы» и прозаические врезки-разграничения.

## Goals / Non-Goals

**Goals:**
- Вернуть FOW-9 исходную силу требования и исходную формулировку неравенства.
- Дать открытым вопросам место рядом с требованиями, к которым они относятся.
- Сделать происхождение EVT-4 прослеживаемым.

**Non-Goals:**
- Не переформулировать другие требования «заодно» — правки строго по списку ревью.
- Не переносить §20 из `docs/architecture.md` (обзорная карта остаётся).
- Не менять нормативный текст EVT-4.

## Decisions

**1. FOW-9: `SHOULD` + «чуть меньше», а не `SHALL` + «не больше».**
Требование адресовано рендеру — слою вне ядра, поведение которого спека не проверяет golden-файлами. `SHALL` здесь ложная строгость. Формулировка «не больше» хуже исходной по существу: равенство радиусов формально её удовлетворяет, но именно равенство возвращает мигание цели на границе, ради устранения которого требование и написано. Строгое неравенство («чуть меньше») — то, что решает задачу. Конкретная дельта радиуса не нормируется: это вопрос ощущения, подбирается рендером.

**2. Open Questions — секцией в спеке, а не отдельным документом.**
Вопрос ищется вместе с требованием, которого он касается: пейс перемотки — в `snapshot-rewind`, стоимость фильтрации — в `netcode`. Альтернатива (единый `open-questions.md`) даёт список, который никто не открывает при правке спеки. Вопросы, живущие на стыке двух capability (FoW × rewind, видимость событий), пишутся в одну спеку и упоминаются ссылкой во второй — по правилу «не дублируй требование в двух capability».

**3. Открытые вопросы пишутся без SHALL/MUST.**
Модальность означает норму; нерешённый вопрос нормой не является. Формат: строка-заголовок + 1–2 предложения контекста + пометка слоя (геймплей / netcode / перф / рендер). Секция идёт в конец файла, после всех требований, чтобы валидатор не принимал её за требование.

**4. EVT-4 — примечание о происхождении, не изменение текста.**
EVT-4 единственное требование без прообраза-ID: оно собрано из врезок «Разграничение с Command Buffer / Event Bus» (§4.5 и §9). Без пометки при следующей сверке с оригиналом оно будет выглядеть как отсебятина. Примечание ставится рядом с требованием — оно про этот конкретный текст, а не про спеку целиком.

**5. Purpose `fog-of-war` — про отключаемость capability.**
Оригинальная врезка §16 говорит, что FoW не расширяет ядро. Ревью просит дописать вторую половину: ядро собирается и без FoW (`determinism-core` DI-3, `physics` PHYS-4), но для этой игры FoW обязателен — без per-client фильтрации по `Visibility` клиент получает данные о невидимых врагах. Это Purpose, а не требование: нормативная часть уже покрыта NET-12..15.

## Risks / Trade-offs

- **Дублирование открытых вопросов между `docs/architecture.md` §6 и спеками** → расходятся при правке. Принято сознательно: architecture.md — карта («какие вопросы вообще открыты»), спека — место, где вопрос виден при работе с требованием. При закрытии вопроса правятся оба; список короткий.
- **`SHOULD` в FOW-9 читается как «можно игнорировать»** → сценарий «Цель ровно на границе обзора» остаётся и показывает, что́ ломается при игнорировании.
- **Примечание о происхождении — прецедент** → ставится только там, где прообраза-ID нет; остальные 162 требования сохранили исторические ID и в пометке не нуждаются.
