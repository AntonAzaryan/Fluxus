# Design: dsl-cost-axis

## Context

- **Оси стороны тика уже есть по образцу.** `npc-stress` — документ нагрузки `npc-stress.load.json` и размеры `npcStressSizes()` (прореживание/размножение агентов той же нагрузки); `nav-path` — сценарий golden-набора и `navPathSizes()`. Оба прогоняются `runScenario` со стоком диагностики, секция одна — `tick`; форма документа `{ axis, small, large, cost: { small: { tick }, large: { tick } } }`. `footprint.test.ts` снимает те же нагрузки в `*.footprint.json`.
- **Фикстуры сцен строятся инлайн** в `integration-ts/test/fixtures.ts` (`duelScene`, `churnScene`, `buffScene`) — JSON-системы с выражениями и действиями DSL, без `content/` (CONT-4).
- **Счётчик `expressions`** инкрементируется в `dsl/expr.ts` на каждое вычисление узла; `commandsApplied` — применённые команды. Оба уже в `TICK_COST`.

## Goals / Non-Goals

**Goals:** одна ось, одна величина (число сущностей), фиксированный набор систем, два размера, документы `dsl-scale.cost.json` и `dsl-scale.footprint.json`, регенерация `golden:cost`.

**Non-Goals:** не ось «число систем» (второй величины у оси быть не может, PERF-6; при надобности — отдельная ось отдельным change); не бенч evaluator'а по времени (PERF-5 покрывает записями); не правки DSL.

## Decisions

### D1. Нагрузка

Сцена `dslScene(entities)` в `fixtures.ts`/`benchLoad.ts`: компоненты `Position`, `Velocity`, `Health`, `Tag`; сущности из одного префаба, размещённые сеткой. Набор JSON-систем — фиксированный и репрезентативный:
1. движение: действие `set` по выражению над `Position`/`Velocity` на каждую сущность запроса;
2. условие с ветвлением: выражение `if`/сравнение над `Health`, действие `add`;
3. запрос с фильтром: система над запросом с `filter`-выражением, действие с командой;
4. эмиссия события: действие `emit` по условию раз в N тиков.
Никаких запросов внутри действий: линейность — ожидаемое свойство нагрузки, и ось должна её показывать.

### D2. Размеры

`small` = 64, `large` = 256 сущностей (×4, как у `scaling`), 24 тика (как у `npc-stress`/`nav-path`). Размеры — из одной функции по числу, не два рукописных документа (тот же довод, что у `AxisSize`).

### D3. Ожидаемые отношения

`expressions`, `commandsApplied`, `eventsEmitted` (счётчик из влитого change `tick-cost-coverage`) — L/S = 4 РОВНО, а не «около»: работа evaluator'а на сущность определяется только вариантом её начальных значений и номером тика, доля вариантов у обоих размеров одна и та же, а пространственных запросов у нагрузки нет вовсе. Линейность здесь — свойство построения нагрузки, а не пожелание к ней, поэтому тест утверждает её сильной формой: точным равенством счётчика отношению ВЕЛИЧИН размеров (тот же приём, что на оси экстракции), без литерального числа в ассерте — точные числа держит эталон (PERF-4).

Сильная форма адресована ИМЕННО этим трём счётчикам. Счётчик, вклад которого в эту нагрузку постоянен на тик или на систему, растёт с осью сублинейно, и PERF-6 это прямо разрешает («отдельный счётчик ВНУТРИ стадии, у которой ось есть, вправе ни одной осью не двигаться»); общая проверка по всей записи краснела бы на нём диффом, которого не снимает регенерация. Нули остальных строк проверяются отдельным тестом — как утверждение о СОСТАВЕ нагрузки (чужих платформ ядра в ней нет), а не о линейности.
