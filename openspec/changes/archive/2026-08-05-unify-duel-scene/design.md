## Context

Мотивация — в `proposal.md`. Технически важное состояние на входе:

- `buildMatchWorld` (`engine/net-ts/src/match/world.ts`) уже принимает `physics?: PhysicsOptions` и регистрирует `PhysicsSystem` условно; `MatchConfig` сервера и опции `MatchClient` это поле уже несут. Не доведено одно: запускалки (`bin/serve.mjs`, `bin/play.mjs`) не читают `physics` из файла матча, а `content/matches/duel.match.json` его не содержит.
- Демо (`engine/client-ts/demo/sim.ts`) регистрирует физику само и добавляет две драфтовые нативные системы: `CastFireball` (фронт кнопки → распаковка `aimDir` → спавн снаряда → событие `CastFireball` с `dirX`/`dirY`) и `FireballImpact` (снятие пола). Обе остаются нативными до этапов 30–31.
- `PhysicsSystem` двигает только сущности с `Position + Collider + Velocity`; снаряд без `Collider` интегрируется системой сцены `FireballFlight` — двойной интеграции нет.
- Реестр систем запрещает равные `order` (DET-3).
- Запись матчей (`match-*` в `engine/tests/golden/`) идёт через инлайн-фикстуру `duelScene()` в `engine/integration-ts/test/fixtures.ts` (CONT-4), а не через дерево контента.

## Goals / Non-Goals

**Goals:**

- Один документ сцены дуэли, который любая оболочка (матч, демо) поднимает с одним и тем же конвейером движения: `Velocity` + интегрирующая `PhysicsSystem`.
- Физика как зависимость сборки в конфиге матча (NTR-14), доведённая от файла матча до обеих сторон.
- Одно имя события каста на обе стороны.

**Non-Goals:**

- Перевод `CastFireball`/`FireballImpact` в JSON (этапы 30–31; блокеры — тригонометрия и снятие пола).
- Поведенческий паритет каста/импакта между матчем и демо: в матче каст пока только эмитит событие.
- Изменение golden-сценариев ядра (`input-drive` и прочие) — они фиксируют механизм ядра и от контента не зависят (CONT-4).

## Decisions

**1. Движение — версия демо.** `Movement` пишет `Velocity = Input × 5243`, интегрирует `PhysicsSystem` (механизм ядра). Альтернатива — `Position += Input` сетевой сцены — отклонена: она не проходит через физику, то есть не даёт ни коллайдеров, ни обрывов, и именно она сделала сетевую сцену несовместимой с демо-геймплеем.

**2. Физика остаётся в конфиге матча, не в сцене.** Так уже устроен `MatchWorldDef` («зависимость сборки, а не данные сцены», DI-3). `duel.match.json` получает `"physics": {}` (значения по умолчанию: компоненты `Collider`/`Velocity`, order 100). `serve.mjs` передаёт его серверу, `play.mjs` — клиенту: у клиента это сборочная зависимость того же рода, что контент-пак, — данные *матча* он по-прежнему узнаёт из `Welcome`.

**3. Событие каста: каноническое одно, драфтовое отдельно.** JSON-система `Cast` объединённой сцены эмитит `CastFireball` с `{ entity, slot, tick }` — единственный факт «каст произошёл», одно имя на обе оболочки (имя из манифеста визуалов: `CastFireball → Spell Slam`). Нативная система демо перестаёт сама детектить фронт кнопки и эмитить этот факт: она читает события `CastFireball` текущего тика (шина событий читаема системами), распаковывает `aimDir` кастера, спавнит снаряд и эмитит **отдельное драфтовое** событие `FireballAimed` `{ entity, dirX, dirY }` — направление для доворота торса (REND-5); `aimEvents` воркера демо переключается на него. Альтернативы: (а) эмитить `CastFireball` и из JSON, и из натива — отклонено: два факта каста на одно нажатие в логе событий; (б) оставить эмит только нативу — отклонено: имя события в матче и демо снова расходится, а в матчевой сборке факт каста исчезает вовсе; (в) не эмитить направление — отклонено: рендер теряет доворот торса. `FireballAimed` умирает на этапе 30 вместе с нативом, когда тригонометрия позволит JSON-касту нести `dirX`/`dirY` в самом `CastFireball`.

**4. Порядки систем** (DET-3, равные запрещены): `Movement` 10, `KillSwitch` 20, `Cast` 30, нативный спавн демо (`FireballLaunch`) 35, `FireballFlight` 40, `FireballImpact` 50, `PhysicsSystem` 100. `Cast` получает `not: ["Dead"]` — мёртвый не кастует, симметрично `Movement`/`KillSwitch`.

**5. Интеграционная фикстура зеркалит конвейер движения, а не документ контента.** `duelScene()` в `integration-ts` получает `Velocity` и `Collider` у Hero и `Movement` демо-версии; `duelConfig()` — `physics: {}`; `RenderBridge` передаёт `physics` в свой `buildMatchWorld`. Террейн, каст и kill-switch в вертикаль не тащим: мост рендера собран под сцену без террейна, а вертикаль проверяет швы, а не геймплей. Фикстура остаётся инлайн (CONT-4) — эталон краснеет от изменения движка, не от ретюна контента. Следствие: `worldInitHash` и позиции в `match-*` меняются по существу; перезапись — `npm run record`, затем `npm run golden` из корня, дифф эталонов идёт в тот же коммит.

**6. Hero стартует в `753664` (11.5; 11.5)** — центр плато демо-террейна. Двое героев матча в одной точке допустимы: сущности без тега `blocksMovement` друг друга не блокируют.

Механизм/политика: в ядре не меняется ничего; всё изменение — контент (JSON-системы, политика), конфиг матча и проводка зависимостей сборки в сетевом слое плюс драфтовые нативные системы демо.

## Risks / Trade-offs

- [Каст в матче — событие без снаряда; поведение оболочек различается за пределами движения] → это заявленная граница этапа 28; снятие — этапы 30–31, зафиксированы в roadmap и в заготовках `cast-fireball-in-json` / `carve-floor-action`.
- [Перезапись эталонов `match-*` может замаскировать случайную регрессию] → дифф эталонов смотрится на ревью; каждое отличие объяснимо решениями выше (hash от новых компонентов, стартовая позиция, скорость 5243/тик вместо шага 65536).
- [Событий на тик каста в демо становится два (`CastFireball` + `FireballAimed`)] → это два разных факта (каст и направление), а не дубль одного; потребители названы поимённо (манифест — первый, `aimEvents` — второй).

## Migration Plan

Развёртывания нет. Порядок внутри коммита: контент и код → `npm run record` → `npm run golden` → полный `npm test` + `npm run typecheck` из корня.
