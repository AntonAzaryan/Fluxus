## Context

Первая реализация ядра. Спеки покрывают поведение, но не раскладку кода и не выбор точек, где спека оставила свободу. Здесь фиксируются только те решения, которые не являются нормой (норма ушла в delta-спеки `rng` и `fixed-point-math`).

Ограничения: `CORE-1` (только TS), `CORE-2` (всё, что опирается на семантику TS, обязано воспроизводиться в Rust), `CORE-4` (без WASM), `DET-2` (никаких float в симуляции).

## Goals / Non-Goals

**Goals:** этапы 1–5 roadmap; каждый нормативный сценарий этих capability проверяется тестом.

**Non-Goals:** expression/action/system evaluator (6–8), сериализация и снапшоты (9), CLI и golden-file (10) — только заглушки в контракте, разрешённые `architecture.md` §5. Производительность: корректность и парность важнее, оптимизация — по замерам позже.

## Ключевые решения

### Q16.16 без BigInt (FP-2)

Произведение двух `i32` не помещается в 53-битный safe integer, поэтому `mul` считает `(a*b) >> 16` через разложение на 16-битные половины и `Math.imul`, собирая результат в `i32` с wrapping. `BigInt` не используется нигде, включая тесты-эталоны: эталон для сверки строится на `BigInt` только в тестовом коде, где hot-path не важен.

Округление — truncate toward zero и в `mul`, и в `div` (`FP-3`), то есть отрицательный результат обрезается вверх, а не арифметическим сдвигом (`>>` для отрицательных даёт floor — это ловушка, которую тест обязан ловить).

### ID: собственный sparse-set с поколениями (ID-1..5)

Стороннней ECS-библиотеки нет (`ECS-1`), поэтому `EntityIndex` свой: `generations`/`alive`/`freeList`/`nextIndex` — только TypedArray, число и массив чисел, что делает его тривиально клонируемым и сериализуемым (`ID-4`).

Упаковка — `id = index + generation * 2^24`, по 24 бита на часть (`ID-1`), арифметикой, а не битовыми операциями: побитовые операторы JS 32-битные и на 48-битном значении врут. Переиспользование слотов — LIFO из `freeList`, чтобы порядок был воспроизводим во второй реализации (`ID-5`).

Отдельная ловушка, стоившая бы молчаливой порчи данных: списки идентификаторов нельзя хранить в `Uint32Array` — запись усекает 48-битный id до 32 бит начиная с `generation = 256`, что для пула снарядов достижимо за один матч. Контейнер — `Float64Array` (целые до 2^53 точны).

### Компоненты: SoA по JSON-схемам, принадлежность — битовой маской

Ядро создаёт SoA-хранилище (`Int32Array` на поле) по JSON-схеме компонента (`ECS-3`), плюс валидацию схем и prefab'ов на загрузке (`ECS-5`). Все поля симуляции — `i32` (Q16.16 или целое); `f32`/`f64` в схеме компонента запрещены (`DET-2`).

Принадлежность компонентов — битовая маска на сущность (`componentMask.ts`), а не проверка по имени: фильтр запроса сводится к одному И по словам вместо строкового `Map.get` на каждую сущность на каждый компонент фильтра. Это тот же приём, что применяют ECS-библиотеки, и он же — предпосылка для архетипного индекса, если тот когда-нибудь понадобится по замерам.

### Command Buffer: массив замыканий-команд, flush per-system

Команда — запись в плоском массиве, применяемая в порядке добавления (`CMD-3`). Flush вызывает Scheduler в конце каждой системы (`CMD-2`), сама система на это влиять не может. `ctx.commands` — единственное, что система получает для записи; ссылки на world из `SystemContext` даются только для чтения (`DET-7`).

`withinRadius` в Query считается в fixed-point по квадрату расстояния — без `sqrt`.

### Query возвращает копию (QUERY-3, CMD-5)

Результат запроса материализуется в `Float64Array` на момент вызова: итерация по живому набору ломалась бы при структурных изменениях и делала `QUERY-3` непроверяемым. Порядок — возрастание raw-индекса сущности (`QUERY-2`), он получается по построению при обходе слотов слева направо, поэтому сортировки нет вовсе.

### RNG: стримы создаются лениво, состояние живёт в world state

`ctx.rng.stream(name?)` возвращает стрим, сидированный по `RNG-3`/`RNG-7`. Стримы кешируются в world state по имени, чтобы повторный вызов внутри тика продолжал последовательность, а не начинал её заново. Состояние всех стримов сериализуемо (`RNG-5`) — четыре `u32` на стрим плюс имя.

Производные методы поверх `next(): u32` фиксируются здесь (не в спеке — они не нормативны, пока нет второй реализации): `nextBelow(n)` — Lemire multiply-shift-reject, `nextFixed()` — старшие 16 бит в дробную часть Q16.16, `nextRangeFixed(lo, hi)`. При появлении Rust-порта их придётся поднять в спеку.

### Заглушки этапов 9 и 12

`TickResult.changes` — пустой `ChangeSet` с тем же интерфейсом, что будет наполнен на этапе 9. `mode` — константа `Running`, `isReplay` — `false` до этапа 12. Поля присутствуют в контракте с самого начала, потребители пишутся против финальной формы (`architecture.md` §5).

## Risks / Trade-offs

- **Своё хранилище вместо библиотеки.** Требования ECS-2 (поведение задаёт спека), ID-5 (единый алгоритм ID) и SNAP-4 (снятие полного состояния с теми же идентификаторами) не покрываются ни одной готовой ECS, поэтому Query, команды, ID-семантика и порядок обхода в любом случае были бы свои. Цена — ~40 строк sparse-set и битовые маски, которые иначе дала бы библиотека.
- **Копирование результата запроса** стоит аллокации на каждый запрос. Осознанно: детерминизм и `QUERY-3` важнее, пул массивов — оптимизация по замерам.
- **Отсутствие golden-file тестов** на этом этапе означает, что парность проверяется только юнит-тестами против зафиксированных в спеке констант. Это устраняется этапом 10, а не расширением текущего.
