# Design: tick-cost-coverage

## Context

Мотивация — proposal.md «Why»; требование — дельта `performance-budget` PERF-3. Что уже есть и что ограничивает решение:

- **Механизм готов.** Счётчики тика — поля `DiagnosticsContext` в `core-ts/src/debug.ts`, калитки вида `countCostX(n)` (`if (ctx === undefined) return; ctx.costX += n;`), одна запись `TICK_COST` в конце Running-тика (`recordTickCost`) на уровне `systems` (DIAG-3). Без стока контекст отсутствует, и калитка — одно сравнение. Аллокаций нет: поля созданы заранее, запись пишет плоский объект `data` только при стоке.
- **Гейт готов.** `integration-ts/test/cost.test.ts` собирает секцию `tick` из полей `data` записи и сверяет с `*.cost.json` точно; регенерация — `npm run golden:cost`. Документов семь: три записи (`match-*`), `npc-stress`, `nav-path`, `scaling`/`extract` (секции `tick` не имеют). Новые поля — новые строки диффа при регенерации, старые значения не меняются.
- **Горячие места.** Скан кандидатов таргетинга — цикл `for (const candidate of ctx.query(spec))` в `abilities/runtime.ts` (один на шаг способности с фигурой); шаги снарядов — цикл `for (const projectile of projectiles)` в `abilities/projectile.ts`; проходы баффов — `apply`/`advance` по `instances` и поиск хозяина `host()` перебором `instances` в `abilities/buffs.ts`; видимость — вложенные циклы наблюдателей × целей в `systems/visibility.ts` (линия видимости идёт через `raycast` Physics API и уже считается `raycasts` — второго счётчика ей не нужно); твины — проход по твинам в `systems/tween.ts`; события — `emit` в `ecs/events.ts`.
- **Тесты записи.** `core-ts/test/tickCost.test.ts` проверяет форму записи и инертность; `traceParity.test.ts`/`traceCli.test.ts` сравнивают трейс с реплеем — новые поля обязаны совпадать между прогонами, что детерминизм калиток и даёт.

## Goals / Non-Goals

**Goals:**
- Семь счётчиков в `TICK_COST`, по образцу существующих: одна калитка на платформу, единица — осмотренный кандидат или исполненный шаг.
- Норма «своя строка у каждой платформы» — в PERF-3, а не в комментарии.
- Эталоны расширены, ни одно старое значение не двинулось.

**Non-Goals:**
- Не оси PERF-6: новые счётчики двигаются существующими осями (`npcAgents` — способностями NPC, записи — таргетингом и снарядами), своя ось им не нужна по оговорке PERF-6 о счётчике внутри стадии с осью.
- Не счётчики вне тика: фильтр снапшота (`sim/filter.ts`) вызывается сервером матча вне `tick()` и меряется на проводе (change `wire-cost-baseline`); переигранные тики отката уже входят в `ticks` по контракту `recordTickCost`.
- Не устранение найденного: если скан таргетинга или `host()` окажутся квадратичными, это станет ВИДНО числом; чинить — отдельным change.

## Decisions

### D1. Единицы и калитки

| Счётчик | Где считается | Единица |
|---|---|---|
| `abilityCandidates` | цикл кандидатов скана таргетинга (`runtime.ts`) | сущность, осмотренная сканом (до фигуры и предиката) |
| `projectileSteps` | проход снарядов (`projectile.ts`) | снаряд, продвинутый за тик |
| `buffSteps` | проходы `apply`/`advance` (`buffs.ts`) | инстанс, обработанный проходом (оба прохода считают) |
| `buffCandidates` | перебор в `host()` (`buffs.ts`) | инстанс, осмотренный поиском хозяина |
| `visibilityPairs` | внутренний цикл наблюдателей × целей (`visibility.ts`) | пара, дошедшая до проверки |
| `tweenSteps` | проход твинов (`tween.ts`) | твин, продвинутый за тик |
| `eventsEmitted` | `emit` шины (`events.ts`) | событие |

Считается ИСПОЛНЕННАЯ работа, как у `commandsApplied`: кандидат, отброшенный фигурой, осмотрен и считается; снаряд, не продвинутый (мёртвый), не считается. Линия видимости отдельного счётчика не получает: она идёт лучом Physics API и уже в `raycasts` — второй счётчик обещал бы одну работу дважды (тот же довод, что у `navNodes`).

Калитка вызывается один раз на цикл с числом (`countCostAbilityCandidates(examined)`), а не на итерацию, там, где число известно после цикла; на итерацию — только для `emit`, где цикла нет. Цена — одно сравнение на вызов, как у `countCostRaycast`.

### D2. Форма записи не меняется

Поля добавляются в `data` записи `TICK_COST`; код записи, уровень и контракт числа записей прежние. `DIAGNOSTIC_CODES` (`types.ts`) не трогается — это не новый код. Порядок полей в `data` — алфавитный, как у существующих, чтобы канонический JSON эталона был стабилен.

### D3. Гейт собирает `tick` без перечня

`cost.test.ts` суммирует все числовые поля `data` записи в секцию `tick` — если сегодня там перечень полей, он заменяется на проход по полям записи: новый счётчик ядра попадает в эталон без правки гейта, а забытая калитка видна отсутствием строки, а не молчанием.

## Risks / Trade-offs

- **Скан кандидатов проходит по запросу к миру целиком** — `abilityCandidates` на записях может быть большим числом. Это и есть цель: число покажет, стоит ли ограничивать запрос сеткой.
- **`visibilityPairs` двигается числом наблюдателей × целей** — на `npc-stress` он квадратичен по построению (все агенты — наблюдатели и цели). Это свойство алгоритма, не дефект счётчика; квадратичность видна в L/S и становится числом для будущего change.
