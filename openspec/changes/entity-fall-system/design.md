# entity-fall-system — design

## Context

Мотивация — proposal.md «Why»; норматив рендера — дельта REND-12. Существующий механизм: `ArenaSystem` (order 110) эмитит `FellThroughFloor` по переходу «был на полу → пола нет» (ARENA-5); события тика видимы системам с большим `order` в том же тике (EVT-2); DSL умеет `forEachEvent`/`eventField`, `addComponent`, `modifyComponent`, `destroyEntity`, `emitEvent` (ACT-1). Рендер-пайплайн: `Extractor` (единственный читатель мира) → плоская `ExtractedTick` → канал оболочки (`client-ts/codec.ts`) → `ViewBuffer` → подсистемы.

## Goals / Non-Goals

**Goals:** играбельное падение в сцене дуэли; переносимый образец политики падения для любых сцен; снижение и анимация в представлении без единого числа в ядре.

**Non-Goals:** отмена падения над восстановившимся полом (потребителя нет — восстановление пола ещё не выражено действием DSL; пересмотреть вместе с ним); урон вместо мгновенной смерти; падение снарядов (у них override уровня, ARENA-6 исключает их из проверки пола); VFX/камера-эффекты на падение.

## Decisions

### 1. Политика в JSON, а не нативная система — пересмотр заметки архива

Заметка `terrain-holes` (2026-08-06) предлагала нативную TS-систему: «она потребует состояния падения и согласования с физикой/FoW». На момент записи в DSL не было реакции на события. Сейчас есть `forEachEvent` + `eventField`, состояние падения — обычный компонент, согласование с физикой сводится к обнулению `Velocity`, с FoW — ни к чему (падающая сущность остаётся в снапшоте до гибели). Прецеденты `cast-fireball-in-json` и `carve-floor-action` зафиксировали границу: в демо нативны только `InputSystem` и `PhysicsSystem` — механизм, которому в JSON не место. Нативная система падения пересекла бы эту границу в обратную сторону и потянула бы за собой правку SER-7 (флаг сцены, порождённые компоненты, нормативный порядок схем). Альтернатива отклонена.

### 2. Порог — в тиках; компонент `Falling { progress, duration }`

По z считать нечего: непрерывной вертикали в симуляции нет (PHYS-1), а её введение — пересмотр PHYS-1, который заметка архива допускала лишь как отдельный change без видимой выгоды: длительность в тиках наблюдаемо эквивалентна. `progress` растёт от 0, `duration` — балансный порог, копируется в компонент при старте падения (значение — в JSON-системе сцены). Пара «прогресс/порог», а не «остаток», чтобы рендер мог нормировать снижение без знания баланса. Оба поля `i32`; компонент объявляет контент, в снапшот и rewind он попадает как любой другой.

### 3. Смерть — конвенцией, отдельной системы нет

`FallProgress` при `progress >= duration` эмитит `EntityDied { entity }` и вызывает `destroyEntity`. Это ровно та конвенция, на которой уже стоят netcode (NET-14: исчезновение из снапшота без `EntityDied` — туман, с ним — смерть), фильтр (`filter.ts`) и рендер (REND-4: one-shot по `EntityDied`). Компонент `Dead` (образец `KillSwitch`) не используется: он оставляет труп стоять, а провалившемуся трупу стоять негде — сущность уничтожается. Блокера нет.

### 4. Старт падения: `forEachEvent` + обнуление скорости; падающие исключаются из управления

`FallStart` (order 120, после арены): по `FellThroughFloor` — `addComponent Falling` и `modifyComponent Velocity → 0`. Обнуление, а не скольжение по инерции: иначе физика уносит падающего с дыры, и он «падает сквозь пол». Запросы `Movement`/`KillSwitch`/`Cast` получают `not: ["Falling"]` — управлять падающим нельзя; это выбор контента, не ядра. Повторный старт невозможен: `FellThroughFloor` идёт по переходу, а стоя́щих переходов у падающего нет.

### 5. Рендер: колонка `fall`, нормировка на границе мира

`Extractor` получает конфиг `fall?: { component, progressField, durationField }` (прецеденты: `velocityComponent`, `stateComponents` — политика по имени). Колонка `fall: Float32Array`: `progress/duration` c клампом в [0, 1], `NaN` — сущность не падает (различимо от нулевого прогресса, REND-12). Нормировка происходит в единственной точке конверсии мира в float (REND-1). `codec.ts` добавляет колонку в f32-блок плоской формы; `ViewBuffer` ведёт `prevFall`/`currFall` со snap-правилами позиции; `models.ts` в `updateFrame` опускает `holder` на `fallDepth · t²` (ease-in — визуально «гравитация»; `fallDepth` — опция подсистемы с дефолтом) и не применяет наклон (REND-10) при `t > 0`. Анимация — запись `"FellThroughFloor"` в `events`-маппинге манифеста, кода не требует.

### 6. Арена в сцене дуэли

Без `arena` в конфиге `ArenaSystem` не регистрируется (SER-7) — событий пола нет вовсе. Дуэль получает окружность, покрывающую карту 24×24 (центр в середине, радиус с запасом): `LeftArena` в дуэли не стреляет, политика края в этот change не входит. Сдвиг ID расставленного от сущности-носителя — законное изменение `worldInit` (SER-7, сценарий «В сцену с расстановкой добавляют арену»). `ArenaState` героя: `support: 0` — проверка по центру; включение опорной области — балансная правка одного числа в контенте.

## Risks / Trade-offs

- [Колонка в плоской форме — правка кодека канала] → формат канала — внутренний контракт client-ts, версионирования не требует; round-trip покрывается тестом кодека.
- [Падающий виден в FoW до гибели] → приемлемо: длительность падения мала, поведение честное (сущность существует). Отдельного правила фильтра не нужно.
- [Пол восстановился под падающим — падение продолжается] → осознанное упрощение (Non-Goals); событие обратного перехода не вводилось ещё в `terrain-holes`.
- [Дыра под точкой спавна] → дефолт `ArenaState` «на полу» даёт событие на первом же тике (ARENA-5) — сущность честно падает, это фича, не дефект.
- [Демо: `FellThroughFloor` от `carveFloor` под героем] → ровно задуманный геймплей: выстрел под ноги роняет.

## Migration Plan

Чистое добавление: сцены без конфига `fall` и без компонента `Falling` рисуются как прежде (REND-12, сценарий «Сцена без падения»); эталоны движка не меняются (CONT-4). Отката данных нет — изменение контента дуэли меняет её `worldInit`-хеш, что законно для контента.
