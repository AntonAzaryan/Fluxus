# @fluxus/desktop-shell

Десктоп-контейнер веб-приложений репозитория — capability `desktop-shell`
(DSK-1..6). Один контейнер запускает и редактор, и игрового клиента; чем они
различаются, выражает **профиль**, а не вторая кодовая база.

Нормативна здесь **граница**, а не Electron: спека описывает словарь моста
(пути, байты, события, диалоги, окно), раздачу бандла и дерева, профили и
сменяемость реализации. Electron — первая реализация; выбор объяснён в
`openspec/changes/desktop-shell/design.md` (D1).

## Три слоя, и граница между ними — требование

| Слой | Что там | Проверяется |
|---|---|---|
| `src/bridge/` | Контракт границы: типы моста и схема профиля. **Ноль импортов** — эти типы вправе брать и контейнер, и приложения | гейт |
| `src/host/` | Чистый Node: корни профиля, атомарная запись, наблюдение, раздача байтов, сборка моста по whitelist | гейт, контрактный сьют |
| `src/electron/` | Тонкий клей: главный процесс, preload, protocol handler | вне гейта: `typecheck:electron`, тот же контрактный сьют в контейнере, smoke-прогон |

Пакетов движка и редактора здесь нет ни одного, и это не соглашение:
`engine/integration-ts/test/desktopBoundary.test.ts` краснеет на импорте и на
зависимости в манифесте (DSK-3), а линт называет запрет там, где импорт пишут.

`npm run check` зелёный в окружении **без установленного Electron** (DSK-6):
клей не входит ни в гейтовый tsconfig, ни в типизированный линт, а контрактный
сьют работает на чистом Node.

Сьют при этом один на все реализации, и Electron проходит его целиком — только
вне гейта: `npm run contract:electron -w @fluxus/desktop-shell` поднимает те
же случаи в настоящем окне (preload, IPC, protocol handler). Вторая реализация
контейнера регистрируется тем же вызовом `describeContainerContract`.

## Профили

`apps/*.app.json` — данные: бандл, корни, whitelist возможностей, окно.

| Профиль | Мост | Дерево контента |
|---|---|---|
| `editor` | `read`, `write`, `watch`, `dialog`, `window` | `content/` на чтение и запись |
| `game` | `service` | `content/` только раздаётся (DSK-5: записи у игры нет) |

Возможность, не объявленная профилем, недостижима не проверкой, а отсутствием
канала: её нет ни в странице, ни в preload, ни в главном процессе. Профиль
фиксируется на старте окна и на живой сессии не расширяется.

## Объявленные сервисы (DSK-7)

Игре нужен свой сервер матча — два человека играют через выделенный стенд, — а
поднять процесс из страницы браузер не может. Возможность `service` даёт ей
ровно это и ровно в объявленных пределах: профиль называет сервис, а страница
называет ЕГО ИМЯ и ничего сверх него.

```json
"services": [
  {
    "id": "match-stand",
    "script": "../../../game/demo-ts/bin/demo-serve.mjs",
    "args": ["--port", "{port}", "--bot-fill-ms", "60000"],
    "address": "ws://127.0.0.1:8080"
  }
]
```

Почему именно так:

- **В мост не приходит команда.** Исполняемого файла, аргументов и пути из
  страницы не бывает — иначе возможность была бы «выполнить произвольное», а
  whitelist профиля не ограничивал бы ничего.
- **Объявляется скрипт, а не бинарь**, и запускает его тот же исполняемый файл,
  которым запущен контейнер (у Electron — с `ELECTRON_RUN_AS_NODE`): `node` в
  `PATH` пользовательской машины может не быть вовсе.
- **Порт живёт в адресе**, а в аргументы приезжает подстановкой `{port}`/`{host}`.
  Две записи одного числа — способ им разойтись.
- **Готовность — соединение по адресу**, а не «spawn не бросил»: иначе первое же
  соединение страницы приходило бы в ещё закрытый порт.
- **Занятый адрес уступается**: стенд, поднятый человеком руками, и есть тот, к
  которому пойдёт страница; своим контейнер его не считает и на закрытии окна не
  снимает. Своё — снимает: переживший окно процесс держал бы адрес занятым.

## Жизненный цикл окна

На Windows и Linux закрытое окно означает закрытое приложение. На macOS — нет:
приложение остаётся в доке, и клик по иконке открывает окно заново. Открывается
оно с **тем же** профилем, что зафиксирован на старте (DSK-5): манифест не
перечитывается, иначе набор выданных возможностей зависел бы от файла на диске
между закрытием окна и кликом. Сессия при этом новая — раздача, мост и
поднятые сервисы (DSK-7) снимаются на закрытии окна и поднимаются заново.

## Как запускать

Бандл приложения собирается **без копии дерева контента**: дерево раздаёт
контейнер, и запечённый в бандл снимок заслонил бы живые байты.

```sh
npm run build:desktop -w @fluxus/editor-ui        # бандл редактора
npm run demo:build:desktop -w @fluxus/demo        # бандл демо игры

npm run start:editor -w @fluxus/desktop-shell     # окно редактора
npm run start:game -w @fluxus/desktop-shell       # окно игры

npm run contract:electron -w @fluxus/desktop-shell  # контрактный сьют в контейнере (вне гейта)
npm run smoke -w @fluxus/desktop-shell            # прогон обоих профилей вне гейта
npm run pack -w @fluxus/desktop-shell -- game     # дистрибутив одного профиля
```

Шага сборки у самого контейнера нет: типы стрипает Node (>=22.18), а хук
резолва в `src/electron/entry.mjs` добавляет `./x.js → ./x.ts` — тот же приём,
что у CLI ядра и импортёра конвейера. Цена та же: в `bridge/` и `host/` нет ни
enum, ни namespace, ни parameter properties.

На машине без дисплея прогоны в контейнере идут под `xvfb-run -a`; под root
Chromium требует `--no-sandbox` (и smoke, и контрактный прогон добавляют его
сами).

## Что остаётся открытым

Иконки, подпись дистрибутивов и структура поставки (дистрибутив на приложение
против общего лаунчера) — вопросы дистрибуции, а не контракта; `bin/pack.mjs`
кладёт дерево контента внутрь дистрибутива снимком, что для игры и есть нужное
поведение, а для редактора годится dev-сборке. Автообновление и магазины в этот
change не входят вовсе.
