# Physics Contract v1

Имя контракта (для ссылок из `schedule.yaml`, поле `contract:`): `PhysicsContractV1`.

Контракт между ядром и провайдером физики. Реализуется в стадии `Physics` расписания. Провайдер — внешний код, не описанный в `systems/`.

Мир 2.5D: XY — плоскость коллизий, Z — высота как скаляр.

---

## 1. Обязанности провайдера

За один вызов провайдер обязан:

1. Прочитать текущее состояние всех физических тел из ECS.
2. Проинтегрировать движение с учётом `dt` из `TimeState`.
3. Обнаружить коллизии и разрешить пересечения.
4. Записать обновлённые `Position` и `Velocity` обратно в ECS.
5. Породить события `Collision`, `RaycastHit`, `TriggerEnter`.
6. Обеспечить стабильный порядок событий (сортировка по `(entity_a, entity_b)` возрастающая).

Провайдер **не имеет права**:
- Читать или писать компоненты, не перечисленные ниже.
- Порождать события, не перечисленные ниже.
- Обращаться к ресурсам, не перечисленным ниже.
- Хранить состояние между тиками вне механизма сериализации из раздела 6.

---

## 2. Входные компоненты

Провайдер читает следующие компоненты у сущностей:

### Обязательные для физического тела
- `Position { x: fixed, y: fixed, z: fixed }`
- `Collider { shape, radius, half_width, half_height, height }`

### Обязательные для динамического тела
Всё из «Обязательных» плюс:
- `Velocity { dx: fixed, dy: fixed, dz: fixed }`
- `DynamicBody { mass: fixed, restitution: fixed, friction: fixed }`

### Обязательные для статичного тела
Всё из «Обязательных» плюс:
- `StaticBody {}` — маркер.

### Опциональные
- `CollisionLayer { layer: u32, mask: u32 }` — если отсутствует, тело сталкивается со всем.
- `Trigger {}` — маркер: тело порождает `TriggerEnter`, но не участвует в разрешении пересечений.
- `Raycast { max_distance: fixed }` — маркер непрерывного детектирования, см. §10.

Сущность без `Collider` для провайдера не существует.

---

## 3. Входные ресурсы

- `dt` — шаг интегрирования, вычисляется как `mul(div(1.0, tick_rate), TimeState.time_scale)` (см. `conventions.md` §4). Не хранится как поле `TimeState` — `TimeState` содержит только `current_tick` и `time_scale`.
- `PhysicsConfig` (опционально, provider-specific) — настройки конкретной реализации.

---

## 4. Выходные мутации

Провайдер вправе изменять:

- `Position.x, y, z` — у сущностей с `DynamicBody`.
- `Velocity.dx, dy, dz` — у сущностей с `DynamicBody` (гашение при коллизии, отражение).

Провайдер **не имеет права** менять `Collider`, `StaticBody`, `DynamicBody`, `CollisionLayer`, `Trigger` и любые другие компоненты.

---

## 5. Выходные события

### Collision
Порождается при разрешении пересечения двух тел с не-Trigger коллайдерами.

```
Collision:
  entity_a: u64        # меньший entity_id
  entity_b: u64        # больший entity_id
  contact_point: { x: fixed, y: fixed, z: fixed }
  normal: { x: fixed, y: fixed, z: fixed }   # нормализован, направлен от a к b
  penetration: fixed   # глубина проникновения до разрешения, >= 0
```

Правила:
- Одна пара тел порождает не более одного `Collision` за тик.
- `entity_a < entity_b` всегда.
- Столкновения тел одного tick'а (например, снаряд появился и сразу столкнулся) — порождают событие в том же тике.

### RaycastHit
Порождается для сущностей с компонентом `Raycast` (используется снарядами для точного попадания).

```
RaycastHit:
  ray_source: u64                              # entity_id снаряда
  hit_entity: u64                              # entity_id цели
  point: { x: fixed, y: fixed, z: fixed }
  normal: { x: fixed, y: fixed, z: fixed }
  distance: fixed
```

### TriggerEnter
Порождается при входе тела в область с `Trigger`.

```
TriggerEnter:
  trigger_entity: u64
  other_entity: u64
```

## 6. Сериализация состояния

Провайдер обязан реализовать интерфейс:

```
serialize() -> bytes
deserialize(bytes)
```

Требования:
- После `deserialize(serialize(state))` следующий тик с тем же вводом даёт бит-в-бит тот же результат.
- Формат байт — внутреннее дело провайдера, но версионируется вместе с провайдером.
- Если провайдер не хранит внутреннего состояния — возвращает пустой массив байт.

Провайдеры без поддержки сериализации могут возвращать признак `unsupported`, но тогда ядро запрещает режимы, требующие rollback.

## 7. Capabilities

Провайдер декларирует свои возможности (не в спеке, а в реализации):

```
capabilities:
  deterministic: bool                    # даёт ли одинаковый результат на одной платформе
  cross_platform_deterministic: bool     # даёт ли одинаковый результат TS ↔ Rust ↔ ...
  rollback: bool                          # поддерживает ли serialize/deserialize round-trip
```

Ядро на старте:
- `cross_platform_deterministic = false` → сетевые режимы недоступны.
- `rollback = false` → клиентский предикт и lockstep недоступны, работает только pure authoritative.
- `deterministic = false` → замена симуляции при рассинхроне только через полный снапшот сервера.

---

## 8. Порядок обработки внутри стадии

Провайдер обязан гарантировать стабильный внутренний порядок обхода:

1. Динамические тела перебираются по возрастанию `entity_id`.
2. При итерации пар — по возрастанию `(min_id, max_id)`.
3. События в выходном буфере сортируются по возрастанию `(entity_a, entity_b)`; для `RaycastHit` — по `(ray_source, hit_entity)`.

Порядок влияет на детерминизм: разные порядки решения коллизий дают разные микро-результаты в fixed-point.

---

## 9. Обработка Z-координаты

- Коллизия считается произошедшей, если пересечение есть **и** в XY, **и** в Z-интервалах.
- Z-интервал тела: `[Position.z, Position.z + Collider.height]`.
- Проверка Z: `interval_overlap(a.z, a.z + a.height, b.z, b.z + b.height)`.
- Нормаль коллизии в Z: если пересечение только в Z-интервале (одно тело над другим и они касаются) — нормаль по Z. Иначе — нормаль в XY, `normal.z = 0`.
- Гравитация применяется вне провайдера, в `GravitySystem` (стадия Simulation).

## 10. Обработка Raycast

Для снарядов, требующих непрерывного детектирования (быстро летящих):

Сущность с компонентом `Raycast { max_distance: fixed }` вместо обычной интеграции:
- Провайдер вычисляет луч из `Position` в направлении `Velocity` длиной `max_distance`.
- Первое пересечение с любым коллайдером в маске порождает `RaycastHit`.
- `Position` тела перемещается либо в точку попадания, либо на полную длину луча за тик.

Без компонента `Raycast` тело интегрируется обычным способом (может «пролететь» тонкие препятствия — TCCM в MVP не требуется).

---

## 11. Ограничения версии v1

Не поддерживается:
- Вращение тел (все коллайдеры axis-aligned или окружности).
- Rigid body с моментом инерции.
- Соединения (constraints, joints).
- Continuous collision detection (кроме `Raycast`).
- Многослойная физика (жидкости, ткани).

Эти возможности — предмет `physics_v2.md`, если понадобятся.

## 12. Пример последовательности вызова

Для одного тика:

1. Ядро завершает стадии `Input`, `Intent`, `Simulation`.
2. Ядро вызывает `provider.step(dt)`.
3. Провайдер читает срез ECS.
4. Провайдер интегрирует и разрешает коллизии.
5. Провайдер записывает мутации в ECS.
6. Провайдер добавляет события в буфер.
7. Ядро продолжает со стадии `Reaction`, где системы читают `Collision`, `RaycastHit`, `TriggerEnter`.
