# Spec Topology & Conventions

Правила организации спецификации игрового ядра. Обязательны к соблюдению при любых правках (человеком или LLM).

Ядро проектируется как **полностью детерминированная чистая функция тика**:

    next_state = tick(prev_state, inputs_for_tick)

Такое ядро одинаково работает в offline, lockstep-мультиплеере и в режиме авторитарного сервера с rollback. Всё, что нарушает детерминизм или чистоту, — вне ядра.

---

## 1. Структура директорий

    spec/
    ├── spec.yaml                    # корневой манифест (meta, версия, include-список)
    ├── topology.md                  # этот файл
    ├── glossary.md                  # словарь терминов RU↔EN
    ├── conventions.md               # правила логики, детерминизма, словарь операций
    │
    ├── resources/                   # глобальное состояние симуляции
    ├── components/                  # атомарные компоненты данных
    ├── events/                      # события (команды и нотификации)
    ├── systems/                     # системы (поведение)
    ├── archetypes/                  # композиции компонентов = шаблоны сущностей
    │
    ├── contracts/                   # контракты внешних провайдеров (физика, звук и т.п.)
    │
    ├── schedule.yaml                # порядок стадий и систем внутри тика
    │
    └── scenarios/                   # data-driven тесты (JSON)

Директории верхнего уровня — фиксированы. Новые категории не создаются без правки этого файла.

---

## 2. Правило «один файл — одна декларация»

- В каждом YAML-файле ровно **одна** верхнеуровневая сущность спеки (один компонент, одно событие, одна система, один архетип, один ресурс).
- Имя файла = имя сущности в `snake_case` + `.yaml`.
- Имя сущности внутри YAML = `PascalCase`.

Пример:
- `components/position.yaml` содержит `Position`.
- `systems/projectile_collision.yaml` содержит `ProjectileCollisionSystem`.

## 3. Назначение директорий

### resources/
Глобальные ресурсы симуляции — единственный экземпляр каждого, не привязаны к сущностям. Обязательные:

- `TimeState` — `current_tick`, `time_scale` (для замедления/остановки времени).
- `RngState` — детерминированный seed + счётчик.
- `GameConfig` — все игровые параметры (скорости, кулдауны, радиусы). В `logic:` систем магических чисел быть не должно.
- `InputBuffer` — команды игроков, принятые к текущему тику.
- `EntityAllocatorState` — монотонный счётчик `entity_id` для спавна сущностей.

Сюда же попадают любые буферы/очереди, которые должны переживать rollback. Ничего вне ресурсов и компонентов между тиками не хранится.

### components/
Атомарные структуры данных, крепящиеся к сущностям. Только поля, никакой логики.

### events/
Три класса событий:
- **Команды игрока** (`PlayerCommand`): единственный легальный вход в симуляцию. Обязаны иметь поля `tick` и `player_id`.
- **Внутренние события**: порождаются системами внутри одного тика, потребляются в этом же тике.
- **Исходящие нотификации** (опционально): триггеры для VFX/звука/UI. На симуляцию не влияют, читаются презентационным слоем.

### systems/
Единицы поведения. Каждая система декларирует:
- `requires` — компоненты и уровень доступа (read/write).
- `triggers` — события, на которые реагирует (опционально).
- `reads` / `writes` — используемые ресурсы (опционально).
- `logic` — псевдокод на русском по правилам из `conventions.md`.

Система обязана быть чистой функцией от своих входов. Никакого хранения состояния между тиками вне ECS.

### archetypes/
Именованные композиции компонентов = шаблоны для спавна сущностей. Список компонентов и их дефолты. Без логики.

### scenarios/
Тестовые сценарии в JSON: `initial_state` → `actions` → `expected_state`. Валидируются JSON-схемой, генерируемой из спеки. Обязаны включать rollback-тесты: `tick N раз → откат к снапшоту → тик N раз → результат бит-в-бит совпадает`.

## 4. Именование

| Что | Регистр | Пример |
|---|---|---|
| Имя файла | snake_case.yaml | damage_command.yaml |
| Компонент | PascalCase | Health |
| Событие | PascalCase | DamageCommand |
| Система | PascalCase + суффикс System | MovementSystem |
| Архетип | PascalCase | Fireball |
| Ресурс | PascalCase + суффикс State/Config/Buffer | TimeState, GameConfig, InputBuffer, EntityAllocatorState |
| Поле | snake_case | current_tick |

---

## 5. Ссылки между файлами

- Ссылки — **только по имени** сущности, не по пути.
- Валидатор спеки резолвит имена в глобальном пространстве.
- Дубликаты имён между категориями запрещены (нельзя иметь компонент `Damage` и событие `Damage` одновременно).

---

## 6. Корневой манифест spec.yaml

Содержит только:
- `meta` (namespace, version, tick_rate, fixed_point_scale).
- Список директорий, которые нужно загрузить (для валидатора).
- Ссылку на `schedule.yaml`.

Не содержит определений компонентов/систем/событий напрямую.

## 7. Инварианты детерминизма

Все инварианты обязательны. Их нарушение — блокер для мерджа.

1. **Ядро — pure**: `tick(state, inputs) -> state`. Никакого I/O, часов, глобалов, скрытых зависимостей.
2. **Никакой плавающей точки**: только fixed-point (`i64` со шкалой из `meta.fixed_point_scale`).
3. **Стабильный порядок итерации**: сущности перебираются по возрастанию `entity_id`, события — по порядку поступления в буфер.
4. **RNG только через `RngState`**: любой рандом продвигает счётчик ресурса. Никаких системных `rand()`.
5. **Время только через `TimeState`**: `dt` вычисляется как `(1 / tick_rate) * time_scale`, читается из ресурса. Никаких `Date.now()` и аналогов.
6. **Snapshot round-trip**: сериализация → десериализация → `tick` даёт бит-в-бит тот же результат, что без сериализации.
7. **Rollback-friendly**: всё состояние симуляции лежит в ECS (компоненты + ресурсы). Никаких статических кэшей, очередей, замыканий вне ECS.
8. **Команды игрока привязаны к тику**: ядро отвергает команды с `tick`, не равным текущему.
9. **Симуляция шагает целыми тиками**: дробного шага нет. Замедление времени = изменение `time_scale`, а не пропуск систем.
10. **Презентация вне ядра**: рендер, интерполяция камеры, звук, ввод с устройств — снаружи. Ядро выдаёт снапшоты, слой презентации их читает.

## 8. Запреты

- ❌ Смешивать несколько компонентов/систем в одном файле.
- ❌ Класть логику в компоненты, архетипы или ресурсы.
- ❌ Создавать директории вне списка из раздела 1.
- ❌ Использовать относительные пути в ссылках между сущностями.
- ❌ Хранить дефолтные значения игровых параметров внутри `logic:` систем — только в `GameConfig` или архетипах.
- ❌ Использовать `f32`/`f64`, системное время, нестабильный порядок обхода, глобальные переменные, любой I/O внутри систем.
- ❌ Писать в Position из системы вне провайдера физики.
- ❌ Использовать 2D-векторы (пары fixed) — все векторы 3D (x, y, z).

## 9. Изменение топологии и правил

Любое изменение структуры директорий, правил именования или инвариантов детерминизма выполняется **правкой этого файла в том же коммите**, что и изменение спеки. Иначе PR не принимается.
